LU-20995 compat: fail cleanly on kallsyms lookups with x86 IBT

On x86 kernels with CONFIG_X86_KERNEL_IBT running on an IBT-enabled
CPU, loading libcfs BUGs with "Missing ENDBR" when Lustre calls
kernel functions through pointers obtained from kallsyms.

find_kallsyms_lookup_name() takes kallsyms_lookup_name() from a
kprobe, and with CONFIG_X86_KERNEL_IBT the probe address is placed
after the ENDBR64 (kallsyms_lookup_name+0x4). Moreover, the kernel
seals the ENDBR of every function whose address is never taken:
objtool lists it in .ibt_endbr_seal and apply_seal_endbr() poisons
it at boot. kallsyms_lookup_name() is one of those functions, as are
alloc/free/apply_workqueue_attrs() and security_file_alloc/free(),
so none of them can be called indirectly from a module, whatever
address is used.

Rewind the kprobe address to the start of the symbol using
sprint_symbol(), so the real entry instruction can be checked, and
verify that the function starts with ENDBR64 when IBT is enabled
before using it. Add and export cfs_kallsyms_lookup_func() to do the
same check for the other functions looked up in
lustre_symbols_init(); it returns ERR_PTR(-EINVAL) if the symbol is
not found and ERR_PTR(-EOPNOTSUPP) if it is not callable.

This does not make Lustre usable on IBT-enabled CPUs: since these
ENDBRs are sealed, libcfs now refuses to load with -EOPNOTSUPP and
a clear error message instead of crashing the kernel with #CP.
Without IBT enforcement, behavior is unchanged. Calling these
functions with a direct call or jmp, which does not need an ENDBR
(e.g. via a module-defined static_call() updated to the kallsyms
address), is left for a follow-up ticket.

In osd-wbcfs, also use cfs_kallsyms_lookup_func() for
flush_delayed_fput(), and fail osd_init() before
class_register_type() if the lookup fails. Previously a failed
lookup left cfs_flush_delayed_fput NULL while the module still
loaded, so osd_umount()/osd_flush_fput() would later call a NULL
pointer.

The sanity runs below only exercise the IBT path if the test nodes
boot an IBT-enabled kernel on IBT-capable hardware; otherwise they
only verify that nothing regresses without IBT enforcement.
