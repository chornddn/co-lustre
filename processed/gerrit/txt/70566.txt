LU-20852 mdt: report a stale FLR file on its last close

A file with a stale FLR mirror or EC parity stays stale until some
external tool runs "lfs mirror resync" on it.  The client that last
wrote the file is a good place to resync it at once, while the data
is likely still in its cache, but it has no way to know that the file
needs it.

On the last close of a file opened for write, have mdt_mfd_close()
check whether the layout is still WRITE_PENDING or SYNC_PENDING, and
if so set OBD_MD_CLOSE_NEED_RESYNC in the CLOSE reply.  This reuses
the OBD_MD_FLXATTRRM bit, which is only sent in setxattr requests, so
old clients ignore it and no connect flag is needed.  The bit is only
a hint: it is not set if a reader closes the file last, and it is
lost if the reply is resent, so files still need a periodic scan.
If the client caches the open handle, the CLOSE is sent only when the
handle is dropped, so a file that is repeatedly opened, written and
closed is not reported (and resynced) after every close.

LOD already tracks the FLR state of a cached layout, so have
lod_attr_get() return it as la_flr_state, which mdd_close() fetches
anyway.  Read the layout xattr only when LOD has not cached it.  Reset
ldo_flr_state when a plain or foreign layout is loaded, so a layout
swapped in from a plain file does not keep a stale state.

The client counts these closes in the llite.*.stats
"close_need_resync" counter.  A later patch will use this notification
to optionally resync the mirror or parity.
