LU-20606 llapi: scan an ldiskfs target directly

Add llapi_scan_device(). It reads the objects of an MDT or OST
directly from the device with libext2fs, and gives the same records as
llapi_scan_namespace(). It needs no mount, no MDS and no kernel change,
so it works on a stopped target, a snapshot, or a failover partner's
LUN. It only reads.

The backend is a plugin, scan_osd_ldiskfs.so, loaded with dlopen() in
the same way as mount.lustre's mount_osd_ldiskfs.so. So liblustreapi
does not link libext2fs. The errors are different so that a caller can
tell them apart:
- ENOTSUP: there is no backend, for example on a client build.
- ENOPKG: the backend cannot open the target. Stock e2fsprogs refuses
  dirdata, so Lustre's e2fsprogs is needed.
- EINVAL: the device is not a Lustre target.

New record fields for a device scan: object id, LMA flags, raw
linkea, parent FID and a class. The target label is read in
all four forms that mkfs.lustre and tunefs.lustre write: '-', ':', '='
and '+'.

New public API:
- lfsp_stats points to a struct llapi_scan_stats that the caller owns.
  It is added after lfsp_got, so older callers are not affected. Both
  scanners fill it. On a completed scan, ss_seen equals ss_filtered +
  ss_skipped + the sum of ss_class. ss_size works like lfsp_size, so
  the struct can grow later.
- LLAPI_SCAN_F_INTERNAL also returns the objects that the namespace
  does not show: the OSD's own objects, DNE agent inodes, and objects
  with no LMA.

So that both scanners give the same answer for one file:
- An object with no LMA on MDT0000 gets its IGIF, built the same way
  as osd_scrub.c does. This is done only on MDT0000, and only from
  inode 12: fid_is_igif() is used, not fid_is_sane(). An OST object
  with no LMA has no FID.
- A directory's own stripe uses LMV_MAGIC_V1, as llite returns.
  LMV_USER_MAGIC means a default LMV.
- stx_attributes has only the flags llite also reports (immutable,
  append, encrypted), and so_attrs_mask says which flags the scan can
  answer.
- LLAPI_SCAN_PARENT is set only when the parent FID is sane.
- An OST scan does not report the MDT index, linkea or parent in
  lfsp_got.
- LLAPI_SCAN_LMV_FOREIGN asked for alone also reads the LMV.

Other fixes in the scanner:
- The LMV buffer is cleared as far as the stripe count reaches, so a
  reader does not see the previous directory's data. The buffer is a
  union of the two structures, so it has the right alignment.
- An inode that cannot be read is counted once, by the chunk that owns
  it.
- If a worker cannot start, the scan goes on with fewer workers.
- If one worker gets a read error, all workers stop.

fid_is_root() moves to the UAPI header, so userspace can use it.
Existing callers are not affected. A hand-written root test that also
accepted a non-zero f_ver now uses it.

The header and the man pages describe what each field is. Each page
says what its scanner offers lfsp_filter, and llapi_scan_device.3 says
what 0 in lfsp_want means for a device scan. The man page example now
escapes its newline correctly.

run_tests() in lustre/tests/llapi_test_utils.{c,h} is split, so that
run_test_tbl() can take a device instead of a mount point.

conf-sanity test_300 checks the MDS version. It fails, not skips, if
the scanner is missing, because that is a broken install. It skips the
OST part for a ZFS, unreachable or older OST, and says so. The
stack_trap calls no longer pass EXIT, which is the default.
