LU-20611 llapi: run find over a device scan

Add llapi_find_device(), which puts llapi_scan_device()'s records
through the same checks llapi_find() applies to a namespace walk.
The checks are not reimplemented: the record is presented as the
lov_user_mds_data every find_check_* helper already reads, and
find_decide() does the rest.

Three things the presentation has to get right.  A field the scan
could not answer for is left out of stx_mask, exactly as llite leaves
it out when the MDT's answer is not authoritative, so the checks that
consult the mask behave the same either way.  The layout arrives as
it is on disk and is byte-swapped in place, lov_mds_md and
lov_user_md being the same bytes.  The directory stripe does not: on
disk it is an lmv_mds_md_v1 and the checks read an lmv_user_md, which
the kernel converts for the ioctl and nothing converts for a scan, so
this does, for the three fields the predicates read.

Both buffers live for the whole scan, so an object without a layout
or a stripe has to say so rather than inherit the last one's: every
object after a 60-stripe file matched --stripe-count 60, a directory
with no layout at all included.

There is no OST to refer a question to, so the MDT's own record
decides a time outright rather than deferring, and -links reads the
directory stripe, which is where a striped directory's link count
comes from.

A scan cannot glimpse, so --size and --blocks are size-on-MDT's
answer or none: fp_lazy is set for the scan, since refusing
trusted.som unless --lazy was typed would leave --size matching
nothing on every striped file.  An object whose size nothing can
settle is counted as undecided and reported at the end, not silently
dropped.  --ost, --mdt, --xattr and -printf need the mounted
filesystem or a path and are refused before the scan starts, because
afterwards "no matches" and "could not answer" look alike.

Documented in llapi_find_device.3.

scan_linkea() is rebuilt around an indexed scan_linkea_entry(), so
that
find_device_prefilter() can run --name against every name in the link
xattr rather than only the first.  That is a decision and not a
refactor: a walk meets a hardlinked file once per link and a scan
meets
it once, so matching one name would answer differently depending on
which link the search was looking for.

A layout read off the target is checked against the buffer it arrived
in before anything walks it.  These bytes come from a device that may
be in service, so an object can be caught mid-update; the consumers
below index by lcm_entry_count and lcme_offset, and a torn composite
EA
claiming a large entry count would be read well past the buffer.  An
EA
that does not describe itself is treated as no layout at all.

fp_get_lmv is set from what the search needs rather than from what the
object turned out to have, which is what the walk does.  Taking it
from
find_rec_to_lmv() skipped find_decide()'s stripe block entirely for an
unstriped directory, so --foreign, --mdt-count and --hash-type never
compared anything and the directory printed as a match.

--maxdepth, --mindepth and --threads join the refused list.  Depth
describes a walk and the thread count is the scanner's own, so they
were being accepted and ignored, which is the quiet mismatch the rest
of that check exists to prevent.

A project id the target cannot answer for is undecided rather than an
error: an inode whose i_extra_isize does not reach i_projid has none
to
give, and failing the object there ended the whole scan after matches
had already been printed.  ss_skipped is reported at the end for the
same reason the undecided count is.

Mostly good, comments inline. The two buffer resets and forcing fp_lazy look correct, and the stale-stripe-count bug they fix is real.

That bug was introduced by the immediately preceding, unlanded patch in this series, 55c88e1300 ("LU-20611 lfs: share find's predicate parsing"), which is where llapi_find_device() and all its helpers actually arrive. Folding the two resets, the flags argument and the lustreapi.h declaration back into that patch would keep each step self-contained; as things stand the series has one commit where lfs find over a scan matches the wrong objects for --stripe-count and a second that repairs it.

Nothing exercises llapi_find_device(). lustre/tests/llapi_scan_device_test.c already exists for the scanner side, and a case that scans a target holding a striped file followed by an unstriped one and a plain directory would have caught this bug directly.
