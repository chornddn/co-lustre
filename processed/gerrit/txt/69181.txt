--- Commit Message ---
LU-20808 mdt: add local/remote MDT rename statistics

There is no way to tell from the MDT statistics how many
renames involve another MDT.  crossdir_rename counts renames
between different parent directories whether or not they are
on the same MDT, and renames that take the BFL may be local
directory renames or remote renames.

Count each rename handled by the MDT as either local_mdt or
remote_mdt in rename_stats.  A rename is remote if either
parent directory (or its stripe) or the renamed object is on
another MDT.  The counters are reset with the other
rename_stats.

Also add a remote_rename counter to md_stats, so remote
renames and their latency are also visible in the export,
nodemap and job_stats.

Tested PS2 with ltvm on rocky9 (5.14.0-611.55.1.el9_7), 2 MDTs:
sanity test_133d passes, including the new local/remote checks.

I checked the classification with eBPF: a kprobe on
mdt_rename_counter_tally() records which MDT counted the rename,
the remote flag and the source/target parent FIDs, and a kretprobe
on mdt_reint_rename() confirms every rename reached the tally
(MDT0000 sequence 0x200000402, MDT0001 0x240000402):

   rename                         counted by  remote  src    tgt
   133d same dir                  MDT0000     0       MDT0   MDT0
   133d cross dir, MDT0 only      MDT0000     0       MDT0   MDT0
   133d file, src dir on MDT1     MDT0000     1       MDT1   MDT0
   133d mrename dir on MDT1       MDT0001     1       MDT1   MDT0
   extra: dir on MDT1 moved       MDT0000     1       MDT0   MDT0
     between two dirs on MDT0

So the test decides the "remote" (source dir) and
mdt_object_remote(mtgtdir) terms, but mdt_object_remote(mold) is
never the only reason a rename is remote: in the third 133d case
the source dir is remote as well. The code handles that case
correctly (extra row: rename_stats on MDT0000 shows remote_mdt 1,
local_mdt 0), but a regression in that term would not fail 133d.

Suggested test improvements:

1. Add a rename where only the renamed object is remote, e.g.

	$LFS mkdir -i 0 $DIR/$tdir/a || error "mkdir a"
	$LFS mkdir -i 1 $DIR/$tdir/a/rdir || error "mkdir rdir"
	(clear rename_stats on mds1)
	mv $DIR/$tdir/a/rdir $testdir2/rdir || error "mv rdir"
	(expect local_mdt=0 remote_mdt=1 on MDT0000)

2. The commit message says remote_rename is also visible in
   job_stats, but only md_stats is checked. It works: after a
   remote rename, job_stats on MDT0000 shows remote_rename with
   one sample for job mv.0, and the export stats match md_stats.
   A check of job_stats (or exports.*.stats) would cover it.
