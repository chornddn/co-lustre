LU-20501 llite: do not derive the dirent from the emitted name

ll_get_name() recovers the directory entry it is examining with
container_of() on the name pointer its filldir gets, which is only valid
while that name points into the lu_dirent.  ll_dir_read() has not
guaranteed that since encrypted directories were added: for those it
emits the name out of the separate llcrypt_fname_alloc_buffer()
allocation, so the derived "lu_dirent" starts 32 bytes before an
unrelated slab object and lde_attrs/lde_fid are read out of bounds.

Tracing the two pointers on an encrypted directory shows the derived
entry landing at name - 0x20 for every entry, with the FID read back out
of the neighbouring allocation -- in one run
[0xffff998306137fe0:0x6137fe0:0xffff9983], a kernel pointer being
compared as a FID.  A plain directory in the same mount never diverges.

Pass the lu_dirent being emitted down from ll_dir_read() so the filldir
works from the entry itself rather than from pointer arithmetic on a name
it does not own.

This fixes the out-of-bounds read only.  NFS export of an encrypted
directory still fails: ll_get_name() calls ll_dir_read() without
llcrypt_prepare_readdir(), which ll_iterate() does before the same call,
and the parent inode reached through ll_iget_for_nfs() ->
search_inode_for_lustre() has no crypt info loaded.  ll_fname_disk_to_usr()
therefore emits the no-key base64 form, and reconnect_path()'s
lookup_one_len() cannot resolve it.  Adding llcrypt_prepare_readdir()
here returns -ENODATA on such an inode, so that needs its own fix and is
deliberately not attempted in this patch.

No suite currently drives ll_get_name() on an encrypted directory --
sanity-sec has no name_to_handle_at()/open_by_handle_at() coverage and
sanityn test_102 uses unencrypted directories -- so the listed suites are
regression coverage for the readdir change rather than for the fixed
path.  A sanity-sec case running check_fhandle_syscalls inside an
encrypted directory is worth adding once the key-loading defect above is
fixed, since until then it could only assert a still-failing path.
