LU-21149 ptlrpc: serialize ping evictor start and stop

ping_evictor_start() and ping_evictor_stop() changed pet_refcount
without a lock, and each start reinitialized pet_waitq.  Since
targets on one server are mounted in parallel, two mounts can each
start an ll_evictor thread, or reinitialize the wait queue under a
thread already sleeping on it so it is never woken.  The orphaned
thread holds its lu_env, which pins mdd, osp and mdt, so rmmod
fails with "Module mdd is in use" (sanity-sec test_31).  A start
soon after the last stop could also run a second thread on
pet_list while the first was still emptying it.

Protect the count with a mutex, initialize the wait queue once, and
let a start revive a thread that has not yet exited rather than
start another.  A revived thread can find pet_list empty after its
wakeup, so it goes back to waiting instead of taking an entry.

This was split from https://review.whamcloud.com/64202, where an
MGS follower stopping and starting on failover hit the same race.
