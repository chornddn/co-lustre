LU-20457 osd-ldiskfs: no assert on name length in lookup cache

In some cases client could pack a name longer than NAME_MAX in the
rpc request, triggering a server assertion:

LustreError: (osd_handler.c:8127:osd_olc_save())
  ASSERTION( ln->ln_namelen <= 255 + 1 ) failed:
LustreError: (osd_handler.c:8127:osd_olc_save()) LBUG
Call Trace:
 lbug_with_loc.cold.8+0x5/0x43 [libcfs]
 osd_index_ea_lookup+0x6f8/0x770 [osd_ldiskfs]
 __mdd_lookup.isra.21+0x286/0x370 [mdd]
 mdd_lookup+0x10d/0x150 [mdd]
 mdt_lookup_version_check+0x59/0x2e0 [mdt]
 mdt_reint_rename+0x99b/0x1e30 [mdt]
 mdt_reint_rec+0x127/0x260 [mdt]
 mdt_reint_internal+0x4ac/0x7a0 [mdt]
 mdt_reint+0x5e/0x100 [mdt]
 tgt_request_handle+0xc0a/0x1b50 [ptlrpc]

With 6210f4ae96 ("LU-18783 llite: ensure dentry name within
ll_namelen") client will not send name longer than NAME_MAX, but still
server should not assert on it.

Do not cache lookups of names longer than LDISKFS_NAME_LEN. Names in
an encrypted directory are decoded before the lookup and are never
longer than that, but the MDD does not check their length, so also
return -ENAMETOOLONG on insert of a name that does not fit in an
ldiskfs directory entry.

Add sanity/24K to rename to a name longer than NAME_MAX, with a new
client fail_loc to skip the client name length check.

Mostly good, comments inline. The osd_olc_save() guard itself looks correct: LDISKFS_NAME_LEN is the real on-disk maximum, so the array shrink back to LDISKFS_NAME_LEN is safe and a 255-byte name still fits exactly.

The new sanity/24J does not appear to reach the code being fixed. On any client carrying 6210f4ae96 ("LU-18783 llite: ensure dentry name within ll_namelen") both ll_lookup_nd() and ll_atomic_open() reject d_name.len > sbi->ll_namelen before an RPC is sent, so the rename fails on the client and osd_olc_save() is never called. Could the test drive the server path directly, e.g. with a fail_loc that skips the llite length check, so it would actually have caught this LBUG?
