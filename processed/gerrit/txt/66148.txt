LU-20099 nrs: add weight based share queueing for mClock

Add a weight dimension to the mClock scheduler. It shares the rate
above the reservations by weight, with the Self-Clocked Fair
Queueing (SCFQ) algorithm. See nrs_mclock_class_insert().

The "weight" rule key takes a value from 1 to 1000, and the default
value is 100. Only a rule start command accepts it. A command of
another kind returns -EINVAL, and a value outside the range returns
-ERANGE. The weight dimension joins the default set. A policy that
starts with no dimension key now uses reserve, limit and weight.
A rule that names a reserved rate alone now also enters the weight
tree. The reservation is then not a ceiling for such a rule. The rule
takes a weight share above its floor.

The policy start command also gets a "weight" dimension key. The two
keys share one name and hold two meanings. On a policy start command
"weight=" is a bool. On a rule start command it is the share weight.
The two parse paths differ, so no command is ambiguous.

The dequeue reads the limit tree first. It moves each eligible class
bucket into the weight tree, up to nh_mcl_peek_max buckets. A
dequeue from the weight tree always gets a token, because the
ceiling already passed the bucket. The deadline minimum reads the
reserved tree and the limit tree alone. A request with no page count
costs one 1 MiB I/O in the weight tree.

A weight only policy has no rate dimension. Its default rule takes
no rate, and the rule dump prints no rate for it.

SCFQ may not hold the weight share when the server has enough
service threads to keep no backlog. The WF2Q+ algorithm is the
alternative for that case.

Add sanityn/test_77vh. With the weights 100 and 200 and 3 service
threads, two fio flows got 574 and 1145 IOPS. Each flow runs 8 jobs
at a queue depth of 16 and a block size of 1 MiB. A heavier profile
asked for about 4 GiB of pinned direct I/O buffers on the client.
The client then stalled in the page fault path.
