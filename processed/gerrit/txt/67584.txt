LU-20527 osp: don't trust OST LAST_ID past precreate window

ofd_create_hdl() answers a precreate request whose last OID is below
the OST LAST_ID with the OST's own LAST_ID + 1 ("trust the OST") and
precreates nothing.  osp_precreate_send() stores that reply into
opd_pre_last_created_fid without touching opd_pre_used_fid, so the
OSP then advertises every object in between as precreated, although
the OST created none of them for this request.  Once the jump exceeds
OST_MAX_PRECREATE * 2 the next lod_statfs_and_check() trips

  ASSERTION( sfs->os_fprecreated <= OST_MAX_PRECREATE * 2 ) failed:
  last_created [0x280000401:0xff02:0x0],
  next_fid [0x280000401:0x1:0x0], reserved 0

LU-15009 introduced that reply, but only for a gap below
OST_MAX_PRECREATE; a larger one was still refused with -EINVAL, so
os_fprecreated stayed under the assertion.  LU-17987 dropped that
refusal and an arbitrarily large jump now reaches it.

Treat a reply beyond the range we asked for as a resync: move
opd_pre_used_fid up together with opd_pre_last_created_fid, leaving
an empty precreate window, the same way that
osp_precreate_cleanup_orphans() handles the equivalent delorphan
reply.

Do this only while the window is already empty, which is the state
the reply is answered in here - it follows a sequence rollover, and
the crash above reports "reserved 0".  It is also the only state in
which moving opd_pre_used_fid is safe: osp_precreate_reserve() grants
a reservation only while opd_pre_reserved is below the number of
precreated objects, so an empty window has nothing reserved from it,
while emptying a window which has would leave opd_pre_reserved above
it and underflow the __u32 os_fprecreated in osp_statfs() - the same
assertion, from the other side.  A non-empty window keeps behaving as
before, so an OSP which simply missed a precreate reply still adopts
the objects the OST really created for it.

conf-sanity test_122a reaches this whenever an OSP rolls over to a
fresh sequence while OBD_FAIL_OFD_SET_OID is still set: the OST
stamps the new sequence's LAST_ID at seq_width - 255 and reports it
back.  MDT0000's OSP always rolls over, since it starts on the IDIF
sequence, so create through MDT0000 as well, and hold the fail_loc
until that OSP has really been given the inflated LAST_ID rather
than racing its rollover.  Check the resulting window directly too:
the os_fprecreated assertion is only reached while seq_width, which
the test framework sets to OSTSEQWIDTH / OSTCOUNT, is above
OST_MAX_PRECREATE * 2.
