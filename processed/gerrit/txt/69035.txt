LU-19699 quota: release grant via DQACQ on qunit shrink

qsd_id_glimpse_ast() returns the surplus space in the glimpse
reply and drops it from lqe_granted right away, but the slave
QSD never learns if the master fails to apply that release in
qmt_lvbo_update(). The master then keeps more grant accounted
than the slave owns, and the leak eventually causes a bogus
-EDQUOT. OBD_FAIL_QUOTA_PREACQ (fail_loc=0xa06) triggers this
and causes test_80 in sanity-quota.sh to fail intermittently.

Only report the surplus in lvb_id_may_rel and let the regular
DQACQ release path return it, then it will be transactional and
retried on failure, so the two sides cannot diverge.

The master still handles lvb_id_rel in qmt_lvbo_update() so that
older slaves keep working during a rolling upgrade. In the other
direction, a patched slave with an unpatched master still releases
via DQACQ, but the old master only waits 2s from "lqe_revoke_time"
before setting edquot, so a transient -EDQUOT is still possible in
that mixed version window.

qmt_adjust_edquot() is now the only thing holding edquot off
until the DQACQ arrives: anchor its grace period to the reply
that claimed the release (lqe_may_rel_time) rather than to
"lqe_revoke_time", which may be much older, and raise the
timeout from 2s to LQUOTA_MAY_REL_TIMEOUT (10s) to cover the
extra round trip and the QSD update thread scheduling, otherwise
the master sets edquot first and clients see a transient
-EDQUOT. The claim is recorded on the pool lqes too in
qmt_lvbo_update(), so that a pool lqe marked edquot by
qmt_set_revoke() is held off as well.

The release does not necessarily return what was advertised:
qsd_calc_adjust() recomputes it from the usage at the time the
request is sent, so part of the surplus may be consumed in the
meantime. The slave accumulates the advertised amounts on its
lqe and returns the sum in qb_usage, guarded by the new flag
QUOTA_DQACQ_FL_MAY_REL, with its next release request; when
there is nothing left to release it sends one without any space.
An unpatched master ignores the flag and behaves as before.

qmt_dqacq0() subtracts that amount, clamped at 0, from
lqe_may_rel of every lqe after the release has been committed:
settling it before the writes would drop the claim even when
qmt_restore_lqes() has to roll the release back. The amount is
per slave, so the surplus recorded for other slaves is kept.

A surplus older than LQUOTA_MAY_REL_TIMEOUT cannot hold edquot
off any more, so both sides drop it: the master in
qmt_adjust_edquot(), the slave in qsd_calc_adjust() and before
accumulating a new one. A claim whose release never arrives,
e.g. from a slave that went away, would otherwise keep delaying
edquot in every following round.
