--- Commit Message ---
LU-20085 llite: client vfs rename hang

ll_splice_alias doesn't try to reuse an existing dir alias
if its name is not equal to the new one.
It leads to a deadlock during rename when VFS tries to lock
inodes to both names/dentries, the same inode getting locked twice.

The code makes an exception for accessing Lustre ROOT inode
by .lustre/fid/<ROOT_FID>, but doesn't allow the same for
.lustre and .lustre/fid, these objects became not accessible
by their FIDs using .lustre/fid/, the corresponding test case
gets disabled.

Recheck of PS3 against PS2, which I gave +1. The delta is Andreas' rename to ll_d_ancestor() and CERROR to CWARN; the logic is unchanged. The idea is right and matches d_splice_alias(): keep one dentry per directory and return -ELOOP when the cached alias is an ancestor of the new name, which fixes a hang any user can trigger with two mounts. Looking at it again next to the HPE version that has landed since (LUS-13174) and next to LU-9868, I have to withdraw my +1.

Main concerns, details inline. The new -ELOOP return makes the statahead caller put the inode reference twice (namei.c:644). The ancestor check runs without rename_lock, and the cross-directory d_move() without the locks __d_unalias() takes; the landed HPE version at least has rename_lock around the check (namei.c:640). A lookup through .lustre/fid now moves a directory's real dentry into .lustre/fid (namei.c:593).

James' PS3 question is still unanswered. LU-9868 (https://review.whamcloud.com/37013, PS35) now fixes the same rename hang with d_splice_alias() for directories, keeps the old handling below .lustre/fid so that sanity 233b keeps working, fixes the statahead reference, and had +1s from Andreas and others on PS33/PS34. Both changes rewrite ll_splice_alias(), so please agree with James and Oleg which one lands; if it is 37013, the sanityn test from here is still worth keeping on top of it (Patrick's 69492 is based on it). On the HSM point from PS2: the copytool opens regular files through .lustre/fid and llapi_open_by_fid() uses open_by_handle_at(), while this patch changes only directory aliases, so HSM is not affected; 233b covers only .lustre and .lustre/fid themselves.

[minor] The change no longer applies to master (wc-checkpatch -1 since June): sanityn has test_122 and test_123 now, so the new test needs another number, and the always_except context changed. [minor] The summary should be in the imperative (in-tree lustre-commit skill), for example "llite: keep a single dentry per directory", and the body should say that such a lookup now fails with -ELOOP and what happens below .lustre/fid. [minor] The always_except line should point at its own ticket (inline).

Tests: without the fix the sanityn scenario self-locks in lock_rename(), which takes the i_rwsem of foo once through each of its two dentries (Patrick reports the same for 69492, which is built on this reproducer). With the fix it passes through the -ELOOP branch (PS3 janitor, ldiskfs+DNE console: cannot reuse a dir alias "foo" ... rc = -ELOOP). The alias-move branch and statahead are not covered (inline).
