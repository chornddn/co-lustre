LU-20157 llite: clear PageUptodate only on reclaim

Client lock replay could deadlock with a buffered read.  Before
replaying locks, ldlm_cancel_unused_locks_for_replay() cancels the
idle locks of the namespace, and discarding their pages in
osc_lock_discard_pages() took invalidate_lock of the inode exclusively
in vvp_io_init().  A reader filling the page cache of that inode holds
invalidate_lock shared while its read RPC waits for the import to
leave recovery, so the replay thread waited for the reader and the
reader for the replay.  A blocking AST or LRU cancel waited the same
way for any reader of the inode (LU-19427).

vvp_page_delete() cleared PageUptodate on every cl_page teardown.
This violates the kernel invariant, relied upon since v5.13
79e3094c53c5 ("mm/filemap: drop check for truncated page after I/O"),
that invalidation leaves PG_uptodate intact.  A buffered read racing
a DLM blocking AST could therefore find a !uptodate folio and return
-EIO (LU-16651) instead of retrying, which is why invalidate_lock was
taken there.

The flag is only needed where page removal can fail after the cl_page
is already gone.  That is ->release_folio: do_release_folio() commits
cl_page_delete() before __remove_mapping() decides whether
folio_ref_freeze() succeeds, so an extra vmpage reference can leave a
folio in the mapping with no cl_page.  Such a folio is invisible to
osc_page_gang_lookup(), which walks osc->oo_tree rather than
mapping->i_pages, and would be served stale forever.  The lock cancel
and truncate paths remove the folio unconditionally: cl_page_discard()
via generic_error_remove_folio(), and ll_invalidate_folio() via
filemap_remove_folio().

Move the clear into do_release_folio(), inside the !cl_page_in_use()
branch so it fires only when the cl_page is actually destroyed.  This
covers reclaim and also O_DIRECT write invalidation, which reaches
->release_folio through invalidate_inode_pages2_range() and never held
invalidate_lock.  The lli_page_inv_lock seqlock is retained for the
reclaim race named in LU-16160.

With lock cancel no longer clearing PG_uptodate, it no longer needs to
exclude page cache filling, so drop ci_invalidate_page_cache and the
filemap_invalidate_lock() pair added by LU-16651.  The
HAVE_INVALIDATE_LOCK configure check has no remaining users and is
removed.

The reclaim refcount race itself is deliberately left alone, and
PG_uptodate is still cleared to mask it.  Gating the teardown on a
page_ref_freeze() of the vmpage was tried and rejected: where the
freeze succeeds the folio is freed and PG_uptodate is never observed,
so skipping the clear gains nothing, while a removal that still fails
in the residual window between the unfreeze and __remove_mapping()
would leave an orphan with PG_uptodate set.  Aborting the release on a
failed freeze does prevent orphans, but changes ->release_folio
semantics for every caller and regressed sanity 255b and 398a.
Closing the window properly requires deferred teardown from
->free_folio.

Add recovery-small test_18d (from Di Wang) and test_18e (from
Alexander Boyko) for the lock replay deadlock, and sanityn test_126a-c
for a blocking AST, an mmap fault reader and an LRU cancel waiting for
a reader of another stripe of the same file.
