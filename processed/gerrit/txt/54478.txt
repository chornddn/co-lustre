LU-10499 pcc: Add dio support for data copy during attach

PCC attach performance is bottlenecked by single threaded
buffered I/O performance.  We could do multi-threading, but
multi-threaded buffered I/O to one file has a very low
performance ceiling.  In order to significantly speed up
PCC attach performance, we need to switch to DIO.

DIO cannot be done from kernel memory due to various
restrictions, so we call out to a usermode helper,
ll_fid_path_copy, for files of at least
llite.*.pcc_dio_attach_threshold bytes (32 MiB by default).
Each I/O is llite.*.pcc_dio_attach_iosize_mb in size (32 MiB
by default, 0 disables the DIO copy).

Note that the helper uses open by fid because given a
file pointer, it's not possible to reliably generate the
path to a file on Lustre due to container namespace issues.
Specifically, the path used by the user may not work for
our helper program due to namespace differences.  So we
must use open by fid for the Lustre side of the copy.
"lctl pcc add" passes the Lustre mountpoint to the kernel as
the "mntpath" parameter of the PCC backend for this.  An old
lctl that does not pass it gets a buffered copy, and the new
lctl retries without it on an old kernel.  If the helper is
missing or fails, e.g. because the PCC backend does not support
O_DIRECT, the kernel does a buffered copy instead.

This patch improves attach performance from about 1 GiB/s
to about 5 GiB/s.  This performance figure includes time to
read the data from Lustre *and* to write it out to PCC.

Fixes from the original patch series:
- a helper that failed was treated as a successful copy,
  since the positive exit status from call_usermodehelper()
  is not an errno, leaving a PCC copy with missing data.
- encrypted files must keep the kernel copy, so that the
  PCC copy holds ciphertext (S_PCCCOPY).
- remove the el7 workaround that unlocked the parent directory
  during the copy from atomic_open().  With HAVE_INODE_RWSEM
  gone it was compiled for all kernels, where it would
  up_write() a lock that may be held shared.
- in ll_fid_path_copy, terminate the getopt option list, only
  join threads that were started, return per-thread errors,
  and fix the chunk size rounding.  Each thread opens its own
  destination fd, so that the buffered fallback for an
  unaligned tail does not clear O_DIRECT for all threads.
- llapi_pccdev_set() returned a positive errno on failure.

Also fix sanity-pcc test_40, which compares async and sync
attach times with paused bulk RPCs, by disabling the DIO copy.

EX-5014 pcc: avoid deadlock during DIO open attach on rhel7

The Maloo testing fails with sanity-pcc/45 due to a deadlock
on the rhel7 kernel, which uses a mutex for inode locking.
During ->ll_atomic_open(), the kernel takes this mutex on the
parent inode, and the user space helper program ll_fid_path_copy
also tries to take it during lookup.

LU-10499 pcc: dio attach failed on non-blksz-aligned file

PCC attach failed due to do DIO copy on files with blksz unligned
file size.  The reason is that the copy tool ll_fid_path_copy
fails on non-blksize-aligned file for PCC backend (such as a local
Ext4 file system) using direct I/O.  This fixes the bug by falling
back from direct I/O to buffered I/O mode when copying the tail
non-blksize-aligned part of the file.

Was-Change-Id: I5287563029269032a91397c0094e2ccede73b9b1

LU-10499 pcc: add threshold to determine direct I/O during attach

This patch adds the threshold tunable parameter to determine doing
direct I/O or buffered I/O for data copying during attach:
	llite.*.pcc_dio_attach_threshold
The default value is same as direct I/O size: 32MiB.

And the usage of the parameter "pcc_dio_attach_size_mb" is
deprecated, and use "pcc_dio_attach_iosize_mb" instead.

Was-Change-Id: I393d6a06523303e749192ba9978449c3d75886ae

LU-10499 pcc: parallel data copy for attach

This patch parallelize the data copying work for pcc attach
by using multiple threads in the ll_fid_path_copy helper,
llite.*.pcc_dio_attach_threads_per_file (4 by default).

Nvidia provided performance numbers for this from their
environment.  This was with 4 MiB I/O size, they reported
speed was similar but *slightly* lower at larger block
sizes. This is probably an EXT4 limitation since Lustre
speed scales with those larger sizes.  (As PCC attach is a
copy from Lustre to EXT4.)

This is for attaching a single 2 TiB file, they also
reported no performance regression for datasets with many
small files.

threads: 1       2         4          8
speed:   4 GiB/s 7.8 GiB/s 14.1 GiB/s 15.2 GiB/s

Performance improved only very slightly past 8 threads,
and 4 threads is clearly the sweet spot for performance.
