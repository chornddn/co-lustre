LU-20157 ldlm: do not block lock replay on invalidate_lock

Before replaying locks, ldlm_cancel_unused_locks_for_replay() cancels
the unused locks in the namespace. Cancelling a lock calls
osc_lock_discard_pages(), which takes invalidate_lock exclusively for
the whole inode mapping:

  ldlm_lock_replay_thread
   __ldlm_replay_locks
    ldlm_cli_cancel_list_local
     ldlm_lock_cancel
      ldlm_cancel_callback
       osc_ldlm_blocking_ast
        osc_lock_flush
         osc_lock_discard_pages
          __cl_io_init
           vvp_io_init
            down_write            <== waits for invalidate_lock

Meanwhile a read thread holds the same lock shared across its read RPC,
and that RPC is delayed until the import leaves recovery. The reader
waits for replay to finish, replay waits for the reader, and neither
completes.

Skip invalidate_lock for the lock replay thread. That is safe here for
three reasons.

First, no page cache fill can be in progress under the lock being
cancelled. ldlm_prepare_lru_list() selects it under lock_res_and_lock()
with LASSERT(!lock->l_readers && !lock->l_writers) and sets CBPENDING,
which stops it gaining any, and lock_matches() refuses to match a
CBPENDING lock with no users, so nothing can find it to use it either.
Filling a page requires a DLM reference on a lock covering that page:
cl_io_lock() takes one for reads and for the mmap fault path, and
osc_io_read_ahead_prep() takes one for readahead, which is clipped to
the extent of the lock it found. So the fill that invalidate_lock exists
to serialise against cannot exist under this lock.

Second, a page in the extent may still be covered by another lock and be
in use under it. That is the LU-16651 case: a reader sitting between
->readpage() unlocking its page and its own PageUptodate() check, which
holds no page lock. Such a reader holds a lock over the page with
l_readers set, so check_and_discard_cb() finds that lock and keeps the
page. Use check_and_discard_cb() in this mode even when discarding, so
the page is left to the lock that covers it.

Third, what keeps a page from outliving the lock that covered it does
not change. Pages which are discarded are still taken with the blocking
cl_page_own() and removed while holding the page lock, and the discard
still runs inside the cancelling AST and completes before
ldlm_lock_cancel() releases the lock. invalidate_lock was not what
enforced either of those.

Note that a read of an already cached uptodate page takes neither a DLM
lock nor invalidate_lock, so it is not serialised against a discard with
or without this patch. ll_read_from_cache() calls
generic_file_read_iter() with no cl_io, and in the read path
invalidate_lock is taken only while filling - filemap_create_page() on a
miss and filemap_update_page() under !PageUptodate - and by readahead in
page_cache_ra_unbounded(), each of which releases it before returning.
filemap_read() then copies out of the page holding only the reference
taken by filemap_get_read_batch(). A discard can land between that
reference and the copy either way, so this patch does not change that
exposure.

Only lock replay is affected. Blocking ASTs, the LRU shrinker, lru_size
and namespace cleanup take invalidate_lock as before.

Add recovery-small test_171, which checks that the import recovers while
a read is holding invalidate_lock of an inode with an idle lock on it.
