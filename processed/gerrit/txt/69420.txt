LU-20875 ptlrpc: let be less strict for max frags

The server might reduce the maximum bulk size after the initial
connection, and this could cause large extents to be created
and prepared for sending. Therefore, it might exceed the current
limit. Let's make the bulk size checking less strict.

Instead of rejecting the whole bulk descriptor at creation time, do
the capacity check in the place which knows the real descriptor state.
add_kiov_frag() was declared void, so a fragment which does not fit
could only be reported with an LASSERT, and both limit checks were
done after the store, so an out of bounds write into bd_vec[] or
bd_mds_off[] happened before the panic.

Check the bd_max_iov and PTLRPC_BULK_OPS_LIMIT bounds before storing,
return -EOVERFLOW instead, and make every add_kiov_frag() caller fail
the RPC.

Some concerns, see inline comments. The removed check also caught max_brw == 0 and acted as the only bound on client-supplied nfrags before the bd_vec allocation, so removing it outright re-exposes both. Keeping a relaxed check (e.g. against LNET_MAX_IOV * PTLRPC_BULK_OPS_COUNT, plus max_brw == 0) would fix the reconnect ENOMEM without that. A regression test would also help: lower obdfilter.*.brw_size, force a client reconnect with large dirty extents cached, and check the writes complete.
