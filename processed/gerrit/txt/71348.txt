--- Commit Message ---
LU-6654 osd-ldiskfs: do not keep iobuf wait queue in the iobuf

osd_bio_fini() drops dr_numreqs to 0 and then calls
wake_up(&iobuf->dr_wait).  The service thread waiting in
osd_trans_stop() or osd_do_bio() checks dr_numreqs without the wait
queue lock, and finish_wait() does not take the lock either once
autoremove_wake_function() has removed the entry.  So the service
thread can see 0 and move on while the completion side still holds
dr_wait.lock: its next request re-initializes the iobuf, and
init_waitqueue_head() writes 0 into the held spinlock, or the service
thread exits and osd_key_fini() frees the osd_thread_info that holds
the iobuf.

With paravirt spinlocks on KVM guests the first case shows up as
  pvqspinlock: lock 0x... has corrupted value 0x0!
  WARNING: ... __pv_queued_spin_unlock_slowpath
  __wake_up+0x44/0x60
  osd_bio_fini+0x47/0x70 [osd_ldiskfs]
under sustained OST write load.  The second case is the freed-memory
GPF in __wake_up_common() of the original LU-6654 report.

Remove dr_wait and wait with ___wait_var_event() on &dr_numreqs, woken
by wake_up_var().  The hashed variable wait queues are static, and the
completion side only uses the address of dr_numreqs as a key, so it
no longer touches the iobuf after the decrement.  The waiter keeps the
lockless fast path for transactions without data I/O, reads the
counter with acquire semantics so the later dr_error/dr_elapsed loads
are ordered after it, and still sleeps in io_schedule() so the time is
accounted as iowait.
