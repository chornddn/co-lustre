LU-21236 gnilnd: free vmalloc buffers atomically

kgnilnd_free_fmablk_locked() frees the mailbox block with
vfree() under gnd_fmablk_lock, and vfree() may sleep. Use
kvfree_atomic() for gnilnd vmalloc buffers, as LIBCFS_FREE()
does for large LNet buffers.

--- Message (Andrew Perepechko, 2026-11-20 07:50:27.000000000) ---
Patch Set 5:

The change replaces vfree() with kvfree_atomic() in kgnilnd_vfree(), the single free helper for gnilnd's vmalloc buffers. kgnilnd_free_fmablk_locked() calls it while holding the gnd_fmablk_lock spinlock, and vfree() may sleep, so the original code could schedule out the lock holder; kvfree_atomic() fixes every caller of the helper at once.

I checked the deferred-free path on both kernel variants: kgnilnd_vzalloc() always uses __vmalloc(), so the buffers are always vmalloc-backed and the free is deferred to a workqueue everywhere — mainline kvfree_atomic()/vfree_atomic() and the compat_vfree_atomic() implementation use the same per-CPU llist plus system_wq design, and both handle NULL. On the lifetime side, the block is removed from the device list and its descriptor is freed under the same lock, and the free only runs after all mailboxes are released and no purgatory holds remain; deferring the actual vfree only extends the buffer's validity window, so I see no new use-after-free or reuse race.

Two notes, neither blocking: gnilnd is only built when GNI headers are present, so the review build and the Maloo sessions do not compile this file; the substitution is a direct API swap and the declaration chain is the one gnilnd.h already uses for LIBCFS_FREE(), which calls kvfree_atomic() the same way. And with the free now deferred, freed buffers are held until the workqueue drains, which is transiently visible during bulk teardown or stack reset — the established trade-off of atomic freeing.

checkpatch and the build are green; the Maloo sessions for build 137152 were still running at the time of this review. Looks good to me.
