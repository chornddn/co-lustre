--- Commit Message ---
LU-20949 llite: wait for the folio lock in ll_io_zero_page

On an encrypted file, truncate in the middle of a page calls
ll_io_zero_page() to zero the end of that page and write it. It
previously got the folio with FGP_NOWAIT, and failed the truncate with
-EOPNOTSUPP when another thread held the folio lock, as a page fault
through mmap, readahead, reclaim or page migration did briefly. This
could cause issues if multiple threads truncated the file
concurrently.

Now wait for the folio lock instead, as other truncate paths do. Only
the extent lock on the page is held at this point, and the IO paths
also take the folio lock after the extent lock, so this does not
invert the lock order.

Fixes: adf46db962f6 ("LU-12275 sec: support truncate for encrypted files")

Looks good; no need to re-spin. I traced the folio holders this can now wait on (fault/mkwrite, readahead, write_begin, setattr truncate_inode_pages, reclaim/migration). Each one takes the folio lock after its extent lock, or never waits on a DLM lock while holding the folio, so I found no lock inversion. The one optional suggestion is for whenever the patch is next refreshed: this fixes a user-visible failure (truncate(2) of an encrypted file returning EOPNOTSUPP), so a small regression test would be nice. For example, a sanity-sec subtest could run several concurrent unaligned truncates on an encrypted file, maybe alongside an mmap reader of the same page, and check that none of them fails.
