LU-21204 lod: do not let another component's OSTs cost stripes

A plain component whose stripe count is larger than the number of OSTs
is clamped to the OST count and flagged LOD_USES_DEFAULT_STRIPE, so
only 3/4 of the count has to be found before allocation succeeds.
lod_ost_alloc_rr() keeps its first pass off the OSTs used by another
component of the file and retried only while short of that minimum, so
a trailing PFL component could stop one OST short: -c 40 on an 8-OST
file system, with one OST taken by an earlier component, allocated 7
stripes instead of 8 and capped the file at 112 TB, while -c 8 reused
the OST and got all 8.

An OST used by another component is only a preference, so it must not
cost stripes: when the first pass kept such an OST off and the
component is still short of the requested count, repeat that pass with
the preference relaxed.  The OST kept off may have been unusable for
another reason too, in which case the repeat finds nothing new.  Only
that preference is relaxed, so slow, degraded and reconnecting OSTs
are still avoided, and an allocation that is short of healthy OSTs
behaves as before.

That repeat is gated on the requested count rather than on the
minimum, so it also runs where the count is not default-striped.  This
is intended, and changes two other cases:

- -c -1 is clamped and flagged like -c 40, so the last component of a
  default PFL layout now shares the earlier components' OSTs where it
  used to stop an OST short of them.

- An EC data component with more than one raid set, without
  overstriping, used to stop at its 3/4 minimum and let
  lod_ec_shrink_data_geometry() shrink the layout; it now keeps the
  requested geometry by reusing such an OST.  A multi-raid-set parity
  component, whose minimum is 0, also takes the extra pass before
  lod_ec_add_parities() fills the rest from the data component.

Record the two decisions in lod_rr_retry_comp() and
lod_rr_retry_slow() and move them, with lod_stripe_count_min(), into
lod_internal.h so that a test module can cover them without exporting
a symbol.  The KUnit cases live in lustre/kunit/ and are packaged with
the other test modules, so lod.ko never depends on KUnit, which is not
installed on most systems and taints the kernel when it runs.
