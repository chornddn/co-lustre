LU-19804 quota: enforce projquota on PROJINHERIT rename

When renaming a file into a directory with the project inherit flag,
it will inherit the new project ID, then the project quota should be
enforced on this project ID.

This patch reserves the quota space before the rename and releases
it after the rename completes. If the rename overwrites the last
link of a file charged to the same project, the space freed by
unlinking that file in the same transaction is credited to the
reservation.

The reservation is released when the MDT transaction commits, while
the OST objects change project ID later, when the osp sync thread
replays the setattr, so the check is per rename: back-to-back
renames can exceed the limit, while concurrent ones are checked
together. A chgrp reservation has the same window.

The size and blocks of the object are not known on the MDT, since
the data lives on the OSTs, so the client sends them in the rename
request, but only for the renames that are charged. The MDT then
charges the largest of the client values, the MDT inode attributes
and the lazy SOM (LSOM) attributes read from trusted.som, which are
only the minimum size that a client could have reported. A strict
SOM is exact and is used instead of all of them. An old client which
sends nothing is covered by the same rules, its request then carries
the MDT inode and LSOM values on their own.

A file released by HSM has no data in the filesystem anymore, only
the size and blocks of what was archived are kept in the inode and
in the SOM, so moving it does not consume any project space. The
state is read from trusted.hsm and the space is charged again when
the file is recalled.

Before the rename, the client writes back its dirty pages and
glimpses the OSTs, so that the block count it sends is the one
already allocated. Without the writeback, the pages not written out
yet are counted as the LU-417 placeholder of one block, and a large
file is charged about one block.

Data that has not reached the OST is not accounted. The MDT can not
see pages that are dirty in another client's cache, that become
dirty again after this writeback, or that are left over from a
failed writeback. Such data is written out after the rename with the
project ID the client still has cached, and the project ID change on
the OST does not enforce quota, so it is never charged to the new
project. Rename can not stop other writers, so only the space
already allocated on the OSTs is checked.

The size and blocks the client sends also raise the lazy SOM of the
source object, in the same transaction as the rename: a rename can
not be replayed if only part of it was committed, so the update can
not run in a transaction of its own. A strict or stale SOM is left
alone, and a file without a SOM gets one from its next close, as
mdt_lsom_update() does. The SOM is read again under the object write
lock, so a value already committed by a close or a truncate is kept
and this update never lowers it; a close that read the attributes
earlier can still lower it afterwards. The values are the cached
ones of the client, without a lock, so they can leave the lazy SOM
larger than the real size until the next truncate.

MDS_RENAME_SIZE_VALID reuses the bit of the obsolete MDS_SOM flag
instead of taking a new one, since a rename request never carries
the close-time meaning of that bit, so no additional bit of the
32-bit mds_op_bias is consumed.

The mdd_attr_set() group quota code is refactored onto the new
mdd_quota_reserve()/mdd_quota_commit_or_release() helpers, which are
shared with the rename path, qsd_reserve_or_free_quota() also gets a
bypass so that root renames charged to a project ID are not enforced
against PRJQUOTA when the active nodemap grants ignore_root_prjquota
role and the QSD's root_prj_enable is off. The space reserved for a
group change is now the largest of the value sent by the client and
of the MDT inode attributes, so a chgrp can reserve a little more
under the new group than before, and be refused with -EDQUOT where
it used to succeed.

The test_101 is added in sanity-quota, it also checks that a rename
raises the LSOM of the source object and that the data kept on the
MDT is charged.
