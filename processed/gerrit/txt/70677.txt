LU-21127 mdt: set HSM dirty on close of a lost open handle

When a client is evicted while holding an archived file open for
write, mdt_export_cleanup() sets HS_DIRTY without a changelog record
(uc_enable_audit == 0). The client keeps writing, and its final close
then uses the lost open handle: mdt_close_internal() returns -ESTALE
and MDS_DATA_MODIFIED is ignored, so changelog-driven archivers never
see the change.

When a close of an unknown handle carries MDS_DATA_MODIFIED, have
mdt_close() set HS_DIRTY on an archived file the caller may write,
raising CAP_FOWNER as mdt_add_dirty_flag() does so that non-owner
writers are covered. If HS_DIRTY is already set, clear it first so
that a CL_HSM dirty record is logged. Closes that never reach the MDT
(the client never closes, or the close fails before the import
recovers) are not covered.

Add sanity-hsm test_52b for owner, non-owner and never archived files;
rename test_52 to test_52a.

Some concerns, see inline comments.

The commit message traces the missing record to mdt_export_cleanup()->mdt_ctxt_add_dirty_flag(), which runs with a fresh session ucred where uc_enable_audit == 0, so mdd_changelog_enabled() suppresses the CL_HSM record. hsm_init_ucred() in mdt_coordinator.c already sets `uc->uc_enable_audit = 1` for internal HSM activity. Would setting the same flag in mdt_ctxt_add_dirty_flag() be the more direct fix for the eviction-time record? It would also cover clients that never come back after eviction (crash/reboot, the common case), and clients that close while the import is still invalid. In that case md_close() fails with -EIO, the follow-up ll_hsm_state_set() RPCs fail the same way, and LLIF_DATA_MODIFIED has already been consumed by test_and_clear_bit(). The client-side part still seems useful for writes made through the stale fd after reconnect, so the two pieces look complementary.
