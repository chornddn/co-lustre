LU-20842 lnet: fix peer discovery ref leak

A peer with both `lp_ping_mdh` and `lp_push_mdh` outstanding gets
both unlinked by `lnet_peer_cancel_discovery()` during queue cleanup
1. `LNetMDUnlink()` may deliver one unlink inline if idle and the
other deferred if busy. The inline event moves the peer off
`ln_dc_expired`, allowing cleanup 2 to stop waiting and cleanup 3 to
dequeue it. When the deferred event finally arrives,
`lnet_peer_queue_for_discovery()` finds `lp_dc_list` empty, takes a
fresh reference, and re-queues the peer onto `ln_dc_request`,
ultimately causing a reference leak.

Rather than tracking outstanding MD unlinks, fix this at its single
root cause: `lnet_peer_queue_for_discovery()` must not take a new
reference once discovery is no longer running. Add a check for
`the_lnet.ln_dc_state != LNET_DC_STATE_RUNNING` in the branch that
handles a peer not currently queued: `list_empty(&lp->lp_dc_list)`.
A peer that is still queued is unaffected by this check and continues
to be moved between queues as before, so cleanup 2 can still drain
`ln_dc_expired` and return without hanging.

AI code review results below, please doublecheck

Problematic, see inline comments. The counter only works when every cancelled MD produces an LNET_EVENT_UNLINK, but a busy MD's unlink arrives on its SEND/REPLY/ACK completion event instead. That leaves lp_dc_mdunlinks permanently non-zero on surviving peers, which can later stop the peer from being requeued and hang cleanup 2. The case where both MDs are busy also still leaks the peer. A smaller fix may be to have lnet_discovery_event_handler() skip taking a fresh queue reference (lp_dc_list empty) once ln_dc_state is no longer LNET_DC_STATE_RUNNING, as lnet_peer_queue_message() and lnet_peer_push_event() already do. A sanity-lnet case that cancels discovery with a ping/push in flight would also help.
