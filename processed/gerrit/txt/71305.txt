LU-21037 o2iblnd: negotiate path MTU both sides can carry

On RoCE there is no SA to hand out a path record, so the active
side builds it from its own netdev MTU and the passive side copies
the path MTU out of the CM REQ. The passive side never compares it
with what its own netdev can actually carry.

When the two ends run with different netdev MTUs, the connection is
built with the larger MTU and every message that does not fit into
the smaller netdev's frames is dropped. Small messages still work,
so the link looks half dead: a client can fail to mount because the
~8KB MGC config log read never completes, while lnetctl ping to the
same peer succeeds, and nothing is logged about the MTU mismatch.

Reject connection requests that the local port cannot carry, and
let the active side reconnect with a smaller MTU:

- advertise IBLND_REJECT_MTU support and the local port's enum
  ib_mtu in the unused ibm_credits field of IBLND_MSG_CONNREQ;

- in kiblnd_passive_connect(), compare the path MTU of the CM REQ
  with the RoCE port's active_mtu and reject it with
  IBLND_REJECT_MTU when it is too large, returning the local MTU in
  the byte that used to be ibr_padding, so the wire format does not
  change;

- in kiblnd_check_reconnect(), remember the peer's limit in the new
  kib_peer_ni.ibp_max_mtu so that later reconnects are capped
  straight away, and give up rather than reconnect when the peer's
  limit does not actually lower the MTU, to avoid a reject loop;

- cap the path MTU in kiblnd_setup_mtu_locked() with the minimum of
  the path record, ib_mtu and ibp_max_mtu. As part of that, ib_mtu
  can now only lower the path MTU: raising it above what the route
  resolved to built a QP larger than the fabric can carry, and
  would also undo the peer's cap on every reconnect.

Peers that do not set the negotiation bit are still accepted, only
a warning is logged, so a mixed cluster behaves as before and the
mismatch becomes visible in dmesg. The check is made only when
rdma_port_get_link_layer() reports Ethernet, so native IB and iWARP
are not affected.

mtu_negotiate=0 makes a node opt out completely: it neither rejects
connection requests nor advertises its port MTU, so it behaves as
before the patch. A limit learned from a peer is remembered for that
peer_ni only, and is dropped when its last connection goes away.
