LU-20590 ldlm: never file an LRU-excluded lock on the LRU

ldlm_cli_inodebits_convert() returns a lock to the client LRU with no
examination of LDLM_FL_NO_LRU. A lock which its owner holds out of the
LRU can therefore become a reclaim candidate again.

No lock reaches this today. The reason is not that the flag is rare
on a client. mdt_remote_object_lock_try() enqueues LDLM_IBITS, and
osp_md_object_lock() passes LDLM_FL_NO_LRU. An MDT which acts as a
client thus does hold ibits locks with the flag. The reason is the
caller set. ldlm_cli_convert() has exactly one caller,
ll_md_blocking_ast(). Only the regular ibits locks of a client file
system reach the convert path, and those never carry the flag. The one
llite lock which does, the lease, uses ll_md_blocking_lease_ast
instead.

The rest of this series gives the flag a second owner. That owner does
reach the convert path. LU-20590 is an IO which restarts without end
after the client reclaims a layout lock. The layout itself did not
change. The correction holds that layout lock out of the LRU for the
length of the IO. A layout lock is a regular ibits lock of a client
file system. The refusal below must therefore land first.

Refuse to file such a lock in ldlm_lock_add_to_lru_nolock(). Two of
the three callers decide list membership without an examination of the
flag. The convert path and ldlm_lock_touch_in_lru() are the two.
ldlm_lock_decref_internal() does test the flag itself. The refusal
therefore belongs at the point which files a lock, and not at each
caller.

The refusal alone does not cover a lock which is already on the LRU
when the flag arrives. LDLM_FL_NO_LRU therefore carries a duty for
whoever sets it, which the comment at the refusal states. The next
patch of this series honours that duty.
