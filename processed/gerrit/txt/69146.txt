LU-18461 mdd: fix merge buffers and refresh the merged layout

mdd_xattr_merge() only clears mdi_buf[0] once it has read the layout
of the victim, while the rest of the MDD makes that very slot point
at a buffer owned by someone else, mdd_buf_get() style:
mdd_links_write() leaves it pointing at the link xattr buffer of the
thread.  A victim with no layout to give, or a failure of the
project ID declare, leaves the function through 'stop', where
lu_buf_free() then frees a buffer the thread info still holds, which
KASAN reports as a use after free in linkea_data_new().  Claim both
slots before the first error path may free them.

lod_declare_layout_merge() also reloaded the striping of the target
from the merged layout it had just built.  A declare may still be
rolled back, so the target was left with an in-memory layout its
inode does not carry, and only the rollback path dropped it, by way
of the LU_XATTR_REPLACE set.

Refresh the striping in the execute phase instead, once the new
layout is on disk, exactly as a split already does.  A failed
lod_striping_reload() drops the cached striping itself and a
rollback goes through LU_XATTR_REPLACE, which frees it as well, so
no explicit invalidation is needed and the layout no longer has to
be declared last.  As the declare no longer bumps the generation,
lod_save_layout_gen_intrans() records the pre-merge one and
lod_check_layout_gen_intrans() detects a foreign change instead of
the value the declare itself stored.  Only the buffer checks the
reload used to perform are kept in the declare, as
lod_comp_md_check().

The layout built by the declare is kept in a buffer owned by the
MDD, described by struct md_layout_build, and stored as is by
lod_layout_build_store().  lod_layout_gen_next() is split out of
lod_obj_inc_layout_gen() for a declare that computes a generation
without publishing it.  A layout join is built on top of all of
those.

lod_invalidate() left the cached striping behind while its caller
asks for everything to be read again, make it drop that as well.
