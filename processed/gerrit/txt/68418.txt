LU-20650 lfs: find --changelog, the log as source

--since treats the changelog as a candidate set and verifies each hit
against the live object, so it answers as it is now.  --changelog
replaces the source: it reads the log and nothing else, and answers as
it was recorded.  That is why -name here matches the name in the event
rather than the object's current one, and why an object unlinked since
the event is in this answer and cannot be in --since's.

Three rules keep the two apart, and each is a refusal rather than an
approximation.  A predicate the changelog cannot answer -- -size,
-blocks, the layout options, -projid, -printf -- is refused naming
itself, unless --resolve is given to look the object up.  An object
time is refused outright, because a record carries an event time and
the two are not the same question; the message says --since 1d is how
to ask it.  --maxdepth and --mindepth describe a walk, and --ost and
--mdt need something a per-MDT log does not have.

The path argument means the filesystem rather than a subtree, since a
changelog knows nothing about where an object sits, and a path below
the mount is refused unless --resolve makes a pathname to match
against.  Output is a pathname where the FID still resolves to one and
the FID where it does not, which is the whole point of asking.

--resolve fills what the stream lacks and never restates what it has,
so the merge starts from the looked-up record and puts every field the
event answered for back over it.  Only the type bits of the mode are
taken from the event, because a record says what kind of object was
created and never its permissions, so -perm still reads the live one.

--changelog takes an MDT name or "all", required rather than optional
because getopt_long() accepts an optional argument only as
--changelog=VALUE.  One named MDT is also what makes a bare --since
index unambiguous, the index being paired with the log it came from.
