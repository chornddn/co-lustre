LU-20650 lfs: find --changelog, the log as source

--since treats the changelog as a candidate set and verifies each hit
against the live object, so it answers as it is now.  --changelog
replaces the source: it reads the log and nothing else, and answers as
it was recorded.  That is why -name here matches the name in the event
rather than the object's current one, and why an object unlinked since
the event is in this answer and cannot be in --since's.

Three rules keep the two apart, and each is a refusal rather than an
approximation.  A predicate the changelog cannot answer -- -size,
-blocks, the layout options, -projid, -printf -- is refused naming
itself, unless --resolve is given to look the object up.  An object
time is refused outright, because a record carries an event time and
the two are not the same question; the message says --since 1d is how
to ask it.  --maxdepth and --mindepth describe a walk, and --ost and
--mdt need something a per-MDT log does not have.

The path argument means the filesystem rather than a subtree, since a
changelog knows nothing about where an object sits, and a path below
the mount is refused unless --resolve makes a pathname to match
against.  Output is a pathname where the FID still resolves to one and
the FID where it does not, which is the whole point of asking.  With
--resolve the subtree is tested the way --since tests it, over every
name the object has rather than the one linkno 0 answered with.

That fallback needs saying in the code and not only here.
find_decide() resolves a FID through the mount for a target scan too,
and there an object with no pathname is counted rather than printed --
the target's own objects never had a name, and half a line is worse
than none.  An object unlinked since its event did have one, and the
record is the answer, so this source asks for the FID instead.
Without it the case --changelog exists for -- the one --since cannot
report -- came back silently missing, counted as "no pathname" while
the man page said it would be named.

This is also the caller that hands find_prefilter() a record with no
name at all: cr_namelen is 0 for a MARK, and for an event on a FID
whose name the log never held.  fnmatch() would take that NULL, so the
guard for it moves here, where the caller that needs it is.

--resolve fills what the stream lacks and never restates what it has,
so the merge starts from the looked-up record and puts every field the
event answered for back over it.  Only the type bits of the mode are
taken from the event, because a record says what kind of object was
created and never its permissions, so -perm still reads the live one.

--changelog takes an MDT name or "all", required rather than optional
because getopt_long() accepts an optional argument only as
--changelog=VALUE.  One named MDT is also what makes a bare --since
index unambiguous, the index being paired with the log it came from.

--resolve now hands find_decide() what the lookup found.  The merged
record carries sr_path, sr_parent_fd and sr_fd and they were dropped,
so the decider ran with no path and no descriptor and -size, -blocks,
-projid and -printf were undecidable for every object -- the run exits
0, reports nothing, and warns that the changelog had no answer, which
is the opposite of what the man page promises --resolve is for.  A
striped file's size lives on the OSTs and only a stat through the path
glimpses it, so passing the path is what makes the promise true.

The subtree is applied on that path too.  A path argument below the
mount is refused with "add --resolve to search below it", but nothing
on the --resolve path consulted it, so the search answered for the
whole filesystem and printed objects outside the subtree.  Only the
lookup can say where an object is, so the test goes where the path
arrives.

Four more options are refused rather than answered from a record that
cannot carry them.  --xattr was the loud one: it reached
llistxattr(NULL, ...) and printed an error per object.  -perm, -links
and --attrs were quieter and worse -- the record's fields are zero, so
"--perm 644" matched nothing and its negation matched everything,
which is the approximation the refusal exists to prevent.  All four
are answerable once --resolve supplies the object, so they sit with
the rest after that test.

--resolve on its own is refused at parse time.  lfs find only routes
to llapi_find_since() when --since or --changelog is given, so the
flag was parsed and never read, and lfind(1) shares this parser and
never reads it at all.

The demand mask names its fields instead of relying on 0.  Zero is
"everything" to llapi_scan_changelog(), but the comment here read the
other way, and a reader had to know which.

A merged record no longer claims a parent it does not carry: sr_valid
is OR'd from the event, so sr_parent_fid has to come with its bit or
the record reports [0x0:0x0:0x0] as though it were an answer.
