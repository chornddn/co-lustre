LU-20522 obdclass: size the llog header swab to its buffer

lustre_swab_llog_hdr() reads and swabs the header tail that
LLOG_HDR_TAIL() locates from lrh_len, without checking lrh_len.
That length is raw data from disk or the wire, and the first
print_llog_hdr() reads it before the swab, so even a valid
foreign-endian 8KB header has its tail read about 2MB past the
buffer. recovery-small test_154a crashes in print_llog_hdr() when
the random header it writes over a catalog passes
LLOG_REC_HDR_NEEDS_SWABBING(), about one header in 4096.

Pass the swab the size of the buffer the header was read into and
touch the tail only when lrh_len places it inside that buffer. The
bound has to be the caller's: the header reply and the stale update
log check read 8KB, llog_osd_read_header() up to 32KB. Also swab
only a byte-swapped LLOG_HDR_MAGIC: the swab check matches only the
type prefix, so other record types such as CHANGELOG_REC and
UPDATE_REC would reach swabbers that trust unvalidated lengths and
counts. Callers already reject a header with a bad lrh_type, and
lod_sub_prep_llog() renews such a log.

llog_client_read_header() now bounds lrh_len by its buffer and the
reply before using it; an lrh_len below 8 made LLOG_HDR_TAIL() read
in front of the buffer. It and llog_osd_read_header() also reject
an llh_bitmap_offset other than that of llh_bitmap, the only value
ever written.

Outside test_154a, a corrupt header on an expired update log
reaches the swab during stale log cleanup, and a corrupt or
foreign-endian peer reaches it through RMF_LLOG_LOG_HDR.
recovery-small test_154c plants a byte-swapped LLOG_HDR_MAGIC and
a byte-swapped CHANGELOG_REC header with an out-of-range lrh_len,
and checks that the MDS rejects the log.
