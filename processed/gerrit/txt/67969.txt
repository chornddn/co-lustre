LU-18298 pcc: recover a PCC file handle degraded at open

A file descriptor that misses the PCC cache when it is opened never uses
PCC again, because pcc_file_read_iter() and pcc_file_write_iter() bail
out on a NULL pccf_file before reaching pcc_io_init(), and so does
pcc_file_splice_read(). The only reset of that state is
pcc_file_release().

Open time is easy to miss. pcc_try_auto_attach() refuses to attach at
PIT_OPEN whenever the client holds no valid layout, and the client loses
its layout generation on any layout blocking AST, not just on an HSM
restore, as the comment there claimed; correct that comment too. A
conflicting open on the MDT is enough: vvp_conf_set() sets
CL_LAYOUT_GEN_NONE and detaches the PCC inode while the racing open is
still in flight.

For a PCC-RW file the consequence is not just a lost cache hit. The
O_TRUNC of the same open() re-attaches the inode through
pcc_inode_setattr(), which truncates the PCC copy, but the write that
follows still bypasses PCC, so it lands on the HSM released layout,
forces a restore and detaches the cache again. The PCC copy is left at
the size the truncate gave it. That is the sanity-pcc test_1c/test_1d
failure "expected <pcc copy> size: 7654321 got: 0".

Open the PCC copy for such a descriptor on its first read, write or
splice, once the inode is attached again. This only ever uses an already
attached PCC inode, so it takes no layout lock and issues no Lustre RPC.
Refreshing the layout at open time instead does not work: pcc_file_open()
is reached by the HSM copytool opening the very file it is restoring, and
cdt_restore_handle_add() holds MDS_INODELOCK_LAYOUT EX for the whole
restore, so the copytool deadlocks against its own restore. That was
measured, not deduced - every restore hung with three copytool threads
in ll_layout_refresh() under pcc_file_open().

An encrypted file is deliberately left out, even though pcc_file_open()
takes its copy for PCC-RO when the key is available. pcc_file_splice_read()
hands the copy to the VFS without the llcrypt decryption that
pcc_file_read_iter() does, so it returns whatever a previous read left in
the copy's page cache. Gating only the splice would not help, as a
descriptor that read first and spliced afterwards would still reach it.

This does not restore auto attach for such a descriptor. It only picks
up a PCC inode that something else has already attached, so a descriptor
that is never re-attached between open and I/O still bypasses PCC.

A descriptor whose VMA maps Lustre pages must keep using Lustre for all
of its I/O, so record that in pccf_mmap_fallback and never reopen those.
pccf_fallback cannot serve here: every descriptor this can reopen took
one at open, so it does not single out the ones holding a Lustre VMA.
Without the new bit such a descriptor would read and write its PCC copy
while its own VMA still faults on Lustre, two page caches for one file,
and for PCC-RW the restore would orphan what went through the copy.
Reopening can install the handle before the mmap() as easily as after
it, so the I/O path tests the bit ahead of the handle rather than only
where the handle is installed. The bit shares a word with pccf_fallback,
so once the descriptor is reachable by other threads both are only
written under the PCC inode lock, which is why pcc_file_mmap() takes it
earlier than before.

pcc_mmap_io_init() sets the bit as well. Its fallback branches call
pcc_vma_file_reset(), which points the VMA back at the Lustre file, so
such a descriptor faults on Lustre from then on exactly like one that
fell back in pcc_file_mmap(), and would otherwise keep being handed the
copy for its read and write.

Checking the bit in pcc_file_mmap() also stops a descriptor that mmapped
while the inode was detached from taking a PCC VMA once it is attached
again, which would rehost the mapping out from under its live Lustre
VMA. That one is a pre-existing bug, fixed here because this patch pays
for the machinery anyway. It is fixed only per descriptor: the same race
across two descriptors of one inode is the inode-wide gap below.

Barring the copy for the whole descriptor also covers one that got its
handle at open() and only later fell back at mmap(), which until now
kept reading and writing the copy under a Lustre VMA. Such a descriptor
loses PCC for the rest of its life, and for PCC-RW its next write
restores and detaches the file, so it takes the lli_pcc_mapneg vote at
that point too, as it now does Lustre I/O like any other fallback.

The descriptor keeps its lli_pcc_mapneg vote until close, as before.
Returning it once the handle is installed would let another descriptor
PCC mmap the inode while a Lustre I/O is still in flight on this one,
because pcc_mmap_mapping_set() only waits for PCC I/O. The inode-wide
gap this leaves - a Lustre VMA created without a vote when the inode is
detached - is pre-existing and deliberately left alone here.

Publishing the handle from the I/O path also makes its order matter:
pcc_fsync() reads pccf_file and pccf_type without the PCC inode lock, so
the type has to be visible first or a concurrent fsync could miss the
PCC-RO bail. Hence the smp_store_release()/smp_load_acquire() pair.

pcc_fsync() deliberately keeps its old bail: moving the PCC-RO test
after pcc_io_init() would let a reopened read-only descriptor skip
cl_sync_file_range() and lose dirty Lustre pages. It also has to report
not cached once the descriptor maps Lustre pages, since from then on its
writes go to Lustre while the copy still holds what it wrote before
that, so both need flushing. ll_fsync() no longer drops the copy's error
when it goes on to flush Lustre, and reports that one in preference to
the OST error when both fail.

Do not pick up a copy that has been unlinked behind the client's back
either, as that would keep a doomed backend inode alive until the
descriptor is closed. This makes the reopen stricter than
pcc_file_open(), which still takes such a copy for a newly opened
descriptor.

pcc_file_init() zeroes the two bits explicitly. The allocator already
returns them zeroed, so this is redundant today, but the file's own
invariant is that a set bit bars the descriptor and nothing else
establishes it.

New sanity-pcc test_1h reproduces this: it drops the cached layout lock
and uses OBD_FAIL_MDS_NO_LL_OPEN so the write open gets no layout lock
back, then checks that the file is still HSM released afterwards. It
stops there rather than detaching, so that it does not also depend on
the detach race fixed later in this series.
