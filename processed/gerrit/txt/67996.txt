LU-20590 llite: pin the layout lock for a starving IO

can_populate_pages() asks ll_file_io_generic() to restart the IO.
The restart happens when the cached layout generation of the inode is
the invalid sentinel.  Local reclaim of the MDC ibits lock which
carries the layout produces that sentinel.  With the lock cache under
pressure a reader or a writer then goes round the restart loop.  The
loop can run until the budget is gone, and move no data at all.

Count consecutive restarts which moved no bytes and found no cached
generation.  After LL_LAYOUT_PIN_RESTARTS of them, hold the layout
lock out of voluntary LRU reclaim for the rest of the syscall.  The
pin takes no mode reference.  The server can still revoke the layout
at once, and the existing generation checks stay in force.

The counter is a heuristic.  The count does not prove that a layout
drop caused the restart.  All it records is that the try moved no
bytes, and that the generation read the sentinel at that instant.
This test is a correlation.  A mirror failover retry which moves
nothing and races a concurrent cancel advances the counter too.  The
cost of a wrong guess is one spare pin, which the syscall drops on
the way out.  A restart which a real layout change caused leaves a
valid generation behind, or has already moved data.  Such a restart
resets the counter.  The threshold only has to clear the one-shot
paths, where a single restart is enough.

A try at the pin can fail.  A layout which no thread can pin now is
no more likely to be pinnable on the next restart.  The counter
therefore restarts after each try, and one syscall makes no more
than LL_LAYOUT_PIN_TRIES tries.  That bounds the added MDS intent
RPCs at four, instead of one for every remaining restart.  One try
which succeeds is all it takes to end the starvation.  A failed try
never aborts the IO, because the restart budget already bounds it.  A
try which returns -EALREADY ends the tries at once.

While a thread starves on a file, cancel_lru_locks and an
lru_size=clear no longer drop that file's layout lock.

Add a fault injection which drops the unused locks of the MDC
namespace inside the window the IO uses.  The restart then needs no
memory pressure and no racing lru_size=clear.  The injection goes
through the LRU cancel path, not a direct invalidation of the object.
The condition under test is therefore the real one.  The injection
fires only after the layout refresh succeeds.  A drop of the
namespace LRU on the way out of a failed refresh does no good.
The injection also gates on the IO
type, because vvp_io_init() serves every llite cl_io.

The reclaim is best effort, so the injection can bite fewer times
than the test needs.  Every injected restart moves no bytes, so the
client owes a pin only from LL_LAYOUT_PIN_RESTARTS restarts on.  The
count of locks queued goes to the debug log, together with the file
identifier.  The test skips when the log holds fewer restarts than
the threshold.  A test which did not run must not report a failure.

Add sanity test_251c.  The test checks that such an IO completes.
The test also checks that the pin held the layout lock out of the
LRU.

ldlm_cancel_lru() moves to a public header, and llite is a module of
its own, so the patch exports the symbol.  The injection site needs
it, and the correction itself does not.

The move also corrects the description of ldlm_cancel_lru().  The old
text named LCF_ASYNC for both cases.  The return section named a
parameter which the function does not have.
