LU-18823 fld: replicate the full FLDB to every MDT

Only MDT0000 holds a complete FID Location Database (FLDB).  Each
other MDT keeps only its own sequence ranges on disk, fetched once
at mount, and caches other ranges in memory without persisting
them, so no MDT other than MDT0000 has a copy that could rebuild
the FLDB if MDT0000 were lost.

Keep a full on-disk copy of the FLDB on every MDT:

 - fld_server_read() returns the whole FLDB (all MDT and OST ranges)
   when the request range type is ANY.
 - fld_update_from_controller() fetches the entire FLDB at mount on a
   non-MDT0 MDT whose local FLDB was just created, instead of only
   that MDT's own ranges.  An existing MDT fills in its copy on its
   first lookup miss, below.  If MDT0000
   returns no entries for the ANY read, it is an older server that
   cannot read the whole FLDB, so only this MDT's ranges are read.
 - mdt_register_lwp_callback() no longer skips the one-time FLDB
   refresh when the super-sequence is still being allocated from the
   controller (-EINPROGRESS/-EAGAIN) at the connect point.  The
   FLD_READ RPC is retried until the controller is ready.
 - a range that a non-MDT0 MDT has to look up on MDT0000 schedules a
   refresh of the whole FLDB from MDT0000 in a work item, so ranges
   allocated after the mount refresh, including those of targets this
   MDT never looks up, are added to the local FLDB.  Refreshes start
   at most once every 10 seconds, and the work item runs outside of
   any transaction of the caller.  The lookup itself is still
   answered by an FLD_QUERY to MDT0000, as before.
 - fld_replicate_entry() adds each range read from MDT0000, checking
   the on-disk index rather than the cache, so a range that is only
   cached so far is still written.  A local range for another target
   is kept and reported.
 - fld_client_rpc() returns a full FLD_READ reply (-EAGAIN from the
   server) to the caller, which continues after its last range,
   instead of resending the same request forever.  This would hang
   the reader whenever the FLDB did not fit in one reply page.
 - fld_server_read() scans the whole index for each FLD_READ and
   returns the matching ranges with the lowest starts after the
   request range, in order.  It positioned the iterator with the
   request range end, which is not a valid load cookie for either
   OSD (a CPU-order key for an IAM index of big-endian keys, a ZAP
   cursor on ZFS, where iteration is in hash order), so a second
   batch would have skipped most of the remaining ranges.
 - the fld.srv-*.fldb dump keeps the iterator cookie from store() as
   its seq_file position.  It kept the record key, which load() does
   not accept, so a dump larger than one read() buffer (about 90
   ranges) stopped after the first buffer.

The FLDB on any MDT can then be dumped from fld.srv-*.fldb and
written back to MDT0000 to restore it.  MDTs run in lockstep within
a filesystem, so no connect flag is used to negotiate the full read.

Add conf-sanity test_68a for FLDB replication and test_68b for an
FLDB larger than one FLD_READ reply.
