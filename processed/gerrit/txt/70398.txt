LU-21119 osp: allow recovery abort to break remote lock wait

During DNE recovery, a replayed request may need a lock on a remote
MDT, while a thread on that MDT holds a conflicting lock and waits
for this MDT to finish recovery. For example, MDT0001 finished
recovery and handles a getattr intent: it holds the parent directory
lock and sends osp_attr_get() to MDT0000 for a remote child. That
RPC is not marked rq_allow_replay because MDT0001 is not recovering,
so ptlrpc_import_delay_req() delays it until the import to MDT0000
is FULL, which only happens after MDT0000 recovery completes.
Meanwhile, tgt_recover_0 on MDT0000 replays an unlink in that
directory and waits in ldlm_completion_ast() for a conflicting lock
on the same directory on MDT0001.

ldlm_completion_ast() waits for the lock forever. When the lock times
out, it only reconnects the import and keeps waiting. Recovery abort
is checked only between replays, so neither "abort_recovery", the
hard recovery timeout, nor umount can break the deadlock, and the
target stays in RECOVERING state:

  tgt_recover_0: ldlm_completion_ast <- ldlm_cli_enqueue <-
    osp_md_object_lock <- lod_object_lock <-
    mdt_remote_object_lock_try <- ... <- mdt_reint_unlink <-
    handle_recovery_req <- replay_request_or_update
  mdt00_002: ptlrpc_set_wait <- ptlrpc_queue_wait <-
    osp_remote_sync <- osp_attr_get <- osp_object_init <- ... <-
    mdt_getattr_name_lock <- mdt_intent_getattr

When the target recovery thread enqueues a remote lock, use a
completion AST that waits for the lock in intervals and gives up
once recovery of the target is aborted or the target is stopping.
The failed enqueue is cleaned up by the existing failed_lock_cleanup()
path, the same as an enqueue interrupted by a signal, and the
replayed request fails as recovery is being aborted anyway.
