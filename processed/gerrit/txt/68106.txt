Some concerns, see inline comments. The build error needs a refresh; the rest can ride along in the same cycle.

The bigger question is what this test can actually detect: each thread writes a value derived from the offset but nothing ever reads the mapping back, and mmap_tst13() returns 0 on every normal path. So it can only catch a crash or a hang, not the data corruption the commit message says it verifies. Since ptr[offset] is deterministic ((unsigned char)offset), a verification sweep over the mapping after the joins would make the test able to fail when the two mounts disagree.

(4 comments)

This adds case 13 to mmap_sanity. Eight threads, four on each sanityn mount, store into their own MAP_SHARED mappings of one 8 MiB file for 360 seconds. The case runs only when SLOW starts with y or t. A long two-mount mmap stress is worth having. As written, though, it cannot detect the data exchange problem the commit message names, and its setup error paths are unsafe.

Main concerns, inline. First, nothing checks the file content after the run (1141), so only a crash, a hang or a SIGBUS can fail the test. Second, the setup loop returns or exits while earlier threads still run on its stack data, and it leaks the fds, the mappings and the file (1114). Third, the SLOW gate in C reports the case as PASS when it does not run (1090).

None of the eleven Gerrit AI review comments on PS3 has a reply or a code change yet, because PS4 is a plain rebase. One of them is wrong: nr does not break the build. gcc does not warn about a variable that is only incremented, Jenkins built PS4, and gcc 13 -Wall -Werror is clean here, so nr is just dead code. The others still apply, including the file name mmap_tst11 (1093), the second unlink of the same file through the other mount (1142) and the nunmap typo (1135).

[minor] Process. The subject has a typo (additinal), and per the commit message rules a test change should say what it adds, for example LU-20608 tests: add shared mmap stress to mmap_sanity. The commit message speaks of two nodes, but sanityn runs both mounts on one client. The three identical Test-Parameters lines start three sessions: if three runs are wanted, please say so, otherwise one line is enough.

[minor] Rebase. Patrick-Bot reports a conflict with 70506 (LU-18952, migrate mmap_sanity to llapi_test_utils, in master-next), and a trial cherry-pick confirms it. After that rebase the case needs a wrapper and a test_tbl entry, and it must join the !dir2 skip list in main(). tte_skip then gives a proper skip report for the SLOW case. Open change 68104 (LU-20607) also adds an mmap_tst13 with .tc = 13 to this file, so whichever lands second has to renumber.

Tests and CI: Maloo V+1 on build 135574. The three custom sanityn sessions with ONLY=18 and SLOW=yes passed, and case 13 took 370.64, 381.31 and 370.68 s there, so it did run. In the regular sessions it is a no-op that is still logged as PASS. The remaining failures are unrelated: sanity 805b (LU-20873) on review-dne-zfs-part-1, which passed on retest, and sanityn 102 (LU-20501) on PS3.

Testbed, a single-node test machine: one build of master 54dc726b56 plus PS4, plus a local read-back check that runs only when MMAP_VERIFY is set and is not part of this change. sanityn 18 with SLOW=yes passed twice, case 13 taking 362.09 s and 362.17 s, and neither run's kernel log shows an error during the test. The second run set MMAP_VERIFY. It counted 3.92 million stores. Read back through either mount, 3152601 bytes held the stored value, 5236007 still held Q and none held anything else.
