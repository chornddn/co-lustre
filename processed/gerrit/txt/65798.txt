LU-20238 ec: GFNI-accelerated EC primitives

Portable C-intrinsics build of ISA-L that drops the patented
PSHUFB nibble-table technique used by the AVX2/SSE kernels.
A follow-on patch in this series adds a non-GFNI byte-indexed
table-lookup (GF_REGION_MUL) for the scalar fallback path.

Add a runtime-dispatched GFNI fast path to the existing libec.a
(LU-19465).

On x86_64 CPUs with GFNI:

  - AVX-512 + GFNI: ec_encode_data / ec_encode_data_update /
    ec_init_tables route to AVX-512 GFNI kernels.  Both encode
    (dot_prod) and update (mad) peel parity rows off in groups
    of up to 6 per FPU pass (full 1/2/3/4/5/6-output kernel
    ladder is shipped for each); arbitrary m is supported via
    repeated passes.
  - AVX2 + GFNI:    same dispatcher with AVX2 GFNI kernels.
    Encode peels in groups of up to 3 per pass (kernels for
    1/2/3 outputs); arbitrary m via repeated passes.
  - Everywhere else (or when GFNI isn't compiled in): the
    existing ec_*_base() path is used, unchanged.

The GFNI kernels are written in C using compiler intrinsics
(_mm{256,512}_gf2p8affine_epi64_epi8) gated per-function with
__attribute__((target("avx2,gfni"))) or
target("avx512f,avx512bw,gfni"), so the build needs only
GCC >= 8 / clang >= 8 and does NOT depend on NASM.  The encode
path uses only the GF(2^8) affine intrinsic (vgf2p8affineqb)
and standard XOR / load / store; no PSHUFB-style nibble-table
lookup is used anywhere.

The multi-output AVX-512 kernels read the GF coefficient as an
EVEX {1to8} embedded-broadcast operand of vgf2p8affineqb, so
the 8-byte broadcast folds into the affine's own load micro-op.
This keeps the broadcast off the vector-ALU port: gcc/clang
lower _mm512_set1_epi64()+affine to a GPR-source vpbroadcastq
on Port5, which made the first-gen multi-vect encode ~25%
slower than NASM on Sapphire Rapids.  The compilers will not
emit {1to8} from intrinsics, so a short inline-asm macro is
used.  The single-output kernels keep the plain set1 form (no
competing affines, so no Port5 contention to avoid).

Performance on rd07 (Intel Raptor Lake-P, AVX2 + GFNI, single
thread, median of 3) vs ISA-L's NASM kernels on the same host:

  Benchmark                            | NASM      | C intrinsics
  -------------------------------------+-----------+--------------
  gf_vect_mul_perf                     | 42.5 GB/s | 56.8 (+34%)
  gf_vect_dot_prod_perf                | 50.1 GB/s |  46.9 (-6%)
  erasure_code_perf encode             | 18.2 GB/s | 20.0 (+10%)
  erasure_code_perf decode             | 20.8 GB/s |  22.5 (+8%)
  erasure_code_update_perf encode      | 16.4 GB/s |  16.8 (+2%)
  erasure_code_update_perf single_src  | 54.7 GB/s |  56.8 (+4%)

Intrinsics match or beat NASM on 5 of 6 AVX2 benchmarks; the
one slower case is by 6%.

AVX-512 + GFNI on a Xeon Platinum 8481C (Sapphire Rapids, GCP
c3, single thread, median of 3), same benchmarks, dispatch-
confirmed (gdb) to the *_avx512_gfni kernels on both builds:

  Benchmark                            |    NASM    | C intrinsics
  -------------------------------------+------------+-------------
  gf_vect_mul_perf                     |  31.1 GB/s |  31.4 (+1%)
  gf_vect_dot_prod_perf                |  79.0 GB/s |  79.7 (+1%)
  erasure_code_perf encode             |  44.0 GB/s |  43.0 (-2%)
  erasure_code_perf decode             |  54.3 GB/s |  51.4 (-5%)
  erasure_code_update_perf encode      |  35.8 GB/s |  35.9 (+0%)
  erasure_code_update_perf single_src  | 115.8 GB/s | 115.2 (-1%)

The {1to8} embedded broadcast brings the AVX-512 multi-vect
dot_prod kernels to parity with NASM (+1% to -5%), closing the
~25% gap the first-gen set1-broadcast intrinsics showed.

A configure-time probe (EC_GFNI_SUPPORT in
config/lustre-erasurecode.m4) compile-tests the affine intrinsic
and, on success, defines LUSTRE_EC_GFNI for the libec.a build
and enables the new sources via the EC_GFNI automake conditional.
When the probe fails (non-x86_64, older toolchain), no GFNI
objects are built and ec_base_aliases.c collapses to the base
path unchanged.

For this patch, the dispatcher is gated to userspace only by the
guard #if defined(LUSTRE_EC_GFNI) && !defined(__KERNEL__).  The C
sources are already __KERNEL__-aware and build into ec.ko;
a follow-on patch in this series will add the lustre/ec/Makefile
(Kbuild) plumbing and define LUSTRE_EC_GFNI for the kernel build
so ec.ko also dispatches to GFNI.

A standalone smoke test (gfni_ec_test, noinst_PROGRAMS) is built
inside the tree and verifies that the GFNI dispatcher and base
path produce byte-identical output on randomised input.  It
accepts k/m/len command-line arguments (default k=4 m=2
len=4096, constraint 1<=k, 1<=m, k+m<=256).  lustre/tests/
sanity-ec.sh test_0 sweeps a representative set of geometries
through it.

The vendored gf_*_gfni.c kernels are reflowed for lustre
checkpatch and intentionally diverge from canonical isa-l;
see lustre/utils/erasurecode/GFNI_VENDORED.md.

Patch Set 12:

PS12 fixes the PS11 Gerrit-Janitor compile failure (rocky8.10/9.6). Root cause: current master now compiles ec_base_aliases.c into liblustreapi, and this patch had defined LUSTRE_EC_GFNI globally in config.h, so liblustreapi took the GFNI dispatch path but does not link the GFNI objects (they live only in libec.a) -- undefined references to isal_have_gfni / ec_encode_data_*_gfni broke lustre_rsync, llog_reader, ofd_access_log_reader, etc. Fix: scope -DLUSTRE_EC_GFNI to the libec.a build via libec_a_CPPFLAGS (AC_SUBST EC_GFNI_CFLAGS) instead of a global AC_DEFINE, so only the objects linked with the GFNI kernels enable the dispatch; liblustreapi uses the base path (unchanged from master). Verified: full lustre/utils build links clean; gfni_ec_test passes.
