--- Commit Message ---
LU-21075 llite: do not shrink i_size down to KMS

vvp_prep_size() wrote KMS into i_size unconditionally. KMS is a lower
bound only: osc_lock_lvb_update() clamps it to the end of the granted
DLM extent, and sub-objects with no valid KMS contribute nothing to
the merged value. On a PFL file whose size lives in a component the
client holds no lock on, that publishes the end of the component being
read as the file size, and a concurrent stat() reports it.

Extend i_size up to KMS instead, and never lower it here. cat_size is
no upper bound for it either: a remote truncate lowers the KMS of the
objects whose locks it cancels only, and an object nobody enqueues
again keeps reporting the size the file had before, so the merged
size still describes the old file.

Bound what the page cache may serve by KMS instead. lli_kms records
how far the locks this client holds reach: vvp_prep_size() publishes
it, vvp_attr_update() zeroes it when a lock is cancelled, and
ll_read_from_cache() stops there, so the generic read loop - which
runs to i_size with no further control from llite - cannot return
zeroes between a new EOF and a stale i_size. While i_size is above
KMS with no lock behind it, vvp_prep_size() takes one glimpse, which
makes the attributes, and lli_kms, current again - sanityn test_16i
and test_16n.

Patch Set 7:

Patch set 7 looks right to me on the code side. vvp_prep_size() now only extends i_size up to KMS and takes one glimpse when a cancel has left i_size above KMS, which closes the stale-cat_size scenario from the patch set 1 review and the zeroes-past-EOF symptom; publishing lli_kms in ll_merge_attr_nolock() also fixes the DoM fast-read regression, and the RA_STAT_FAILED_FAST_READ accounting on the early return addresses the test_101j finding. My patch set 5 comments on test_271ba are addressed: the stats are cleared after the first stat and the second stat must show no glimpse line, and the $glc_m_old typo is gone. I verified the new test_16i variants and test_16n fail on the unfixed code (lov_merge_lvb_kms() marks cat_kms valid with only the locked stripe and merges 0 for the rest, so the old code shrank i_size to the locked extent) and pass with the fix.

[major] One test problem remains, carried since patch set 1: test_16l's racing reader is `dd if=$tf2 of=/dev/null bs=4k count=1 skip=100`, and coreutils dd calls fstat() on the input for skip=. That fstat goes through ll_getattr_dentry() and is the second arrival at OBD_FAIL_LLITE_STAT_SIZE_RACE, so cfs_race() wakes the parked stat() before the read ever reaches vvp_prep_size(). On the unfixed code the stat then samples the unshrunk 2M size and elapsed < 5 still holds — the race the test is about never happens, and the test passes trivially. Please use a reader that does not stat, e.g. `$MULTIOP $tf2 oz409600r4096c`.

The wc-checkpatch -1 is real: patch set 7 does not cherry-pick onto master — it conflicts with LU-20690 ("ec: store EC parity like RAID10") in vvp_prep_size(), where master now guards i_size_write(inode, kms) with !io->ci_parity_io. The rebase should keep that guard: `if (!io->ci_parity_io && i_size_read(inode) < kms)`. Only vvp_io.c conflicts; the sanity scripts apply cleanly.

Minor leftovers from the earlier rounds, worth folding into the refresh: the vvp_prep_size() header still says "clamp it to the object size" although the code only extends; the lli_kms comment in llite_internal.h says "Updated under ll_inode_size_lock()" while vvp_attr_update() and ll_merge_attr_nolock() write it under cl_object_attr_lock(); the ll_read_from_cache() comment about ll_readpage() counting the miss reads backwards; the commit message still splits the trailer block (Change-Id before Signed-off-by, HPE-bug-id last) and does not mention the test_16d/test_16j wait_delete_completed additions and the $tfile.2 fix; test_16n sits between test_16i and test_16j but refers to test_16l below; and the OSTCOUNT >= 1 check in test_16l can never skip.
