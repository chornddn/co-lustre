LU-21075 llite: do not shrink i_size down to KMS

vvp_prep_size() wrote KMS into i_size unconditionally. KMS is a lower
bound only: osc_lock_lvb_update() clamps it to the end of the granted
DLM extent, and sub-objects with no valid KMS contribute nothing to
the merged value. On a PFL file whose size lives in a component the
client holds no lock on, that publishes the end of the component being
read as the file size, and a concurrent stat() reports it.

Extend i_size up to KMS instead, and use cat_size as the upper bound.
cat_size is max(lvb_size, loi_kms) per stripe, merged as a max over
the instantiated components, and the OSC layer lowers it only on an
authoritative update such as another client's truncate. Keeping that
clamp is what stops the generic read loop, which runs to i_size with
no further control from llite, from returning zeroes between a new
EOF and a stale i_size after a remote truncate - sanityn test_16i.

i_size is sampled once for both tests, since ll_update_inode() writes
it without ll_inode_size_lock() and a second read may differ, and the
debug lines print the value actually written.

Some concerns, see inline comments. The cat_size clamp only gives a correct upper bound when every stripe's LVB is fresh. On a striped file it can leave a stale i_size after a remote truncate, which the old i_size = kms code did not. Note also that LU-21073 (https://review.whamcloud.com/70226), later in this series, makes stat() report cat_size from a snapshot instead of i_size. That change alone appears to fix the stat() symptom described here without changing what i_size means on the IO path.
