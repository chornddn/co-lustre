LU-21073 llite: report the size and times the objects report

stat(), lseek(SEEK_END/SEEK_DATA/SEEK_HOLE), O_APPEND writes and
fallocate glimpse the file, then read i_size and the timestamps back
out of the inode.  Between the merge and that read i_size can be
rewritten by writers that do not take ll_inode_size_lock(), such as
ll_update_inode() for an MDS reply, truncate or another merge, so the
size used is not the one the merge produced.  ll_merge_attr() writes
the timestamps in two steps, MDS values first and then the merge with
the OST ones, so a racing reader can see the intermediate values.
LU-17753 closed that for stat() alone by holding the size lock across
the copy.

Take one snapshot and report from it.  ll_merge_attr() fills a caller
cl_attr under the size lock with the merged size, blocks and times,
and cl_glimpse_lock()/ll_glimpse_size0() return 1 when they filled it.
Paths that do not glimpse (size from the MDS, PCC, AT_STATX_DONT_SYNC,
restore, directories) fill it from the inode with ll_attr_from_inode()
under the same lock.  ll_getattr_dentry(), ll_file_seek(), the lseek,
append and fallocate IO paths, and vvp_prep_size() use the snapshot
instead of i_size.  lseek seeds it from the inode in case the merge is
skipped.

cl_attr carries seconds only, so stat() now reports tv_nsec 0 on every
path, as the glimpse path already did.  i_size keeps its meaning for
the IO path.

I went over my patch set 4 [major] again against the lock each of those paths takes, and I overstated it. An append locks the whole initialized region (lov_io_rw_iter_init() sets wr_append_lockpos to the end of the last initialized component), and SEEK_DATA/SEEK_HOLE lock [start, EOF], so the merge they do runs on fresh LVBs and cat_size cannot be below the real end of file there. fallocate locks only its range, but it only uses that size to decide whether to extend, and vvp_io_setattr_end() and the OST only ever grow the size. So I see no path where the size the merge refuses does harm, and I withdraw the [major]. Sorry for the noise.

What remains is a consistency question, not a bug: 70225's commit message names exactly these three callers as the ones that need the kept MDT size, and with this patch they no longer read it. If the snapshot should describe the size the merge adopted, the one-line else branch I proposed does that; otherwise 70225's message could drop those callers. Either is fine with me.

Patch set 5 moves the LU-417 check onto @attr, as Andreas suggested, which is right. My patch set 4 [minor] (say in the commit message that the fix-up now also runs on the write-end merges) and the two [nit]s (LUS-12265 in the comments, the seed in vvp_io_lseek_start()) still stand; none of them blocks.
