LU-20050 ptlrpc: fix sepol_helper decode and import ref leak

sepol_helper() declared ret as signed short while
call_usermodehelper() returns int, and decoded with a single
"rc = ret>>8". That shift is only correct for a normal exit. A
kernel-level launch failure returns a negative errno rather than
a wait status, and shifting collapses it (-ENOMEM becomes
-EPERM; any errno in [-255, -1] becomes -1 or 0). A helper
killed by a signal leaves the signal in the low 7 bits, so
ret>>8 is 0 and the failure is reported as success.

Widen ret to int and decode the three cases separately, with raw
bit tests since WIFEXITED/WEXITSTATUS are userspace macros:

  ret < 0            ->  kernel failed to launch the helper
  (ret & 0x7f) == 0  ->  normal exit (WIFEXITED)
  (ret >> 8) & 0xff  ->  exit code   (WEXITSTATUS)

The exit code must be sign-extended, not negated: l_getsepol
returns -errno whenever stdin is not a tty, always the case
under call_usermodehelper(), and exit() keeps only the low byte.
The old signed short truncation did that by accident.

  -ENODEV  ->  exit byte 237  ->  (signed char)237 == -19

sptlrpc_sepol_get() special-cases exactly -ENODEV as "SELinux is
disabled, report nothing", so decoding 237 as -237 makes that
branch unreachable and turns those mounts into "Unknown error
237". This extends 8a6788b508db, which fixed a positive rc
reaching ERR_PTR() undetected.

A positive exit status is not an errno at all, so negating it
invented a plausible but wrong error: 127 from the dynamic
loader became EKEYEXPIRED and 126 from a failed exec became
ENOKEY, pointing at key management rather than a broken helper.
Report -EPROTO for those, and log the raw wait status so the
real exit code is still recoverable.

Second, the IS_ERR() branch in ptlrpc_connect_import_locked()
calls ptlrpc_request_free(), which returns the request slab but
does not release the import reference taken by
ptlrpc_request_alloc(). That keeps client_obd_cleanup() from
running, strands the LDLM namespace kobject in sysfs, and the
next mount fails with -EEXIST. Use ptlrpc_req_put() instead.

The same leak exists at the eight other sptlrpc_sepol_get()
error paths in mdc_locks.c, mdc_reint.c and mdc_request.c,
reached by ordinary create/unlink/link/rename/open/setxattr
syscalls rather than only by connect. They cannot simply call
ptlrpc_req_put(): each shared an error tail with the failure
path of mdc_prep_elc_req()/ldlm_prep_enqueue_req(), whose
ptlrpc_request_bufs_pack() out_free label already drops the
reference without clearing rq_import, so that would double-put.
Give the sepol failure its own err_put_rq label, calling the new
mdc_elc_req_put() helper. Those paths leak the queued LDLM locks
too -- ownership passes to the prep helpers, but the sepol check
runs before either is called -- so the helper releases them as
well.

sepol_helper() can no longer return a positive value, so drop the
now unreachable rc > 0 case in sptlrpc_sepol_get().

Add sanity-selinux test_21d, which stubs l_getsepol (overwriting
in place so its SELinux label survives) and mounts with
send_sepol=-1: exit 237 must sign-extend to -19 and the mount
still succeed; exit 234 must fail with -EINVAL; removing the
helper must fail with -ENOENT. Both failures are matched against
the expected strerror() text, as the old decode also yielded a
named errno and a check for "Unknown error" would pass either
way. After each failure the helper is restored and the client
mounted again -- that second mount catches the leaked reference.

test_21c leaves a persistent sptlrpc.send_sepol=0 in the MGS
config log, which every later mount replays over a local
setting.  test_21d drops that entry before setting send_sepol
itself, and checks the value survived the first mount: without
that the helper is never consulted and each mount succeeds for
the wrong reason.

test_21d deliberately creates no nodemap: with
nodemap.<nm>.sepol set, req_check_sepol() refuses any connect
carrying no policy (test_21a covers that), which is exactly what
the -ENODEV case produces, so the mount would fail for an
unrelated reason.

AI code review results below, please doublecheck

The C changes look correct to me: ptlrpc_req_put() on a freshly allocated, unpacked request is safe (rq_refcount is 1 from ptlrpc_cli_req_init(), __ptlrpc_free_req() takes imp_lock and it is not held at any of the nine sites), the err_put_sepol tails really are only reachable after ptlrpc_request_bufs_pack() has already dropped the import ref, and the (signed char) decode reproduces exactly what the old signed short truncation did. Two things about completeness, plus comments inline.

The same leak survives one step up the same call chain. ptlrpc_request_alloc_internal() in lustre/ptlrpc/client.c does:

    request = __ptlrpc_request_alloc(imp, pool);   /* class_import_get(imp); imp_reqs++ */
    if (unlikely(imp->imp_state != LUSTRE_IMP_FULL)) {
        if (ptlrpc_reconnect_if_idle(imp) < 0) {
            atomic_dec(&imp->imp_reqs);
            ptlrpc_request_free(request);
            return NULL;
        }
    }

imp_reqs is balanced but the class_import_get() is not, and ptlrpc_reconnect_if_idle() fails precisely by returning the rc of ptlrpc_connect_import_locked() - including the sepol PTR_ERR this patch is fixing. So on an idle MDC import, a broken l_getsepol still strands one import reference and reproduces the -EEXIST remount the commit message describes. Worth folding in here, or at least a note that it is a separate change.

Eight of the nine changed sites are in mdc, and none of them are exercised: test_21d only drives the connect path. Mounting first, then breaking the helper and running touch/unlink/rename/setfattr, would cover the new err_put_rq labels and the ldlm_lock_list_put() that goes with them.
