LU-21066 ldiskfs: avoid FORTIFY warning in ext4_set_dirdata()

ext4_set_dirdata() writes the LUFID record after the filename
through de->name[], which is declared as char name[EXT4_NAME_LEN].
For names of 238 bytes or longer the 17-byte LUFID record runs past
the end of that array.  The bytes are still inside the directory
record, but on kernels built with CONFIG_FORTIFY_SOURCE (all EL10
kernels) the memcpy() triggers:

  memcpy: detected field-spanning write (size 17) of single field
    "&de->name[de->name_len + 1]" at ldiskfs/namei.c:1720 (size 16)
  WARNING: ... at ldiskfs/namei.c:1720 ldiskfs_set_dirdata+0xc2/0xe0

on the MDS, from mdt_create() -> ... -> add_dirent_to_buf(), for any
client create with such a name.  With panic_on_warn this panics the
MDS.

Use unsafe_memcpy() for the write, matching the existing workaround
for the same FORTIFY_SOURCE false positive in
ext4_htree_store_dirent().  The dirdata bytes lie past the
EXT4_NAME_LEN bound but within the directory entry's rec_len; the
on-disk format and the bytes written are unchanged.

This covers the ext4-dirdata-core.patch copies: rhel10.0, rhel10.1,
linux-6.12, linux-6.18 (also used by rhel10.2) and linux-7.0 (also
used by ubuntu26).  The same memcpy() pattern in ext4_insert_dentry()
in the ext4-data-in-dirent.patch series (ubuntu24, the 6.6-6.11
mainline and rhel9 kernels) is left for a follow-up.
