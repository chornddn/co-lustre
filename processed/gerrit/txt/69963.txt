--- Commit Message ---
LU-21023 mdt: redirect an unlink whose child was migrated

An unlink of a name whose file was being migrated could fail with
-ENOENT though the name still existed. In mdt_reint_unlink():

- The client sends the unlink to the MDT of the child it knows. If
  the name now resolves to a different remote FID, the name points to
  another object, e.g. the child was migrated or renamed over
  meanwhile: return -EREMOTE with that FID, as for a first try,
  rather than -ENOENT. Keep -ENOENT when it is the same FID.
- An unlink that waited for the child's lock behind a migration then
  found the child destroyed. If the locked child was destroyed, look
  the name up again, up to 5 times. Add mdt_object_destroyed() for
  this: a dying object may still be live, e.g. after layout LFSCK
  dropped it with dt_object_put_nocache(), and only a destroyed one
  fails attr_get with -ENOENT.

AI code review results below, please doublecheck

Looks good, with no code issues found. A Fixes: note is inline on the commit message, and it would be good to have a regression test for this race (see below). No re-spin is needed just for these.

The race has a reproducible form: two hard links in one directory, D/a and D/b. Migrating D/a takes the PDO lock on D only for the hash of "a", and mdt_migrate_links_lock() skips spobj, so an unlink of D/b gets its parent lock, looks up b, then blocks on the child lock behind the migration. A sanityn case could pause the migration with a new fail_loc after mdt_rename_source_lock() (the existing OBD_FAIL_MIGRATE_LOOKUP_DELAY fires before any lock is taken, so it can't hold this window open), run `rm D/b` from the second mount, and check that the unlink succeeds and that b is gone afterwards. Without this patch the unlink returns -ENOENT.
