LU-16781 obdclass: account kernel thread RPCs to the job

Only BRW RPCs used the jobid cached in the inode; every other RPC
took its jobid from the thread queueing it, so work done by kernel
threads for an application was not accounted to that application:

- pages written only through mmap were flushed with a stale or empty
  inode jobid, since CIT_FAULT never updated lli_jobinfo, and with
  uid/gid -1 for a file never read or written;
- the async readahead worker replaced the application's cached jobid
  with its own;
- statahead, AGL, PCC-RO attach, closing a cached open handle from a
  lock callback or inode eviction, and batch RPC resend sent their
  RPCs under the thread's name, or with no jobid at all;
- with jobid_var naming an environment variable, threads matching a
  fixed list of names (including userspace irqbalance) got no jobid,
  other kernel threads got jobid_name expanded, and with
  procname_uid each ptlrpcd, mdt or ldlm thread had its own jobid.

Update the inode's job_info for CIT_FAULT as well, and not from the
readahead worker, so its BRWs keep the reader's jobid.  Pass the
inode's job_info in md_op_data when a kernel thread closes a file.
Where there is no inode job_info to use (statahead, AGL, PCC-RO
attach, batch resend), add lustre_jobinfo_task_set() so a kernel
thread working for a process records that process's job_info once
per thread or work item, and use it in lustre_msg_set_jobinfo() and
lustre_get_jobinfo().  lustre_msg_get_jobinfo() reads it from the
batch request being resent.  A BRW for an inode with nothing cached
yet now takes the sending thread's identity instead of uid/gid -1.

Replace jobid_name_is_valid() with a PF_KTHREAD check: kernel threads
have no environment, so they always expand jobid_name, and "%e"
drops the instance suffix from their name ("ptlrpcd_00_01" becomes
"ptlrpcd") so background load shows up as one job per thread type.
