LU-20501 llite: skip dot/dotdot in NFS get_name for striped dir

sanityn test_102 intermittently fails on ZFS DNE with a spurious
ESTALE from open_by_handle_at() of a striped subdirectory whose
parent is also striped:

  open_by_handle_at(subdir) error: Stale file handle

The handle decodes fine; the ESTALE is produced by the kernel NFS
reconnect path.  reconnect_one() gets the disconnected dentry's
parent, then calls exportfs_get_name() (ll_get_name()) to find the
child's name in that parent, and finally lookup_one() on that name.

ll_get_name() walks the parent's dirents and matches each entry's FID
against the child FID with do_nfs_get_name_filldir().  It does not
skip the "." and ".." entries.  For a DNE striped directory the merged
readdir rewrites the "." and ".." entries to the master / parent FID in
lmv_striped_read_page(), using op_data->op_fid3 for "..".  ll_readdir()
sets op_fid3, but ll_get_name() does not, so on this path ".." carries
a stale FID that can equal the child FID being searched.  When it does,
ll_get_name() returns "..", reconnect_one() then does lookup_one(".."),
which fails with -EACCES, and exportfs_decode_fh() turns any decode
error into -ESTALE -- hence the intermittent failure.

A child is never reached through "." or "..", so do_nfs_get_name_filldir()
must never match them (the generic get_name() is immune because it
matches by inode number rather than FID).  Skip both entries.

Reproduced and fixed on a ZFS DNE cluster: sanityn test_102 failed
~15% of runs without the fix and 0/120 runs with it.
