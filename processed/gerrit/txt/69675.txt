LU-19344 llite: report EOF for read racing local append

A read issued at EOF must report EOF even if the file grows while it
is in flight.  i_size cannot express this: osc_page_touch_at() raises
kms and the inode size as soon as the pages enter the cache, so a
paused reader resumes with the appended data already visible.  A
glimpse cannot help either, since the client holding the extent lock
owns the kms.

Add a per inode counter, lli_size_gen, bumped around a write by this
client that publishes a larger size: in vvp_io_write_commit() on both
sides of cl_io_commit_async(), which raises kms page by page, and in
ll_do_tiny_write(), which can extend the file inside an already dirty
page.  do_file_read_iter() snapshots i_size and the counter on entry
and rechecks at the end; if the read started at or beyond the
snapshotted EOF and the counter moved, ki_pos is restored, the iter
reverted and 0 returned.

The counter is advisory.  It is not ordered against the size store and
is per inode rather than per range, so it can move for an unrelated
local write and a reader can still miss a write committing in the
window between the two bumps.

The counter moves only for local writes, so a size learned from
another node is still returned normally.

AI code review results below, please doublecheck

Some concerns, see inline comments. The main one is that the EOF check can discard data that was already in the file, so a reader such as cat or cp can see a false EOF.

A broader design question: POSIX doesn't seem to require a read issued at EOF to return EOF when a write lands while the read is in flight. A read that overlaps a write may observe it, and a local filesystem returns the appended bytes in exactly the 251b scenario, because filemap_read() samples i_size when it copies. 240cad9a0a removed 251b for that reason. What changed to make the stricter semantics a requirement again, and is it worth a check on every read() plus two atomics on every write commit?
