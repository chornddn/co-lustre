LU-17364 mdc: ignore no-object in truncate path

when DoM component is presented the following race is possible:
1) 1st process initiates a truncate by filename, refreshes layout and
   about to enqueue ldlm locks on data objects (incl. DoM component)
2) 2nd process does unlink which removes the file and given the file
   is not open - kills MDT object, then releases corresponding LDLM
   lock on MDT
3) 1st process enqueues LDLM lock on DoM component, but MDT can not
   find corresponding object and returns -ENODATA in LVB's lvb_blocks
4) cl_io_loop() needs to start IO on all involved components starting
   from DoM: mdc_io_setattr_start() fails due to missing attributes
   and expected osc_io_setattr_start() is not called.
5) a part of IO starting process is osc_cache_truncate_start() which
   is to prepare data extents, so the extents belonging to OSCs are
   ignored
6) in osc_io_setattr_end() those extents are found in a unexpected
   start which is the reason for LBUG:
(osc_page.c:144:osc_page_delete()) Trying to teardown failed: -16
(osc_page.c:146:osc_page_delete()) ASSERTION( 0 ) failed:

the fix is to ignore such an error in mdc_io_setattr_start()

Patch Set 3: Code-Review-1

(9 comments)

The change makes mdc_io_setattr_start() return 0 instead of -ENODATA when the DoM component has no valid LVB and the io is a truncate, adds a new fail point 0x143a in cl_io_loop() to pause a truncate between cl_io_iter_init() and cl_io_lock(), and adds sanity-dom test_9 for the unlink vs truncate race. The direction is right: lov_io_call() stops at the first sub-io whose cio_start fails and lov_io_end_wrapper() then skips cl_io_end() for the sub-ios that never reached CIS_IO_GOING, so one failing DoM sub-io cancelled the truncate of every OST component and left their pages in extents, which is what later makes osc_teardown_async_page() return -EBUSY and osc_page_delete() LASSERT. Two things need attention: the same -ENODATA abort is left open on the fallocate branch of the very same function, and the new test can pass on unpatched code because it unlinks $MOUNT/$tfile while it created $DIR/$tfile and because it only sleeps 0.3s instead of waiting for the fail point to fire. The new fail point costs nothing on the IO path: it is a cl_io_is_trunc() test plus the usual fail_loc check, not a new operation. Authorship is consistent - author, committer and uploader are all bzzz@whamcloud.com.
