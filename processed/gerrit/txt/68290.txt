LU-18298 pcc: purge the shared page cache before removing a PCC copy

An encrypted file and its PCC copy share clear text in one page cache and
cipher text in the other, so pcc_inode_put() drops both when the last
reference to the PCC inode goes away. It reaches the PCC inode through
pcci_path.dentry->d_inode.

pcc_ioctl_detach() removes the copy before that, and vfs_unlink() ends in
d_delete(), which turns the dentry negative when nothing else holds it.
pcc_inode_put() then sees no PCC inode, skips both truncations, and the
cipher text pages this inode picked up while the copy was attached stay
in its page cache. The next read of the file returns them, so
sanity-pcc test_21j reports the file as corrupted after a PCC-RO detach.

Do the purge while the copy is still named, and keep it in
pcc_inode_put() as well since a detach is not the only way to get there.
Truncating twice is harmless.

This is only reachable once "LU-18298 utils: do not write open a file to
detach it from PCC" lands. Before it, lfs pcc detach opened the file
read-write, the resulting layout blocking AST detached the PCC inode
through pcc_layout_invalidate() while the copy was still there, and the
purge happened on that path instead. The ioctl then found nothing
attached and did nothing, which is the bug that patch fixes.

Both truncations move from truncate_inode_pages_final() to
truncate_inode_pages(). The _final form is the ->evict_inode helper and
sets AS_EXITING for good, which stops reclaim recording workingset
shadow entries for the mapping; neither inode is being evicted here, and
the Lustre one is about to be read again. That also affects the existing
pcc_inode_put() path, which had been setting the flag on a live inode.

Purging from the ioctl also widens when it happens: pcc_inode_put() only
reached it with the last reference gone, while the detach does it with
other descriptors still holding the copy open. That is safe for the one
case this covers, an encrypted PCC-RO copy, as a write to such a file
detaches it in pcc_io_init() before it can dirty anything.

The same ordering exists on the attach failure paths, in
pcc_readonly_attach(), pcc_readwrite_attach_fini() and
pcc_attach_data_archive(), which remove a copy they have already copied
data through. Those are unchanged here: they are reachable only when an
attach fails, no test covers them, and they are as old as the purge
itself rather than something this series disturbs.
