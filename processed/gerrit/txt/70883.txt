LU-21218 ksocklnd: accept connects while own connect is stuck

When a server must send to a client it has no connection to (a bulk
reply, an LDLM callback, an LNet ping), ksocknal_connect() dials the
client.  If the client side silently drops that SYN, e.g. a firewall
that only allows client->server connections to the LNet port, the
blocking connect hangs for the whole SYN retry period (127 s with
tcp_syn_retries=6) with ksnr_connecting set.  During that time
ksocknal_create_conn() rejects every connection the client opens as
"connection race resolution" (EALREADY), because the client NID is
lower and the server thinks it is already connecting.  CONTROL may
get through between server dials while BULK_IN/BULK_OUT do not, so
bulk falls back to CONTROL, the ZC-ACK has no BULK_IN connection to
use, and the server closes everything on "stale ZC_REQs ...
resid: 0".  The cycle repeats until the client is evicted:

  Not creating conn 12345-<client>@tcp type 1: connection race
  resolution
  Total 4 stale ZC_REQs for peer_ni <client>@tcp detected; ...
  This client was evicted by <fsname>-OST0000

Resolve the race by whichever side gets through first instead.  Add
ksnr_race to the conn_cb, reset before each of our connect attempts.
Once our TCP connect gets through, ksocknal_connect() marks the
attempt OURS and goes on to HELLO; from then on an incoming
connection from a lower-NID peer is refused as before.  If the
peer's connection arrives first, ksocknal_create_conn() accepts it
and marks the attempt PEER; when our TCP connect gets through later,
we drop our socket before HELLO and re-check which connection types
are still wanted.  Both transitions are under ksnd_global_lock, so
the two connects can never both go on and then refuse each other as
duplicates, and a connect whose SYN is never answered can no longer
lock the peer out.  When we drop our socket after TCP is up, the
peer logs one "Error -104 reading HELLO" for it.

Add sanity-lnet test_239: two NIs on one node with conns_per_peer 1
and SYNs from the higher NID to the lower one dropped.  While the
higher NID's connect is stuck, the lower NID must be able to ping it
at once, and the higher NID's queued ping must complete over the
lower NID's connections.  Once the SYNs are let through, the higher
NID must not keep a connection it opened itself, and both directions
must work.

Without the fix test_239 fails at the first ping; with it, it
passes.  On a cluster with the client NID lower than the servers',
inbound SYNs to the client's LNet port dropped, continuous reads, a
90 s network cut and conflicting writes from a second client:

               race rejects  stale ZC  conns back  evictions
  unpatched    580-604       4         never       2
  patched      0             0         ~20 s       0

The sanity-lnet failure set is the same as without the patch.
