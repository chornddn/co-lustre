LU-21274 tests: don't zero max_create_count in sanity 823

test_823 sets max_create_count=0 on every OSP before raising it on
OST0000 alone. LOD can cache the resulting statfs, in which no OST
is usable, for up to 2 x qos_maxage, so object allocation keeps
failing with -ERANGE for about ten seconds after the test has
restored the original values. sanity test_831, 833 and 834 then
fail with "Numerical result out of range", on both 4KB and 64KB
page size clients.

Only change max_create_count on OST0000, which is the OSP the test
checks, and never set it to 0. Register the restore trap before the
first change, and also save and restore OST0000's create_count,
which the test overwrites. create_count has to be saved after
max_create_count, because restoring the max clamps create_count.

test_831 ignored the exit status of createmany, which hid this
failure. Check it, so that an unexpected create error fails the
test.

Test-Parameters: trivial testlist=sanity env=ONLY="823 831 833 834"
