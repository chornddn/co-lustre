DRAFT LU-21180 kunit: add optional kmemleak check to ku

Add support to catch memory leaked by a kunit module's test run.

-k requires a kernel with kmemleak enabled; it is off by
default since forcing a scan is slow.

Before loading a module ku clears kmemleak's list of suspected
leaks, and after unloading it waits for kmemleak's minimum object
age (MSECS_MIN_AGE, 5s in mm/kmemleak.c: an object is not reported
as unreferenced until it has been allocated at least that long)
before triggering a scan and reading the list back, failing the test
if anything is reported. Scanning right after rmmod without this
delay misses this run's leaks (they are too young to be reported)
and only surfaces them, misattributed, on a later run. This scopes
the check to just that module's load/unload instead of whatever
kmemleak had already logged elsewhere.

The sleep plus the forced scan add 6+ seconds per module regardless
of what is loaded, so -k is not meant for routine fast test runs.

Also fail early with a clear message if ku is not run as root, since
insmod/rmmod of the test modules need it anyway, rather than letting
insmod fail partway through the run.

Example, a leaked 64-byte allocation from lod_comp_prep_create():

  unreferenced object 0xffff913f809e1680 (size 64):
    comm "kunit_try_catch", pid 3316, jiffies 4295099075 (age 18.455s)
    hex dump (first 32 bytes):
      00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  ................
      00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  ................
    backtrace:
      [<00000000eae94f93>] kmalloc_trace+0x25/0xa0
      [<00000000cb6aca88>] lod_comp_prep_create+0x198/0x1980 [lod]
      [<000000000ebbc798>] 0xffffffffc190b410
      [<000000001e467737>] 0xffffffffc190b6f7
      [<000000007b9a4303>] kunit_generic_run_threadfn_adapter+0x13/0x30 [kunit]
      [<00000000a1a25ad0>] kthread+0xdd/0x100
      [<00000000e623718c>] ret_from_fork+0x29/0x50
