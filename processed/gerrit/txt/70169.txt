LU-19686 lod: gate update llog thread on distribute txn

lod_sub_recovery_thread() dereferences lut->lut_tdtd, which
lod_prepare_distribute_txn() only publishes partway through
lod_prepare().  lod_add_device() gates starting that thread on
lod_initialized, which lod_prepare() sets much earlier, so an MDT
registering in between starts a thread that faults on a NULL
lut_tdtd at offset 0xb8 (tdtd_recovery_threads_count):

  Unable to handle kernel NULL pointer dereference
   lod_sub_recovery_thread+0x98/0x10f4 [lod]
   kthread+0x11c/0x128

This was seen on a 2.15 server.  The window is the same here and
wider, because lod_update_log_dir_gc() reads every update llog
header on the MDT inside it.

Gate on the distribute txn instead, and serialise the two callers
with a new lod_llog_mutex.  lod_add_device() runs on the config
thread and lod_sub_init_llogs() on the mount thread, so an unlocked
check leaves both able to see a NULL *taskp and start two threads on
one ltd_recovery_task.  Then the loser in lod_sub_prep_llog() trips
its !ctxt->loc_handle assertion, and the second *taskp assignment
overwrites the first, leaving that thread with nobody to
kthread_stop() it.

*taskp alone does not say "already handled", because a thread that
finished cleared it with xchg(), so got_update_log is tested as well.
Without that, a target whose thread had already completed could have
its update llog read and its records inserted into the replay list a
second time, after tdtd_replay_ready was set.

Both are read under lod_lock, which the recovery thread holds when it
sets got_update_log and drops before the xchg(): either the bit is
set, or the thread has not reached it and *taskp is still its task.
That thread never takes lod_llog_mutex, so two plain loads outside
lod_lock could straddle it and see neither.

lod_prepare() publishes lut_tdtd and walks the MDTs under the same
mutex, so a deferring caller either sees lut_tdtd, or the walk has
not run yet and will start the thread for every target registered by
then -- including the one lod_add_device() registered before calling
us.  The lod_initialized test moves out of lod_add_device() and into
that critical section for the same reason: a caller skipping on it
took no lock at all, so nothing ordered its ltd_add_tgt() against the
walk, and the walk is lock-free.  A weakly ordered CPU could let it
miss the target and start no thread for it.  Registering under
ltd_mutex and then releasing lod_llog_mutex is enough; the add need
not be inside the latter.

conf-sanity 139 drives the race: it stalls a plain MDT in
lod_prepare() inside that window and mounts an MDT whose index has
never been registered.  A fresh index is required -- a re-registered
MDT appends no add_mdc record, so the MGS pushes nothing and the race
cannot fire -- so the test leaves the last MDT formatted but
unmounted and mounts it late.  It also checks that MDT ends up with
its update llog, so a deferral that never completes is caught.
