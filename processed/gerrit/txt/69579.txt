LU-20277 osd-zfs: do not lose OI repairs during scrub

A ZFS OI scrub could report completion while a FID it had
found inconsistent was left without a valid OI mapping. The
object was then unreachable by FID, so an unlink by name
failed with ENOENT and the parent directory could not be
removed, which is how sanity-scrub test_10a fails with
"Fail to cleanup the env!" on ZFS.

There were two ways to lose a repair. The LFSCK object table
iteration looks up each object as the scrub reaches it. When
that lookup read the stale mapping just before the scrub
fixed it, the LMA mismatch made it delete the FID's OI
entry, removing the mapping the scrub had just written. Only
delete the entry if it still holds the stale dnode, checked
under os_rwsem, which the scrub holds across its own check
and update. If the scrub has installed a new mapping, retry
the lookup with it. Release the state of the first dnode
fully before such a retry, which the REMOTE_PARENT_DIR retry
did not do either.

A scrub resumed from a checkpoint never checked the object
at its resume position, because dmu_object_next() returns
only objects after the position it is given. Start one
object earlier. The LFSCK object table iteration had the
same off by one when it resumed.
