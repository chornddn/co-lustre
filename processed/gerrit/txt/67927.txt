LU-20580 o2iblnd: don't sleep in atomic in kiblnd_startup()

kiblnd_startup() queried the net device from inside the
write_lock_irqsave(&kiblnd_data.kib_global_lock) section.
lnet_get_link_status() takes rtnl_lock(), which is a mutex and
can sleep, so the query ran with preemption disabled and
interrupts off.

While rtnl_mutex is free the mutex fast path does not schedule
and nothing is reported. When another task holds rtnl_mutex,
__mutex_lock_slowpath() calls schedule_preempt_disabled() and
the kernel reports "BUG: scheduling while atomic". This is
reached at boot, when the network subsystem holds rtnl_mutex
while LNet is configured, and the node does not boot.

schedule_debug() then calls preempt_count_set(PREEMPT_DISABLED),
which leaves the count unbalanced.

Take kib_global_lock only to link the net, then query the
interface after the lock is dropped. The net is on ibd_nets
before the query, so a link event that arrives during the query
is seen by the netdev notifier, which walks that list. A second
short lock section applies the result, because
kiblnd_set_ni_fatal_on() also walks ibd_nets.

The query result is now used only when the device is found. The
old code called dev_put() even when dev_get_by_name() returned
NULL, which faults on kernels where dev_put() has no NULL check.

The query was already inside the lock before the Fixes commit,
but did not sleep until that commit added rtnl_lock() to
lnet_get_link_status(). The RCU read section that once wrapped
the query was removed later, which left the sleep in place.
