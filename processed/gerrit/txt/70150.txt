LU-19823 lod: fit EC raid sets to the OSTs without domains

With "lfs setstripe -c 6 --ec 6+3" on 8 OSTs, QoS shrank the single
raid set to 5+3 so that its parity fit, while RR placed all 6 data
stripes and then failed with ENOSPC when it found only 2 OSTs left
for the parity.  Which one ran depended on the free space balance of
the OSTs, so sanity-ec test_27h passed or failed depending on the
earlier tests.

lod_ec_fit_fdoms() already fits the raid sets to the failure domains
before either allocator places the data.  Without failure domains,
count each active OST as a domain of its own, so RR and QoS fit the
same K.  Make the fit depend only on the stripe count that fits the
OSTs: a -c count is reduced to the active OSTs first.  If the largest
raid set of that count does not fit into the domains with its parity,
or a -c holds data on all OSTs in raid sets smaller than K, use raid
sets as large as fit, at most K and at least 3/4 of K, as many as
there are data stripes for, and leave out the other data stripes
rather than use more, smaller raid sets, e.g. "-c 16 --ec 8+2" on 9
OSTs is 7+2 rather than {5, 4}+2, and on 12 OSTs {6, 6}+2.  Below 3/4
of K, keep the smaller raid sets if they fit, otherwise fail with
ENOSPC, as with too few domains.  As with domains, a layout may
be stored with the smaller K of its raid sets.  Describe this in
lfs-setstripe.1, ec.txt and failure-domain.txt.

ec_split_stripes() split an odd number of data stripes with K=2 into
raid sets of 2 and one set with a single data stripe, e.g. {2, 2, 1}
for 5 stripes.  The parity of that set is only a copy of its one data
stripe, but it needs as many parity stripes as a full raid set, and
the extra set made layouts such as "-c 5 --ec 2+2" fail the check that
the parity stripes fit in the data stripe count.  Use one raid set
fewer in this case, so the residual stripe goes into the first raid
set, {3, 2} for 5 stripes and {3, 2, 2} for 7.  K=2 with an odd total
of 5 or more stripes is the only case that made a single-stripe raid
set, other splits are unchanged.  All users of the split size their
buffers from esc_k0 rather than K, as a 3-stripe file with K=2 already
gives one raid set of 3.  The split is computed from the layout rather
than stored in it, so it has to change before EC layouts are in use.

A 3-stripe raid set needs one more OST or failure domain than the
others.  If there are only enough for K=2, lod_ec_fit_fdoms() leaves
out one data stripe, so "-c 5 --ec 2+2" with 4 failure domains is
two raid sets of 2+2, and with 5 it is 3+2 and 2+2.

lod_ec_shrink_data_geometry() reduced the split one data stripe at a
time when fewer OSTs were available, which could leave a single-stripe
raid set, e.g. {2, 2, 1} for 5 of 6 stripes, unlike the split that
clients compute from the layout.  Use ec_split_stripes() for the
reduced count instead, and use lod_ec_shrink_data_geometry() for the
RR shrink to 75% of the stripes too.
Since the fitted raid sets were checked against the failure domains,
never make a raid set larger when shrinking: use the largest raid set
as K if a single raid set of K would be larger, and leave out one more
stripe if an odd count with K=2 would make a raid set of 3.  Move
lod_ec_shrink_data_geometry() after lod_comp_find_linked(), which it
now uses to set the smaller K in the parity component too.
lod_stripe_count_min() counted every kept raid set as esc_k0 stripes,
so with the new split "-c 9 --ec 2+1", {3, 2, 2, 2}, could not shrink
at all.  Leave out the smallest raid sets instead.

The parity mirror has the same extent and stripe size as the data, so
the parity of all raid sets must fit into the data stripes, as checked
at setstripe and again at resync.  Smaller raid sets need more parity,
so a fitted layout could break this, e.g. "-c 9 --ec 3+3" on 7 OSTs
as {3, 2, 2} with 9 parity stripes for 7 data stripes.  The file would
be created, but every resync would fail with "too many parities", so
its parity would never be written.  Add lod_ec_fit_parity(), used when
fitting to the OSTs or failure domains and by
lod_ec_shrink_data_geometry(), which leaves out up to 1/4 of the data
stripes to make the raid sets large enough, as other fits already
leave out data stripes, so the example is two raid sets of 3+3.  If
that is not enough, e.g. "-c 4 --ec 4+4" on 7 OSTs as 3+4, fail the
create with ENOSPC, also when it would be shrunk at allocation, and
have the QoS shrink of a single raid set keep at least as many data
stripes as parity.  If leaving out data stripes does not help a
component whose extent holds too few stripes for its parity, keep it,
as the fit did not cause it, e.g. "-E 1M -c 2 --ec 2+2", which the MDS
limits to one 1MiB data stripe.

A data component that has K but no linked parity component, which
llapi does not create, has no raid set split for a shrink to keep to,
so split it by its own K, and do not shrink a component without raid
sets.  A parity component that is already instantiated, which llapi
does not create either, keeps its raid sets, so its data component is
not fitted or shrunk.

Have sanity-ec test_27h check that a layout which can't fit fails, and
one that can gets fewer data stripes, with both the RR and QoS
allocators, in a pool of at most 12 OSTs.  Add test_31h to check the
new raid sets with --ec-map and that "-c 5 --ec 2+2" works, test_27i
for the parity fit of the two examples above with both allocators,
test_27j for a shrink at allocation without a 1-stripe raid set,
test_27k for the raid sets of a -c wider than the OSTs, and test_65e
for recovery of a 3-stripe raid set.

Patch Set 4:

PS4 is rebased on master now that 69493 has landed, and fixes the sanity-ec test_1h, test_6a and test_24b failures of PS3.

As Patrick Bot found, lod_ec_fit_parity() failed a component that lod_qos_parse_config() had already limited to the stripes its extent holds, e.g. the [0, 1M] component of "-E 1M -c 2 -E -1 -c 4 --ec 4+2" gets one 1MiB data stripe for 2 parity stripes.  Changing "*count == 0" to "*count <= 1" fixed those tests, but not the same case with more stripes, e.g. "-E 2M -c 4 --ec 4+3" gets 2 data stripes for 3 parity.  So the parity fit now first tries to leave out data stripes as before, and if that does not help a component whose extent holds too few stripes for its parity (new lod_ec_extent_too_small()), keeps it as master created it, since the fit did not cause it.  Also, the stored K is no longer lowered for a single raid set narrower than K, so a narrow component keeps the K that master stores, and test_27j resets its fail_loc with stack_trap.
