LU-13833 obdclass: account lu_object caches as reclaimable

Every cache created by lu_kmem_init() is accounted as unreclaimable
slab, because kmem_cache_create() is called without any flags. For the
caches holding lu_object layers that is wrong: a client object is
destroyed together with the inode that owns it (cl_object_kill() marks
it dying and lu_object_put() then frees it), and a server object is
freed from the lu_site LRU by the lu_site shrinker. Either way the
memory is reclaimable, yet it is reported as SUnreclaim and does not
contribute to MemAvailable.

On a client caching tens of millions of inodes this makes a healthy
metadata cache look like a leak: the case behind LU-14408 read a 189
GiB osc_object_kmem as unreclaimable slab and was escalated as a
possible memory leak, when all of it was released as soon as the inode
cache was dropped.

Add a flags field to struct lu_kmem_descr and set SLAB_RECLAIM_ACCOUNT
on the caches that hold lu_object layers: osc, lov, lovsub, vvp, mdd,
mdt, ofd, lod, osp and osd-zfs. Per-thread and per-environment scratch
caches are left alone, and so are the caches holding objects that are
not lu_objects (ldlm, quota, xattr, lu_ref, cl_env).

This changes how those slabs are accounted and the page migratetype
they are allocated from; it does not add or speed up a reclaim path.
The objects are still freed by inode eviction on a client and by the
lu_site shrinker on a server. Note that the memory now also counts
towards MemAvailable, which is the point: it is recoverable, at the
cost of dropping the cache that holds it.
