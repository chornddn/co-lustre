LU-20640 pcc: do not wait for active ios in fault path

pcc_mmap_io_init() is called from ->fault() and ->page_mkwrite()
with mmap_lock held for read. When it detaches the file from PCC
(e.g. a store into a MAP_SHARED mapping of a PCC-RO file) or
switches the mapping to the PCC copy, it waits for all active I/Os
on the PCC copy to finish under pcc_inode_lock() and mmap_lock.
This can deadlock:

P1: PCC read
->pcc_file_read_iter()
  ->pcc_io_init(): increase pcci_active_ios
  ->copy_page_to_iter()
    ->page_fault(): waits for read mmap_lock, queued behind P3

P2: mmap write fault
->ll_page_mkwrite(): holds read mmap_lock
  ->pcc_page_mkwrite()
    ->pcc_mmap_io_init()
      ->pcc_inode_detach_put()
        ->pcc_inode_mapping_reset()
          -> waits for pcci_active_ios == 0

P3: mmap()/munmap() waits for write mmap_lock held by P2

Before waiting there, if there are active I/Os, back off instead of
waiting under mmap_lock:
- if the fault may be retried, drop pcc_inode_lock() and mmap_lock,
  wait for the active I/Os to finish without them, and return
  VM_FAULT_RETRY, in the same way as filemap_fault() waits for a
  locked page;
- otherwise, e.g. ->page_mkwrite() which is called without
  FAULT_FLAG_ALLOW_RETRY, return VM_FAULT_NOPAGE so that the caller
  releases mmap_lock and the access faults again.
Lustre file mappings have no ->map_pages(), so these handlers are
always called with mmap_lock held, not a per-VMA lock.

Add sanity-pcc test_104 to reproduce the deadlock with
OBD_FAIL_LLITE_PCC_MKWRITE_PAUSE.
