LU-20888 ptlrpc: send MDT LWP setup RPCs to the FLD portal

A restarted MDT must connect its LWP to MDT0000 before recovery
can finish: lod_sub_recovery_thread() looks up the FLD for each
peer's update llog through it.  The LWP's default portal is
MDS_REQUEST_PORTAL, and if MDT0000's regular mdt threads are all
blocked in osp_remote_sync() waiting on the restarted MDT, the
connect is never admitted.  FLD_QUERY (rq_no_delay) then fails
locally and lod_sub_recovery_thread() retries in fld_client_rpc()
forever, while MDT0000's osp import to the restarted MDT waits in
REPLAY_WAIT.  Recovery deadlocks until MDT0000's threads are freed.

With GSS on mdt2mdt the LWP first needs a security context, and
its SEC_CTX_INIT has the same problem: after the context upcall
succeeds, the request is queued on the service like any other
normal-priority request with no export.

Add cli_setup_portal to struct ptlrpc_client, the portal for an
import's connect and GSS context init RPCs (0 keeps
cli_request_portal), and have client_obd_setup() set it to
FLD_REQUEST_PORTAL for an MDT's LWP.  On MDT0000 the FLD threads
only do local lookups and never wait on another MDT, and the
LWP's first FLD_QUERY already depends on them, so this adds no
new dependency.  tgt_request_handle() handles connects and context
init on any target portal.  Other requests on the LWP keep their
portals, and the MDT-MDT OSP already sends everything to
OUT_PORTAL.

Add recovery-small test_171, which caps mds.MDS.mdt.threads_max
on MDT0000, stops MDT0001, blocks MDT0000's remaining mdt threads
on lookups of directories that live on MDT0001, and restarts it.
Without this patch MDT0001's recovery stays in WAITING on MDT0000
with MDT0000's import to MDT0001 in REPLAY_WAIT; with it,
recovery completes.

Test-Parameters: testlist=recovery-small mdscount=2 mdtcount=4 env=ONLY=171,SHARED_KEY=true,SK_S2S=true
