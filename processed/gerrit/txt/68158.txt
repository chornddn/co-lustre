LU-20611 lfs: share find's predicate parsing

lfind(8) runs lfs find's predicates against a scan of a target, and a
second copy of that vocabulary would be a second copy that drifts.
This moves the option table, the loop that reads it and the argument
helpers it calls into lfs_find_parse.c, arranged so that lfind can
compile it the way callvpe.c is already shared between lfs and
lustre_rsync; lfind itself arrives later in this series.  Nothing is
exported from the library and no ABI is touched.

The moved code keeps lfs.c's SPDX identifier and copyright notices,
since that is where it comes from.

No behaviour change.  The moved loop is byte-identical to what it
replaces apart from param. becoming param->, &param becoming param,
and goto err becoming goto out; the helpers move verbatim.  Only the
nine of them lfs.c calls lose their static and reach the header; the
seven used solely by the parse loop keep it, since names as broad as
set_time() and name2attrs() should not gain external linkage just
because the code they live in moved.

The include block is the one that comes with a moved file: cut back to
what this code compiles against, which drops zlib and lnetconfig from
anything that builds it, and _GNU_SOURCE is carried across for
strptime() rather than left to the makefile's AM_CFLAGS.  The enum of
long-option values and FP_DEFAULT_TIME_MARGIN move to the header,
since several other lfs subcommands read them.

One wrinkle the check turned up: several failures in that loop give
up without setting ret, so lfs find has always printed the error and
exited 0 for a bad --comp-flags or --mirror-state.  The caller cannot
tell that from a clean parse by the return value, so the parser says
so through a stopped flag.  Preserved rather than fixed: fixing it
changes what the command returns, and that is its own patch.

Two failures in that loop returned CMD_HELP directly and so left the
flag alone, which is the one place the move did change behaviour: a
bad --foreign type fell through to the caller's pathname check and
printed a second error line.  Both now leave through the same exit as
the rest, which is what the header promises and what restores the
output the unmoved code had.

Checked by running thirty argument combinations against the binary
built before and after: every deterministic case is identical, and
the ones that are not differ from themselves between two runs of the
same binary, because lfs find interleaves its threads' stderr.
sanity 56* is the real proof.
