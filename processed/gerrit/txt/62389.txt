--- Commit Message ---
LU-19566 lustre: add layout flags to lfsck

EC parity mirror components hold parity, not file data,
so LFSCK must restore them as parity components when it
rebuilds a layout from orphan OST objects. It restored
each component with only LCME_FL_INIT, losing the parity
flag and any other component flags.

Store the long-lived component flags (prefer, nosync,
parity, nocompr) in a new ff_comp_flags field at the end
of filter_fid. The client sends them in the obdo field
that was o_uid_h, now o_comp_flags, under the unused
OBD_MD_FLCOMPFLAGS bit, and the OST passes them to the
MDT in the orphan record, so LFSCK restores them. A
rebuilt parity component also gets the parity pattern,
which clients use to keep reads off it, and LFSCK now
accepts that pattern when it checks a layout, so it can
add further orphans to such a file and checks EC files
rather than skipping them. The EC geometry and mirror
link are not in filter_fid and stay unset.

STALE is not stored: resync writes an object while its
mirror is still stale, so a stored STALE is backward and
can rebuild a layout whose mirrors are all stale, which
LBUGs the MDS when it loads that layout.

filter_fid stays 52 bytes when no flag is set, so that
older tools still read it. Servers without this change
do not handle the 56-byte form: their LFSCK and MDT
migration get -ERANGE reading it, and an OST keeping the
parent FID in LMA (256-byte inodes) refuses to have it
written. Such an OST has no room for the flags, and with
this change it does not store them.

sanity-lfsck test_46, test_47 and test_48 cover prefer,
mirrors after resync and EC parity. test_45 now waits
for LFSCK to finish on every target, not only on the OST
it checks, so that the next test can start LFSCK.

PS16 rebased on master with the review addressed, and the two failures that took this out of the EC series fixed:

- conf-sanity test_32c: an OST with 256-byte inodes keeps the PFID in LMA, and osd_xattr_set_pfid() refused the 52-byte filter_fid written when no flags are set, so writes on the upgraded images failed. It now takes 52 or 56 bytes; LMA has no room for the flags, so they are not stored there.

Patch Set 16:

Open gap, to be resolved: LFSCK cannot yet rebuild a usable EC file from orphan OST objects.

https://review.whamcloud.com/62389 stores the component flags in filter_fid, so a rebuilt parity component now gets LCME_FL_PARITY and LOV_PATTERN_PARITY: clients no longer read it as file data, and the data mirror is intact. But three pieces of an EC component are not in filter_fid, and LFSCK leaves them zero:

- lcme_dstripe_count (k, data stripes)
- lcme_cstripe_count (p, parity stripes)
- lcme_mirror_link_id, which ties the parity mirror to the data mirror it protects

filter_fid's ost_layout holds only stripe size and count, the component extent and the component id. Without the link id the parity mirror is never used: lov_io.c looks up the data mirror by lsme_mirror_link_id and returns early when none matches. So after LFSCK rebuilds an EC file, its parity cannot be resynced, and it cannot reconstruct data if a data object is also lost. That is the case EC is for. (Read from the code; not yet tested on a rebuilt file.)

Ways to close it:
1. Store k, p and the link id in filter_fid too. They fit in one more 32-bit field (8+8+16 bits). Each growth of filter_fid has the same mixed-version problem as ff_comp_flags (older LFSCK and MDT migration get -ERANGE on the larger xattr, older 256-byte-inode OSTs refuse it), so if this is the route, it should go into the same format change as ff_comp_flags rather than a second one.
2. Derive them in LFSCK after the orphans are attached: p is the parity component's own stripe count, k the stripe count of the data component with the same extent, and the link id that data component's mirror id. This is unambiguous only when one data mirror covers that extent.
3. Option 2 as a fallback for objects written before option 1.

Option 1 has to be decided before 62389 lands, since it changes the on-disk format that patch introduces.
