LU-13833 llite: hook client object cache to sb shrinker

The VFS per-superblock shrinker accounts for the dentry and inode
caches through sb->s_dentry_lru and sb->s_inode_lru, but it knows
nothing about the lu_object cache hanging off every cached inode: one
mdc/lov object per inode plus one lovsub and OSC object per stripe.
Those come from lu_kmem_init() without SLAB_RECLAIM_ACCOUNT, so they
are reported as unreclaimable slab, and since an object referenced by
a cached inode never reaches the lu_site LRU, the global lu_site
shrinker cannot see it either until that inode is evicted.

On a client caching tens of millions of inodes and their stripes this
leaves a large, apparently unreclaimable population that only
drop_caches, or enough pressure to drive inode eviction, ever frees -
what LU-14408 and LU-13833 describe.

Hook llite into super_operations::nr_cached_objects() and
->free_cached_objects().  The kernel has had these since v3.0 and adds
the filesystem count to the dentry and inode LRU counts in
super_cache_count() (checked against v4.18 and v6.17), so
super_cache_scan() proportions its budget over the three populations
and hands ->free_cached_objects() the share that belongs to the
lu_object cache.

Report only objects on the site LRU, i.e. those that can be freed
without evicting an inode, so that the number stays honest; objects
still held by an inode show up here once prune_icache_sb() has evicted
it in the same scan.  free_cached_objects() caps itself at 1024
objects per call and takes the site lock and the purge mutex with
trylock, so it can never queue behind a long purge (drop_caches) nor
use lu_shrink_env concurrently with the global lu_site shrinker.

The LDLM lock cache is left alone: cancelling locks needs the ldlm
pool state machine and its own thread, and lru_size/lru_max_age
already bound it on the client.  Per-node and per-memcg accuracy of
the count is left to LU-18175.

Add sanity test_921, which populates the client object cache with a
small metadata workload and then checks that reclaim drains it: the
lu_site must grow while the inodes are cached, its lru_purged counter
must advance by at least one object per inode after drop_caches, the
hash must shrink, and osc_object_kmem must return to its baseline.

AI code review results below, please doublecheck

Problematic, see inline comments. The new hooks only report and purge objects that are on the lu_site LRU, but client cl_objects practically never reach that LRU: cl_inode_fini() calls cl_object_kill() on the top object, and lov_delete_raid0()->lov_subobject_kill() kills every stripe sub-object, so lu_object_put() frees them directly (they are DFREE and dying) instead of adding them to lsb_lru. Whatever does land on the client LRU is also already counted and purged by the existing global lu_site_shrinker, because the client site is on lu_sites (lu_cache_shrink_count() and lu_cache_shrink_scan() walk every site). As far as I can tell, nr_cached_objects() will report ~0 on the LU-13833/LU-14408 workload and the per-sb shrinker's behaviour does not change. The comment in test_921 says the same thing ("nothing ever reaches the site LRU"). Also, test_921 does not exercise the new code: drop_caches evicts inodes and frees their objects through cl_inode_fini() with or without this patch, so the test would pass without the patch.
