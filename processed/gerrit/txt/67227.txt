LU-17957 mdd: POSIX interface for non-root immutable files

Allow a non-root file owner to make their own file immutable,
without CAP_LINUX_IMMUTABLE or root, by setting the file's atime
at least 24 hours into the future and removing all write
permissions from the file.

When mdd.posix_immutable is enabled and both conditions are met,
the MDS sets LUSTRE_IMMUTABLE_FL automatically. A new LMA compat
flag, LMAC_RETENTION (wire flag LUSTRE_RETENTION_FL), marks the
file as auto-set this way, distinguishing it from a plain
chattr +i file, which must never auto-clear.

Expiry and authorization
-------------------------
A file is expired when it has both IMMUTABLE_FL and RETENTION_FL,
no write bits, and atime <= now. This is checked by
lu_posix_immutable_expired(), and combined with an owner-or-cap
check in lu_posix_immutable_owner_or_cap(), both in md_object.h.

lu_immutable_access_check() uses these to build one authorization
rule. Without expiry, only CAP_LINUX_IMMUTABLE can clear the flag
directly via chattr -i, as before, and the operation must wait until
the flag is cleared. Once expired, the owner or a CAP_LINUX_IMMUTABLE
holder may perform the operation directly, without first clearing
the flag. This rule is now enforced at every place LUSTRE_IMMUTABLE_FL
is checked, including setattr, unlink, rename, migrate, open for
write/trunc/append, layout merge/split, layout swap, layout change,
and mirror/component add. Enforcement itself is unconditional and
applies to plain chattr +i files too. Only mdd_layout_change()'s
MD_LAYOUT_WRITE case is gated on mdd.posix_immutable, since it only
guards a TOCTOU race that is unique to the auto-expiry feature.

Whoever bypasses the check on an expired file also clears the flags
on disk via mdd_clear_expired_posix_immutable(), in the same
transaction. mdt_getattr_internal() additionally hides
IMMUTABLE_FL and RETENTION_FL from the reply to the owner or a
CAP_LINUX_IMMUTABLE holder once expired, without persisting anything,
so getattr stays read-only. Other callers still see the real flags.

Client side
-----------
llite gains LLIF_POSIX_IMMUTABLE and ll_refresh_posix_immutable(),
called from ll_revalidate_dentry(), before the VFS IS_IMMUTABLE()
check, and from do_file_write_iter(), to re-fetch flags from the MDS
and drop S_IMMUTABLE once IMMUTABLE_FL is gone. The file stays
mode a-w, so writes still fail with EACCES until write permission
is restored. Only the immutability is lifted. Refresh RPCs are
rate-limited to 5 per second per client and only triggered for
LLIF_POSIX_IMMUTABLE files, so plain chattr +i files see no change.

fileattr_get() is refactored to share ll_md_getattr_flags() with the
revalidation path, and hides LUSTRE_RETENTION_FL from userspace so
chattr -i is not rejected as an unrecognized flag. RETENTION_FL is
otherwise safe for old clients to ignore, since it travels in
lma_compat, and ll_ext_to_inode_flags() already uses an explicit
flag whitelist, so an old client simply drops any bit it does not
recognize.

hsm_swap_layouts() gains a SWAP_LAYOUTS_MDS_RELEASE bypass in
mdd_layout_swap_allowed(), and calls ll_refresh_posix_immutable()
before the swap, so root-driven HSM restore and lfs migrate work
again once retention has expired.

Storage layer
-------------
osd-ldiskfs and osd-zfs osd_attr_set() are reworked from a one-way
OR of LMA flags to a compute-and-diff set/clear update, since
RETENTION_FL, unlike ORPHAN/ENCRYPT, must be clearable.

While la_atime is in the future, normal access never moves it
backwards, so atime-based retention/purge scans will treat the file
as recently accessed and skip it. This is harmless, since the file
is immutable and cannot be removed until it becomes writable again.

Testing
-------
mdd.posix_immutable defaults to off. Only the auto-set behavior is
gated by it, everything else, enforcement, client refresh, and LMA
flag handling, is unconditional and unchanged for plain chattr +i
files.

sanityn.sh test_106d covers flag set, retention expiry, mode-only
failure after expiry, root denied and allowed before and after
expiry, and owner delete after expiry. test_106e covers lfs migrate
by the owner and by a CAP_LINUX_IMMUTABLE holder after expiry.
test_106f covers write and unlink denied to a non-owner,
non-privileged caller on an expired but not yet cleared file.

Problematic, see inline comments. The core issue is that nothing on disk distinguishes a POSIX-retention file from an ordinary `chattr +i` file, so `lu_posix_immutable_expired()` also matches the classic `chmod a-w; chattr +i` recipe and silently strips IMMUTABLE from those files. Separately, `mdd_clear_expired_posix_immutable()` takes `mdd_write_lock()` and is reached from call sites that already hold that lock, which trips the `LASSERT(dt->dd_owner != env)` in `dt_write_lock()`. Both look like they need rework before this can land; a persistent on-disk marker (an LMA/xattr bit or a dedicated flag) distinguishing retention-immutable from chattr-immutable would address the first, and hoisting the clear out of the permission/delete predicates would address the second.
