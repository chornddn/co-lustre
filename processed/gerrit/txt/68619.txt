LU-19895 obdclass: back page pools with compound pages

The next patch backs unaligned DIO bounce buffers with large
folios from these pools, but only the order 0 pool hands out
real pages.  Higher orders use OBD_ALLOC_LARGE, which can
return a vmalloc address - no compound head, so never a folio;
no in-tree caller used them.

Allocate higher order objects as compound pages (__GFP_COMP),
so an order N object is a folio of 2^N pages.  They are not
__GFP_HIGHMEM, unlike the order 0 pool.  That flag only has an
effect on 32 bit CONFIG_HIGHMEM builds, which are no longer
supported, and on one it would be wrong anyway: a caller takes
a high order object to get a contiguous buffer it can address,
and a highmem compound page cannot be mapped whole, since
kmap() covers a single page.  Order 0 objects keep it -- they
are bulk data, only touched under kmap.  They are
opportunistic caches: grown on demand with __GFP_NORETRY and
reclaimed to empty under pressure, since a DIO buffer that
cannot get its order just falls back to order 0.  Pools above
MAX_PAGE_ORDER are dropped, as alloc_pages() cannot serve them.

A high order pool also grows by exactly what was asked for
rather than a minimum batch: the batch is all or nothing, and a
high order object is already large enough to amortise the grow,
so a floor only means one failed contiguous allocation discards
the objects that did succeed.

The shrinker also switches its count/scan unit from objects to
pages, so a high order pool reports its free objects as the
memory they actually are, and returns SHRINK_STOP when it has
nothing left rather than a bare 0.

The order-taking API changes are mechanical.  Coming with the
high order users: bounds checks on the by-order accessors,
clearing the caller's array on the cannot-happen -EPROTO exit,
and demoting an expected high order grow failure to CDEBUG.

The pool_max_memory_mb description is rewritten while it is
here: it said "default unlimited", but obd_pool_init() has
always capped an unset pool at totalram/POOLS_COUNT, and the
limit is per pool rather than global.  get_pool_index()'s
CERROR also reports pools_count rather than POOLS_COUNT, which
differ once the MAX_PAGE_ORDER clamp applies, and a pool the
node is too small to hold even one object of is cleared before
the loop breaks -- hygiene rather than a fix, since that path
returns 0 and never reaches the error label.

Two fixes ride along: the old void * obd_pool_put_objects()
dereferenced the buffer as its object pointer, and the -ENOMEM
path leaked opp_pages_short.

COMMIT_MSG: added a paragraph on the shrinker switching its count/scan
unit from objects to pages and returning SHRINK_STOP when it has
nothing left, and the existing paragraph names obd_pool_max_objects().

page_pools.c:33 (size formula): correct, it was off by a factor of
two.  Rewritten to say the largest object is PAGE_SIZE <<
(pools_count - 1), with the MAX_PAGE_ORDER clamp as a separate clause,
rather than quoting a size that only holds on 4K pages.

page_pools.c:588 (all-or-nothing grow): taking the second half of the
suggestion.  The minimum batch of 8 now applies only to the order 0
pool; a higher order pool grows by exactly what was asked for.  A high
order object is already large, so the minimum batch bought nothing and
made a single failed contiguous allocation discard up to seven
multi-MB objects that had succeeded.

Not keeping a short batch instead of discarding it: the caller's
fallback is deliberately a single step.  ll_allocate_dio_buffer()
makes one attempt at its chosen order and drops the whole middle of
the buffer to order 0 if that fails, rather than walking intermediate
orders, so a partially satisfied high order batch has no consumer.
__GFP_NORETRY keeps the failed attempt cheap.

page_pools.c:1012 (put side indirection): agreed, and for the reason
given -- the bug this patch fixes on that function was a wrong
indirection.  It now takes struct page * and passes &page internally.
The get side keeps struct page ** as an out parameter.
