LU-20327 tests: list only own files in recovery-small 155

test_155 compares "ls -l $DIR" from before a client remount
against the same listing after it, so every file any earlier
test left in $DIR has to survive the comparison. The remount
drops the attributes the client had cached, and a file whose
cached size the servers never agreed with then changes size
across it.

test_131 leaves exactly such a file. Its buffered write is
discarded by the eviction the test arranges, so the OST
object stays empty while the client goes on reporting 512
bytes. The client does glimpse the object again -- the MDT
returns no size for a striped file -- but the eviction races
with the cancel that would roll back the known minimum size
the write recorded, and when the cancel loses, the 0 the OST
answers is clamped back up to it. The remount is the first
thing that drops it, and the flush added by
commit 2b762bdd15d8 ("LU-14708 tests: improve recovery-small test_155")
does not help. That stale size is a client bug in its own
right and is left to its own patch. This is every Janitor
failure sampled, all of them on ZFS.

List only the directory this test creates, on the MDT that
fails over, and have test_131 remove the file it can no
longer describe.

The MDT commit is the other half. The client that creates
$tfile unmounts before the failover, so it cannot replay the
create, which therefore has to reach disk before the replay
barrier drops writes. Removing the commit step loses the
file on every run, which is the second failure recorded on
this ticket. Commit the way the replay suites do rather than
by syncing the server host, which does not reach an osd-zfs
target at all.
