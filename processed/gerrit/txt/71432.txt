LU-21326 gss: send context init reply to the request's source

With SSK, a mount can hang when the client and server share more
than one LNet network. The client's context init request arrives
on one network, but the server replies to the client's primary NID
on another. With no route between the two, LNet drops the reply
("Unable to send message from ... - Route table may be
misconfigured"), the import stays CONNECTING and the mount waits.
LNet spreads a multi-rail peer's requests over every network the
two share, so this also hits servers that share several networks.

The cause is in gss_svc_upcall_handle_init(). It needs the sender's
primary NID to find the SK context, and gets it from
LNetPrimaryNID(), which overwrites the NID it is given. Since
1c250cbfa127 it passes req->rq_source itself, so the request loses
the NID it came from, and ptlrpc_send_reply() sends the reply to
the primary NID instead.

Look the primary NID up on a copy, as the code did before that
commit.

Add sanity-sec test_202: give the client and mds1 a second network,
send the client's requests to mds1 over it with a UDSP rule, and
mount. It needs an SK flavor and a client apart from mds1.
