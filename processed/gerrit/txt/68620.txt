LU-19895 clio: use large folios for unaligned DIO

The unaligned DIO bounce buffer was filled from the order 0
pool, one page and one cl_page per PAGE_SIZE, so it never
benefited from the multi-order folio extents the aligned path
now builds.  It matters more than the aligned case in practice:
the client allocates this buffer itself, so no THP backed user
buffer is needed, and hybrid IO routes ordinary buffered writes
into exactly this path.

Fill the buffer from the compound page pools: the bulk from the
largest order which fits (within one brw_ext), the remainder
from order 0.  Per-chunk bookkeeping falls from one
cl_page/oap/brw_ext per PAGE_SIZE to one per folio extent -
16384 entries to ~320 for a 64MiB chunk.

The buffer is capped at half the order 0 pool and the caller
loops; previously a request above the pool limit failed with
-EINVAL.  A zero length request still fails with -EINVAL.
Encrypted files keep order 0 entries (cdp_no_coalesce).

The read side now selects copy_folio_to_iter() on a dedicated
LC_HAVE_COPY_FOLIO_TO_ITER probe rather than inferring it from
the older __filemap_get_folio(), which does not imply it: the
former arrived in v5.19, the latter in v5.16, so kernels in
between did not build.

Keeping it in this patch rather than splitting it out: the same probe
is what gates LL_DIO_POOL_MAX_ORDER here, so a separate change would
have to land first for this one to be correct.

cl_io.c:1938 (read clamp): right, it is dead, and for exactly the
reason given.  Removed it and LL_DIO_READ_COPY_SPANS with it.

Taking that rather than the other option -- dropping the
HAVE_COPY_FOLIO_TO_ITER term from LL_DIO_POOL_MAX_ORDER -- because
that term is deliberate.  Without copy_folio_to_iter(), a multi-page
entry has to be read back a page at a time, and each pass flushes the
whole folio, so the flushing cost grows with the square of the entry
size.  Order 0 on 5.16-5.18 is the cheaper of the two.  The comment on
LL_DIO_POOL_MAX_ORDER already records this, so the coupling is not
lost with the macro.

cl_io.c:1596 (unit check robot): the flagged expression, npages -
head, no longer exists; the count is now built up in a local.
