LU-14917 llite: Switch mmap readahead logic

The mmap specific readahead logic does badly for some workloads,
e.g. kdb and clustered reads such as vLLM loading model weights
from safetensors files through mmap.  Add the tunable
llite.*.mmap_read_ahead_logic (default 1) to let page faults use
the read() readahead logic instead.

With mmap_read_ahead_logic=0:
- ll_fault() feeds each fault to ll_ras_enter_fault(), but skips
  faults retried after VM_FAULT_RETRY (FAULT_FLAG_TRIED).  Faults
  on pages still being read ahead are retried, and the retry looked
  like a backward seek that reset stride detection.
- ll_ras_enter_fault() holds back one fault away from the stream
  and drops it if the next fault continues the stream, so a single
  b-tree interior page does not reset the window twice.
  ras_update() keeps the window for the held page.
- ll_read_ahead_pages() skips pages already in the page cache
  instead of giving up after 3 busy pages, as processes faulting
  on the same file read ahead over each other's pages.
- The fast fault path does not add an LCC_MMAP context, which only
  carries LL_RAS_MMAP, unless the thread has one already: adding it
  took lli_lock for write twice per fault, and 30% of the CPU time
  was spent spinning on it with 16 processes on one file.
- ll_io_read_page() and do_read_folio() do not pass LL_RAS_MMAP,
  and ll_io_read_page() does not apply the skip index.

For every reader, is_loose_seq_read() now treats a read that starts
less than 128KiB (RAS_LOOSE_GAP_BYTES) past the end of the previous
one as continuing the sequential stream, instead of 8 pages, and
readahead reads the gap too.  A vLLM tensor parallel rank reads 1/TP
of every row of a row parallel tensor, skipping 42-49KiB of every
56KiB row of Llama-3-70B; as a stride, readahead sent RPCs full of
holes and the OSTs did a 16KiB disk I/O per hole.  Larger gaps are
still detected as a stride.  A single process reading small chunks
with gaps below 128KiB now reads the gaps as well.

Also check the fault offset before blocking signals in ll_fault(),
so the VM_FAULT_SIGBUS return does not leave them blocked.

Fix sanity/101f, which hid iozone failures: check the return codes
and use a record size of at least PAGE_SIZE.  Add sanity/101k,
which compares misses with both settings using multiop, and 101n,
which checks that a strided mmap read skips 192KiB gaps and that a
strided read() reads through 60KiB gaps.  101f stays excluded until
LU-14921 is fixed.  Add the man page llite.mmap_read_ahead_logic.4.

Results: one client (24 cores, 87GiB, 50Gb/s TCP), 8 ldiskfs OSTs
on 2 OSSs, 4MiB stripes and RPCs, cold client cache.

vLLM-like load of a Llama-3-70B-like checkpoint: 27 safetensors-like
shards, 139GB in total, more than the client memory.  Each tensor
parallel rank maps one shard at a time and reads a 1/TP block of
rows of q/k/v/gate/up and 1/TP of every row of o/down.  Time of the
slowest rank; 8 processes reading 8 shards each in order (no TP)
reach 5.7GB/s.  "before" is this patch without the 128KiB gap rule
and the fault fixes, i.e. the original change rebased:

  ranks  mmap logic=1  mmap logic=0  pread() of the same slices
         before/after  before/after  before/after
    4     110s/ 56s     349s/36s     101s/40s
    8     319s/ 71s        -/32s     235s/41s

Other workloads through mmap, median of 2 runs, values for
logic=1/logic=0.  "secs" is the run time and "Actual Data Read" the
data the client read from the OSTs (sum of read_bytes in
osc.*.stats).  It shows how much a setting reads ahead that the
workload never uses:

  sequential 8GiB                 3.48/2.84        8192/8192
  4 x 2GiB sequential             2.01/1.55        8192/8192
  strided, 64KiB of 256KiB        1.53/1.65        2048/2132

  kdb-like, scan 8 columns        4.80/4.43        8192/8192

  SQLite full table scan          3.87/1.43        1744/1856

With the gap rule the default mmap logic and read() are 2-6x faster
on the 70B load; mmap_read_ahead_logic=0 is a further 1.5-2.2x
faster there, 2.7x on SQLite table scans and 2.6x on clustered
access.  The 4KiB of 64KiB stride read 512MiB before the gap rule
and takes 1.57s with either setting.  Short scans at random offsets
read up to 6x more, since the window is rounded up to full RPCs.
So the default stays 1 until more mmap workloads are measured.
