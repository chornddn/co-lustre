LU-20650 lfs: find --since, warn when the log was cleared

A time or a bare index can reach back past records that another
changelog user has already cleared. The scan then starts at the oldest
record left, so the answer is short, and the run said nothing and
exited 0. On a site where a policy engine consumes the changelog this
is the normal state, so "--since 1d" could return much less than a
day of changes without saying so.

Before each MDT is scanned, find_since_gap() reads its oldest record
with find_cl_first(), the same one-record read the cookie's stale
check uses. Changelog indexes start at 1, so a log that still holds
record 1 has lost nothing since it started, and a new filesystem gives
no warning. Nor does a log restarted at 1, after its last user went and
the MDT was remounted, or an empty log.

For a bare index the loss is certain, and the warning says so. For
a time it is not: a client cannot see when the last cleared record
was written, so the cleared records may all be older than the
window. The warning then says only where the log starts and that
anything cleared after the anchor is missing. The log is read only
when there is an anchor to compare, so --changelog without --since
costs nothing more.

This is a warning and not a refusal. A cookie is refused because the
run would move its anchors past the lost records for good. A time or
an index writes nothing, so the next run can be asked differently.
The cookie keeps its own check and is skipped here.

sanity 160Af clears the log and checks that a window reaching back
past the clear warns, for a time and for an index, and that a window
inside what the log holds does not.
