LU-20749 obdclass: diagnose OSD module load failures

When a server target is mounted, the OSD type is looked up with
class_get_type(), which asks the kernel to load the matching
module with request_module() if that type is not registered yet.
request_module() runs modprobe through call_usermodehelper(),
which discards its error output, and class_get_type() discards
the return code as well, so the only trace left of a failure is:

  LustreError: Can't load module 'osd-ldiskfs'

and ENODEV from the mount, which mount.lustre reports as "Are the
lustre modules loaded?". Every cause looks the same that way: the
module not being installed, a kABI or relocation mismatch, a
rejected signature, or modprobe just not being runnable at that
moment.

Report the return code of request_module(), and try once more
before giving up, since the failure can be transient: modprobe
may fail to run, or the previous instance of the module may still
be going away.

Also load the backend OSD module from mount.lustre, where the
mount type is already known from the on-disk data and modprobe
can report on its own why it failed, the same way zfs_init()
already loads zfs for a ZFS target. Name that module in the ENODEV
hint of mount.lustre, so that it no longer points only at the Lustre
modules, which are loaded in that case.

Add conf-sanity test_165, which makes every attempt to load the
OSD module fail and checks that both mount.lustre and the kernel
say why, that the load is retried, and that the filesystem starts
again once the module can be loaded. Add conf-sanity test_166,
which reproduces the sequence a server goes through when it is
restarted with its modules reloaded, and leaves the servers without
their OSD module so that mounting a target is what has to load it.
