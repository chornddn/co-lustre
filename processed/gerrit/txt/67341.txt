LU-19569 tests: guard sanity-lfsck test_45 against ENOSPC

sanity-lfsck formats 100MB OSTs (~69MB usable), and test_45 forces a
30MB write onto OST0000 with "setstripe -i 0 -c 1".  In aggregate runs
that dd fails with ENOSPC:

  dd: error writing '/mnt/lustre//f45.sanity-lfsck-0': No space left on device
  sanity-lfsck test_45: @@@@@@ FAIL: write /mnt/lustre//f45.sanity-lfsck-0 failed

The OST is not out of space when it refuses the write.  The BRW that
fails returns rq_status 0 with no transaction and carries -ENOSPC only
in the per-niobuf rc vector, which is the ofd_preprw_write() path that
sets lnb_rc = -ENOSPC for buffers whose OBD_BRW_GRANTED was cleared by
tgt_grant_check().  That happens when tgt_grant_space_left() -- the
cached os_bavail minus tgd_tot_granted -- falls below one RPC, and it
did so while the client's own statfs still reported 58MB free on that
OST.  Checking "lfs df" before the write does not help: ofd_statfs()
subtracts dirty and pending from os_bavail, but not the space already
granted to the other client mounts, so the free space it reports is not
the space the OST can still hand out.

Ask for less space, reclaim the grant the clients are not using, place
the file on whichever OST the MDS considers emptiest, and check the
space that OST can actually grant instead of what "lfs df" reports on
its own.  The subsequent stop/mount/chown/start of the backing
filesystem and the LFSCK status wait now follow the OST that was picked
instead of always using ost1.

Reproduced by mounting eight extra client instances so that OST0000
holds 62668KB free but 44966464 bytes granted: the unpatched test fails
with ENOSPC after 25 of 30MB, while the patched test passes both when
the file lands on OST0000 and when it lands on OST0001.
