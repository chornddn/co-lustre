LU-12187 lod: add an EC layout version to lcme_cstripe_count

The EC parity stripe count lcme_cstripe_count is limited to
LOV_EC_MAX_CODING_STRIPES (15), so only the low 4 bits of the
byte are needed.  Make it a 4-bit field and use the high 4 bits
as lcme_ec_version, before the EC layout format is in a release.
The fields are reversed under __BIG_ENDIAN_BITFIELD so the count
is in the low 4 bits of the on-disk byte on every host.

Every reader recomputes which data stripes a parity stripe covers
from the layout: the raid-set split from ec_split_stripes(), the
parity stripe placement and the encoding matrix.  Any later change
to these would make an older client silently pair parity with the
wrong data, so the version names the whole mapping.  Version 0
(LCME_EC_VERSION_0) is the mapping 2.18.0 is released with, and
LCME_EC_VERSION_MAX is the latest one this code knows.

The version is kept in the parity component, which defines the
mapping for its pair; it is zero in data components.  The MDS sets
it when it allocates the parity stripes in lod_comp_prep_create():
a new parity gets the version asked for in a template or in a
layout from a user, limited to LCME_EC_VERSION_MAX, so clients
never need to negotiate one.  A parity without objects is also
stored with at most LCME_EC_VERSION_MAX, since this MDS will map
it when it is instantiated.  A later MDS can keep writing an
older version until its clients understand the new one, e.g. with
a connect flag or a tunable.

For a parity with a later version than LCME_EC_VERSION_MAX:
- the LOV client treats its data as unlinked, so the data stripes
  are read as plain RAID0 and never reconstructed from parity;
- llapi leaves the parity stale when it resyncs the rest of the
  file, refuses to verify it with -EOPNOTSUPP, and 'lfs getstripe
  --ec-map' prints the version instead of a raid-set split it
  would compute wrongly;
- LOD keeps the layout as loaded from disk and writes the version
  back unchanged once the parity has objects, does not resize or
  re-stamp the parity when its objects are given by a layout swap or
  open replay, and lod_verify_striping() rejects such a version for
  a parity with objects in a layout from a user.

The in-memory llc_cstripe_count (LOD and llapi) and
lsme_cstripe_count (LOV) become 4-bit fields, with the version
in llc_ec_version and lsme_ec_version.

Add sanity-ec test_1m to check that the MDS limits a later version
in a template to the one it knows for a new parity, and test_1n
(ldiskfs) to check that a file whose parity has an unknown version
on disk is still readable and writable, that its parity is not
verified or resynced and keeps its version, and that a parity
instantiated later in the same file gets the MDS version.
