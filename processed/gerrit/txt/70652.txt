LU-21171 ofd: don't read past the FIEMAP reply buffer

A count-only FIEMAP request has fm_extent_count = 0, so the reply
buffer holds only the fiemap header. ofd_fiemap_get() still sets
fm_mapped_extents to the real number of extents. With
FIEMAP_FLAG_SYNC (OBD_FL_SRVLOCK), lock_zero_regions() then walks
fm_mapped_extents entries and reads past the end of the reply.
KASAN reports this as slab-out-of-bounds in sanity test_44f.

Walk only the extents that are in the buffer. For a count-only
request the whole range is then locked once. Also skip the locking
when the first fiemap call fails, as fm_mapped_extents is then not
set by the server.

dom_has_zero_regions() in mdt has the same bug for DoM files, so
fix it the same way. mdt_fiemap_get() also never dropped the DoM
lock it takes there, so a later write to the file, and the MDT
unmount, wait on it forever. Drop it after the second fiemap call.
sanity test_44i checks this with dom_lock=never, so that the open
gives the client no DoM lock.

The OFD change looks correct. One whole-patch point, raised here because the file isn't in the diff: the DoM FIEMAP handler has the same out-of-bounds read. dom_has_zero_regions() in lustre/mdt/mdt_io.c still loops `for (i = 0; i < fiemap->fm_mapped_extents; i++)` over fiemap->fm_extents[]. mdt_fiemap_get() sizes the reply the same way, with fiemap_count_to_size(fm_extent_count). lov_object_fiemap() sends fm_extent_count = 0 per component for a count-only request (fs_cnt_need = fiemap_size_to_count(sizeof(struct fiemap)) = 0). mdc_object_fiemap() sets OBD_FL_SRVLOCK when no lock is cached. So a count-only FIEMAP_FLAG_SYNC on a DoM file should hit the same slab-out-of-bounds read on the MDS. Should that loop get the same min(fm_mapped_extents, fm_extent_count) bound, here or in a follow-up? That copy came in with 5921e1571f ("LU-14510 dom: fiemap support for DoM files").
