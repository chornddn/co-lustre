LU-20911 lfsck: check the layout of EC files

LFSCK only accepted the layout of an EC file, with its parity
components, when it rebuilt it from orphan OST objects.  Its scans
skipped EC files, and when an OST with lfsck_verify_pfid enabled asked
the MDT to verify an EC object whose parent FID or stripe index did
not match the RPC, the MDT refused it, so the OST kept returning
-EINPROGRESS and the client resent the I/O forever.

LFSCK checks layouts and the consistency of MDT and OST objects, not
file contents, and that works for the objects of parity components as
for those of data components, so accept EC layouts everywhere, and
drop the argument of lfsck_layout_verify_header() that selected them.

A repair that gives a component a new empty OST object, for a dangling
reference with "lfsck --create-ostobj" or for an object shared with
another file, would leave an EC component without its parity or data.
A data component of an EC pair whose parity is in sync gets a dummy
slot instead, as the orphan handling leaves for a lost object, so that
EC reads rebuild that stripe from parity, as clients with
https://review.whamcloud.com/71263 ("LU-20911 lov: rebuild EC stripes
with no object from parity") do, and the object of the other file is
no longer referenced.  It does so even when its raid set has lost more
stripes than the parity can rebuild, so that a read of them fails
rather than returns zeroes, or wrong data rebuilt from parity that an
empty object no longer matches, and the parity stays in use for the
other raid sets.  If the parity has a newer EC version than LFSCK
knows, the stripe gets the empty object, and the parity is marked
stale.  A parity component still gets the new object, but is marked
stale first, with the file write pending, so that a resync rewrites
it, unless no data mirror would then be in sync.  If its data
component has a dummy slot, a resync could not regenerate the parity,
so its lost object also gets a dummy slot, and the parity stays in
use.

When an OST with lfsck_verify_pfid enabled was asked to verify the
parent FID of an object that it was already verifying, it would leak
a reference on the object, and the OST would then hit an LBUG at
unmount.  Take the reference only when the object is queued.

Add sanity-lfsck test_55 to read and resync an EC file whose data and
parity objects name a parent that does not exist, with
lfsck_verify_pfid enabled, test_56 to repair an EC file whose parity
objects are lost, test_58a to repair a 2+2 file that lost one data and
one parity object, test_58b to repair a 2+1 file that lost both data
objects, and test_59 to repair an EC data object shared with another
file.
