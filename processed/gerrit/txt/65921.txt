LU-19548 lfs: mirror extend support for EC

Add three EC modes to 'lfs mirror extend':

--mirror-id N --ec D+P   attach a parity mirror to existing data
                         mirror N (N >= 1)

-N [K] --ec D+P          add K new data+parity mirror pairs
                         (K defaults to 1)

--ec D+P                 auto mode: attach a parity mirror to the
                         file's lone data mirror. Resolved per file:
                         files with exactly one mirror succeed; 2+
                         mirrors error with a disambiguation message.
                         Covers the non-FLR case where the user just
                         wants to add EC protection to a plain file.

The new mirrors are in sync when the command returns, matching the
regular extend behavior of never leaving a new mirror stale: new data
mirrors are populated by a copy before the layout merge, and new
parity mirrors are computed in place with the same client-side
machinery 'lfs mirror resync' uses.

A parity mirror is attached by merging a layout that holds only the
new parity components, while the data mirror they protect stays where
it is. Splitting the pair across two files this way needs two changes
in lod.

lod_qos_prep_create() sizes a parity component from the data component
it protects and rejects a parity component that has none. The data
component of an extend is not in the volatile file being created, so
the client sends that component's stripe count as the parity
component's own stripe count, and lod derives the raidset count from
it when there is no local data component to pair with. A transient
link id is still required to resolve within one layout.

lod_declare_layout_merge() copies the incoming entries verbatim, so
only the parity -> data half of the link would be stored. It now also
stamps the matching data component with the mirror id assigned to the
parity component, so an EC pair created by 'lfs mirror extend' is
linked in both directions like one created by 'lfs setstripe --ec'.
Without this 'lfs mirror split' cannot see the pair from the data
side and leaves the parity mirror behind when the data mirror it
protects is split out.

The new llapi_layout_comp_add_parity_only() builds the parity-only
layout. llapi_layout_comp_add_ec() cannot serve that case: it derives
the parity extent, stripe size and pool by searching for the data
component in the same buffer, and pairs the two with a transient link
id that is resolved during creation. The two functions share their EC
stripe-count validation. Client-side layout sanity likewise had to
stop requiring a data component for every parity component.

Attaching a second parity mirror of a different geometry to one data
mirror, which would let a file's EC protection change without
rewriting its data, is not implemented: the merge ioctl takes one
mirror at a time and lod_qos_prep_create() resolves a parity component
to a single data component. It is rejected for now, and no test
asserts that rejection.

'--mirror-id 0' is rejected by the parser; id 0 is reserved for
non-FLR layouts and is not a valid target. Use auto mode instead.

Because an MDS that predates this change refuses a parity-only create
buffer outright, the new sanity-ec subtests are gated on the server
version so an interop run skips them instead of failing.

collect_mirror_id() writes into a caller-supplied array with no way
to tell where it ends, and three of its callers sized that array for
128 mirror ids while a file may carry LUSTRE_MIRROR_COUNT_MAX (256).
Raising lod.*.mirror_count_max past 128 and creating that many
mirrors would run off the end of the stack array. struct
collect_ids_data gains a cid_max capacity that the callback honors,
and the three arrays are sized from LUSTRE_MIRROR_COUNT_MAX. Two new
callers are added here, which is why the fix rides along.
