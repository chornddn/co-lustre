LU-21295 ptlrpc: add tracepoints for the RPC lifecycle

Per-RPC latency is visible only in the debug log.  kprobes on
ptlrpc functions break across releases, and reading Lustre structs
from them needs module BTF, which most server builds lack.

Add trace system "ptlrpc" with five events:

  ptlrpc_cli_send     in ptl_send_rpc(), just before the request goes
                      on the wire, including every resend
  ptlrpc_cli_reply    in after_reply(), once the reply is unpacked,
                      with the latency since the last send
  ptlrpc_cli_timeout  in ptlrpc_expire_one_request()
  ptlrpc_srv_start    in ptlrpc_server_handle_request(), when a
                      service thread takes the request, with the time
                      it waited in the queue
  ptlrpc_srv_done     in ptlrpc_server_handle_request(), after the
                      handler returns, with service and total time

They carry the xid, opcode, target or service, peer NID and jobid,
so one RPC can be followed from the client to the server and back.
Add contrib/eBPF/ptlrpc_latency.bt for per-opcode latency histograms,
and sanity test_60n, which checks that one RPC is traced on both the
client and the MDS.

Benchmark: single-threaded createmany, statmany after a lock cancel,
and unlinkmany of 10000 files in one directory, from one client, with
1 MDT and 3 OSTs on VMs and the default debug mask on every node.
Each build ran on a fresh mount; rows are in run order, so the two
"before" and two "after, off" rows show the drift over the session.
Microseconds per operation, median of 7 runs:

  before           the parent commit, without the tracepoints
  after, off       this patch, tracepoints compiled in but disabled
  after, on        all ptlrpc events enabled through tracefs on every
                   node, writing each record into the trace buffer
                   with no reader attached: the cost a node pays
                   while traced with trace-cmd or tracefs, excluding
                   the reader itself
  after, bpftrace  ptlrpc events disabled in tracefs, and
                   ptlrpc_latency.bt attached on every node instead;
                   each event runs its BPF program and updates the
                   histogram maps rather than writing to the buffer

                  create   stat  unlink
  before             698    496     704
  after, off         681    501     716
  after, on          708    514     713
  after, bpftrace    724    490     708
  after, off         703    488     695
  before             702    497     710

Disabled, the tracepoints add no measurable cost (within 2%).
Enabled on every node, either way, they add up to 4%, within the
spread of about 10% between single runs of one build.
