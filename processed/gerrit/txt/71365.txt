LU-21309 llite: avoid extra HSM RPC on setattr after write

A non-size setattr (chmod, utimes, chown) on a file with uncommitted
writes sends a dedicated MDS_HSM_STATE_SET RPC to set HS_DIRTY right
after the setattr RPC. That block was introduced by LU-5823, and
LU-6817 later only lowered its error message level. On files that are
not HSM-managed, which is the common case, the MDT rejects that
request with -EINVAL, so the RPC is wasted and costs one synchronous
round trip per setattr.

The close path and the size-change branch of ll_setattr_raw() already
notify the MDT about data modification by packing MDS_DATA_MODIFIED
into the RPC itself, and mdt_reint_setattr() handles this bias for
any setattr via mdt_add_dirty_flag(). Do the same for non-size
setattrs: pack MDS_DATA_MODIFIED into the setattr RPC and consume
LLIF_DATA_MODIFIED there.

The explicit MDS_HSM_STATE_SET RPC after ll_md_setattr() is kept for
the case it was introduced for in LU-5823: a file restored from a
released state during this setattr, where the MDT refuses to set
HS_DIRTY yet. vvp_io_setattr_fini() re-sets LLIF_DATA_MODIFIED after
ll_md_setattr() in that case, and the existing block picks it up.

If ll_md_setattr() fails, the flag consumed above is restored, so a
later close() still notifies the MDT with MDS_DATA_MODIFIED, exactly
as before this change.

With this change a "write, chmod, close" sequence issues 2 metadata
RPCs for the chmod instead of 3 (layout enqueue + setattr instead of
layout enqueue + setattr + hsm_state_set), and HS_DIRTY is still set
on HSM-managed files by the same setattr RPC.

Verified on a 2-node rig with a 2.17.62 client (this change) against
a 2.15.91 server: "write, chmod, close" on a file with HS_EXISTS ends
with state 0x3 (exists|dirty), the same as "write, close"; server
counters show mds_hsm_state_set going from +1 to +0 per setattr, with
the notification now carried by the mds_reint_setattr RPC.
