LU-20403 ptlrpc: refresh export conn on primary migration

A client's LNet primary NID can migrate while its connection to a
server stays up, which happens for any unlocked peer when a net is
reconfigured or discovery re-elects a primary. Say the client's
primary moves C1 -> C2 and the client stops advertising C1. At
connect time the server keyed everything for that client on C1: the
export connection, the target NID hash, and the reverse import used
for lock callbacks. Two things then break:

  - The obd NID hash stays keyed on C1, so NID-keyed lookups such as
    evict_client and the nodemap walks no longer find this client.

  - Blocking and completion ASTs are sent on the reverse import, also
    keyed on C1. Once the client drops C1 the callback targets a dead
    NID, is never delivered, times out, and the server evicts the
    client.

The client-side import refresh cannot cover this. It detects a
migration by looking up the primary of the NID its own connection
holds, but the server's reverse import holds C1, and once discovery
prunes C1 LNetPeerPrimaryNID() can no longer find it and reports it
unchanged. The reverse import is blind to its own peer's migration
and has no path from C1 to C2.

The only place the server authoritatively learns C2 is an incoming
request: rq_peer is the primary NID LNet resolved for the request at
parse time. ptlrpc_server_handle_request() therefore compares rq_peer
against the NID the export is keyed on. Because rq_peer is stable
across a multi-rail client's NICs, the gate stays quiet until a real
migration and needs no lookup of its own. On a change it calls
ptlrpc_refresh_export_primary(), which re-keys the export connection
on the new primary, mirroring the connect-time swap
(obd_nid_del/obd_nid_add) so the target NID hash stays consistent.

The same refresh moves the reverse import, the only place it can
learn of the migration. exp_imp_reverse is stable under exp_lock, and
the import paths that hold imp_lock do not take exp_lock, so the
nesting order is exp_lock -> imp_lock. rev_import_reconnect() takes
imp_lock around its own connection swap so it serializes with this
refresh.

A reverse import owns no DLM export of its own: the server's DLM
export for that client is the obd_export the reverse import hangs off,
and it is refreshed directly. import_switch_connection() therefore
skips the DLM export step for IMPF_DLM_FAKE imports rather than
reporting -EINVAL, and is no longer static so the export refresh can
reach it.

Extend conf-sanity test_73g to also migrate the client's own primary
NID, so the servers detect the change on the next request and refresh
both the export and its reverse import, exercising the server-side
refresh.

Some concerns, see inline comments. The main one is that the new gate trusts rq_peer unconditionally, with nothing that keeps the export moving forward in time, so an older queued request can pull a correctly-keyed export back onto the pruned NID.

The added test_73g steps exercise the new path but assert nothing about it - the two wait_clients_import_ready() calls only check client-side import state, so the test passes identically without this patch. Consider asserting the server side, e.g. checking the servers' export NID (obd_nid hash / exports listing) or the new D_HA message, so a regression in ptlrpc_refresh_export_primary() would actually fail the test.
