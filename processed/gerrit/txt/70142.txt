LU-20099 nrs: dispatch BRW requests in per-object batches

A server runs one NRS policy per head, so a site must choose between
the object locality of ORR and the QoS of TBF or mClock.  Under TBF or
mClock, the BRW requests of many clients reach the backend in arrival
order, interleaved across objects and offsets, which turns sequential
streams into random I/O on hard disks.

Add per-object batches to the classful scheduler, so TBF and mClock
both get them.  A class bucket of a batching rule queues each OST_READ
and OST_WRITE request by object FID, in logical offset order, and
dispatches a batch of one object, counted in whole pages, before the
next.  Other requests stay on the FIFO nc_list, and the older of that
list and the next object goes first.  A batch dispatches the lowest
queued offset of its object first, so a stream that falls behind,
such as a slow rank writing a shared file, catches up rather than
waiting for the streams ahead of it.  A request that arrives during a
batch joins the current round of its object, the round closes at the
end of the batch, and later requests join the next round, so requests
at lower offsets cannot hold back the rest of a round for more than
one batch.

By default, a rule batches only the requests to a target on rotational
storage, without OS_STATFS_NONROT in the statfs that the target
caches, and a batch holds as much as one RPC of the client that starts
it, from exp_max_brw_size().  A full size RPC then forms a batch of
its own, and smaller RPCs of one object are gathered into one RPC's
worth.  The new batch_kb= key of a policy start command sets the batch
size of every rule that does not name one, for every target, and the
key of a rule start command sets it for that rule; batch_kb=0 turns
batches off.  A rule shows its batch size only when it has one, so the
rule output of TBF does not change.

The policy charges a class bucket for its next request, so
nrs_class_req_first() keeps its choice until that request leaves the
bucket.  TBF and mClock now share one request type, nrs_class_req,
and use nrs_class_req_add/del/first/pop() instead of nc_list.  Move
the FID and offset parsing of ORR into nrs_brw_fid_get() and
nrs_brw_range_get(), which also count the niobufs from the request
buffer size rather than ioo_bufcnt.

Add sanityn test_77tj and test_77tk for TBF and mClock batches, and
test_77tl for the default batch size on rotational and non-rotational
OSTs.

Patch Set 2:

Results on a single HDD OST, where requests queue in NRS.

Setup: 1 MDT, 1 OST on a 100 GB image on a 7200 rpm HDD (cache=none,
rotational, so batches are on by default), 16 clients x 8 ranks,
max_rpcs_in_flight=32, ost_io threads_max=16.  With the default 128
ost_io threads nothing was ever queued in NRS (all requests waited in
threads and the disk queue), so the order did not matter.  With 16
threads NRS held 82-94 queued requests on average.

Fixed-size ior-hard write pattern, no stonewall, 12 GB total:
  lfs setstripe -C 4; ior -C -Q 1 -g -e -w -a POSIX -t 47008 -b 47008 -s 2000

                                MiB/s   total   rank avg/max
  fifo                           8.66   1325s   1163/1324s
  tbf opcode batch_kb=0          7.75   1482s   1351/1480s
  tbf opcode, PS1 elevator       8.79   1306s   1229/1304s
  tbf opcode, PS2 lowest first  10.19   1126s   1111/1124s

Lowest offset first is 18% faster than fifo, 31% faster than TBF
without batches and 16% faster than the PS1 elevator.  The ranks
finish within 13s of each other, against 75-160s for the others,
so slow ranks catch up rather than holding up the end of the job.
The OST I/O sizes are the same in all runs (82-90% 64KB).  One run
of each.

The first PS1 elevator run crashed the OSS:

  BUG: scheduling while atomic: ll_ost00_004/48295/0x00000002
   schedule
   nrs_class_findadd
   nrs_class_res_get
   nrs_resource_get
   nrs_resource_get_safe
   ptlrpc_nrs_req_hp_move
   ldlm_server_blocking_ast
   tgt_blocking_ast
   ldlm_work_bl_ast_lock
   ...
   ldlm_handle_enqueue
   tgt_enqueue
  LustreError: (client.c:613:ptlrpc_request_cache_alloc()) ASSERTION(...) failed
  LBUG
  Kernel panic - not syncing: LBUG in interrupt.

nrs_class_findadd(), added in https://review.whamcloud.com/65730
("LU-20099 nrs: abstract rule-based classful NRS scheduler"), calls
schedule() to retry when it loses a race with a class being freed.
ptlrpc_nrs_req_hp_move() calls it under scp_req_lock (moving_req is
true), and nrs_class_res_get() already allocates with GFP_ATOMIC in
that case, but the retry still sleeps.  The retry needs cpu_relax()
when moving_req is set, or to fail the HP move.  This patch does not
change that code, so it can hit the same crash.  The rerun of the
same test completed without problems.
