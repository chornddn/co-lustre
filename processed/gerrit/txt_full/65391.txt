LU-20090 nrs: add static and dynamic classify conf for TBF policy

This patch adds static and dynamic classify setting for TBF
policy.
Under the static strategy, the class type of each rule can be
only the global classification type;
Under the dynamic strategy, the class type of each rule can be
automically detected according to the rule's conditions, i.e.
The global rule is NID which is configured via:
ost.OSS.ost_io.nrs_policies="tbf nid"
A newly adding rule:
nrs_tbf_rule="start r1 nid={10.0.0.1@tcp}&uid={50} rate=100"
will be with class type of "nid+uid" instead of the global
class type "nid".

The classify strategy can only be configured by sysfs interface
"nrs_policies" when startup the TBF scheduler and cannot be
changed during runtime:

i.e.
- ost.OSS.ost_io.nrs_policies="tbf nid+opcode classify=dynamic
- ost.OSS.ost_io.nrs_policies="tbf nid+opcode classify=static

The classify strategy can also be displayed by sysfs interface
"nrs_tbf_classify":
- $LCTL get_param ost.OSS.ost_io.nrs_tbf_classify
  reg_classify:dynamic
  hp_classify:static

Add sanityn/test_77ta to test the setting of the classify
strategies.

LU-20090 nrs (PS3): the config plumbing for static/dynamic classify is in good shape overall, but I have a few correctness and polish concerns before this lands.

Main things:

1. nrs_tbf_parse_value_pair() silently accepts unknown keys in the SCHED_START path. Only 'classify=' is checked; any typo (e.g. 'classfy=dynamic', 'classify=foo' would error but 'foobar=static' returns 0). This is more permissive than the existing rule path which returns -EINVAL on unknown keys.

2. NRS_TBF_FLAG_DYNAMIC is OR'd into head->th_type_flag and therefore flows into nrs_tbf_cli_gen_key()'s 'valid' and into key->tk_flags. When the admin toggles classify at runtime, every cached client in the rhashtable has the old tk_flags and will never match again; the old entries become dead weight (no flush). This may be deliberate and addressed by later patches in the series, but worth confirming.

3. nrs_tbf_flags_valid() now accepts (NRS_TBF_FLAG_DYNAMIC only), since the only check is 'has any ALL bit, no extra bits'. A flags value with no field type but DYNAMIC set would pass the predicate. In practice nrs_tbf_type_parse guarantees at least one field, but the predicate name implies it validates that fact.

4. classify writer in ptlrpc_lprocfs_nrs_tbf_classify_seq_write(): when neither 'reg_classify:' nor 'hp_classify:' is present, val_reg/val_hp both equal kernbuf and queue is forced to REG (+HP). That ends up applying *the same* value to both heads, which is the intended behavior for the bare 'static'/'dynamic' form -- OK, but please add a comment to make that explicit, because the variable names (val_reg vs val_hp) suggest two distinct values.

5. Commit/comment polish: subject line is 65 chars, exceeds the 62-char cap from the Lustre wiki commit-message rules. Several spelling errors in new comments: 'possiibly', 'optioinal', 'TVF classify' (s/b TBF), 'automically' (s/b automatically), 'vaid' (s/b valid), 'hybird' (older). Test commit message says test_77tab, source says test_77ta -- pick one.

6. sanityn test_77ta: several error strings are wrong-side-of-the-coin (lines 5599, 5605, 5614, 5626 -- they say 'expected reg_classify:static' when the assertion is actually checking for hp_classify, or vice versa). When the test fires, the error string will mislead the next person debugging.

Nothing here is a -1 blocker on its own, but the silent-unknown-key behavior and the comment/string fixes should land before this does.
