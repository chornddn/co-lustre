LU-20527 osp: report the real next precreate id

osp.*.prealloc_next_id reports 1, instead of the object which will
really be handed out next, once the last used object has reached the
end of the OSP's sequence:

	id = unlikely(fid_oid(fid) >= min(OBIF_MAX_OID, seq_width)) ?
		1 : fid_oid(fid) + 1;

Nothing has rolled over at that point.  osp_precreate_thread() only
starts a new sequence once the precreate window is empty, and
osp_precreate_rollover_new_seq() then starts it with oid 1 already
used, so 1 is neither the next object of the current sequence nor the
next object of the one which follows it.  prealloc_next_seq keeps
naming the current sequence and prealloc_last_id has no such special
case, so the three files describe an object which was consumed long
ago.

The window is also left behind the end of the sequence with no
rollover in sight whenever seq.*.width is lowered below the id already
in use: the OST returns its current width in every precreate reply
(ofd_create_hdl()), the OSP keeps it in opd_pre_seq_width, and it then
precreates nothing more until the objects it already has are consumed.
The test framework lowers the width at every OST mount.  Shrinking it
by hand under an idle OSP shows how long the wrong value survives:

  before shrink: next_id=502 last_id=545 next_seq=last_seq=0x2c0000401
  # lctl set_param -n seq.cli-lustre-OST0000-super.width=200
  settled:       next_id=1   last_id=577 next_seq=last_seq=0x2c0000401

where the window really is 536-577.

Every consumer of the file turns the pair into a count, so all of them
are then wrong by the length of the sequence:

	createmany -o $dir/f $next_id $((last_id - next_id + extra))

that is consume_precreations() and precreated_ost_obj_count() in
test-framework.sh - and through them exhaust_precreations() and
force_new_seq(), which the replay suites run at setup - along with
sanity test_27y and test_220, and replay-single test_67b and test_88.

Report opd_pre_used_fid + 1 unconditionally, and take the id out of
the fid with osp_fid_to_obdid(), which prealloc_last_id_show() is
switched to here as well so that the two cannot drift apart again.
Add conf-sanity test_122c: within one sequence the id the OSP will
hand out next only moves forward, so lowering the OST's width under a
live window must not send it back to 1.

This is not the LU-20527 LBUG, but it is filed under it because the
window check in conf-sanity test_122d, which the next patch adds,
reads this value: without this fix that check misreads a healthy
32-object window as 33554208 objects and fails.
