LU-20972 utils: bound the memory used by parallel find

Parallel find queues a work unit for every subdirectory it finds, with
a deep copy of the find_param, and does not limit the number of queued
units. The copy is about 75 KB per subdirectory: it is OOM-killed on a
1.4 GB VM for a directory with 20000 subdirectories, while the serial
traversal needs 3 MB.

These buffers are refilled for every object, so do not copy them
into the work units. Each worker thread owns one set, sized as
common_param_init() and xattr_match_info_append() size them, and
lends it to the work unit it processes, as the serial traversal
uses a single set. This also fixes a 1-byte heap overflow: the copy
of xattr_value_buf had XATTR_SIZE_MAX bytes instead of
XATTR_SIZE_MAX + 1, and find_check_xattrs() writes a '0' after a
value that is not NUL-terminated.

Also bound the work queue: when FIND_QUEUE_MAX_UNITS work units are
queued or being processed, a thread traverses the subdirectory it
finds inline, as the serial code does, instead of queuing it. Making
the producers wait for room could deadlock, as the producers are the
worker threads themselves.

A thread that traverses a subdirectory inline keeps open the directory
it was reading, so its open files grow with the depth it walks inline,
where a worker used to hold about two. To stay within the soft limit
of open files, parallel_find() derives from it how many levels each
thread may walk inline. A thread at that depth queues the
subdirectory, even if the queue is full.

With these changes, "lfs find" on the 20000 subdirectories peaks at
7.5 MB, and on a tree of 50000 directories at 7 MB.

Add sanity test 56Em to exercise this.
