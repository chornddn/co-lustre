LU-18298 utils: do not write open a file to detach it from PCC

lfs pcc detach opens the file O_RDWR only to issue LL_IOC_PCC_DETACH on
the resulting descriptor. When llite asks for an open lock with that
open, which its opencache heuristics do once a file has been opened a
few times or is reopened shortly after a close, the MDT takes a CW lock
on MDS_INODELOCK_LOOKUP|OPEN. That conflicts on the LOOKUP bit with the
client's own cached PR lock, and that lock usually also carries
MDS_INODELOCK_LAYOUT. Cancelling it runs vvp_conf_set(), which sets
CL_LAYOUT_GEN_NONE and detaches the PCC inode. Without the open lock
only trybits are asked for, no blocking AST is sent and nothing is
cancelled, which is why the failure comes and goes.

The ioctl then finds no attached PCC inode, takes the
"!pcci || !pcc_inode_has_layout(pcci)" path in pcc_ioctl_detach() and
returns success with hsm_remove still false, so the HSM archive of a
PCC-RW file is never removed. sanity-pcc test_1c, test_1d and test_13a
then fail their following wait_request_state with "request on <fid> is
not SUCCEED on mds1".

Do not open the file for I/O at all instead. An O_PATH descriptor does
not call the file open method, so it takes no lock and cannot attach
anything, and llapi_pcc_detach_fid() only opens the mount root and
detaches by FID, which is what that ioctl exists for. Opening read-only
would avoid the
CW lock as well, but an O_RDONLY open is exactly what
pcc_try_readonly_open_attach() acts on, so detaching a file that was not
cached could attach it first, and for a file above the async threshold
the attach then outlives the detach.

The by-FID ioctl only detaches an inode that is still in the client
cache, so keep the O_PATH descriptor open until it returns, and take the
FID from that same descriptor rather than resolving the path a second
time. Dropping it first would leave a window in which the inode can be
evicted and the ioctl would again return success having detached
nothing; resolving twice would let a rename in between leave us holding
one inode and detaching another. Resolve the path first as well, since
llapi_search_mounts() matches it against the mount table.

LL_IOC_PCC_DETACH_BY_FID applies the same pcc_inode_permission() check
as LL_IOC_PCC_DETACH, which tests the file mode against pccs_mode and
inode_owner_or_capable() and never the mode a descriptor was opened
with, so the permission semantics that sanity-pcc test_1g checks are
unchanged. Neither path needs the encryption key, so the O_CIPHERTEXT
open this replaces is no longer needed either.

This does not close the window completely: any other write open of the
file can still cancel the layout while the detach is in flight, and
pcc_ioctl_detach() returning success without removing the archive in
that case is a separate defect. It does remove the one trigger the
detach inflicts on itself, which is the one these tests hit.
