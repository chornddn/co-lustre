LU-21278 mgc: retry config log enqueue on ENOTCONN

After the MGS restarted, a client MGC import could still report FULL
while holding a stale connection handle: nothing sent an MGC RPC in
between, and the MGC ping is suppressed while imperative recovery is
in use.  The next MGC RPC was then the config log ldlm_enqueue of a
new mount.  The MGS did not know the handle and replied -ENOTCONN, so
after_reply() called ptlrpc_request_handle_notconn(), which
invalidated the import and bumped its generation, and
ptlrpc_abort_inflight() flagged the enqueue rq_err, so
ptlrpc_check_set() completed it with the -ENOTCONN of its own reply.
Only an enqueue submitted after the import had become invalid gets
the -ESHUTDOWN of ptlrpc_import_delay_req().

mgc_process_log() retried the enqueue only for -ESHUTDOWN, so the
-ENOTCONN fell through to the local copy of the config log.  A client
has none, so mgc_process_cfg_log() returned the -ENOTCONN, which
lustre_process_log() passed back to ll_fill_super(), and the mount
failed with it:

  LustreError: MGC<mgs>@tcp: operation ldlm_enqueue to node
      <mgs>@tcp failed: rc = -107
  Lustre: Evicted from MGS (at <mgs>@tcp) after server handle changed

Retry the enqueue for -ENOTCONN as well, so that the MGC forces the
pinger, waits for the import to leave recovery and re-enqueues the
log on the new connection.  As for -ESHUTDOWN it retries only once.
The one new cost is when the MGS replies but has no usable export
for us for another reason, such as while it is unmounting: the mount
now waits up to obd_timeout before failing with the same error,
instead of failing immediately.

sanity test_160j mounts a second mount point after 160a and 160h
restart the MDS of a combined MGS/MDT0000, which leaves exactly this
stale handle: 7 failures in 15 runs on aarch64 clients, while x86_64
passed.
