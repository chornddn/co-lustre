LU-20730 llapi: read and write LFU Object Stream chunks

A scan passes its caller one object per callback, as a struct that
holds pointers and file descriptors. Such a record cannot be saved to
a file or sent to another process, and a caller that wants many
objects at once has to collect them itself.

The LFU Object Stream is a format for many objects at once: a buffer
of fixed-size slots, each holding one chunk, which is a Cap'n Proto
LfuChunk message with a list of LfuInode records and their EA values.
Timothy Day defined it in lfu.capnp.

Add lfu.capnp to include/uapi/linux/lustre, installed with the other
headers, and lustre_lfu_capnp.h with its enum values and the offsets
of the fields, so that C code needs no Cap'n Proto compiler. LfuInode
carries the object's inode number on the target and the nanoseconds
of its four timestamps, besides the seconds, and LfuEa carries the
encryption context, which says whether a directory's names are
encrypted.

Add liblustreapi_lfu.c, which writes and reads the chunks that the
Lustre scanners produce. The writer builds a chunk in place, records
from the front of the slot and EA values from the back, so nothing is
copied twice. It stays internal (lustreapi_lfu.h) until a scanner uses
it. The reader is public: llapi_scan_chunk_parse(),
llapi_scan_chunk_inode() and llapi_scan_chunk_skipped(). It checks
every pointer against the slot and refuses what it cannot follow, and
a record written by an older schema reads as zero past its end.
struct llapi_scan_inode keeps spare room, so a field added to the
schema later does not change its size.

llapi_lfu_test, run by sanity 56En, reads a chunk that libcapnp wrote
and one whose LfuInode records are 12 data words, as an older writer
would produce, writes and reads back records over 16 slots, and checks
a record too large for its slot, a chunk of skipped objects only, bad
input, and every one-bit corruption of a slot.
