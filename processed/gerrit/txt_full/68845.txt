LU-20327 tests: list only own files in recovery-small 155

test_155 compares "ls -l $DIR" from before a client remount
against the same listing after it, so every file any earlier
test left in $DIR has to survive the comparison. The remount
drops the attributes the client had cached, and a file the
servers never agreed with then changes across it.

test_131 leaves exactly such a file. The eviction the test
arranges discards its buffered write, so the OST object ends
up empty while the client keeps the size and the block count
the write recorded. Nothing later clears them: the ls does
glimpse the object -- the MDT returns no size for a striped
file -- but the eviction races with the cancel that would
roll the size back, and the 0 the OST answers is clamped
back up to what the client has. Repeating 131 then 155 on
ZFS, 14 of 20 runs disagreed across the remount, 10 of them
in the block count and 4 in the size. The remount is the
first thing that drops them, and the flush added by
commit 2b762bdd15d8 ("LU-14708 tests: improve recovery-small test_155")
does not help. Those stale attributes are a client bug in
their own right and are left to their own patch. This is
every Janitor failure sampled, all of them on ZFS.

List only the directory this test creates, placed with
mkdir_on_mdt0 on the MDT that fails over, and have test_131
remove the file it can no longer describe.

The MDT commit is the other half. The client that creates
$tfile unmounts before the failover, so it cannot replay the
create, which therefore has to reach disk before the replay
barrier drops writes. Removing the commit step loses the
file on every run, which is the second failure recorded on
this ticket. Commit with osd*.*MDT*.force_sync the way the
replay suites do, rather than by syncing the server host,
which does not reach an osd-zfs target at all.
