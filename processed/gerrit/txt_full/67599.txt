LU-20531 mdc: fix cross-MDT close blocking-AST thread deadlock

Problem
=======
On a DNE (multi-MDT) filesystem, a cascading deadlock can drain an
MDS's ldlm_bl (LDLM blocking/cancel) thread pool and stall lock
cancellation fleet-wide, requiring a full MDS reboot to clear.

The trigger is entirely local to one MDS.  An ldlm_bl thread performs
a routine LRU cancellation of a cross-MDT LDLM lock that happens to
cover an open file.  Cancelling that lock drives the inode's final
release (ll_md_blocking_ast -> ll_lock_cancel_bits -> iput -> evict ->
ll_md_real_close), and releasing an open inode issues a synchronous
MDS_CLOSE RPC to the remote MDT that owns the inode.

If the MDC import to that remote MDT is not LUSTRE_IMP_FULL (the peer
is failing over / in recovery), the close cannot be transmitted.  It
parks in ptlrpc_import_delay_req() while holding the single "close"
modify-RPC slot (cl_close_rpcs_in_flight == 1).  Every other ldlm_bl
thread that subsequently reaches mdc_close() then blocks in
obd_get_mod_rpc_slot(), because a close is only granted a slot when no
other close is in flight.  Those waits are TASK_UNINTERRUPTIBLE with
MAX_SCHEDULE_TIMEOUT and are woken only on RPC completion via
cl_mod_rpcs_waitq -- there is no wakeup on import state change.

With the whole pool parked, the MDS can no longer answer any lock
cancellation, including the blocking ASTs its own server needs, so it
evicts its internal client and customers while peers evict it.  The
close needs the import FULL; the import needs the bl threads; the bl
threads are all parked on the close slot.  The cycle cannot self-heal.

This is proven from production logs (fs-0b0daf7d49224771a, 16-MDT DNE,
Lustre 2.15): 10 ldlm_bl threads on the victim MDT blocked >122s in
obd_get_mod_rpc_slot via mdc_close, the stuck lock holding bits 0x5
(LOOKUP|OPEN), and the MDC import to the recovering peer never
reaching FULL (the OSP import restored, the MDC did not).  Replayed
cross-MDT LDLM_ENQUEUEs to the peer aborted with status 301
(ELDLM_LOCK_ABORTED), so the peer's recovery never completed and the
MDC was ultimately evicted and marked IMPF_INVALID.

Fix
===
Two complementary changes are required.  The first lets a close that
*can* complete proceed during the peer's recovery; the second makes a
close that *cannot* complete fail fast instead of hanging forever.

1) mdc_close(): allow the cross-MDT close during the target's recovery
   (lustre/mdc/mdc_request.c)

   When the MDS-internal client (OBD_CONNECT_MDS_MDS) closes a file on
   a remote MDT while the local top device is recovering
   (OBDF_RECOVERING on ld_site->ls_top_dev), set req->rq_allow_replay.
   ptlrpc_import_delay_req() then transmits the close during the
   import's REPLAY/REPLAY_LOCKS/REPLAY_WAIT/RECOVER sub-states instead
   of parking it.  rq_allow_replay does not set MSG_REPLAY on the wire,
   so this remains an ordinary MDS_CLOSE; the server already accepts
   MDS_CLOSE during recovery via tgt_filter_recovery_request() ->
   target_queue_recovery_request().  This mirrors the existing OSP
   cross-MDT CANCEL handling (ldlm_cli_cancel_req) and the SEQ/FLD
   during-recovery idioms.  It is scoped to OBD_CONNECT_MDS_MDS +
   OBDF_RECOVERING, so a customer-client close is never affected.

   This covers the pre-eviction window only: while the import is still
   in a recovery sub-state, the close is allowed out and completes,
   releasing the close slot.

2) Abort the mod-RPC-slot wait on an invalid import
   (lustre/obdclass/genops.c, lustre/ptlrpc/client.c,
    lustre/ptlrpc/import.c, lustre/include/lustre_net.h,
    lustre/mdc/mdc_request.c)

   rq_allow_replay is not sufficient by itself.  Once the peer's
   recovery aborts and the MDC import is evicted and marked
   IMPF_INVALID, the close no longer parks in a recovery sub-state --
   it hits -ESHUTDOWN in ptlrpc_import_delay_req() -- but any threads
   already sleeping in obd_get_mod_rpc_slot() for the close slot are
   never woken, because the slot is only released on RPC completion
   and the RPC will never complete.  The slot wait needs to become
   import-state aware:

   - genops.c: add a bool "aborted" to struct mod_waiter.  In the
     custom wake function claim_mod_rpc_function(), before evaluating
     slot availability, check the import: if cli->cl_import is NULL or
     IMPF_INVALID is set, mark the waiter aborted, wake it, and return.
     The abort must live inside claim_mod_rpc_function() rather than at
     a plain wake_up site: for a close waiter, the custom wake function
     deliberately refuses to wake the thread while another close is in
     flight, so an ordinary wakeup would not rouse the stuck thread.
     obd_get_mod_rpc_slot() detects wait.aborted after
     __remove_wait_queue(), drops the lock, and returns tag 0 (the
     existing "no slot acquired" sentinel) without allocating a bitmap
     tag.  The LU-18826 kthread/PF_MEMALLOC force-grant branch and the
     LU-15947 wakeup precision are left unchanged.

   - client.c / lustre_net.h: ptlrpc_get_mod_rpc_slot() now returns int
     instead of void.  A returned tag of 0 is translated to -ENOTCONN;
     the success path sets the tag, reassigns the xid, and returns 0.
     The other callers (ldlm_request, mdc_reint, mdc_request open/
     intent paths, osp_trans, ptlrpc batch) ignore the return value,
     which is source-compatible.

   - mdc_request.c: mdc_close() checks the return of
     ptlrpc_get_mod_rpc_slot() and, on error, GOTO(out, rc) before
     ptlrpc_queue_wait().  Because the abort path never claimed a slot
     and the close bails before ptlrpc_put_mod_rpc_slot(), the
     cl_close_rpcs_in_flight accounting stays balanced.

   - import.c: ptlrpc_deactivate_import_nolock() -- the single point
     that sets IMPF_INVALID -- calls
     wake_up_all(&imp->imp_obd->u.cli.cl_mod_rpcs_waitq) immediately
     after ptlrpc_abort_inflight().  This is the event that drives the
     parked waiters to re-run claim_mod_rpc_function(), observe
     IMPF_INVALID, and abort.  Both invalidation entry points
     (ptlrpc_deactivate_import and ptlrpc_invalidate_import) funnel
     through the nolock form, so both are covered.

Together the parked close is woken, returns -ENOTCONN, releases the
close slot, and the next waiter is woken to the same fast-fail; the bl
pool drains and lock cancellation resumes without a reboot.
