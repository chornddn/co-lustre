LU-20531 llite: don't park lock cancel on a close to a down MDT

Lock cancellation callbacks run on ldlm_bl threads, a pool shared by
every namespace on the node.  ll_lock_cancel_bits() can send a
synchronous MDS_CLOSE from there in two ways:

- directly, when an OPEN lock is cancelled (ll_md_real_close());
- through eviction: ll_prune_aliases() -> d_prune_aliases() drops the
  pruned dentry's reference on its parent, and that dput() kills every
  ancestor left unused and invalid.  Evicting one closes its cached open
  handle from ll_clear_inode().  This is the stack in the report.

If the MDT holding that handle is down, ptlrpc_import_delay_req() parks
the close until the MDT returns, and the ldlm_bl thread with it.  The
eviction route is cross-MDT: cancelling a lock from a healthy MDT can
evict a directory whose open handle is on the down one, so cancellation
for the healthy MDT stops.  The direct route ties up one ldlm_bl thread
per cancelled OPEN lock for the length of the outage, until the pool,
shared by every namespace on the node, runs out.

Send these closes from a per-superblock workqueue instead:

- OPEN-lock cancel: the close always runs in the workqueue and the
  cancelling thread waits for it, so it still reaches the MDT before
  what the cancel lets through (an ELC'd conflicting open, the cancel
  reply).  A kernel thread stops waiting once the import is not FULL; a
  user thread or nfsd (ELC) waits as before.  If the MDT is reachable
  but the queue has not started the close, the waiter sends it itself,
  so closes parked on a down MDT cannot hold up closes to healthy ones.
- eviction: ll_prune_aliases() pins the aliases' parent dentries, and
  ll_prune_negative_children() the directory's own alias, and drops
  the pins from the workqueue when that can kill them, so the whole
  cascade runs there.  The cancel's own final iput, and two other
  iputs on the cancel path, go through ll_iput_later(), which defers
  the iput when the inode has a cached open handle.

The closes are still sent, so no open handle or setattr is lost.  The
queue is flushed in ll_kill_super(), before the dcache is shrunk, and
in ll_put_super(), before the MDC export is torn down.

Measured on a 2-MDT filesystem with MDT0001 stopped:
- test_172 (lru_size=1 on MDT0001): unpatched, an ldlm_bl thread waits
  in mdc_close() for MDT0001; patched, the closes wait in the workqueue
  and no ldlm_bl thread does.
- test_173 (lru_size=clear on MDT0000 evicts a directory whose open
  handle is on MDT0001): unpatched, the cancel never completes and
  ldlm_bl parks in ll_clear_inode() -> mdc_close(); patched, it
  completes and the close waits in the workqueue.
On a healthy filesystem the RPC order for exec-then-truncate of the
same file is unchanged.

You're right on both counts, and I'm abandoning the "skip the close" approach.
Below is what I found when I went looking for a replacement, including the
checks I ran to convince myself the alternatives actually work before putting
them in front of you.

== Conceding the current patch ==

The atime point is correct, and it's broader than atime. mdc_close_pack()
(mdc_lib.c:663) packs a full mdt_rec_setattr via mdc_setattr_pack_rec() -
sa_atime/mtime/ctime, sa_size, sa_blocks, sa_uid/gid/projid, sa_attr_flags -
plus the ioepoch and the close intents (HSM release, layout swap,
resync-done), and the LSOM lazysize/lazyblocks update. Dropping the RPC
discards all of it silently. That atime rides on close clearly isn't
incidental either, given the LU-8041 workaround sitting in that same
function.

There is also a defect I should own that's worse than the atime loss. The
early return in PS13 lands *after* the mod fixup block, which has already
done mod->mod_open_req->rq_replay = 0 (mdc_request.c:968). So the patch
suppresses replay of the open and then skips the close. The commit message's
claim that "the server will clean up open state on reconnect (replay)" is
false - this path is precisely what disabled that replay. The handle leaks
until eviction or unmount, and mod_close_req is left holding an extra
reference on a request that was never sent (mdc_request.c:1015). Not
salvageable.

== Corrected root cause ==

I also had the mechanism described imprecisely - it isn't primarily ldlm_bl
pool exhaustion, it's a single-thread circular wait:

  1. ldlm_replay_locks() raises imp_replay_inflight to 1 and spawns the
     "ldlm_lock_replay" kthread (ldlm_request.c:2988-2994).
  2. That kthread runs __ldlm_replay_locks() ->
     ldlm_cancel_unused_locks_for_replay() (ldlm_request.c:2933) ->
     ldlm_cancel_lru_local().
  3. ldlm_cancel_callback() invokes the blocking AST *synchronously in that
     kthread* (ldlm_lock.c:2464-2468).
  4. For an ibit lock holding MDS_INODELOCK_OPEN: ll_md_blocking_ast() ->
     ll_lock_cancel_bits() (llite/namei.c:264-288) -> ll_md_real_close() ->
     mdc_close().
  5. mdc_close() -> ptlrpc_queue_wait(), and ptlrpc_import_delay_req()
     defers it: rq_send_state is FULL, imp_state is REPLAY_LOCKS, so it
     takes the delay = 1 branch (ptlrpc/client.c:1416-1433).
  6. imp_replay_inflight therefore never drops to 0, so
     ptlrpc_import_recovery_state_machine() can never advance
     REPLAY_LOCKS -> REPLAY_WAIT (import.c:1712-1714) and on to FULL.
     But the deferred close is only released once the import is FULL.

The ldlm_bl pile-up we measured is secondary: other threads touching the same
lock land in the uninterruptible wait_event_idle(lock->l_waitq,
is_bl_done(lock)) at ldlm_lock.c:2476-2480, and further closes serialize
behind the one above-max close slot (cl_close_rpcs_in_flight == 0,
genops.c:2330-2331).

== On the extra reply_data slot ==

I don't think more slots resolves this one, and I'd like to check that
reasoning with you. The blocking wait isn't slot acquisition - it's the
import-state gate in ptlrpc_import_delay_req() above. Granting more slots
just moves threads from the queue in obd_get_mod_rpc_slot() into
ptlrpc_queue_wait(); the ldlm_lock_replay kthread is still parked and
imp_replay_inflight still never reaches 0. So it changes the shape but not
the outcome.

== Option A (preferred): send the close during recovery ==

Set rq_allow_replay on the MDS_CLOSE once the import has passed
LUSTRE_IMP_REPLAY, so ptlrpc_import_delay_req() lets it through during
REPLAY_LOCKS/REPLAY_WAIT/RECOVER instead of deferring it:

	if (imp->imp_state >= LUSTRE_IMP_REPLAY_LOCKS &&
	    imp->imp_state < LUSTRE_IMP_FULL)
		req->rq_allow_replay = 1;

atime and every other attribute survive, the slot turns over, the replay
kthread makes progress, and nothing changes on the server - no extra
reply_data slot needed.

Four things had to hold for this to work, so I checked each against master
rather than assuming:

  1. rq_allow_replay lifts exactly the gate that is deferring us -
     client.c:1425-1430 covers REPLAY, REPLAY_LOCKS, REPLAY_WAIT, RECOVER.
  2. The MDT will actually *process* the close rather than queue it while
     it is itself recovering. This was the one that could have killed the
     idea. tgt_filter_recovery_request() routes MDS_CLOSE to
     target_queue_recovery_request() (tgt_handler.c:509-531), which returns
     1 - "continue request processing" - when transno == 0
     (ldlm_lib.c:3237-3241). A fresh close has transno 0: the client only
     stamps transno into rq_reqmsg in after_reply(), for the benefit of a
     later replay (client.c:1727-1730). So it is handled immediately, not
     parked on obd_req_replay_queue.
  3. The server has the open handle back by then. import.c:1700-1705 only
     transitions REPLAY -> REPLAY_LOCKS when inflight == 0 &&
     imp_replay_inflight == 0, i.e. every request replay has completed and
     been replied to. Hence gating on >= REPLAY_LOCKS rather than just
     "not FULL" - during REPLAY the handle may not exist yet.
  4. If ordering ever did slip, mdc_close() already maps -ESTALE on a
     committed open to success (mdc_request.c:996-1007).

Precedent for the same deadlock class: ldlm_cli_cancel_req() already sets
rq_allow_replay = 1 so a cross-MDT cancel isn't blocked in recovery
(ldlm_request.c:1565-1580). That is also the code whose OBD_CONNECT_MDS_MDS
gate I copied in PS2 - which is what your "just a regular lustre client"
comment was getting at. I understand that now. And close is already
special-cased twice for deadlock avoidance: the MDS_READPAGE_PORTAL redirect
(bug 7034, mdc_request.c:934-938) and the one-above-max close slot
(Bugzilla 3462, genops.c:2302-2303).

== Option C: don't cancel OPEN-bit locks before replay ==

Skip locks with MDS_INODELOCK_OPEN in ldlm_cancel_unused_locks_for_replay()
so they are replayed instead of canceled, keeping close out of the recovery
path entirely. Costs more locks to replay.

What convinced me this is sound rather than speculative: "replay instead of
cancel" is already a shipped, supported path. The whole cancel pass is
behind ldlm_cancel_unused_locks_before_replay (ldlm_request.c:2933), a
writable sysfs attribute defaulting to 1 (LUSTRE_RW_ATTR,
ldlm_lockd.c:3225). Setting it to 0 skips the pass wholesale. Option C is
just doing that selectively for the one lock class whose cancel has an RPC
side effect.

That tunable is also useful independently of the fix: it should be an
immediate client-side workaround for affected sites, and it's a zero-build
way to confirm the diagnosis on an unpatched client. I'll run that
experiment either way.

== Option B: get the RPC out of the AST context (direction, not a proposal) ==

Stop calling ll_md_real_close() inline from the AST and queue it instead, so
no RPC is ever issued from AST context. Structurally the nicest of the three
and it would help beyond this bug, but it's a larger llite change - och and
inode references have to be held across the handoff, and the lock ends up
canceled before the close is sent. I have not convinced myself of the
lifetime rules yet, so I'm flagging it as a direction rather than putting a
patch behind it.

== Question ==

My preference is A now, with B as a follow-on cleanup if you think the AST
context should be RPC-free on principle. Do you have a preference, or an
objection to A's assumption that a transno-0 close is safe to let the MDT
process mid-recovery? I'd rather respin once against whichever you'd
actually take.

Independent of the choice, the reproducer stands: on an unpatched client
recovery-small test_171 leaves the MDT0001 import wedged at REPLAY_LOCKS
(3/3 runs), and it reached FULL (3/3) with the PS13 code. I'll re-verify it
against whichever fix we settle on. It's also posted standalone as change
68014 (not for merge) so the failure is reproducible without any fix
applied.

Patch Set 15:

Patchset 15 replaces the approach. Instead of skipping the close, it lets it
through: one line in mdc_close(), req->rq_allow_replay = 1.

Briefly, the close is parked by the very recovery it is blocking. mdc_close()
holds the reserved close modify-RPC slot across ptlrpc_queue_wait(), and the
import cannot leave recovery until that same thread returns. Full detail is in
the commit message and the ticket.

Measured with a matched A/B on real hardware, same harness, this one line as
the only variable:

                                   unpatched      patched
  o35 "req waiting for recovery"       1             0
  o35 "allow during recovery"          0            26
  ldlm_bl parked (state S)           727 samples    0 of 730
  imp_replay_inflight              stuck at 10    drained to 0
  recovery outcome                  COMPLETE      COMPLETE

Also built and smoke-tested on 2.15.8 (kernel 5.10) against a live 3-MDT DNE
filesystem: all MDCs and OSCs reach FULL, normal I/O timings.

This is option A. The in-tree precedent is ldlm_cli_cancel_req(), which
already sets rq_allow_replay for a cross-MDT LDLM_CANCEL to avoid an analogous
deadlock; it is gated on OBD_CONNECT_MDS_MDS, so it never covers a close
issued through llite.

Option C looks like a no-op to me: mdc_cancel_weight() already returns 0 for
any lock holding MDS_INODELOCK_OPEN, and the replay pass is the no-wait policy
that consults it. The close in the reported stack also came from a LOOKUP/PERM
cancel rather than an OPEN cancel, so protecting OPEN-bit locks would not have
prevented it. Happy to be shown wrong.

test_171 is a regression guard, not a reproducer: it passes with and without
the fix, and checks that admitting the close does not lose the close or the
attribute update it carries - recovery COMPLETE, zero evictions, and every
seeded file still at its original size with a matching checksum. The size
matters because mdc_close() carries an mdt_rec_setattr, so a lost close shows
up as a short file. There is no reproducer because the condition is not
observable through any stable interface: mdc.*.import has no delayed-request
counter, which leaves only the CDEBUG text from ptlrpc_import_delay_req(), and
those two strings are the two branches of the very "if" that rq_allow_replay
controls.

What this does not establish: the original field condition is not reproduced.
Every lab variant either self-heals once the target returns or requires the
target never to return, and the import state was never captured in the field,
so identifying it as REPLAY_LOCKS is inference from the timeline.

I am abandoning 68014. Its test number 171 is reused here, without the LU
number in the description, per your comment there.

The flag is set unconditionally, so a close can now go out during
LUSTRE_IMP_REPLAY, where the server may not have reconstructed the open handle
yet. I believe that is safe: target_queue_recovery_request() processes rather
than queues a request with no transno, which a fresh close has, and
mdc_close() already maps -ESTALE on a committed open to success. The alternate
would be to set the flag only for closes issued from the cancel path, plumbed
through md_op_data.

A narrower fix that keeps the close off the lock replay thread (defer the iput()/close, or skip locks whose cancel would evict an inode with a cached open handle) may avoid both. test_171 doesn't exercise either case. A test that keeps a file open across failover and closes it while replay is paused would show whether the close leaks the server open handle.

This patchset replaces the approach. mdc_close() is untouched; the fix is
in llite, and rq_allow_replay is gone - the review of patchset 16 was right
on both counts (a fresh close during REPLAY can find no handle, and its
transno can collide with another client's replay).

What the bl thread was actually doing. The reported stack is an ordinary
ldlm_bl LRU cancel, not the replay thread (ldlm_cancel_unused_locks_for_replay()
uses the no-wait policy, and mdc_cancel_weight() refuses OPEN locks, so replay
never closes a handle). It reaches mdc_close() through eviction:

  ll_lock_cancel_bits -> ll_prune_aliases -> d_prune_aliases -> dput(parent)
  -> evict -> ll_clear_inode -> ll_md_real_close -> mdc_close

The evicted inode is not the lock's inode - that one is held by
ll_inode_from_resource_lock(). It is the parent directory, whose last dentry
reference is the one d_prune_aliases() drops. If that directory has a cached
open handle on an MDT that is down, the bl thread parks. With DNE this is
cross-MDT: cancelling a lock from a healthy MDT parks on the down one.

Reproduced on mainline, 2 MDTs, MDT0001 stopped: D on MDT0001 with a cached
open handle, E on MDT0000 inside D, lru_size=clear on MDT0000's namespace.
Unpatched, ldlm_bl parks with exactly the reported stack and the cancel never
completes. This needs the parent to be evicted on its last iput; in the lab I
force that with llite.*.inode_cache=0.

The patch:
- eviction: ll_prune_aliases() pins the aliases' parent dentries and drops
  the pins from a per-sb workqueue when that can kill them, so the whole
  dput cascade (and any close) runs there. The cancel's own final iput goes
  through ll_iput_later(), which defers only when the inode has a cached och.
- OPEN-lock cancel: the close always runs in the workqueue, and the
  cancelling thread waits for it, so it still precedes what the cancel lets
  through (an ELC'd conflicting open, the cancel reply). A kernel thread stops
  waiting when the import leaves FULL; a user thread waits as before. If the
  MDT is reachable but the queue has not started the close, the waiter sends
  it itself.
- the queue is flushed in ll_kill_super() and ll_put_super().

An earlier version deferred only when the import was not FULL at dispatch.
That was flaky: a close dispatched while the import still looked FULL, just
after the MDT died, parked the bl thread.
