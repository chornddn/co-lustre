LU-17000 llite: pin fa_nr against a double fetch in ll_rmfid()

ll_rmfid() reads the caller's fa_nr with get_user() and sizes both the
lfa FID array and the rcs[] status array from that value, then
copy_from_user()s the header again.  lfa->fa_nr is therefore a second,
independent read of the same user field, and nothing downstream
revalidates it against the size the buffers were allocated for.

mdc_rmfid() sizes the RMF_FID_ARRAY and RMF_RCS request buffers from
fa->fa_nr and memcpy()s fa->fa_fids into the RPC; mdc_rmfid_interpret()
memcpy()s fa_nr ints from the reply back into rcs[]; lmv_rmfid() walks
fa->fa_fids[] to the same count and sizes its per-target arrays from it.
The second fetch never goes back through the nr > OBD_MAX_FIDS_IN_ARRAY
test, so lfa->fa_nr is an arbitrary __u32, not a value capped at 4096.
A caller that raises it between the two fetches makes the client copy
FIDs out of a much smaller allocation into an outgoing RPC and write
that many ints past the end of rcs[]: a heap overread onto the wire and
a heap overflow.  mdc_rmfid() computes flen as an int, so a large enough
value also truncates or goes negative before it reaches
req_capsule_set_size() and memcpy().

Pin lfa->fa_nr to the value every buffer was sized from.
