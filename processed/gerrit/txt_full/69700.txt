LU-20606 llapi: limit a scan's rate

Add lfsp_max_rate to struct llapi_scan_param: the most objects a scan
examines per second, all of its threads together. 0 is no limit. Both
llapi_scan_namespace() and llapi_scan_device() honour it, so a scan
can be kept from loading the filesystem or the device it reads.

The field is carved out of lfsp_padding, which was reserved for this.
The struct does not grow, so the fields that other changes append
after lfsp_stats are not affected. A library older than this refuses
a non-zero value with -EINVAL, as it refuses any set reserved byte,
rather than ignoring the limit.

Objects are paced one interval apart: each takes the next slot under a
lock and sleeps until it. A scan that falls behind does not catch up
in a burst; a lag of up to 1 ms is kept, since a sleeper wakes a
little late and without it 100k objects/s ran at 32k. With no limit
set, nothing is taken and nothing waits. The
stop is checked before the wait, so an entry reached after a
stop takes no slot, and again after it, so a thread that slept past
a stop does not deliver once it wakes. A sleeper is not woken by a
stop, so a stopped scan can take up to lfsp_thread_count intervals
to return; llapi_scan_namespace.3 says so.

A namespace walk counts an object when it reads its directory entry. A
device scan counts it when it reads the inode or dnode, before
lfsp_filter, because that read happens either way. An object it skips
there, as torn or unreadable, takes a slot too.

lfs find does not set it yet. An option for lfs find --device follows.

llapi_scan_test test19 and llapi_scan_device_test test7 check that a
paced scan takes at least the paced time and still delivers every
object; test19 also stops a paced scan with four threads and checks
that the consumer is not called again, and that the scan returns
without a slot for each entry it did not reach. test6 sets
lfsp_padding[2], the array now being three bytes.
