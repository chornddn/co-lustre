LU-19566 lfsck: rebuild parity that no object shows

When LFSCK rebuilt an EC file from its OST objects and none of the
objects of the mirror that the data links to showed parity, as when
they keep the PFID in LMA, it left that mirror a plain mirror and
marked it stale. After a resync the file lost its EC protection.

The parity component holds the EC geometry. LOD copies it, with the
link to the parity mirror, into the data component it protects, and
the objects of each component keep their component's copy in
filter_fid, so the data objects still give the geometry when no
parity object shows it.

Make such a mirror parity, with the parity pattern, the EC geometry
from the copy in the data and the link to the data, and stale until a
resync writes the parity, if its layout is that of the parity of the
data that links to it. Each component must have the extent and stripe
size of the data, and a stripe count of the code stripe count times
the number of raid sets of the data, which the new
ec_parity_stripe_count() gives as LOD allocates it. Its objects must
not have EC fields of their own, which would show it was written as
data protected by other parity. All the data must be in one mirror
that links only to this mirror, is in sync, and has the component of
this mirror for each of its components that links to it, since a
component found later takes parity from the others. If the mirror is
a plain copy of 2+2 or 3+3 data, it has the same layout, and parity
protects the data better than a copy once resynced. If every raid set
is 1+1, parity is a copy of the data and adds nothing, so the mirror
is left plain.

A component that joins a parity mirror takes parity whatever its
layout. If that does not fit the data it protects, make the mirror
plain and stale again, as it cannot be used as parity.

sanity-lfsck test_53b rebuilds 2+1, 2+2 and PFL EC files none of
whose parity objects has the EC fields, test_53c one whose data's
copy of the geometry names more code stripes than the parity mirror
has, and test_53d a 1+1 EC file. test_53 becomes test_53a.
