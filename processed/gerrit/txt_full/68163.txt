LU-20613 llapi: ZFS backend for llapi_scan_device

scan_zfs.so reads a Lustre-on-ZFS MDT or OST dataset through libzpool,
the way zdb reads it, and emits the same objects to the same sink as
the ldiskfs backend.  A second backend is the test that the backend
ABI generalises past the one it was written for.

A device string naming a block device or an existing file is
ldiskfs's; anything else is a pool/dataset name.  The pool is located
by reading vdev labels, under /dev or under sp_search, a new member of
the versioned scan param, since a pool on file vdevs is invisible to a
/dev scan.  An imported pool is refused with EBUSY rather than read
behind the kernel's back.  A string with no pool name in it -- a
mistyped device path, which the routing above sends here -- is refused
with ENOENT, rather than probing the kstat directory for a pool called
"" and answering that it is in use.

llapi_find_device() takes that search path as a fourth parameter, an
incompatible change to an exported prototype with no released version
behind it, and lfind grows --search to pass it.  Its man page gains
the argument here rather than where the page was added, so the two
never disagree at any point in the series.

Only ESRCH ends the dnode walk.  dnode_next_offset() passes up
dbuf_read()'s errors, so treating any non-zero return as the end told
every other worker the target was finished and returned success: a
truncated object set read as a complete one, which for a scanner a
cleanup tool acts on is the wrong direction to fail in.

The osd-zfs-mount file list is built in %install from what the build
produced, not substituted into the spec.  Whether the plugin exists is
decided by the ./configure that %build runs, so freezing the answer a
build earlier meant a published srpm rebuilt on a host with a
different zfs devel layout either packaged a file that was not built
or left one unpackaged, and rpmbuild treats both as fatal.

One dnode hold per object rather than two, and one SA_ZPL_DXATTR
unpack for every Lustre xattr, so tier 1 costs what tier 0 costs; an
EA too large for the SA is read from its spill znode.  Objects with
zero links are delivered, since osd-zfs's own hierarchy carries them
while live.

The DMU headers exist twice and only the libzpool set compiles in
userspace, so configure probes with a compile test and the backend
takes its own ZFS_SCAN_ENABLED conditional.  The probe includes what
libscan_zfs.c includes and names the libzpool functions it calls, so
that a header set which satisfies the probe but not the source fails
configure rather than make.  The plugin links -lzpool
-lnvpair and never -lzfs, whose second copy of the fletcher code need
not be the one kernel_init() initialised.  liblustreapi still links
neither libext2fs nor libzpool.

Verified on a real osd-zfs target: the contract tests pass unmodified
against an MDT, an OST and a snapshot, the object set is identical
from 1 to 16 threads, and conf-sanity 165 passes with FSTYPE=zfs.

That verification is a lab's and not autotest's, which is worth saying
because a skip reads like a pass.  The build hosts answer "checking
zfs libzpool headers usable from userspace... no", so they install no
scan_zfs.so, and conf-sanity 165 skips there rather than exercising
this backend: a green run says nothing about the code in this patch.
Covering it in autotest needs libzpool's userspace headers to compile
on the build hosts, which is a build-environment question rather than
one this patch can settle.
