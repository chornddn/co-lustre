LU-19686 lod: gate update llog thread on distribute txn

lod_sub_recovery_thread() dereferences lut->lut_tdtd, which
lod_prepare_distribute_txn() only publishes partway through
lod_prepare().  lod_add_device() gates starting that thread on
lod_initialized, which lod_prepare() sets much earlier, so an MDT
registering in between starts a thread that faults on a NULL
lut_tdtd at offset 0xb8 (tdtd_recovery_threads_count):

  Unable to handle kernel NULL pointer dereference
   lod_sub_recovery_thread+0x98/0x10f4 [lod]
   kthread+0x11c/0x128

This was seen on a 2.15 server.  The window is the same here and
wider, because lod_update_log_dir_gc() reads every update llog
header on the MDT inside it.

Gate on the distribute txn instead.  lod_add_device() registers the
target before calling us, and lod_sub_init_llogs() -- a later
statement of the same lod_prepare() -- starts the thread for every
target registered by then, so deferring loses nothing and needs no
ordering between the two threads.

Both callers can now reach the same target, so skip one that already
has a recovery thread.

conf-sanity 139 drives the race: it stalls a plain MDT in
lod_prepare() inside that window and mounts an MDT whose index has
never been registered.  A fresh index is required -- a re-registered
MDT appends no add_mdc record, so the MGS pushes nothing and the race
cannot fire -- so the test leaves the last MDT formatted but
unmounted and mounts it late.  It also checks that MDT ends up with
its update llog, so a deferral that never completes is caught.
