LU-20908 llapi: add llapi_ost_object_migrate()

Emptying an OST with lfs migrate rewrites every file that has an
object there, along with all its other objects, and lfs migrate can
neither take a file by FID nor avoid the side effects of a group lock
on mirrored and PFL files.

Add llapi_lov_object_iterate() to walk the OST objects of a raw
lustre.lov buffer, as fgetxattr() or llapi_scan_chunk_inode() return
it, and llapi_ost_object_migrate() to move one object to another OST
with the single-object layout swap.  The object is read at its own
offsets through OBJECT I/O scope, so no stripe arithmetic is done
here, and copied into a one-stripe volatile file, skipping holes,
under a read lease.  The objects are swapped when the MDS closes the
lease, and only if no open for write broke it, so that no writer can
come in between; no lock is taken, so no component is instantiated and
no mirror made stale.  LLAPI_OBJ_MIGRATE_LOCK_COPY takes a group lock
instead, for files that stay open for writing.

OBJECT I/O scope is LU-20802 (69511), which this needs to read an
object of a striped file; without it only single-stripe files can be
moved.  It needs a component, so the objects of plain striped layouts
cannot be read.  An encrypted file is refused: the copy ends at the
end of its last encryption unit, and the volatile file has no
encryption context to truncate it back to the file's size with.

The MDS allocates the new object, as for any new object, unless the
caller names an OST with LLAPI_OBJ_MIGRATE_DST_OST, and then the call
fails with -ENOSPC if the MDS put the object on another one.  The
object is never put on an OST the caller excludes, nor beside another
copy of its data: another stripe of a component that is not
overstriped, or a mirror or parity covering the same extent.  A
progress callback lets the caller limit the bandwidth or stop the
copy.

The copy reads and writes 64 MiB at a time, as lfs migrate does, or
lom_io_size, with lom_io_threads threads (2 by default) that take the
next piece from a shared cursor: while one thread writes a piece,
another reads the next, and a large object is copied in several
places at once.  On a test VM, one 1 GiB object moved at 313 MB/s
with one synchronous 4 MiB piece at a time, and at 830 MB/s with
64 MiB pieces.
