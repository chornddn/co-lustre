LU-21139 ptlrpc: serialize evictor thread start/stop

pet_refcount was changed without locking by ping_evictor_start()
and ping_evictor_stop(), which run from target setup and cleanup in
mdt_init0(), mgs_init0() and oss_device_init(), and targets on one
server are mounted in parallel.  Each start also re-initialized
pet_waitq, possibly under a thread still sleeping on it, and
ping_evictor_stop() did not wait for the thread to exit, so a start
soon after the last stop could run a second thread on pet_list.
Two evictor threads could both class_decref() the same obd, hitting
the OBDF_ATTACHED assertion in class_decref_free() (conf-sanity
test_153c).  An orphaned thread kept its lu_env, which pins mdd, osp
and mdt, so rmmod failed with "Module mdd is in use" (sanity-sec
test_31, LU-21149).

Serialize start/stop with pet_mutex, declare pet_waitq statically,
and have the last ping_evictor_stop() end the thread with
kthread_stop() after it has drained pet_list.  Replace pet_state
with pet_ready, which tells ping_evictor_wake() under pet_lock
whether a thread will drain pet_list.  If the thread can't be
created, keep the reference, since callers always call
ping_evictor_stop(), and retry on the next start.  If lu_env_init()
or lu_env_add() fails, the thread releases the queued obds and
exits, and the next start reaps it and retries.

Alex, PS3 could deadlock: ping_evictor_start() holds pet_mutex while it waits in wait_event_idle() for pet_state == PET_INIT, and the exiting thread now needs pet_mutex to set PET_INIT.

PS4 reworks this with a kthread_stop()-based approach. The last ping_evictor_stop() sets PET_TERMINATE under pet_lock, then calls kthread_stop(), and the thread exits once pet_list is drained. Start never waits for an old thread, and the lu_env pinning mdd/mdt/osp is gone by the time the last target unmounts (LU-21149). pet_state now only changes under pet_lock. A failed kthread_create() keeps the reference and the next start retries. If lu_env_init() fails, the queued obds are released.

Tested on a 2-node VM cluster: sanity-sec test_31 x5, conf-sanity test_153c x5, and 23 rounds of parallel target umount/mount (including dropping to zero targets). There was never more than one ll_evictor thread, there was no LBUG, and lustre_rmmod was clean.
