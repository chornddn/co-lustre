LU-11484 ofd: don't walk extents on count-only FIEMAP

The OSS can crash in ofd_get_info_hdl() reading past the reply
buffer when a FIEMAP probe with fm_extent_count == 0 arrives with
OBD_FL_SRVLOCK, e.g. from multiop in sanity/44f on a PFL file.

A count-only FIEMAP returns the number of extents in
fm_mapped_extents without filling fm_extents[], but
lock_zero_regions() and dom_has_zero_regions() walk that many.

Bound both loops by fm_extent_count, so a count-only request
locks the whole requested range before the extents are counted.
Drop the DoM PR lock mdt_fiemap_get() takes: it was never released,
so it could not be cancelled and blocked conflicting locks and umount.

(2 comments)

This bounds the extent walks in lock_zero_regions() and dom_has_zero_regions() by fm_extent_count, so a count-only FIEMAP with OBD_FL_SRVLOCK locks the whole requested range instead of reading extents past the reply, and it releases the DoM PR lock that mdt_fiemap_get() leaked.

For requests from unmodified clients both parts look right to me. The OSD and the ldiskfs fiemap helper never map more than fm_extent_count extents, so min() changes nothing for a normal walk. For a count-only request the whole-range PR lock flushes at least what a full walk flushes before the second ofd_fiemap_get() counts, so fm_mapped_extents with FIEMAP_FLAG_SYNC stays right, and the lov count-only path (one RPC per object, no continuation) is not affected. There is no wire change, so a server upgrade also fixes older clients.

tgt_data_unlock() after the second mdt_dom_fiemap() drops the reader reference that ldlm_cli_enqueue_local() returned, as the other tgt_mdt_data_lock() callers do; without it the lock could never be cancelled.

One problem is left on the error path, see the inline comment in lock_zero_regions(): when the first ofd_fiemap_get() fails, fm_mapped_extents is still the value from the request and fm_extent_count need not describe the reply, so the walk can still read past the buffer. Skipping the lock and the second call after a failed first call, as mdt_fiemap_get() does, fixes it.

The same fixes are in flight twice more: #70652 (LU-21171) has both loop bounds, the DoM unlock, the rc check above and sanity test_44i, and #68117 (LU-20609, open since August) has the DoM unlock with sanity-dom test_9. The three changes conflict, so it would be good to agree with Hiroshi and Sohei which one lands and to close the duplicate tickets.

[minor] There is no regression test. Since LU-20617 sanity/44f sends the count-only SYNC probe on PFL files, but the read past the reply usually shows only under KASAN; the DoM lock leak can be tested directly, as the two changes above do. A test of this server-side change needs an MDS1_VERSION check (OST1_VERSION for the OFD part) on the patch's own build version, not on the next tag (lustre-test-scripts skill, Version checks for interop).

[minor] Commit message: the AI review comment on the trailer order and the second Signed-off-by is still open, Assisted-by should carry the exact model ID (lustre-commit skill), and the subject names only ofd although the DoM lock leak in mdt is a separate bug with its own ticket (LU-20609).
