LU-10499 pcc: output valid state for valid cached files

There are two cases where the command 'lfs pcc state' reports
'none' for PCC status of a file:
- File has not been cached at all into PCC. When the file is read,
  data will come from remote Lustre filesystem.
- File was cached into PCC but was detached later, while keeping
  the PCC copy (e.g. 'lfs pcc detach -k').  When the file is read,
  its layout version is compared against the PCC copy, and if the
  version matches, the file is attached again and the data will
  come from PCC.  The inode must still be cached on the client
  with its layout, so this is not reported after the client cache
  is dropped (e.g. 'sysctl -w vm.drop_caches=3').

This patch adds a valid flag to distinguish between these two
states. For the latter case, the command 'lfs pcc state' will
output as follows:
$ lfs pcc state /mnt/lustre/f105.sanity-pcc
file: /mnt/lustre/f105.sanity-pcc, type: none, flags: valid

Fixes from the original patch:
- check the PCC copy against the cached layout generation, as at
  open, so that 'lfs pcc state' does not refresh the layout with
  a layout lock RPC.
- do not set PCC_DATASET_NONE on the inode when no valid PCC copy
  is found, which would stop the file from being auto attached.
- also report the valid flag for a detached PCC inode that is not
  freed yet.
- only report the valid flag if the PCC backend auto attaches files,
  which would use the PCC copy.

Document the existing 'aborting' flag in lfs-pcc-state.1 as well.
Clear the state for each file in 'lfs pcc state', since the flags
of a file that is not cached on the client are not set, and would
otherwise be printed from the previous file.

Add sanity-pcc/test_105 to verify it works as expected.
