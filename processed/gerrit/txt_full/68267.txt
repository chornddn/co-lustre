--- Commit Message ---
LU-20633 ldlm: fix mixed clock bases in target_bulk_io()

target_bulk_io() computed start/deadline using ktime_get_seconds()
(monotonic, boot-relative), but clamped and compared them against
req->rq_deadline, which is set from ktime_get_real_seconds() (epoch-
relative, wall clock) in ptlrpc_hpreq_reorder()/target request
handling. Since the two clocks differ by billions of seconds:

- The "if (deadline > req->rq_deadline) deadline = req->rq_deadline"
  clamp intended to cap bulk transfer time at the request's own
  deadline never actually fired, since the boot-relative deadline is
  always numerically far smaller than the epoch-relative rq_deadline.
  This allowed a bulk transfer to run for the full bulk_timeout even
  after the client's rq_deadline had already passed.
- The timeout DEBUG_REQ() message computed
  ktime_get_real_seconds() - deadline, printing a nonsensical, huge
  elapsed-time value in the logs.

Use ktime_get_real_seconds() consistently for start, deadline, and the
loop's timeoutl computation so all values share the same (REALTIME)
clock base as req->rq_deadline.
