--- Commit Message ---
LU-20984 socklnd: check hello source PID before using it

ksocknal_recv_hello() takes the peer's process id from the
received HELLO and ksocknal_create_conn() uses it to create the
peer.  The source NID is already checked for LNET_NID_ANY, but the
source PID is not checked at all.  A kernel LNet peer always uses
LNET_PID_LUSTRE, and an outgoing connection already requires the
peer to reply with the PID it was expected to have.

Reject a HELLO from a kernel peer whose source PID is not
LNET_PID_LUSTRE with -EPROTO.  Userspace peers, whose PID is
derived from their port, are not affected.

Looks good; the check is reachable on the passive path for any peer connecting from a reserved port, and every in-tree LNetNIInit() caller uses LNET_PID_LUSTRE, so legitimate kernel peers are unaffected. One optional commit-message nit inline, no need to re-spin for it.

On the open question of whether PID checks are still worth having: beyond LNET_PID_ANY, a kernel-branch HELLO could previously claim a PID with LNET_PID_USERFLAG set. The resulting peer is then treated as a userspace peer, so ksocknal_peer_failed() never notifies LNet that it died and ksocknal_process_receive() rewrites the source of every header. If PIDs are being phased out, forcing recv_id.pid = LNET_PID_LUSTRE and ignoring kshm_src_pid would close the same holes. Rejecting the HELLO, as done here, also points out a misconfigured peer, so either approach seems fine.
