LU-20828 tests: run xfstests' fsx against Lustre

Lustre's fsx.c and xfstests' ltp/fsx.c share a distant ancestor
but diverged into different tools; the xfstests copy exercises
I/O paths ours never reaches. Vendor it unmodified and run it
against a single mount as a new sanity-fsx-xfs suite, with each
test's op mix kept in the script rather than in a patched fsx.c.

fsx.c, global.h and statx.h are pinned to kdave/xfstests commit
a370dcbed43563f0462801e889e0eceb93c7cfad. xfstests normally
builds fsx.c against its own generated config.h; the needed
HAVE_* macros are supplied on the command line instead, without
HAVE_XFS_XFS_H, so global.h does not pull in xfsprogs headers
this tree has no use for. fsx.c itself uses getopt_long() and
struct option without including <getopt.h>, which upstream's own
build reaches transitively through those same xfsprogs headers;
a small new compat header force-includes it directly instead,
and also silences a clang-only warning-as-error on an unsigned
llabs() at fsx.c:2317 that gcc does not flag.

The O_DIRECT op mix is page-aligned and excludes copy_file_range
(-E), matching what was validated on LU-20828: page-aligned
O_DIRECT combined with copy_file_range corrupts file content on
Lustre, though not on every run. Reproduced here too (1 failure
in 3 x 20000 ops); a real bug, but a separate one from standing
up this suite.
