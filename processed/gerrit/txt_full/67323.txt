LU-19955 osd: flush the fallocate range even when it fails

osd_execute_fallocate() only flushes the range it punched back out of
the page cache when the fallocate itself returned success:

	rc = file->f_op->fallocate(file, mode, start, end - start);
	if (rc == 0)
		osd_partial_page_flush_punch(d, inode, start, end - 1);

ldiskfs dirties as it goes and can fail afterwards.  ldiskfs_punch_hole()
zeroes the partial blocks at the edges of the range first, and only then
removes the extents:

	ret = ldiskfs_zero_partial_blocks(handle, inode, offset, length);
	if (ret)
		goto out_stop;
	...
	if (stop_block > first_block) {
		...
		ret = ldiskfs_ext_remove_space(inode, first_block,
					       stop_block - 1);

so an error from the extent removal returns from a fallocate that has
already left dirty pages in the page cache.  The caller ignores the
error by design and only logs it, so the object stays in use with those
pages still dirty and never written back.

That is not only the LU-19955 assert.  A partial write landing on such a
page makes osd_write_prep() read the block back from disk to complete
it, which overwrites the zeroing the page was still holding, so the
zeroed range silently reverts.  With the error injected, fsx reports
data corruption long before it reaches the assert:

  READ BAD DATA: offset = 0x16991, size = 0x6bf2

The flush was unconditional when it was introduced by LU-14640, and
became conditional while the surrounding code was reworked to use
alloc_file_pseudo().  Restore the unconditional flush; it is harmless
on a range that was not touched.

Add OBD_FAIL_OSD_FALLOCATE_ERR to report an error out of a fallocate
that already did its zeroing, which reproduces the corruption on demand:
sanity/150id fails in 14s without this patch and passes with it.
