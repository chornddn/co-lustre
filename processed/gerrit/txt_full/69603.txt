LU-20934 lmv: fix ".." via stale master FID after migrate

When a striped directory is migrated between MDTs with
"lfs migrate -m", its master object is replaced: a new master
object is created with a new FID and the old master object is
destroyed after the migration completes. A client which already
has the old master FID cached in its LMV layout (e.g. it had
resolved the directory before another client migrated it) keeps
using that stale master FID until its cached layout is refreshed.

When the VFS resolves ".." through such a directory (parent
lookup during path walk, NFS get_parent, "ls dir/../file"
access), lmv_getattr_name() sends MDS_GETATTR_NAME to the MDT
hosting the stale master FID. Since the old master object no
longer exists, the MDT returns -ENOENT/-ESTALE and the whole
path resolution fails on the client. The client never gets a
chance to refresh its layout, because the failing lookup is
exactly the operation that would trigger the refresh.

The existing retry logic in lmv_getattr_name() only handles the
case of a migration in progress (lmv_dir_retry_check_update()),
not the case of a migration already completed by another client.

Fix it by retrying the ".." lookup once via the first stripe's
FID when it fails with -ENOENT/-ESTALE on a striped directory:
the directory stripes survive the migration and their ".."
entries are updated to point to the new master, so the lookup
returns the new master FID, which flows back through
ll_prep_inode() -> ll_update_lsm_md() and permanently heals the
client's cached layout. Guard the retry with a dir_stale flag
so it happens at most once. Client-side fix only, no server
change is needed.

Add sanity test_230D: two clients; client2 warms the subdir
master FID, the subdir is migrated between MDTs twice, client2
drops its dcache and MDC locks and resolves ".." through the
stale master FID after each migration.
