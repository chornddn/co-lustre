LU-21296 ldlm: add tracepoints for the lock lifecycle

Lock waits and contention are visible only in the debug log, which
has to be enabled before the problem and wraps under load.

Add trace system "ldlm" with five events:

  ldlm_lock_enqueue      a lock request starts: in ldlm_cli_enqueue()
                         on the client, ldlm_handle_enqueue() on the
                         server (not again for a resent request),
                         ldlm_cli_enqueue_local() for a server's own
                         locks, and ldlm_cli_enqueue_placeholder()
                         for a client-only placeholder lock
  ldlm_lock_grant        when the lock is granted: in
                         ldlm_grant_lock(), and in
                         ldlm_process_flock_lock() for flock locks
                         on the server
  ldlm_lock_blocked      in ldlm_add_bl_work_item(), when a granted
                         lock conflicts with a new one and will get a
                         blocking AST; it names both locks
  ldlm_lock_bl_callback  in ldlm_callback_handler(), when a client
                         receives that blocking AST
  ldlm_lock_destroy      in ldlm_lock_destroy_internal(), once per
                         lock: after a cancel, or for a lock that was
                         never granted, such as a replaced intent lock

They carry the namespace, resource name and type, granted and
requested modes, flags, pid, and both the local and remote handle
cookies, so tools can pair enqueue with grant and destroy, and a
client lock with its server lock.  Add contrib/eBPF/ldlm_wait.bt for
per-namespace lock wait histograms and blocked-resource counts, and
sanity test_60p, which checks that the MDS's ldlm_lock_blocked and
the client's ldlm_lock_bl_callback name the same pair of locks.

Benchmark: single-threaded createmany, statmany after a lock cancel,
and unlinkmany of 10000 files in one directory, from one client, with
1 MDT and 3 OSTs on VMs and the default debug mask on every node.
Microseconds per operation, median of 7 runs:

  before           the parent commit, without the tracepoints
  after, off       this patch, tracepoints compiled in but disabled
  after, on        all ldlm events enabled through tracefs on every
                   node, writing each record into the trace buffer
                   with no reader attached: the cost a node pays
                   while traced with trace-cmd or tracefs, excluding
                   the reader itself
  after, bpftrace  ldlm events disabled in tracefs, and ldlm_wait.bt
                   attached on every node instead; each event runs
                   its BPF program and updates the start-time and
                   histogram maps rather than writing to the buffer

The "fresh mount" rows each ran right after deploying and mounting
that build.  The "aged mount" rows ran one after another on a mount
that had already run sanity tests, where create is about 9% slower
in every configuration, so compare rows only within one group:

                     create   stat  unlink
  fresh mount
    before              695    493     693
    after, off          695    470     700
  aged mount
    after, off          760    476     706
    after, on           768    508     730
    after, bpftrace     777    501     734

Disabled, the tracepoints add no measurable cost.  Enabled on every
node, either way, they add 1-7%.
