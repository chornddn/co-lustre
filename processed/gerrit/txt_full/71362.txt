LU-20090 nrs: add the rule key type= for TBF

The TBF policy type sets the key of every class bucket. A rule cannot
use a field outside that type, and two rules cannot have different
bucket granularity.

Add the rule key type=. It sets the fields of the bucket key of the
rule, and type=none gives one bucket for the rule. A rule can test
any field. The rule cache key holds the fields of the live rules. A
rule command that adds a field logs it on the console, from the first
service partition. A type change gives the rule a new ID, so its
requests move to buckets of the new type. The old buckets stay on the
rule, so a rate change or a stop of the rule still reaches them.

    nrs_policies="tbf uid"
    nrs_tbf_rule="start admins uid={1000 1001}&opcode={ost_read}
      type=uid rate=500"
    CPT 0: key=opcode+uid, rule_type=default, miss 0, walk 0,
      checked 0, lru_free 0, rerate 0, rcache 0, class 0
    admins uid={1000 1001}&opcode={ost_read} 500, id 2, type=uid,
      ref 0

Add the policy argument rule_type=default|auto. It sets the type of
a rule with no type= key:

- default: the rule takes the policy type. TBF uses this value when
  the policy start has no rule_type= key.
- auto: the rule takes the fields that its conditions test. A rule
  with OR terms takes the union of the fields of the terms.

The longest policy argument grows from 16 to 256 bytes, so that
"nid rule_type=default" fits. A policy argument that starts with a
key=value pair has the generic type, so "rule_type=auto" is valid.

An explicit type= key overrides rule_type=. The default rule has no
conditions, so it takes the policy type under the two values. The
key type= has no auto value. After a change of type=, a stop and a
new start give the rule its rule_type= type again. A new
rule_type= value restarts the policy, as for each argument change.
The CPT line of the rule dump shows the value:

    nrs_policies="tbf nid rule_type=auto"
    nrs_tbf_rule="start one uid={500}"
    CPT 0: key=nid+uid, rule_type=auto, miss 0, walk 0, checked 0,
      lru_free 0, rerate 0, rcache 0, class 0
    one uid={500} 10000, id 2, type=uid, ref 0

Add sanityn/test_77t{a,B,h,b,c,p,q,r,s,t}. 77tp checks that the LRU
counter lru_free grows, and that a class bucket frees with its last
rule cache entry. 77tq checks rule_type=auto. 77tr checks that 2
rules of 1 type give 1 client 2 buckets. 77ts checks that a
type=none rule gives 2 clients 1 rate. 77tt checks that a rule stop
and a rate change reach the old bucket with no new request. One stop
also takes a field out of the class key.

77ki now starts the rule that it expected to fail. 77kj also starts a
nodemap= rule under a nid policy. The 77kh and 77ki cleanups now stop
every rule that the tests start.

A rule on a new field can change the IDs that the other rules see.
Under a uid policy, a projid rule adds the project ID to the key. A
client before 2.17 does not send the project ID in ptlrpc_body. The
fallback in nrs_tbf_id_cli_set() then read all IDs from the request
body. For a write, the body holds the owner of the file. So a uid
rule lost the writes of its user to the files of other owners. The
fallback now fills only the IDs that ptlrpc_body does not give.

A rule start or a type change can add a field to the class key after
a request reads it. When the matched rule tests that field, the
request classifies again with the new key. This patch does not yet
cover a higher rule that tests the field. The next patch in the
series does.

The rule parse no longer reads the policy type. A rule start still
fails with -EINVAL when TBF does not run on each queue of the
command. No rule thus starts on only some of the heads. A rule
change checks its rank= target first, so a bad rank= changes
nothing on the head.
