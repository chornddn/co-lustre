--- Commit Message ---
LU-20943 lnet: fix off by one in recovery key list alloc

lnet_debug_recovery_show_dump() builds a dynamic ln_key_list to
describe the NIDs currently sitting in a recovery queue. The number
of keys is computed as:

        count = debug_recovery_attr_list.lkl_maxattr +
                drlist->lgdrl_count - 1;

but the buffer for the flexible lkl_list[] array was sized for only
'count' entries. The key list is indexed by the netlink attribute
number, which starts at 1 (index 0 is the unused *_ATTR_UNSPEC slot),
so valid entries run from 0 to lkl_maxattr inclusive and 'count + 1'
elements are required.

As a result, filling in the last "nid-N" key and later walking the
list in lnet_genl_parse_list() touch one ln_key_props past the end of
the allocation, which KASAN reports as a slab-out-of-bounds write and
which can panic the node:

 BUG: KASAN: slab-out-of-bounds in lnet_debug_recovery_show_dump
 Write of size 8 at addr ffff88810489e828 by task lt-lnetctl

Hit by sanity-lnet test_210 and test_211 ('lnetctl debug recovery').

Allocate room for 'count + 1' key properties so the whole index range
is backed by the allocation.
