--- Commit Message ---
LU-21023 mdt: end the migrate lease before locking the source

lfs migrate takes a lease on a regular file, and the migrate request
carries it to close. The client cancels its copy locally and sends no
cancel, so the MDT has to. It did that in mdd_migrate_close(), after
taking the source lock, whose OPEN bit conflicts with the lease. If
an open had already got the lease's blocking AST acked, nothing else
would cancel it: the migration waited on its own lease until the
client was evicted.

End the lease in mdt_migrate_lease_end() once the permission checks
have passed, since the lock is named by the client, and before any
lock is taken. A lease that is canceled but not yet destroyed, or
that another open is waiting on, is broken: the migration returns
-EAGAIN and the client retries with a new lease. A lease already
destroyed gives -ESTALE, which is ignored as before; an open since
then fails the migration with -EBUSY in mdd_migrate_sanity_check().
mdd_migrate_close() only closes the file.

Some concerns, see inline comments; the cancel ordering against the permission checks needs a refresh.

The hang seems to come from the lease no longer being cancel-on-block. LU-11926 (ae7ca90713) made leases LDLM_FL_CANCEL_ON_BLOCK so they "are not supposed to block anything". That flag is set in mdt_object_local_lock() only for `mlh_reg_mode == LCK_EX && *ibits == MDS_INODELOCK_OPEN`. LU-13668 (2869f429dd) then changed the lease to LCK_PW in mdt_object_open_lock(), so the flag is never set any more, and the comment "Lease lock are granted with LDLM_FL_CANCEL_ON_BLOCK" is now wrong. Was restoring cancel-on-block for PW leases considered, or is the non-cancel-on-block behaviour now intended? If it is intended, the mdt_handler.c check and comment are dead and could be cleaned up. Either way, a sanityn case that races a write open against a regular-file migrate (using OBD_FAIL_MIGRATE_LOOKUP_DELAY) would show the hang without the fix.
