LU-20730 llapi: read a device scan as LFU chunks

llapi_scan_device() calls back once per object, so a consumer that
wants objects in bulk, to write them out or hand them to another
process or node, copies each record into a batch of its own.

Add llapi_lfu_open(), llapi_lfu_read(), llapi_lfu_info() and
llapi_lfu_close(), the LfuOpen/LfuRead/LfuClose operation of
lfu.capnp as a function call. Each read fills the caller's buffer
with whole LfuChunk slots, written in place by the codec, and returns
the cursor to go on from. The first source is LFU_SOURCE_DEVICE.

A device stream reads in the caller's thread with one backend worker.
Parallelism is by shard: shard i of n is the i-th n-th of the
backend's units of work. A cursor names a unit and the first object
id in it not yet sent, so a read stops when the buffer is full and
the next read, or a new stream after a restart, resumes at that
object; ids below it are dropped before any xattr is read. A cursor
another target or shard wrote is -ESTALE.

Records carry the inode's own attributes and the EAs the demand mask
needs, as stored: trusted.fid names an OST object's file. An object
without a FID is counted, not sent: the stream names objects by FID,
and has no field for the target's own id, so lli_want never has
LLAPI_SCAN_INO. An object too large for a slot gets a jumbo chunk if
the consumer reads them, otherwise it is counted in the chunk's errors
and named in its skipped list. scan_obj_fid() is split out of
scan_sink_object() so both paths compute the FID the same way.

llapi_scan_device_test test8, run by conf-sanity 300a and 300b,
reads the MDT and an OST in 3-slot reads of 4 KiB and checks that the
stream sends exactly the objects llapi_scan_device() delivers, also
when resumed on a new stream and when read as 3 shards, and that
foreign cursors and bad parameters are refused.
