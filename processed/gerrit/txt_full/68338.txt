LU-19404 lnet: retry netlink dump on ENOBUFS

lnetctl net show -v and other DLC netlink dumps can fail
transiently with exit 234, empty output and a cYAML error of
"Out of memory" on a host with plenty of free memory. A rerun
succeeds.

Each dump chunk is built in an skb of at least cb->min_dump_alloc
bytes. lnet_net_show_start() set this to U16_MAX, an order-4
alloc_skb() on every node. LU-20221 sizes it from the configured
NIs instead, about 6.5KB per NI plus 3.5KB per net, so a node with
three or more NIs still needs order 4 and a large multi-rail
config needs far more. Above PAGE_ALLOC_COSTLY_ORDER these
allocations fail under memory fragmentation regardless of free
memory, and the kernel reports ENOBUFS: as an NLMSG_ERROR if the
first chunk fails, or as a socket error on recvmsg() if a later
one does. Neither can be resumed on that socket, because the
kernel only refills a dump from recvmsg() after a successful
dequeue, so only a new request recovers.

Retry the whole request on a fresh socket, bounded with
exponential backoff, when a dump fails with ENOBUFS or ENOMEM. The
retry is shared by yaml_lnet_config_ni() and yaml_lnet_route(),
the two dumps whose kernel side raises cb->min_dump_alloc. libnl
maps ENOBUFS to NLE_NOMEM, whose text is "Out of memory", so
report ENOBUFS as "No buffer space available" on both paths, and
return the real errno from yaml_lnet_config_ni() instead of
-EINVAL so the exit status, errno and message agree.

Add CFS_FAIL_NET_SHOW_DUMP to fail lnet_net_show_dump() with
-ENOBUFS, and sanity-lnet test_306 to check that lnetctl net show
retries a single failure and reports a persistent one.
