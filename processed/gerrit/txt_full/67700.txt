LU-20354 qmt: add per-slave DT usage cache for GETQUOTA

Build an in-memory per-slave DT usage cache on QMT so the
master can track block usage from slaves. Cache warming and
refresh land here; serving aggregated usage on GETQUOTA
stays disabled.

Warm the cache from QSD DQACQ/REL piggybacked qb_usage
(QUOTA_DQACQ_FL_USAGE). Refresh stale or missing entries
via an MDT helper (local OSD or OSP Q_GETOQUOTA). On fetch
failure, keep a valid cached value when present, otherwise
fall back to granted from that slave's local index.
Populate real DOM MDT indexes via qmt_pool_dom_add() on
connect so DT usage slots use real target indexes.

qmt_usg_serve remains off: qmt_get_usage() skips sum/refresh,
so GETQUOTA leaves usage unset and clients keep legacy
fan-out. A follow-on enables serve once MD inode
aggregation is ready.

Expose qmt.*.usage_cache_ttl (seconds; 0 means never
expire) and qmt.*.usage_cache_stats (hit/miss/fetch_rpc/
fallback). Keep pool membership in sync via extend/shrink
callbacks; usage-cache lifetime follows the lqe.

Add sanity-quota/310.

Some concerns, see inline comments. The main one is in qsd_handler.c: piggybacking usage onto the request body overwrites the qb_usage that the existing QUOTA_DQACQ_FL_REPORT path sets, which changes how much quota space the master grants back. That part is live today and is independent of the usage cache.

Beyond that, nearly everything the patch adds is unreachable as landed. qmt_usg_serve is assigned 0 in qmt_device_init0() and there is no tunable or ioctl that can set it, and sanity-quota 310 is unconditionally skipped, so roughly 500 lines of new code have no execution path and no test coverage. Would it be cleaner to land only the cache warming, the pool-membership plumbing and the tunables here, and hold the serve-side machinery (qmt_get_usage(), qmt_sum_lqe_usg(), qmt_refresh_lqe_usg(), qmt_setup_lqe_usg(), qmt_granted_lqe_usg(), mdt_qmt_fetch_usage(), osp_quotactl()) for the follow-on that turns it on?
