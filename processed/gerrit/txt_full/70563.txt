LU-10948 mdt: grant write open locks without LOOKUP

With the default opencache tunables, repeated opens of a file for
write never used the cached open handle.  The CW LOOKUP|OPEN open lock
conflicted with the PR LOOKUP lock that the client itself held from
the earlier lookup, and cancelling that lock invalidated the dentry.
Every later open then went through ll_atomic_open(), which sent an
open RPC and closed the duplicate handle, so 20 appends to one file
needed 20 lock enqueues and 20 close RPCs, as with opencache disabled.
A lookup of the name from another client also revoked the cached
write handle.

Grant the CW open lock with only the OPEN bit, and LOOKUP as a try
bit, so it does not revoke PR LOOKUP locks of this or other clients.
If the LOOKUP bit is granted, a lookup from another client still
revokes the cached handle, as before.

The LOOKUP bit of the open lock was also what made an unlink, a
rename over the file or an rmfid close cached write handles on other
clients.  Add the OPEN bit to the EX lock on such a victim if it is a
regular file, so that a removed file does not stay an orphan until the
client drops the handle, and rmfid does not fail with -EBUSY.  This
also breaks leases on the file, even if other links to it remain.

An exec of a file with cached write handles revokes them since
LU-21074 "mdt: revoke cached open handles on exec conflict", so it
does not fail with -ETXTBSY.

A getattr of the file by the copytool also used to revoke the cached
write handle when an HSM archive started.  Without it, the close that
reports the data as modified arrived only after the archive completed,
so the file was marked dirty and could not be released.  Revoke cached
write handles explicitly when the copytool starts an archive.

Add sanity test_441a to check that appends use the cached open handle,
sanityn test_124 to check that unlink and rename close it, and
sanityn test_14e to check that an exec from another client is not
denied by it.
