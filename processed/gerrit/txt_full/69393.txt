LU-20871 lod: fix NULL deref on unordered do_index_ops read

An MDS servicing MDS_READPAGE can take a NULL pointer dereference in
lod_it_init():

  pc : lod_it_init+0x4c/0xdc [lod]
  Call trace:
   lod_it_init+0x4c/0xdc [lod]
   dt_index_walk+0xb0/0x4e8 [obdclass]
   mdd_readpage+0xc0/0x5bc [mdd]
   mdt_readpage+0x788/0xd00 [mdt]

The NULL is dt_object_child(dt)->do_index_ops. lod_index_try() sets
the layer below's .do_index_ops before its own, but a consumer reads
the two independently: dt_try_as_dir() returns early once the upper
layer's is set, so it neither re-runs ->do_index_try() nor orders the
reads, and a weakly ordered CPU may satisfy the second load before
the first store is visible. dt_index_walk() checks only the upper
layer's ops, so it does not catch this.

Order the stores with smp_wmb() in lod_index_try() and the reads with
smp_rmb() in lod_child_index_ops().

Consume the field through lod_child_index_ops() as well, so an unset
layer below is handled rather than dereferenced. It re-establishes
the ops with dt_try_as_dir(), which is idempotent for directories,
rather than returning an error: lod_index_try() never runs again once
ours are published, so an error would leave the directory unreadable
until it was evicted from the object cache. lod_lookup() and
lod_striped_lookup() use it too, where an assertion in dt_lookup()
would otherwise LBUG the target.

Add sanity test_132: it arms a fail_loc that makes a consumer observe
the layer below's ops as unset, then checks that readdir still
succeeds, that the repair ran, and that the directory is not wedged.
