LU-17831 osc: batch discard adjacent pages on cancel

Lock cancel discarded each cacheable page with cl_page_own() and
cl_page_discard().  That takes a folio lock and a
generic_error_remove_folio() call per page, which dominates when
a large extent lock covers many GiB of cache.  Truncating a
contiguous file range with truncate_inode_pages_range() walks the
page cache once and drops the whole run without per-page
ownership, so it is much cheaper when many adjacent pages can go
together.

A full-object truncate is still unsafe: the pages of one OST
object can span file ranges that hold pages of other stripes.
With invalidate_lock gone (LU-20157), truncating those ranges
waits on the folio lock of a reader of another stripe and
reintroduces the deadlock sanityn 126a-c cover.

Discard file-contiguous runs with a range truncate when a run is
long enough and no page in it is being freed.  A hole ends a run;
a short run or a page left after truncate is discarded page by
page.  Add cl_object_discard_range() and coo_discard_range, so osc
asks llite to truncate the range in vvp_discard_range() and the
page cache is handled only in llite.  Split
cl_page_discard_prepare() out of cl_page_discard() so the batch
path runs cpo_discard before truncation removes the unowned
folios.  Both check_and_discard_cb() and osc_discard_cb() share
this path, so punch and DoM write-lock discard benefit too.

osc_discard_range_ok() checks that no page in a run is being
freed before truncating its file range.  A folio leaves the page
cache only after its cl_page is deleted, so this also catches a
page that is no longer mapped.  The check narrows the race window
but does not close it.  The range truncate empties the whole file
range: it also removes a folio added to a slot of the run after the
check, or after its first pass freed the slot, and waits for that
folio's lock.  Only a clean folio read under another lock can be
added there (a PR lock granted during the cancel, another FLR
mirror, or an EC placeholder), so the cost is a dropped cache page
and a wait for its read.

Cancelling 8 GiB of cached pages on an 8-vCPU VM (1 MDT, 4 OSTs,
hybrid_io=0, median of 3 runs against the LU-20157 baseline; LRU
clear uses osc_discard_cb, 2-mount BAST uses check_and_discard_cb):

  Case (layout)             Before    After   Change
  write LRU  (c1, 1M)      1307 ms  1147 ms   -12.2%
  write LRU  (c4, 1M)      1318 ms  1162 ms   -11.8%
  write LRU  (c4, 64K)     1478 ms  1312 ms   -11.2%
  read  LRU  (c1, 1M)      1330 ms  1127 ms   -15.3%
  read  LRU  (c4, 1M)      1358 ms  1186 ms   -12.7%
  read  LRU  (c4, 64K)     1525 ms  1355 ms   -11.1%
  read  BAST (c1, 1M)      1341 ms  1253 ms    -6.6%
  read  BAST (c4, 1M)      1454 ms  1282 ms   -11.8%
  read  BAST (c4, 64K)     1617 ms  1439 ms   -11.0%

Add sanityn 126d and 126e: LRU cancel of one stripe must not wait
for a paused reader of another, and must keep the other stripe's
cached units.
