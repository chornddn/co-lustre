LU-19536 obdclass: fail a short unaligned DIO user copy

When the copy between userspace and the bounce pages of an
unaligned DIO stops part way, on EFAULT after repeated short
copies or on a fatal signal, the copy returned the number of
bytes copied so far. Its callers only check for a negative
return, so the short copy was taken as success. A write
sent the BRW for the whole sub DIO, including bounce pages
never filled from the user buffer. A read reported the whole
sub DIO as read, though part of the user buffer was never
filled.

Treat a short copy as a failure of the sub DIO in both
directions: return the error, and store it for the other
threads waiting on a write copy.

Add OBD_FAIL_LLITE_DIO_COPY_SHORT to make the copy short
from a given bounce page on, sanity test_119v, which checks
that such a write does not send uncopied bounce page data to the
OST, and test_119w, which checks that such a read fails.

Fixes: 7194eb6431d2 ("LU-13805 clio: bounce buffer for unaligned DIO")
Fixes: 9fc5497ecbc2 ("LU-19536 obdclass: use wait queue for DIO copy sync")

Patch Set 2:

Tested PS2 on a RHEL 9.6 client (5.14.0-570.37.1) on top of master 54dc726b562, together with 65690 (LU-19458) and two local tests of mine, 3 runs each:
- sanity 119v from this patch: write() = -1 EFAULT and the region keeps the old data (A=24576, C=0). Without the fix the same test gets write() = 24576 with 17384 bytes of another file's data.
- one unaligned O_DIRECT write from a buffer whose last page is PROT_NONE, with 65690 applied: write() = EFAULT and the region is unchanged. With 65690 alone the write returned 24576 with 4096 bytes of another file's data.
- the mprotect() race test from LU-19536 (8 MiB writes, delays swept from 0 to 40 ms, 400 iterations): no write left foreign data. The writes in the race window now fail with EFAULT (163-165 failed instead of 140 on master, where 26 of them returned success with other data).

The change looks right to me: a write copy is now all or nothing, the error is stored for the waiters, which return csd_write_status, and the LASSERT() in osc_build_rpc() is only reached on the success path. The only other user of csd_write_copied is the wait loop in __ll_dio_user_copy(), so nothing else takes it as success.

65690 is safe on top of this patch; it may be worth making it depend on this one, so that it cannot land first.
