LU-20935 osc: fix decryption of a page with a sub-page hole

A client whose PAGE_SIZE is larger than
LUSTRE_ENCRYPTION_UNIT_SIZE (4KB), for instance aarch64
with 64KB pages, could read a file with a hole smaller
than a page and get back ciphertext: the units after the
hole were returned to userspace still encrypted.

osc_brw_fini_request() decrypts a page one encryption unit
at a time and stopped at the first all-zero unit, on the
assumption that a zero unit means the whole page is a hole.
A punch hole only has to be aligned to
LUSTRE_ENCRYPTION_UNIT_SIZE, so on a 64KB page it can zero
a single unit in the middle of the page and leave the
following units as valid ciphertext. Those units were never
decrypted.

This is not specific to a punch done by the same client.  A
sparse write from a 4KB-page client does it too: it writes
one file page and leaves the units before it unallocated on
the OST, because osc_brw_prep_request() widens an encrypted
write to start at the writer's own page boundary.  A
64KB-page client reading that range then sees a hole
followed by data and hits the same break.  The loop
predates the rejection of unaligned punches.

Skip the zero unit (leave it as zeros) and keep decrypting
the rest of the page.

This also changes ll_io_zero_page() for a page whose first
unit is a hole and whose later units hold data.  Such a page
no longer clears PagePrivate2, so an encrypted truncate that
lands inside it now zeroes and rewrites the page, instead of
skipping that step and leaving the page cached with none of
its units decrypted.  PagePrivate2 is still cleared when the
whole page is a hole, so that case is unchanged.

The same loop is fixed in do_dom_read_folio() for the DoM
read path and in the PCC-RO read path in pcc.c.
