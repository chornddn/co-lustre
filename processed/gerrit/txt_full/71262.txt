LU-21281 ldlm: avoid quadratic scan in ldlm_extent_shift_kms()

A client that holds tens of thousands of PR extent locks on one object
can spend minutes cancelling them.  This happens when many clients
share one file and access it with unaligned records.
ldlm_extent_shift_kms() runs for each cancel under the resource lock.
It walks every lock in the extent tree whenever no remaining lock
protects the old KMS, so the work is quadratic.  The other threads
that need the resource lock spin behind it.  The ldlm_bl threads miss
the 100s callback timeout, the OST evicts the client, and ll_imp_inval
then reports soft lockups while ldlm_namespace_cleanup() cancels the
same locks.

Prune the walk with l_subtree_last, the highest extent end of a
subtree, and skip subtrees that cannot raise the KMS.  Only locks
being cancelled, which are marked kms_ignore, are visited.  The result
is unchanged.  Drop the PW special case, as the pruning covers it.

On seven clients sharing one file, cancelling 20000 adjacent PR locks
takes 4.9 to 6.5s without this patch and 0.13 to 0.23s with it.  The
kunit case costs 9us per call from 10 to 100000 locks with the patch,
and grows to 350us at 27000 locks without it.

Add sanity 255e, which takes many adjacent PR locks with lockahead and
compares the time to cancel them from the lowest and from the highest
offset.  Add test 24 to lockahead_test for it, and a kunit case for
the many-locks, high-KMS case.
