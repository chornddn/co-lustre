LU-20720 osd: check the generation around a raw inode parse

The OSD scanner parses a raw inode with no lock, so the inode can be
freed and reused by another file while it is copied: the FID can come
from one file and the attributes from the next.  The check at the
xattr read does not see it, since it compares a generation read after
the copy.

ldiskfs: read the generation before and after the parse.  ext4 zeroes
a new inode before filling it in, so on x86 once any field of the new
file is visible the old generation is gone.  If it changed, parse once
more, then skip the inode and count it stale.  A copy taken while the
inode was being zeroed can still show the old generation, but then it
has no file type or no change time: parse it once more, then take the
object through the inode path.  The xattr read compares the generation
before and after it copies the value.  This holds on x86; on other
CPUs it is best effort.

ZFS: next() reads the generation with the other attributes, and an
xattr read from the xattr directory checks it again on every outcome,
so a reused object gets -ESTALE rather than a definite -ENODATA.
dos_stale is now reported on ZFS.
