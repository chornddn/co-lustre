LU-20350 o2iblnd: Bounce cross-NUMA bulk via NIC-local pool

On a dual-socket client the HCA hangs off one socket's PCIe root
complex, so any RDMA against memory on the other socket crosses the
inter-socket link. Without PCIe Relaxed Ordering that path serializes
toward single-outstanding-write and burns link bandwidth shared with
the CPUs. Lustre lands the bulk in the application buffer, placed
wherever the job ran, so a cross-socket job pays this on every bulk.

The client bulk is passive and connection-bound: the server drives the
RDMA over the connection the request arrived on, so the only per-I/O
client lever is which NI the request egressed on, since the server
bulk-backs to that NID. Stock LNet already steers that egress by the
bulk buffer's NUMA node. The request MD carries LNET_MD_BULK_HANDLE
(niobuf.c) and lnet_cpt_of_md() ranks the egress NI by the bulk
buffer's own first page via lnet_get_first_page() (lib-md.c). So on a
multi-rail client with a healthy buffer-local rail the bulk already
lands NIC-local and this patch changes nothing there.

The gap is any client whose HCAs do not cover every NUMA node a job
can land a buffer on, that is fewer rails than NUMA nodes. A
single-HCA dual-socket client is the extreme case, but a multi-rail
client is stranded the same way whenever a buffer lands on a node with
no local rail: there is no buffer-local NI to select and the bulk
crosses to whatever rail the server picks. numactl can avoid that by
binding the job's memory to an HCA-local node, but only by
surrendering the application's own NUMA locality, and for O_DIRECT the
job has to place the buffer itself. The bounce gives HCA-local DMA
without constraining where the job allocates.

Stage the bulk through a per-HCA arena allocated on the HCA's own NUMA
node and pay a CPU copy for the last hop. A cross-socket CPU copy is
cheaper than a cross-socket NIC DMA and is immune to the ordering
penalty. The bounce lives entirely in ko2iblnd, so it is transparent
to ptlrpc/osc/llite and to the server, with no wire change. We bounce
the read path: advertise the slot's REMOTE_WRITE rkey as the PUT sink
and run the slot->app copy-out off the CQ poller on an HCA-CPT-bound
workqueue, with lnet_finalize() deferred behind the copy. GPUDirect
pages bypass the bounce.

The workqueue belongs to the pool and shares its lifetime, so an
ib-bonding failover that moves the interface to a different HCA gets a
worker on the new HCA's node together with the new pool, and the old
pool keeps its own worker for as long as a transfer still holds one of
its slots. The consumer reaches the worker through the slot it already
holds, so it always finds the one on that slot's node. The deferred
copy-out takes a connection reference of its own, dropped only once
kiblnd_tx_done() has returned, so a copy-out is visible to anything
that waits on ibn_nconns and the slot's pool and worker stay pinned
through the HCA the connection holds.

bounce_enable is tristate (0 off, 1 auto, 2 force) and defaults off.
auto allocates the arena only on a multi-node NUMA box and engages
only when the buffer is NUMA-remote (node_distance > LOCAL_DISTANCE),
so local I/O stays zero-copy. The distance test is only sound if we
know the HCA's own node, so when the platform won't report one auto
warns and declines to allocate. force engages unconditionally and
allocates even on a single-socket box, for selftests.

HCA reads are barely penalized, so for a Lustre write the added
copy-in costs more than it saves. I measured a 16% throughput loss for
writes, so the write path stays direct.

|  read buffer  |  mode  |  throughput  |  % of LOCAL       |
|  placement    |        |              |  ceiling          |
|---------------|--------|--------------|-------------------|
|  LOCAL        |  off   |  8707 MiB/s  |  100% (baseline)  |
|  FAR          |  off   |  1847 MiB/s  |  ~21%             |
|  FAR          |  on    |  7422 MiB/s  |  ~85%             |
|  FAR          |  *on   |  8382 MiB/s  |  ~96%             |
* With bounce_scrub=0 (disabled)

The above numbers were generated with fio running on a single-HCA,
dual-socket client against two single-HCA OSSes, each hosting two
OSTs (all HCAs 200 Gbps, IB).

Because a slot is recycled, a non-conformant peer that RDMA-writes
fewer bytes than advertised yet reports success could leak the slot's
prior-transfer bytes in the untransferred tail. Zero each slot on
release to close this; the copy-out fuses the zero into the read-out
while the line is cache-hot, so the common path adds no separate pass.
bounce_scrub (default on) gates the zeroing so a trusted fabric can
drop it. It is writable, and turning it back on does not clean slots
parked while it was off; each one is clean again after its next
full-slot release, so the pool recovers over the following traffic
rather than at once.

The new module parameters are bounce_enable, bounce_pool_mb (64),
bounce_min_nob (65536), bounce_scrub (on) and
bounce_copyout_max_active (2), which sets the copy-out workqueue
concurrency. Slot size is fixed at LNET_MTU. Read
/sys/kernel/debug/lnet/o2iblnd_bounce_stats for the engaged,
exhausted, inflight, fallback and byte counters.

sanity-lnet 313 covers an intact bounced read with bounce_enable=2,
314 covers the bounced->direct fallback with fail_loc
CFS_FAIL_O2IBLND_BOUNCE_RD, and 315 covers the pool and worker rebuild
with dev_failover=2.

Two supporting refactors come with this. The kiov skip loop at the top
of kiblnd_setup_rd_kiov() becomes kiblnd_kiov_skip(), so the sink
rd-build and the copy-out walk the sink the same way.
kiblnd_alloc_pages() grows a kiblnd_alloc_pages_node() variant, since
cfs_page_cpt_alloc() rotates over every node of a CPT and cannot pin
the arena to the HCA's node; that variant passes __GFP_THISNODE,
because alloc_pages_node() only prefers a node and would otherwise
leave the arena off-node under memory pressure, which defeats the
purpose of this feature.

At bounce_enable=0 the sink rd-build reads the tunable, branches and
reroutes nothing; kiblnd_should_bounce() makes that its first test, so
a disabled build never walks the sink kiov.

## Summary

### The Compile Errors

The patch introduced two compilation errors related to **const-correctness**:

1. **Error in `kiblnd_setup_rd_kiov`**: Passing `const struct bio_vec **` to `kiblnd_kiov_skip()` which expected non-const `struct bio_vec **`
2. **Warning in `kiblnd_recv`**: Passing `const struct bio_vec *` (from `to->bvec`) to `kiblnd_recv_build_sink()` which expected non-const `struct bio_vec *`

### Root Cause

The existing function signatures in the codebase use `const struct bio_vec *kiov` parameters (e.g., in `kiblnd_setup_rd_kiov`), but the new bounce pool code introduced helper functions that didn't respect this const-ness. This violated C's type safety rules when these helpers were called from const-aware contexts.

### The Fix

I added `const` qualifiers throughout the bounce code chain:

1. **`kiblnd_kiov_skip()`** helper: Changed parameter from `struct bio_vec **kiov` to `const struct bio_vec **kiov`
   
2. **`kiblnd_bounce_copy_in()`**: Changed from `struct bio_vec *kiov` to `const struct bio_vec *kiov`

3. **`kiblnd_bounce_copy_out()`**: Changed from `struct bio_vec *kiov` to `const struct bio_vec *kiov`

4. **`kiblnd_bounce_first_page()`**: Changed from `struct bio_vec *kiov` to `const struct bio_vec *kiov`

5. **`kiblnd_reply_build_src()`**: Changed from `struct bio_vec *kiov` to `const struct bio_vec *kiov`

6. **`kiblnd_recv_build_sink()`**: Changed from `struct bio_vec *kiov` to `const struct bio_vec *kiov`

### Rationale

This fix is **correct and safe** because:

- These functions only **read** from the `bio_vec` arrays (they iterate and copy data, but never modify the bio_vec structures themselves)
- The const qualifier accurately documents this read-only contract
- It allows the functions to be called from both const and non-const contexts
- No functionality is changed—only type safety is improved
