LU-20994 osd-ldiskfs: end bios on RAID row boundaries

osd_do_bio() fills each bio until the disk blocks stop being
contiguous or bio_add_folio() fails. How far a full bio reaches
depends on how many of the buffer pages merge into multi-page
bvecs, so it usually ends in the middle of a RAID row (full
stripe). The RAID device then gets that row in two bios and must
take its partial-stripe path for it: a read-modify-write, or a
slower stripe-cache path instead of a full-row write.

On md RAID6 8+2 OSTs with 1 MiB rows and 4 MiB O_DIRECT writes,
about half of the requests reached md in 2-4 bios cut mid-row, and
23% of the rows were written as partial stripes; md wrote 17.2
GiB/s against 21.4 GiB/s in a run where 90% of the requests
happened to be a single bio.

Start a new write bio at every row boundary. A row of up to
BIO_MAX_VECS pages then always reaches the device in one bio. Use
the ldiskfs stripe as the row size: mount -o stripe=, else the
superblock's stripe width, else its stride (the RAID chunk). Only
cut at a page start, since the T10-PI code takes a bio segment's
guards from the start of its page. Reads and OSTs without a stripe
are unchanged.

The brw_stats counters fed by record_start_io() count bios, so on
OSTs with a stripe "disk fragmented I/Os", "disk I/O size" and
"disk I/Os in flight" now follow the RAID geometry: a 4 MiB write
shows at least 4 fragments with 1 MiB rows, and about 32 with
128 KiB chunks. That is not allocator fragmentation.

Test: md RAID6 in a VM, 4 MiB O_DIRECT writes, 1-16 streams, bios
traced at md0 (block_bio_queue), 3 runs each, with this patch and
with a variant that ends a bio only where the next row does not fit
in it, keeping bios longer than a row:
  8+2, 1 MiB rows: 2.5-4% of the rows split across bios without
  either, none with either; same throughput, with 3.6x more bios
  for this patch; data verified
  stride only, 128 KiB chunks: none split, 30x more bios for this
  patch, no slower
  6+2, 1.5 MiB rows: no difference; rows are split between RPCs

The site results below were measured with the variant, not with
this patch. On a site with 8+2 RAID6 OSTs (1 MiB rows), 3 clients
writing 4 MiB O_DIRECT, the variant raised the share of rows
written as full stripes from 77-94% to 100%, and client writes from
16.4 to 20.8 GiB/s with 2 OSTs on one server (+26%) and from 33.1
to 35.4 GiB/s with 4 OSTs on two servers (+7%). This patch was not
run at the site; in the VM runs it splits no rows either.

PS5 has the same code as PS4. The patch ends a write bio at an ldiskfs stripe (RAID row) boundary when the next row, or the rest of the I/O, does not fit in the bvecs left in the bio, and stops a fragment inside a page at a row start.

I checked the bvec count against bio_add_page() merging (one bvec per physically contiguous run, one less when the row's first page continues the last bvec), the new indexes (last stays below block_idx_end, so no new out-of-bounds access), partial rows at both ends of the I/O, rows that need more than BIO_MAX_VECS bvecs, the partial osd_do_bio() calls after a transaction restart, and reads and OSTs without a stripe (stripe is 0, nothing changes).

A cut only submits the current bio earlier, through the same path as a full bio, so every block keeps its sector and its memory and bios can only get shorter; no queue limit can be exceeded because of it. I also ran a small model of osd_do_bio() with and without the patch (4 KiB and 64 KiB pages, aligned and unaligned starts, merging and non-merging buffers, disk gaps, 3000 random cases): the data placement was identical, and the patch never split more rows than the old code. Looks correct to me.
