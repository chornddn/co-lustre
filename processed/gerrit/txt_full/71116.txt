LU-21245 osd: OI scrub thread waits in TASK_IDLE

The OI scrub thread throttles itself and waits for the LFSCK
consumer with wait_var_event(), which sleeps in
TASK_UNINTERRUPTIBLE. While the consumer is stalled, e.g. with
OSTs unreachable after an MDS failover, the idle scrub thread
stays in D state longer than hung_task_timeout_secs, so the hung
task detector reports it, and a node with kernel.hung_task_panic
set panics. These waits were wait_event_idle() before the scrub
moved to native kthreads.

Add wait_var_event_idle(), a TASK_IDLE variant of
wait_var_event(), and use it for the idle waits of the scrub
thread in osd-zfs and osd-ldiskfs: the window throttle, the wait
for the iterator user, the waits of osd_inode_iteration() and the
synchronization with scrub_stop(). The waits of the otable
iterator run in the LFSCK thread and are left as they are.

Add sanity-lfsck test_63, which stalls namespace LFSCK with
OBD_FAIL_LFSCK_DELAY1 so that the OI scrub fills its window, and
checks that the scrub thread is not reported as hung.

Patch Set 1:

This is the upstream port of HPE LUS-13554, which landed there for osd-zfs only. osd-ldiskfs has the same waits, and test_55 shows it: without the fix it fails on ldiskfs with "task OI_scrub blocked for more than 3 seconds", the scrub thread sleeping in osd_scrub_exec(). So this patch covers both backends.

Tested on RHEL 9.6 with ldiskfs (no zfs here): test_55 fails without the fix and passes with it 3 times out of 3, also with MDSCOUNT=2; sanity-scrub passes in full (one skip). With the hung task timeout at 3 seconds the LFSCK assistant thread (lfsck_assistant_engine()) is reported as well while it idles; that wait is in the LFSCK code and not changed here, and test_55 checks the OI_scrub thread only.

Test number 55: 47 to 54 are taken by open changes 64875, 62389 and 63322.
