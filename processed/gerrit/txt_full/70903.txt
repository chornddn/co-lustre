LU-9989 llite: copy data into pipe for splice on old kernels

On kernels without copy_splice_read() (before Linux 6.5: RHEL 8,
RHEL 9.0-9.4, SLES15 SP2-SP5, Ubuntu 20.04/22.04, 6.1),
pcc_file_splice_read() reads with generic_file_splice_read(), which
puts the page cache pages themselves into the pipe.  If such a page
is dropped before the pipe is read, page_cache_pipe_buf_confirm()
fails the reader with ENODATA (page removed from the page cache) or
EIO (page still cached, but not uptodate), so read() from the pipe
fails, and sendfile() and splice() return an error, 0 or a short
count:

 => page_cache_pipe_buf_confirm
 => iter_file_splice_write
 => direct_splice_actor
 => splice_direct_to_actor
 => do_splice_direct
 => do_sendfile

->release_folio() clears PG_uptodate of the pages it deletes from
Lustre.  An O_DIRECT write, lockless by default, invalidates the
cached pages of its range on the writing client before any lock is
cancelled, and invalidate_inode_pages2_range() removes them in spite
of the pipe reference: ENODATA.  Reclaim, and drop_caches or
POSIX_FADV_DONTNEED on kernels whose invalidate_inode_page() does not
check the page refcount (RHEL 8, RHEL 9.0), release such a page as
well, but cannot remove it while the pipe holds it, so it stays
cached, not uptodate: EIO.  Before LU-20157
(https://review.whamcloud.com/69332), a lock cancel also cleared
PG_uptodate when it discarded the pages: ENODATA; with that change,
the pipe keeps the data spliced under the lock.

Add ll_copy_splice_read() for these kernels.  Like copy_splice_read()
of Linux 6.5, which newer kernels already use, it reads the data with
->read_iter() into new pages under the usual DLM locks and adds them
to the pipe with add_to_pipe() and nosteal_pipe_buf_ops, so no page
cache page gets into the pipe.  compat_pipe_free_slots() limits the
read to the free pipe slots for both pipe layouts (head/tail since
Linux 5.5, curbuf/nrbufs before).  Also drop the dead
default_file_splice_read() case, whose check LU-19179 removed.

Add sanity test 443 and the multiop commands Xp (splice into a pipe)
and XP (read the pipe back and compare it with the file).  The test
splices from a Lustre file and reads the pipe after an O_DIRECT write
of the same data over the spliced range, which failed with ENODATA,
then after a lock cancel, which failed the same way before LU-20157.
It can only fail on clients without copy_splice_read(): RHEL 9.5+ and
Linux 6.5+ clients already copy and always pass, hence the el8.10
client session.

Patch Set 2:

PS2 changes the trigger of sanity 443; the fix code is unchanged (only its kernel-doc comment and the commit message are updated).

https://review.whamcloud.com/69332 (LU-20157, in master-next) stops clearing PG_uptodate when a lock cancel discards pages, and page_cache_pipe_buf_confirm() checks ->mapping only for pages that are not uptodate. With 69332 the PS1 test (cancel_lru_locks between the splice and the pipe read) passes without the fix: 3/3 on master + 69332 PS13 with the pre-6.5 splice path. The bug remains, since ->release_folio() still clears PG_uptodate: an O_DIRECT write from the same client (lockless, so invalidate_inode_pages2_range() releases and removes the spliced pages before any lock is cancelled) fails the read with ENODATA, and reclaim with EIO. The test now reads the pipe after an O_DIRECT write of the same data, and then after a lock cancel as before, which still matters without 69332.

Testbed, RHEL 9.6 client with generic_file_splice_read() forced (lb_cv_export_filemap_splice_read=no, emulating RHEL 8 / 9.0-9.4): without the fix 3/3 FAIL with ENODATA after the O_DIRECT write, both on master and on master + 69332; with the fix 3/3 PASS on both. Default builds (kernel copy_splice_read()) pass. Reclaim through memory.reclaim of a memory cgroup also fails the read without the fix (EIO) on both and passes with it. drop_caches and POSIX_FADV_DONTNEED cannot be the trigger: since RHEL 9.1 mapping_evict_folio() skips a page with an extra reference, so they never call ->release_folio() for a page held by a pipe (RHEL 8 still does).
