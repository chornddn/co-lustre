LU-20730 llapi: run find over a device's LFU chunks

llapi_find_device() takes its records one callback at a time from
llapi_scan_device(), so lfs find --device does not exercise the LFU
Object Stream at all.

Read the target through llapi_lfu_open() instead, 64 slots of 64 KiB
a read, and judge each record with the same find_device_cb(). Add
scan_device_lfu_rec(), which puts a chunk's LfuInode and raw EAs back
into the object a backend hands over and builds the record with
scan_rec_build(), split out of scan_sink_object(), so both paths read
the bytes alike. The FID is the producer's. Without the linkea, which
is sent only when the search needs it, the class is the target's own
subject matter, as only that is sent by default.

The stream has no field for the object's id on the target, so a
search that needs it, -printf %i or LLAPI_SCAN_F_INTERNAL with its
FID-less objects, still reads records. printf_format_want() now
reports %i as LLAPI_SCAN_INO to tell. An object whose LMA names no
valid FID is not sent, and so not printed, on the chunk path; the
search warns how many there were, from the chunks' error count.

A search that prints pathnames still reads records: the names are
composed from the directories the scan meets, which a chunk does not
carry. So does one given a --fid2path mount, whose filesystem the scan
checks against the target's label.

conf-sanity 300a compares lfs find --device -printf '%LF' (chunks)
with -printf '%LF %i' (records); it fails with a decoder that flips
one FID bit and passes with this patch. conf-sanity 300a-300d pass.
On a 100k-file MDT the search takes 0.45 s over chunks against 0.43 s
over records.
