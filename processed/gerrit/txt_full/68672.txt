LU-18598 mdt: take UPDATE and LAYOUT locks of migration source

Migrating a file that has more than one hard link decrements its
link count once per extra link (mdd_update_link()) and then
destroys it, but the source is locked with LOOKUP|XATTR|OPEN only.
The other names of the inode are meant to be covered by name locks,
but mdt_migrate_links_lock() deliberately skips a link whose parent
is the source or the target parent.  A second name in the source
parent is still excluded by the EX LOOKUP lock that migration holds
on the inode on that MDT, but a second name in the target parent,
when that is on another MDT, is not locked at all.  An unlink of it
needs EX UPDATE of the inode, a bit migration never takes, so it
can drop the link count to zero and destroy the object in the
window where mdd_migrate_create() has released the source object
lock.  osd_ref_del() then only warns about nlink == 0 and
mdd_migrate_create() destroys the object a second time, hitting
ASSERTION( !lu_object_is_dying(dt->do_lu.lo_header) )
in osd_destroy().

The new object also takes over the OST objects of the source, but
client layout locks of the source are never revoked.  A client
that still has the old layout cached fails to set up the new
object with -EIO, because its stripes still belong to the old one.

Take MDS_INODELOCK_UPDATE and MDS_INODELOCK_LAYOUT of the source as
well when a file inode itself is migrated, so that everything which
changes its link count is excluded for the whole migration and
clients invalidate the old layout.  An HSM restore holds EX LAYOUT
until the restore completes, so such a migration now fails with
-EBUSY while a restore of the file is running, rather than waiting
for it with the rename lock and parent locks held.

Dirent-only migration goes through mdd_migrate_update(), which
keeps the inode and its layout, and is left alone so that directory
restripe does not revoke client locks per entry.  Directory
migration is left alone too: a directory has no other names to
update and no OST objects, and UPDATE on it would conflict with the
PDO lock that every create and unlink inside it takes, serializing
all namespace changes in the directory for the whole migration.

Also return the real error from mdt_rename_source_lock() rather
than 0.  Both mdt_reint_rename() call sites already tested the
return value, but a failed mdt_object_lock() of the source was
swallowed there too, and rename went on to mdo_rename() with the
source unlocked.
