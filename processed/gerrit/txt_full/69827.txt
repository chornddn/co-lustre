LU-20995 compat: call kallsyms functions via static_call

On x86 kernels with CONFIG_X86_KERNEL_IBT running on an IBT-enabled
CPU, loading libcfs BUGs with "Missing ENDBR" when Lustre calls
kernel functions through pointers obtained from kallsyms.

The kernel seals the ENDBR of every function whose address is never
taken: objtool lists it in .ibt_endbr_seal and apply_seal_endbr()
poisons it at boot. kallsyms_lookup_name() is one of those
functions, as are alloc/free/apply_workqueue_attrs() and
security_file_alloc/free(), so none of them can be called through
a pointer from a module, whatever address is used.

A direct call or jmp does not need an ENDBR. With IBT, define a
static_call() in libcfs for kallsyms_lookup_name() and for each
function that lustre_symbols_init() looks up, and point it at the
kallsyms address with static_call_update(). The call sites are then
patched into direct calls to the kernel function. Other kernels keep
calling through a function pointer, behind the same
CFS_DEFINE_SYMBOL(), cfs_symbol_call() and cfs_symbol_set() helpers.

find_kallsyms_lookup_name() takes kallsyms_lookup_name() from a
kprobe, whose address is not always the symbol start: with IBT it
is after the ENDBR64 (+0x4), and on ppc64le (ELFv2) it is the local
entry point (global+8), or with KPROBES_ON_FTRACE the ftrace call
site, so calling it skipped the r2/TOC setup or part of the
prologue. Rewind the address to the start of the symbol using
sprint_symbol(). On other architectures the kprobe address is
already the symbol start.

In osd-wbcfs, look up flush_delayed_fput() before
class_register_type() and fail osd_init() if the lookup fails.
Previously a failed lookup left cfs_flush_delayed_fput NULL while
the module still loaded, so osd_umount()/osd_flush_fput() would
later call a NULL pointer. flush_delayed_fput() is exported since
v5.4, before IBT support was added in v5.18, so on IBT kernels it is
called directly and its ENDBR is never sealed.

The sanity runs below only exercise the IBT path if the test nodes
boot an IBT-enabled kernel on IBT-capable hardware; otherwise they
only verify that nothing regresses without IBT enforcement.

Some concerns, see inline comments. The patch replaces the #CP BUG with a clean module-load failure, which is an improvement. But on an IBT-enabled CPU it looks like libcfs can never load: kallsyms_lookup_name() and most of the other looked-up functions have sealed ENDBRs. A module-defined static_call() updated to the kallsyms address might be worth investigating, but a follow-up ticket for that seems reasonable.
