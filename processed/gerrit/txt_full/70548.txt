LU-21140 lmv: snapshot a changing directory for readdir

While a striped directory is being split or migrated, readdir can
list a name twice or not at all. LMV reads each stripe in its own
RPCs, at different times, and merges the pages by hash, so a name
that moves from an old stripe to a new one between two reads is
seen in both or in neither.

While a directory auto-splits, "ls -U dir | sort | uniq -d" prints
duplicated names, and "ls -U dir | sort -u | wc -l" returns fewer
files than were created.

Read every stripe of a directory whose layout is changing into pages
kept on the open file, and serve the listing from them. The snapshot
is taken at the first read after the layout is seen to be changing,
at whatever offset that read has, and is dropped at EOF, on seek, on
close and when the stripe count changes. Each stripe is read under a
PR UPDATE lock that is kept until the last stripe has been read, so
no name can move between the stripes in the meantime. A move takes a
conflicting lock on both stripes, in stripe index order, so the
locks are taken in that order too. Only the first page of a stripe
enqueues the lock; reading the other pages under the lock already
held avoids a new request queuing behind a conflicting lock that is
waiting for ours to be cancelled. All the locks are dropped before
the snapshot is returned. The start page of a stripe is found by
bisection, as the pages are in hash order.

A listing that started before the layout began to change, or that
continues across the end of the change, is not covered: its position
is a hash from the old layout, so a name that moved can be returned
twice or missed. If the snapshot cannot be taken, readdir reads the
stripes directly as before.

The first read of such a directory waits for all stripes, and
creates, unlinks and moves in it wait for that time. The pages are
kept until EOF, seek or close, with no limit on their number. The MDT
does not extend the lock callback timeout, so a read that outlasts it
can get the client evicted when a conflicting lock is waiting.

Add the lock hand-over to md_readdir_info and mdc_read_page().

Also fix mdt_reint_unlink(), which returned -ENOENT for a file that
still exists. While a directory splits, the file can be migrated
between the client's lookup of the name and its unlink. The client
sends the unlink to the MDT of the child FID it looked up, but the
name now refers to a new FID on another MDT, so the MDT fails the
unlink with "name cannot find FID" and rm reports "No such file or
directory". Return -ESTALE instead, so that the VFS looks the name
up again and unlinks the file under its new FID.

Add sanity test_230D, which lists a directory while it auto-splits
and a background job renames and removes names in it. It is skipped
on an MDS without the -ESTALE change. Without the LMV change it
fails, mostly with duplicated names and sometimes with missing ones;
with it, it passes 100 runs in a row. The same workload also ran
for two days, in a directory holding 1 million files, on a virtual
cluster of 2 MDS nodes and 7 clients without a duplicated or missing
name. The clients ran RHEL 9.8, RHEL 10.2, Debian 13.7, SLES 15.7,
SLES 16.0, Ubuntu 24.04 and Ubuntu 26.04, one distribution each.
