LU-20527 osp: don't trust an OST LAST_ID past the precreate window

ofd_create_hdl() answers a precreate request whose last OID is below
the OST LAST_ID with the OST's own LAST_ID + 1 ("trust the OST") and
precreates nothing.  osp_precreate_send() stores that reply into
opd_pre_last_created_fid without touching opd_pre_used_fid, so the OSP
then advertises every object in between as precreated, although the OST
created none of them for this request.  Once the jump exceeds
OST_MAX_PRECREATE * 2 the next lod_statfs_and_check() trips

  ASSERTION( sfs->os_fprecreated <= OST_MAX_PRECREATE * 2 ) failed:
  last_created [0x280000401:0xff02:0x0], next_fid [0x280000401:0x1:0x0]

LU-15009 introduced that reply, but capped the jump at OST_MAX_PRECREATE
so os_fprecreated stayed under the assertion; LU-17987 dropped the cap
and an arbitrarily large jump now reaches it.

Treat a reply beyond the range we asked for as a resync: move
opd_pre_used_fid up together with opd_pre_last_created_fid, leaving an
empty precreate window, the same way osp_precreate_cleanup_orphans()
handles the equivalent delorphan reply.

conf-sanity test_122a reaches this whenever an OSP rolls over to a
fresh sequence while OBD_FAIL_OFD_SET_OID is still set: the OST stamps
the new sequence's LAST_ID at seq_width - 255 and reports it back.
MDT0000's OSP always rolls over, since it starts on the IDIF sequence,
so create through MDT0000 as well to exercise it every run.

Fixes: 1711e26ae861 ("LU-15009 ofd: continue precreate if LAST_ID is less on MDT")
Fixes: 53940ff3eee8 ("LU-17987 ofd: always trust OST last_id")
