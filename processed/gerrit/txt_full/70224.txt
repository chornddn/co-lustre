--- Commit Message ---
LU-21075 llite: do not shrink i_size down to KMS

vvp_prep_size() wrote KMS into i_size unconditionally. KMS is a lower
bound only: osc_lock_lvb_update() clamps it to the end of the granted
DLM extent, and sub-objects with no valid KMS contribute nothing to
the merged value. On a PFL file whose size lives in a component the
client holds no lock on, that publishes the end of the component being
read as the file size, and a concurrent stat() reports it.

Extend i_size up to KMS instead, and never lower it here. cat_size is
no upper bound for it either: a remote truncate lowers the KMS of the
objects whose locks it cancels only, and an object nobody enqueues
again keeps reporting the size the file had before, so the merged
size still describes the old file.

Bound what the page cache may serve by KMS instead. lli_kms records
how far the locks this client holds reach: vvp_prep_size() publishes
it, vvp_attr_update() zeroes it when a lock is cancelled, and
ll_read_from_cache() stops there, so the generic read loop - which
runs to i_size with no further control from llite - cannot return
zeroes between a new EOF and a stale i_size. While i_size is above
KMS with no lock behind it, vvp_prep_size() takes one glimpse, which
makes the attributes, and lli_kms, current again - sanityn test_16i
and test_16n.

Fixes: 240cad9a0a ("LU-19344 llite: set read size correctly")
