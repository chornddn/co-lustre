LU-12571 llite: drain pinned dcache before cl_sb_fini at umount

On a subdir (fileset) mount, a lookup of /.fscrypt is redirected to the
.fscrypt directory at the real filesystem root (LU-15176).  This
instantiates a cross-tree dcache subtree under the mount root whose
regular-file inodes (the fscrypt protector/policy metadata) carry
cl_objects.  At umount such a subtree can still be pinned by a transient
asynchronous reference at the moment the VFS runs
shrink_dcache_for_umount()/evict_inodes() (before ->put_super), so it is
not reclaimed.  Its inodes then survive into client_common_put_super()
and their live cl_objects trip:

  lu_device_fini() ASSERTION( atomic_read(&d->ld_ref) == 0 ) Refcount
    lovsub_device_free() -> cl_sb_fini() -> ll_put_super()

The straggling reference is released asynchronously moments later, but by
then the teardown has already reached cl_sb_fini().  The window is narrow,
so the failure is intermittent; it is seen most often as sanity-sec
test_54 crashing the fscrypt client on umount.

Before tearing down the cl object stack in client_common_put_super(),
give any straggling references a bounded window to drain, reclaiming the
now-unused dentries with shrink_dcache_sb() -- which evicts their inodes,
SB_ACTIVE being clear -- so the cl_objects are destroyed first.  The loop
is a no-op on a clean umount, where s_inodes is already empty.

Add sanity-sec test_54a as a deterministic regression test.  A new
fail_loc, OBD_FAIL_LLITE_FSCRYPT_UMOUNT_PIN, pins the cross-tree .fscrypt
metadata-file dentries at lookup and releases them via a short delayed
work at umount, modelling the transient reference.  With the fail_loc
armed the orphaned subtree and LBUG reproduce on every umount without the
drain, and never with it; the test crashes the client without this fix
and passes with it.
