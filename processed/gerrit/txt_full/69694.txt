LU-20958 llite: only update blocks after a flush

vvp_io_fsync_end() merges the stripe attributes into the inode after
every flush and OST sync, to update the blocks for LSOM.  Neither
takes a lock on the stripes, so the merged size and blocks are only
what this client last cached for each stripe.  That replaces a valid
i_size, e.g. a strict SOM size from the MDS, with a smaller one, down
to 0, for example in the local flush before lseek(SEEK_DATA).  An
lseek of an EC file with a stripe on an unavailable OST then finds no
data before this EOF.

Only update i_blocks there, which is what LSOM needed, and only grow
it while i_size and i_blocks came from the MDS, e.g. after this client
wrote to the file.

A write only locks the stripes it covers, and a stripe that this
client never held a lock on only has the size last cached for it, 0
if never seen, so the merge after a write, an O_SYNC write or a tiny
write could also shrink i_size, e.g. to 1MiB after a write at offset
0 of a 3MiB file with three 1MiB stripes whose size came from the
MDS.  Have lov_merge_lvb_kms() report such a stripe in the new
cl_attr::cat_kms_partial, and since a write never makes a file
shorter, let these merges only grow i_size then.  When the size of
every stripe is known, they may still shrink i_size, e.g. after a
truncate on another client.  If that truncate changed the layout, a
write merge can keep a stale larger i_size until a glimpse, which
only affects the lazy SOM size sent at close.

Add sanity-flr test_44j, which checks that an fsync does not
shrink the strict SOM size of a mirrored file.
