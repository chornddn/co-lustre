LU-20690 ec: like-RAID10 parity layout so p may exceed k

The k >= p restriction is not a Cauchy/ISA-L limit. It comes from
storing parity as RAID0|PARITY: the p parity objects of a raidset are
concatenated along the file offset, so raidset_count * p * stripe_size
does not fit in a finite PFL extent when p > k (for example
--ec 2+3 -E 2M).

Store EC parity as LOV_PATTERN_PARITY instead. A raidset is an EC
split of the stripe set, and the layout is like RAID10 in that it has
the same two axes:

  - across the raidsets of one stripe set: like RAID0, one
    stripe_size per raidset;
  - within one raidset: like RAID1, the p parity stripes share one
    file offset (the same object_off).

Unlike RAID1 the p parities are not replicas, each one holds a
different parity. The file extent still matches the data component:

  ec_off(stripeset, raidset) = e_start
      + stripeset * (raidset_count * stripe_size)
      + raidset * stripe_size

I/O mapping keys off LCME_FL_PARITY, not the pattern. Within a
raidset, resync/verify must pick one parity via LL_IOC_FLR_SET_STRIPE
/ llapi_mirror_{read,write}_stripe(): the parities differ, so a
RAID1-style fan-out would be wrong. Punch and truncate still hit
every parity object.

Example: -E 128M -c 11 -S 1M --ec 4+2

  data/parity extent [0, 128M)
  raidsets [4,2], [4,2], [3,2] (raidset_count=3)
  parity has 6 OST objects
  one data stripe set = 11M
  one parity stripe set = 3M (not 1M flat, not 6M concat)

  stripeset raidset data_pos    ec_off  concat  objects
  --------- ------- ----------- ------- ------- -------
  0         0       [0, 4M)     0       0       0,1
  0         1       [4M, 8M)    1M      2M      2,3
  0         2       [8M, 11M)   2M      4M      4,5
  1         0       [11M, 15M)  3M      6M      0,1
  1         1       [15M, 19M)  4M      8M      2,3
  1         2       [19M, 22M)  5M      10M     4,5

The concat column is what RAID0|PARITY would have used, and is what
overflows a finite extent. When raidset_count == 1 (e.g. --ec 2+3) a
single raidset still fits p > k in a finite PFL extent. With
--ec 1+N, parity offsets align with each data stripe.

This changes how a parity component is encoded, so
lov_pattern_supported() and lov_pattern_available() now accept
LOV_PATTERN_PARITY on its own in place of RAID0|PARITY, and
lov_entry_type() dispatches on the PARITY bit. EC has not shipped, so
the old combination is not kept. Finite-extent stripe-count shrinking
is skipped for parity components. The p <= k checks in lfs and llapi
are removed; k+p <= 256 and p <= 15 remain.

Tests: sanity-ec 4a and 10 accept p > k; test_300 covers PFL -E 2M
--ec 2+3 create/resync/verify; 12c/34c cover holes and multi-raidset
offsets (34c asserts striping into raidset 1); llapi_layout_test
test47 allows 3+4 and asserts the component pattern is
LOV_PATTERN_PARITY.
