--- Description ---
Description

o2ib does not negotiate the MTU on both ends of the link. The current negotiation is a one-way propagation: the active side passes the path MTU to the passive side via `rdma_connect()`, encapsulated in the CM REQ, and the passive side simply adopts this MTU value when establishing the connection.

	For InfiniBand, not a problem, because the path MTU queried by the active side is already the aggregate value along the path.

	For iWarp, not a problem either, because iWarp does not require a path MTU to be set.

	For RoCE, however, it's a problem: the path MTU is derived from the host's netdev MTU, which is configured independently on each side. The MTU of the whole connection is therefore decided by the active side. If the passive side's netdev MTU is smaller, both QPs still use the larger value chosen by the active side, and messages that exceed what the passive side can carry are dropped on the fabric.

Example

two RoCE nodes

A  netdev MTU 1500  (path MTU 1024)
B  netdev MTU 9000  (path MTU 4096) 

A active, B passive -> both QPs use path MTU 1024; communication works.

B active, A passive -> both QPs use path MTU 4096; packets larger than 1024 are dropped on the fabric and large messages fail.

Solution

One possible solution is to check the path MTU on the o2ib passive side. If it is unsuitable, send a Reject back to the active side with the local MTU, triggering a reconnection negotiation.
