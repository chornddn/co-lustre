--- Description ---
Problem

nodemap_clear_dynamic_nodemaps() links the nodemaps through nm_list under active_config_lock. It then drops the lock and walks the list. Other code relinks nm_list under that lock, and a concurrent call of the function does the same. The walk then follows a list that it does not own.

mgs_iocontrol_nodemap() calls this function after a nodemap change when dynamic nodemaps exist and the MGS has a local target. Thus two concurrent nodemap commands on such an MGS can crash or hang the node. LU-19478 added the function, so all branches with that change have the defect.

Reproduction

On a VM, I added a delay between the unlock and the walk. One nodemap change waited at the delay, and a second change then ran. The node crashed as soon as the delay ended:

Unable to handle kernel paging request at virtual address 0000ffff9906144c
Internal error: Oops: 0000000096000006 [#1] SMP
pc : nodemap_clear_dynamic_nodemaps+0x12c/0x230 [ptlrpc]

The delay widens the window. I did not reproduce the crash without the delay.

Fix

	Copy the dynamic nodemap names under active_config_lock, and delete by name after the unlock.

	Let only one call of the function delete at a time, because nodemap_del() walks nm_subnodemaps without the lock.

	Move the nm_parent_entry unlink in nodemap_destroy() under active_config_lock.

Remaining gaps

	An explicit nodemap_del that runs with a clear still walks nm_subnodemaps without the lock.

	The check that a name is dynamic and the delete are not atomic. If an administrator removes a dynamic nodemap and adds a persistent nodemap with that name in this window, the clear removes the persistent nodemap. The earlier code has the same window.
