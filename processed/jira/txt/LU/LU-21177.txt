--- Description ---
Tools that move files by FID (lfs migrate, lfs mirror extend/split, movers and policy engines through llapi_create_volatile_idx(), the HSM copytool restore) create their volatile files in /.lustre/fid. When the file goes to MDT0, every create cancels the client's UPDATE lock on .lustre/fid, and the cancel runs ll_prune_negative_children(), which walks one cached dentry per FID ever looked up under the d_lock of .lustre/fid. All FID path walks on the client spin on that lock meanwhile.

The cancel is not needed: a volatile file gets no name in the parent, and since LU-14693 (2.14.52) the MDT takes no lock on the parent for it. It happens twice per create:

	mdc_intent_open_pack() cancels the parent's UPDATE lock by ELC for every create, volatile or not.

	liblustreapi's create_volatile() and create_restore_volatile() unlink() the volatile name afterwards (for non-Lustre file systems). On Lustre that is an RPC failing with -ENOENT, and mdc_unlink() cancels the same lock first.

Fix, two patches: no parent ELC in mdc_intent_open_pack() for MDS_CREATE_VOLATILE (an older MDT revokes the lock by blocking callback instead), and no unlink() in liblustreapi when the volatile open succeeded on Lustre, with sanity test_185b.
