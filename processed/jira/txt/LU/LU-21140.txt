--- Description ---
While a striped directory is being auto-split or migrated, a readdir on a client can return the same name twice, once from the old stripe and once from the new stripe.

LMV reads each stripe in its own RPC and merges the pages by hash in lmv_striped_read_page() and lmv_dirent_next(). It never compares names. If a name is read from the old stripe before it moves and from the new stripe after it moves, it is listed twice.

Impact

A tool that processes the names in parallel fails on the second copy. For example:

lfs find -type f -print0 DIR | xargs -0rP 16 -n 1 rm

fails with:

rm: cannot remove '...': No such file or directory

No data is lost. The failure comes from deleting the same name twice.

How to confirm

Check the listing for duplicate names while the directory is migrating:

lfs find --threads=4 -type f $TestDir | sort | uniq -d

Any output is a name that was listed more than once. The migrating flag in lfs getdirstripe $TestDir shows whether a migration is in progress.

--- Comment (paf0186, Fri, 6 Nov 2026 21:11:28 +0000) ---
I looked at this while reviewing https://review.whamcloud.com/70548. The duplicates are half of the problem: the same cause also makes readdir skip names, and client-side deduplication can't fix that.

Cause: LMV merges stripes by lde_hash, but that is each MDT's own htree hash, and every MDT has its own random hash seed (ZAP salt on ZFS). When the restriper moves a name to another MDT, its position in the merged order jumps. A name that moves from behind the readdir cursor to ahead of it is returned twice; one that moves from ahead to behind is never returned.

Measured (2 MDTs, auto-split, master vs. 70548):

Case
master
with 70548

ls -U during split, 20k files
up to 104 dup, up to 45 missing per listing
0 dup, up to 109 missing

one listing open across the split, 100k files
~21% missing
~21% missing

rm -rf while splitting
ENOTEMPTY
ENOTEMPTY

(Also: test_230D uses dir_split_delta=1, so its plain directory never actually splits.)

Options:

	Use one htree hash seed for all MDTs. A name then hashes the same in every stripe and keeps its position; any duplicate lands next to its other copy and is trivial to drop. Doesn't cover existing filesystems (they'd need a rehash) or ZFS.

	Second choice: lock out moves with the UPDATE lock. Readdir of a directory whose layout is changing holds PR UPDATE locks on all stripes for the whole listing, so the restriper can't move a name under it. Exact, and works for ZFS and existing filesystems. The cost is performance: the restriper, and every create/unlink in the directory, waits behind any open listing, and a slow or idle reader can hold that up indefinitely. It would probably need a timeout, or a dedicated ibit so only the restriper waits. (Holding the locks only while each merged page is built isn't enough, since names can still move between pages.)

	Restripe in two phases: copy the names to the target stripes, then delete the source names in bulk, with readers skipping the copies.

	Snapshot the directory on the client while its layout is changing. Needs 2 to be consistent.

	Client-side deduplication (70548): drops duplicates only, and keeps about 1 KB of kernel memory per name for each open fd.

--- Comment (adilger, Fri, 6 Nov 2026 23:11:18 +0000) ---
IIRC the hash seed is per-directory, to avoid pathological workloads/DOS from being able to cause huge hash-chain collisions.  I'm not against using the same hash seed for a striped directory in DNE, and seems like a good idea going forward if we can pass it in easily from a client (RNG and into the backend OSDs).  It seems unlikely we could get a consistent hashing to work with a directory striped across ldiskfs AND ZFS, but I think the risk of of striped directories, a filesystem with different MDT backends PLUS a concurrent migration is vanishingly small (though I guess MDT backend migration might increase the probability rather than decrease it).

The "snapshot on client" is almost free by allowing the client file descriptor to cache the directory contents until the readdir is finished, see LU-3308 (LU-5232 actually provides a more concise description), and is POSIX compliant.  We slurp in the directory stripes in large chunks, cache them/refcount pages on the file descriptor, but don't invalidate the file descriptor cache until the readdir file handle is closed.

We would obviously not want to cache the directory pages only on the file descriptor, but share/refcount them on the FD if the DLM lock is revoked, or cache them on the inode under the DLM lock if the FD is closed.  

That largely decouples what happens in the backend from the readdir lifetime, and should improve performance at the same time.

--- Comment (adilger, Fri, 6 Nov 2026 23:39:20 +0000) ---
The hash seeds are unique per directory, so it would only matter for new striped directories or during restriping (essentially also a new directory as well).  This wouldn't be needed when creating single-striped directories. It wouldn't retroactively fix existing striped directories, but there are few of those, and it could be fixed during the restripe to pick the hash seed of the original parent directory.

There wouldn't be any value to retroactively fix the hash seeds of existing directories, since this is only an issue during restriping, and the only way to fix it would be to restripe the directory.

--- Comment (JIRAUSER24002, Mon, 9 Nov 2026 21:43:42 +0000) ---
Here is an update on what I found today.

Hash seed

I checked the seed on a RHEL 9.8 test setup with two ldiskfs MDTs. It is per filesystem (the ldiskfs superblock s_hash_seed), not per directory. This is what I looked at:

	In ldiskfs/kernel_patches/patches/linux-6.11/ext4-kill-dx-root.patch (used by the rhel9.6/9.7/9.8 series), dx_probe() and make_indexed_dir() both set hinfo->seed = EXT4_SB(dir->i_sb)->s_hash_seed;

	I added debug printks in dx_probe() and osd_mount() on the test setup:
	
		pfs-MDT0000-osd mount: htree hash seed 641cd9cb-7940aeae-18a93482-c582e86d. dx_probe() on dirs ino 259 and ino 2263 on MDT0000 used the same seed as the device.

		pfs-MDT0001-osd mount: htree hash seed c50a22d6-93463bd9-5caf00a6-19809131. dx_probe() on dir ino 32271 on MDT0001 used the same seed as that device.

	
	

So different directories on one MDT use that MDT’s seed, and the two MDTs use different seeds. I did not look at ZFS.

My patch (client-side deduplication, 70548)

I fully agree it should be ranked lowest of Patrick’s options. It only drops duplicates and does not solve the missing-name case.

I modified my test and redid it today, and names can also go missing from the listing while the directory is splitting. The same race can leave a name in neither stripe at the moment each stripe is read. Deduplication cannot help there, because the name is never read. A shared seed would make the two copies adjacent, but it does not close that window either.

Only a consistent snapshot (or locking out the moves) fixes both problems.

Snapshot option

Di Wang’s question is right. To be consistent across a changing layout, all stripes (at least the old and new ones) have to be read before the first entry is returned, and the reads must not race with a name move. Caching the pages on the fd after they were read lazily does not close this, because the race is in the first read of each stripe.

Does this mean the fd cache needs to read all entries pages from all stripes before returning the first entry?

Probably yes, but that is still much less overhead than actually blocking the migrate during readdir (or the reverse) or doing some kind of persistent snapshot on the MDT (which would be complex and overkill for this). This has other performance benefits, like "rm -r" in a directory not ping-ponging the directory cache and DLM locks around.  Once the client has read all of the directory blocks then it doesn't need the directory locks anymore (the readdir is only cached in the FD if an unlink invalidates the DLM lock).
