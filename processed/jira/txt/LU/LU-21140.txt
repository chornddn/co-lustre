--- Description ---
While a striped directory is being auto-split or migrated, a readdir on a client can return the same name twice, once from the old stripe and once from the new stripe.

LMV reads each stripe in its own RPC and merges the pages by hash in lmv_striped_read_page() and lmv_dirent_next(). It never compares names. If a name is read from the old stripe before it moves and from the new stripe after it moves, it is listed twice.

Impact

A tool that processes the names in parallel fails on the second copy. For example:

lfs find -type f -print0 DIR | xargs -0rP 16 -n 1 rm

fails with:

rm: cannot remove '...': No such file or directory

No data is lost. The failure comes from deleting the same name twice.

How to confirm

Check the listing for duplicate names while the directory is migrating:

lfs find --threads=4 -type f $TestDir | sort | uniq -d

Any output is a name that was listed more than once. The migrating flag in lfs getdirstripe $TestDir shows whether a migration is in progress.

--- Comment (paf0186, Fri, 6 Nov 2026 21:11:28 +0000) ---
I looked at this while reviewing https://review.whamcloud.com/70548. The duplicates are half of the problem: the same cause also makes readdir skip names, and client-side deduplication can't fix that.

Cause: LMV merges stripes by lde_hash, but that is each MDT's own htree hash, and every MDT has its own random hash seed (ZAP salt on ZFS). When the restriper moves a name to another MDT, its position in the merged order jumps. A name that moves from behind the readdir cursor to ahead of it is returned twice; one that moves from ahead to behind is never returned.

Measured (2 MDTs, auto-split, master vs. 70548):

Case
master
with 70548

ls -U during split, 20k files
up to 104 dup, up to 45 missing per listing
0 dup, up to 109 missing

one listing open across the split, 100k files
~21% missing
~21% missing

rm -rf while splitting
ENOTEMPTY
ENOTEMPTY

(Also: test_230D uses dir_split_delta=1, so its plain directory never actually splits.)

Options:

	Use one htree hash seed for all MDTs. A name then hashes the same in every stripe and keeps its position; any duplicate lands next to its other copy and is trivial to drop. Doesn't cover existing filesystems (they'd need a rehash) or ZFS.

	Second choice: lock out moves with the UPDATE lock. Readdir of a directory whose layout is changing holds PR UPDATE locks on all stripes for the whole listing, so the restriper can't move a name under it. Exact, and works for ZFS and existing filesystems. The cost is performance: the restriper, and every create/unlink in the directory, waits behind any open listing, and a slow or idle reader can hold that up indefinitely. It would probably need a timeout, or a dedicated ibit so only the restriper waits. (Holding the locks only while each merged page is built isn't enough, since names can still move between pages.)

	Restripe in two phases: copy the names to the target stripes, then delete the source names in bulk, with readers skipping the copies.

	Snapshot the directory on the client while its layout is changing. Needs 2 to be consistent.

	Client-side deduplication (70548): drops duplicates only, and keeps about 1 KB of kernel memory per name for each open fd.

--- Comment (adilger, Fri, 6 Nov 2026 23:11:18 +0000) ---
IIRC the hash seed is per-directory, to avoid pathological workloads/DOS from being able to cause huge hash-chain collisions.  I'm not against using the same hash seed for a striped directory in DNE, and seems like a good idea going forward if we can pass it in easily from a client (RNG and into the backend OSDs).  It seems unlikely we could get a consistent hashing to work with a directory striped across ldiskfs AND ZFS, but I think the risk of of striped directories, a filesystem with different MDT backends PLUS a concurrent migration is vanishingly small (though I guess MDT backend migration might increase the probability rather than decrease it).

The "snapshot on client" is almost free by allowing the client file descriptor to cache the directory contents until the readdir is finished, see LU-3308 (LU-5232 actually provides a more concise description), and is POSIX compliant.  We slurp in the directory stripes in large chunks, cache them/refcount pages on the file descriptor, but don't invalidate the file descriptor cache until the readdir file handle is closed.

We would obviously not want to cache the directory pages only on the file descriptor, but share/refcount them on the FD if the DLM lock is revoked, or cache them on the inode under the DLM lock if the FD is closed.  

That largely decouples what happens in the backend from the readdir lifetime, and should improve performance at the same time.

		pfs-MDT0001-osd mount: htree hash seed c50a22d6-93463bd9-5caf00a6-19809131. dx_probe() on dir ino 32271 on MDT0001 used the same seed as that device.

	
	

So different directories on one MDT use that MDT’s seed, and the two MDTs use different seeds. I did not look at ZFS.

My patch (client-side deduplication, 70548)

I fully agree it should be ranked lowest of Patrick’s options. It only drops duplicates and does not solve the missing-name case.

I modified my test and redid it today, and names can also go missing from the listing while the directory is splitting. The same race can leave a name in neither stripe at the moment each stripe is read. Deduplication cannot help there, because the name is never read. A shared seed would make the two copies adjacent, but it does not close that window either.

Only a consistent snapshot (or locking out the moves) fixes both problems.

Snapshot option

Di Wang’s question is right. To be consistent across a changing layout, all stripes (at least the old and new ones) have to be read before the first entry is returned, and the reads must not race with a name move. Caching the pages on the fd after they were read lazily does not close this, because the race is in the first read of each stripe.

--- Comment (JIRAUSER24002, Tue, 10 Nov 2026 13:18:03 +0000) ---
Progress on the snapshot approach (the snapshot option in Patrick’s list, and Andreas’s fd cache idea), and why I am trying it this way.

What I tried, and why it failed

	Client-side dedup (70548) is not enough. In my new test, names are missing from the listing, not only listed twice. Dedup cannot fix that, because the name is never read. I am no longer pursuing client-side dedup.

	Optimistic snapshot. The client reads all stripes, then checks that none changed (the stripe inode i_version, and the same DLM lock cookie for every page of a stripe), and retries on a change. During an active split, names move continuously, so every attempt saw a change. The client log showed the snapshot failing with -EAGAIN, the code fell back to the old path, and the duplicates stayed. It succeeded only in the quiet gaps between moves, so it cannot work during a sustained migration.

What I am testing now

	Lock-holding snapshot (client only). This is the snapshot option, with the locking it needs to be consistent (Patrick’s second option), but held only while the pages are read. At the first readdir of a directory whose layout is changing, LMV reads every stripe completely into pages kept on the open file. It takes the stripe’s PR UPDATE lock on the first page of each stripe and keeps it until the last stripe has been read. Then it drops all the locks and serves the listing from the pages.
	
		Why this should be consistent: a name can move between two stripes only by taking PW/CW on both (mdt_lock_pdo_mode() takes the whole-dir UPDATE lock in CW to flush client readdir caches). While we hold PR on a stripe, no name can move into or out of it. So each stripe is frozen from the moment we lock it until the snapshot is complete.

		Why not hold the locks for the whole listing: that would block the restriper and every create and unlink in the directory behind a slow or idle reader. Here the locks are held only while the pages are read.

		Deadlock: the client takes the stripe locks in stripe index order. mdt_reint_migrate() also locks the source and target parent stripes in stripe index order, so we never wait for a stripe that a move holds while that move waits for one we hold. I have not audited other paths that lock two stripes (rename, for example).Answer to Di Wang’s question: yes, for a changing layout the snapshot has to read all stripes before the first entry is returned. Caching the pages on the fd as they are read lazily does not help, because the race is in the first read of each stripe. Directories whose layout is not changing keep the lazy path.

	
	

Costs and limits

	The first getdents of a splitting directory waits for the whole read, and moves, creates and unlinks in that directory wait for the same time.

	Memory: every page of the directory is kept until EOF, seek or close. There is no cap.

	A listing that started before the layout became “changing” is not covered.

	Names created or removed during the listing may not show up (POSIX allows that).

	If the snapshot cannot be taken (an error on a stripe), it falls back to the current behaviour.

Status

Prototype only. The lock-holding version has not been tested yet. I will post the result.

Any opinions on this approach are greatly appreciated.

--- Comment (JIRAUSER24002, Wed, 11 Nov 2026 00:19:34 +0000) ---
Just pushed the snapshot approach to the same patch (70548)

LU-21140 lmv: snapshot a changing directory for readdir

How it works

	On the first readdir of a directory whose layout is changing (a split or migration is in progress), LMV reads every stripe completely into pages kept on the open file, then serves the listing from those pages. Directories whose layout is not changing keep the lazy path.

	Each stripe is read under a PR UPDATE lock. The lock is enqueued on the first page of the stripe and held until the last stripe has been read. A name can only move between stripes under a conflicting lock (CW/PW) on both, so while we hold the locks no name can move in or out of a stripe, and the stripes are consistent with each other.

	Locks are taken in stripe index order, the same order mdt_reint_migrate() uses for the source and target parent stripes. This avoids waiting for a stripe that a move holds while that move waits for one of ours.

	Only the first page of a stripe enqueues the lock. The remaining pages are read under the lock already held, using a new lock hand-over in md_readdir_info and mdc_read_page(). Requesting the lock again for each page let the request queue behind a conflicting lock that was itself waiting for ours to be cancelled, and the MDS then evicted the client (“lock callback timer expired”).

	The snapshot is dropped at EOF, on seek, and on close. If it cannot be taken (for example, an error on a stripe), readdir falls back to reading the stripes directly, as before.

Test

	New sanity test_230D lists a directory while it auto-splits (2 MDTs, dir_split_count lowered) and checks for duplicated and missing names. A background process keeps adding and removing files during the listing.

	With the patch, 100 runs passed.

Limitations

	The first getdents on a splitting directory waits for the whole read. Moves, creates and unlinks in that directory wait for the same time.

	Memory: every page of the directory is kept until EOF, seek or close. There is no cap.

	A listing that started before the layout became “changing” is not covered.

	Names created or removed during the listing may not show up (POSIX allows this).

	Other paths that lock two stripes (rename, for example) have not been audited for lock order.

	Tested on ldiskfs with two MDTs only.

Feedback on the approach is welcome.

Hi manhongdai, this sounds mostly good, but you wrote that the locking is done only if the directory is already being modified, but if the readdir starts before the migration then the output may still be inconsistent. I'm wondering if we could do something to cover this case as well.

For example, if the migration thread got a full PW lock on all the stripes in order, then set LMV_HASH_FLAG_MIGRATION on the LMV before it started migrating entries, and dropped the full-dir PW locks, then the client can check for LMV_HASH_FLAG_MIGRATION on the lock refresh and execute the "lock first stripe and read all pages" process to fetch all of the remaining pages.

The other issue that the "read all pages first" should help with is a thread doing "rm -r" in a large directory (whether striped or not).  In the current code the DLM lock on the directory (stripe) will ping-pong every time the userspace process is reading some entries and then the next entry is removed and revokes the lock(s) again, repeat.  Reading all of the entries at the start (or at least a few MB at a time, enough for 99% of directories) and caching them on the file descriptor allows userspace to continue processing entries without the lock ping-pong and re-reading the same directory contents multiple times.
