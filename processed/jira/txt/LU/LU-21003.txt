--- Description ---
sanity test_77b fails intermittently with "file compare failed": cmp of the read-back file differs at byte 1 (the "bad1" pattern that OBD_FAIL_OSC_CHECKSUM_RECEIVE (0x408) injects into the first page of a read RPC).

In the failing run the injected corruption on the final iteration (t10crc512 here; t10ip512 and t10crc512 in the earlier cases) was not reported as BAD READ CHECKSUM on the client or OSS and no redo happened, so the corrupted page stayed in the page cache and cmp saw it. test_77b then exits before set_checksums 0 and set_checksum_type are undone, and the next test, test_77c, fails with "no checksum dump file on Client" for the same reason (the corruption goes undetected so no dump is written). These 77c failures are a follow-on, not the "no checksum dump file on OSS" of LU-17047.

Seen on lustre-reviews on unrelated changes, none touching checksums or the test: change 66253 PS19 (2026-08-21, review-dne-part-1, session 013b4212-e356-4445-9467-d9b0a2e0f289), change 67011 PS3 (2026-07-08, session ef5a25ab-f8e1-4198-8880-8f3750432697), and change 65219 PS35 (2026-10-21, review-dne-zfs-part-1, el10.1, session e1edcae4-4250-450a-8740-dce9824aa9a0). Rate is low (a few per several thousand runs).

Client dmesg of the failing run: for crc32/adler/crc32c/t10ip512 the client logs "BAD READ CHECKSUM ... client X/X, server Y" and redoes the RPC with rc -11; after set checksum type to t10crc512 there is no checksum message at all before "FAIL: file compare failed".
