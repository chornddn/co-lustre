Description

On a busy OSS the LNet monitor thread is held on one CPU long enough for the

kernel soft-lockup watchdog to fire, repeatedly and on every OSS of the system

at once, roughly once every other day under an IOR workload. The task is always

monitor_thread and every trace ends in lnet_finalize_expired_responses().

Kernel 5.14.0 (x86_64), 2.16 Lustre, kfilnd over CXI; the same code is in master.

A third episode 36 s later is the same _raw_spin_lock from the same function

on CPU#43, and three more follow in the next 40 minutes on CPU#17 and CPU#9. The

thread migrating between CPUs and spinning on different locks is consistent with

one long cfs_cpt_for_each() walk progressing through the CPTs, not with a

single stuck lock.

Analysis

Two things make that walk unbounded, and they are independent.

1. The walk is run once per lnet_transaction_timeout/2, not once per pass

lnet_monitor_thread() wakes once a second, but calls

lnet_finalize_expired_responses() only when now >= rsp_timeout and then

re-arms rsp_timeout to now + lnet_transaction_timeout / 2 - 75 seconds

with the default timeout. Every pass therefore faces 75 seconds of accumulated

response trackers at once, walked in a single hold of lnet_res_lock(), which

is a plain spinlock, so preemption is off for the whole walk.

The period of the pass was never meant to be a function of the transaction

timeout: the timeout says when a response is late, it does not say how often

lateness should be looked for. Deriving one from the other also means that

raising lnet_transaction_timeout multiplies the batch, which is the opposite

of what tuning it is for. This was introduced by a57fa1176e7 ("LU-9120 lnet:

timeout delayed REPLYs and ACKs"); dc1f5f08b42 ("LU-11468 lnet: configure

recovery interval") only converted the wakeup counter into a timestamp.

2. What the walk walks is completed traffic, not timeouts

The walk stops at the first entry that has not expired, so the queue prefix it

traverses is not a backlog of timeouts. It is the prefix of requests whose

response has already arrived: lnet_detach_rsp_tracker() only invalidates

the MD handle and leaves the tracker on ln_mt_rstq for the monitor thread to

reap. The cost of the walk is therefore proportional to the traffic that

completed normally since the previous pass - on an OSS, where a tracker is

queued per LNetGet() and per ACK-requesting LNetPut(), that is millions

of entries - on one CPU, holding the resource lock and taking a net lock per

entry.

Adding cond_resched() inside the walk, which is the obvious first fix, only

spreads that cost: the monitor thread still has the same total work to do, now

over an unpredictably long time, and it is the thread that also drives peer and

NI recovery.

Note also that the current code splices the expired entries onto a private list

and then works on them with the lock dropped, while they are still reachable

through the MD - which is the most plausible source of the

__list_del_entry_valid trace above.
