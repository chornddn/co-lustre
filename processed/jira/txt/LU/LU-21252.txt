--- Description ---
Description

Deleting a quota entry while an OST is offline can leave the deleted

entry in the OST's local copy of the global quota index.

The QMT no longer contains the deleted entry, but the OST retains its

previous limit after it comes back online and quota reintegration

completes. The OST still reports glb[1],slv[1] (uptodate), despite

the mismatch.

Triggering quota_slave.force_reint=1 does not remove the stale entry.

In a separate manual test, the stale entry also persisted after

unmounting and remounting OST0000.

A stale limit can affect writes by the user whose quota entry was

deleted. In a buffered-write test, quota acquisition requests for the

affected ID returned -ESRCH from the QMT, and the OST logged

"ID isn't enforced on master". Writes by that user failed with ENOSPC

even though lfs df showed free space on the OST.

The issue was reproduced with user and project block quota entries on

ldiskfs and ZFS. A subsequent manual test on ldiskfs confirmed that a

deleted user entry remained after reintegration and force_reint, while

a different user's changed limit was applied successfully.

Reproduce
1. Configure user block quotas

Enable user block quotas and wait for quota reintegration to complete:

lctl conf_param lustre.quota.ost=u
lctl get_param 'osd-*.lustre-OST0000.quota_slave.info'

Set block quota limits for two user IDs:

lfs setquota -u 60001 -B 8M /mnt/lustre
lfs setquota -u 60003 -B 8M /mnt/lustre

Wait for both limits to appear in the OST's global index copy:

lctl get_param 'osd-*.lustre-OST0000.quota_slave.limit_user'

Both IDs should have a hard limit of 8192.

2. Delete a quota entry while the OST is offline

Stop OST0000. While it is offline, delete the quota entry for user

60001 and change the limit for user 60003:

lfs setquota -u 60001 --delete /mnt/lustre
lfs setquota -u 60003 -B 16M /mnt/lustre

Check the QMT global index:

lctl get_param 'qmt.lustre-QMT0000.dt-0x0.glb-usr'

User 60001 should be absent, and user 60003 should have a hard limit

of 16384.

3. Restart the OST and check reintegration

Start OST0000 and wait for quota reintegration to complete. Check the

OST's quota status and global index copy:

lctl get_param 'osd-*.lustre-OST0000.quota_slave.info'
lctl get_param 'osd-*.lustre-OST0000.quota_slave.limit_user'

Expected result:

The deleted entry for user 60001 is absent from the OST's global

index copy. User 60003 has the updated hard limit of 16384.

Actual result:

The OST reports its quota indexes as up to date. User 60003 has the

updated limit of 16384, but user 60001 remains in the OST's index copy

with the previous hard limit of 8192.

Triggering force_reint does not remove the stale entry:

lctl set_param 'osd-*.lustre-OST0000.quota_slave.force_reint=1'
lctl get_param 'osd-*.lustre-OST0000.quota_slave.info'
lctl get_param 'osd-*.lustre-OST0000.quota_slave.limit_user'

Wait for reintegration to complete before checking the index copy.

In a separate manual test, the stale entry also persisted after

unmounting and remounting OST0000.

Because the OST still considers the ID enforced while its granted

space remains 0, qsd_op_begin0() can report the ID as over quota to

the client. The client marks the ID as out of quota through

osc_quota_setdq(), and buffered writes can fall back to synchronous,

ungranted writes through vvp_io_commit_sync().

Ungranted writes are subject to the space available after outstanding

grants are reserved, as checked by tgt_grant_check(). In this test,

the OST was small, approximately 300 MB, and writes by the affected

user failed with ENOSPC. On larger OSTs, the synchronous write path

may instead result in degraded I/O performance, consistent with the

symptoms reported in LU-6382.

ENOSPC was observed in this test environment; its occurrence may

depend on the workload and environment.

Root Cause Analysis

When a quota entry is deleted, the QMT removes it from the global index

and sends a deletion notification to quota slaves holding the global

lock. An OST that is offline at that time cannot receive the

notification.

When the OST comes back online, qsd_reint_index() fetches the global

index from the QMT. The entries returned by the QMT are processed by

qsd_reint_entries() and qsd_reint_qid(), which update the local copy.

The deleted ID is no longer present in the QMT index, so it is not

included in the transferred entries. The existing reintegration path

does not compare the received IDs with the local index copy to remove

entries that are no longer present on the master.

As a result, the slave can retain the old limit while recording its

global index as up to date.

Before LU-15218, removing a limit was handled by resetting it to zero,

so reintegration could transfer the zero-limit entry. LU-15218 added

deletion of quota entries and a glimpse-based deletion path on quota

slaves, but did not update reintegration to remove entries deleted

while a slave was offline.

Test Results

A manual ldiskfs test compared the behavior before and after the

proposed fix.

Before the fix:

	User 60001 was deleted while OST0000 was offline.

	After reintegration, 60001 remained on the OST with hard limit 8192.

	The entry remained after force_reint.

	The changed limit for user 60003 was updated to 16384.

With the proposed fix:

	The same deletion and limit change were repeated.

	After reintegration, 60001 was absent from the OST's index copy.

	User 60003 remained present with the updated hard limit of 16384.

The new sanity-quota test_7g, added with the proposed fix, shows the following:

Build                 ldiskfs             ZFS
Without fix           FAIL, 3 of 3 runs   FAIL, 3 of 3 runs
With proposed fix     PASS, 3 of 3 runs   PASS, 3 of 3 runs

With the proposed fix, user 60001 completed both 64 MiB buffered

writes on each backend, ldiskfs and ZFS. The test logged no client

"setdq to for" or OST "isn't enforced on master" messages during

those writes.

Default quota behavior, MDT inode quota, and the cost of

reintegration with large quota indexes require further testing.

Proposed Fix

During global index reintegration, record the IDs returned by the

QMT. After a complete transfer at a consistent index version, compare

those IDs with the local global index copy and remove stale entries

that still carry a limit.

ID 0 and entries without a hard or soft limit are not removed.

Pruning is skipped if the transfer or ID collection cannot be used

safely.

The proposed fix is under further validation, particularly for default

quota behavior, concurrent changes, and large indexes.
