--- Comment (JIRAUSER19464, Fri, 14 Aug 2026 00:07:58 +0000) ---
adilger  the real reason for this failure is that

"The real reason for the failure is that in test-5, OBD_FAIL_FID_IGIF only suppressed LinkEA and FID-in-dirent, but still wrote the Normal FID into trusted.lma. Consequently, when LFSCK ran after the backup/restore reformat, it detected the existing trusted.lma and reconstructed the LinkEA and dirent using the Normal FID instead of upgrading the file to an IGIF FID. Because the file remained a Normal FID object and the MDT was started without OI scrub, the OI table lacked an entry for this Normal FID, causing subsequent FID-to-path lookups (lfs fid2path) to fail."

 

(The test occasionally passed previously because if the inode mapping happened to remain in OSD's in-memory OI cache (oti_cache), it bypassed the on-disk OI table check; once evicted from cache, subsequent lfs fid2path lookups failed with error 13).

So the patch suppress writing the FID to trusted.lma as well.  But after this fix, it failed with

The root cause in lfsck_prep 1 1 1 (analyze by gemini, and looks correct to me)

	When createmany -d $DIR/$tdir/d 1 creates directory d0, osd_create() creates the backend inode on disk without trusted.lma. However, the MDT still replies to the client with the Normal FID allocated for the mkdir RPC. The client VFS instantiates and caches the dentry "d0" bound to this Normal FID.

	Immediately on the next step, createmany -m $DIR/$tdir/d0/f 1 tries to create file f0 inside d0.

	The client VFS path walk traverses into d0 and issues an IT_LOOKUP "d0" RPC to the MDT.

	When the MDT looks up d0 on disk, it finds no trusted.lma, so osd_iget_fid() dynamically constructs an IGIF FID [0x0:ino_d0:gen_d0] and returns it in the lookup reply.

	The client receives the IGIF FID from the MDT, which collides with the cached dentry in client dcache (already bound to the Normal FID inode). This dentry alias mismatch causes the lookup to fail with -ENOENT (rc = -2).

To make MDT reply igif FID with this fail_loc will need some efforts.  So I wonder do we still support IGIF now? otherwise can we skip this test? It seems not worth the efforts.

[Claude] Root cause from the MDS debug log of https://testing.whamcloud.com/test_sets/305475fd-8a89-4831-beab-afa95d24396e (review-dne-part-2, el9.8, 2026-10-28). The same failure is on lustre-master full runs, e.g. https://testing.whamcloud.com/test_sets/42c3ccfc-dbff-440e-bd18-90e77cbdb2b6. Since mid-October Maloo auto-links these failures to the DDN-internal EX-14442, so new failures are not showing up on this ticket. It has failed about 5% of review-dne-part-2 runs and 11% of full-part-1 runs over the past 60 days.

The namespace LFSCK and the OI scrub that it starts (the MDT is mounted with noscrub after backup/restore) race on the inode that the scrub is currently processing:

626.310205 osd_scrub_main()) lustre-MDT0000: OI scrub start, flags = 0x4, pos = 12
626.313278 lfsck_master_oit_engine()) lustre-MDT0000-osd: OIT scan failed at find target [0x200005221:0x1:0x0], cookie 198: rc = -115
626.313283 lfsck_namespace_record_failure()) lustre-MDT0000-osd: namespace LFSCK hit first non-repaired inconsistency at the pos [198, ...]
626.313299 osd_scrub_check_update()) lustre-MDT0000: insert OI [0x200005221:0x1:0x0] -> 198/24953255
...
626.315113 osd_scrub_check_update()) lustre-MDT0000: insert OI [0x200005221:0x53:0x0] -> 256/3794704289

The LFSCK otable preload caches inode 198 ($tdir) and looks it up 21us before the scrub inserts its OI mapping. osd_fid_lookup() finds no OI entry while the scrub is running and returns -EINPROGRESS, so LFSCK skips the whole directory. $tdir/dummy never gets its linkEA, and "lfs fid2path" then fails with ENODATA ("(13) Fail to generate linkEA").

osd_preload_next() checks ooc_pos_preload >= os_pos_current before osd_iit_next() advances the preload position. As a result, a preload batch normally ends by caching the inode at exactly os_pos_current. osd_scrub_next() publishes os_pos_current before that inode has been through osd_scrub_check_update().

https://review.whamcloud.com/68662 ("LU-20505 lfsck: fix osd-scrub vs lfsck race") moves the os_pos_current store after osd_iit_iget(). The store is still before osd_scrub_exec()->osd_scrub_check_update(), which is where the OI mapping is inserted. That narrows the window but does not close it, as the Gerrit AI review on PS1 points out. Storing os_pos_current after osd_scrub_check_update() would close it. 68662 PS2 passes CI and still merges cleanly on master.

https://review.whamcloud.com/67474 (suppress LMA under OBD_FAIL_FID_IGIF) addresses a different theory (OI cache eviction). The log above does not need it.
