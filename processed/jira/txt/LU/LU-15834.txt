--- Description ---
When running "lfs mirror extend" to add a mirror to an existing file, it appears that the OST(s) used for the original layout are not taken into account, if OST pools or indices are not explicitly specified:

$ lfs getstripe /myth/tmp/flr
/myth/tmp/flr
lmm_stripe_count:  1
lmm_stripe_size:   1048576
lmm_pattern:       raid0
lmm_layout_gen:    0
lmm_stripe_offset: 1
	obdidx		 objid		 objid		 group
	     1	       2352362	     0x23e4ea	             0
$ lfs mirror extend -N -c 1 /myth/tmp/flr
$ lfs getstripe /myth/tmp/flr
/myth/tmp/flr
  lcm_layout_gen:    1
  lcm_mirror_count:  2
  lcm_entry_count:   2
    lcme_id:             65537
    lcme_mirror_id:      1
    lcme_flags:          init
    lcme_extent.e_start: 0
    lcme_extent.e_end:   EOF
      lmm_stripe_count:  1
      lmm_stripe_size:   1048576
      lmm_pattern:       raid0
      lmm_layout_gen:    0
      lmm_stripe_offset: 1
      lmm_objects:
      - 0: { l_ost_idx: 1, l_fid: [0x100010000:0x23e4ea:0x0] }

    lcme_id:             131073
    lcme_mirror_id:      2
    lcme_flags:          init
    lcme_extent.e_start: 0
    lcme_extent.e_end:   EOF
      lmm_stripe_count:  1
      lmm_stripe_size:   1048576
      lmm_pattern:       raid0
      lmm_layout_gen:    0
      lmm_stripe_offset: 1
      lmm_objects:
      - 0: { l_ost_idx: 1, l_fid: [0x100010000:0x23e4eb:0x0] }

in this case, both the original and mirror copy of the file are allocated on OST0001 because it has the most free space, which isn't helpful in terms of availability or performance for this file.

A previous patch https://review.whamcloud.com/32404 "LU-9007 lod: improve obj alloc for FLR file" added lod_should_avoid_ost() to handle new OST object allocations for different components of a single mirror, but does not appear to handle allocations across FLR mirrors.

Requirements for OST selection on components with overlapping extents should be, in order of decreasing priority:

	objects with overlapping components must not share the same OST.  Implies mirror_count .  In theory this could be relaxed if all replicas have the same stripe_count and stripe_size, then it would only require that the same OST cannot be at the same stripe_index of different components, in which case max replica count == OST count, but this is more difficult to control.

	objects with overlapping components should not share OSTs on the same OSS node (by NID from imp->imp_connection->c_peer.nid, as qos_add_tgt() does) to avoid the shared node failure domain.

	objects with overlapping components should not share OSTs on the same OSS failover pair (by failover NID from imp->imp_conn_list.oic_conn->c_peer.nid, as lprocfs_import_seq_show() does) to avoid the shared storage enclosure/controller failure domain.  There may be other OSS nodes that share the same storage enclosure/controller, but there isn't any way for the client to determine this automatically.

	objects with overlapping components should not be on OSTs on the same network switch, power supply, rack, etc. but this depends on external information that is not currently available to Lustre. That could optionally be added via a separate configuration file/options, but the above cases will automatically cover the most important failure scenarios

--- Comment (adilger, Wed, 21 Oct 2026 07:01:41 +0000) ---
Proposed design for "lfs mirror extend" placement, as an alternative to passing the source FID to the MDS as in https://review.whamcloud.com/50622 ("LU-15834 lfs: mirror extend take current OSTs into account").

Problem

"lfs mirror extend" (mirror_extend_layout() -> migrate_open_files()) allocates the new mirror in a separate volatile file that only has the new mirror's layout, copies the data, and merges it into the source with LL_LEASE_LAYOUT_MERGE. LOD never sees the source file's existing mirrors when it allocates the new objects, so none of the mirror separation applies: lod_collect_avoidance() OST/OSS avoidance, lod_fd_check_flr_allowed() failure domains, and (with the LU-8933/LU-9 RR allocator series) failure domain round-robin and mirror stream continuation. All of these are gated on ldo_mirror_count > 1 or iterate the components of the object being allocated. 50622 passes the source FID in lmm_objects[0].l_ost_oi of a component flagged LCME_FL_FOR_MERGE, and makes the allocator look up and parse the source file's layout under its ldo_layout_mutex. That is a side channel in the layout format, needs lock ordering between two objects during allocation, and would also need the failure domain checks extended separately.

Proposal: add the mirror in place as stale, then resync

Let the MDS add the new mirror to the source file itself without allocating objects, and let the existing FLR resync path instantiate it, so that allocation always sees every mirror of the file.

	Wire: a new XATTR_LUSTRE_LOV sub-operation, e.g. setxattr "lustre.lov.mirror" (name to be decided). lod_declare_layout_change() already dispatches "lustre.lov.add", ".del" and ".set.$field" by suffix, and an older MDS returns -ENOTSUPP for an unknown suffix, which tells the client to fall back to the current volatile file + merge. No connect flag is needed. The value is a lov_comp_md_v1 with only the new mirror's components, as "lfs mirror extend" builds today. It goes through the normal setxattr path: layout lock, layout generation, replay, and the same permission checks as setstripe on an existing file. ".add" is not reused because it is refused for FLR files (-EBUSY) and has different semantics.

	MDS (new lod_declare_layout_mirror()): convert a plain or non-FLR file to composite/FLR as lod_declare_layout_merge() does; assign a new mirror ID and component IDs and check lod_mirror_count_max (-ERANGE); add the new components uninstantiated with LCME_FL_STALE so the mirror is lme_stale; set the FLR state RDONLY/NONE -> SYNC_PENDING, WRITE_PENDING unchanged. No objects are allocated here.

	Allocation happens in the existing resync path: lod_prepare_resync() already instantiates every uninstantiated component of a stale mirror within the resync extent (and lod_prepare_resync_mirror() per mirror ID), through lod_qos_prep_create() on the source object with all mirrors present. All mirror separation then applies without new code, including the failure domain RR allocator once it lands.

	Client ("lfs mirror extend"): build the new mirror layout as today (including --inherit), apply it with the new operation, then unless --no-sync run llapi_mirror_resync_many() for the new mirror ID, which takes its own lease and copies only the needed extents. On -ENOTSUPP fall back to the volatile file + LL_LEASE_LAYOUT_MERGE. "-f victim_file" keeps using merge, since its objects already exist.

Behaviour

	An interrupted extend leaves a valid stale mirror, the same as "lfs mirror extend --no-sync" (LL_LEASE_ALLOW_STALE) today, which "lfs mirror resync" completes or "lfs mirror delete" removes. No orphan volatile file.

	Old clients have understood stale mirrors since FLR in 2.11.

	EC mirrors: parity components must be instantiated together with their data components in the resync path.

	The resync runs on the client and holds the resync lease for the copy, as "lfs mirror resync" does today.

The sanity-flr test from 50622 can be kept to check that the new mirror avoids the OSTs and OSSs of the existing mirrors.
