Description

When a client holds many PR extent locks on one object, cancelling them is       

quadratic in the number of locks. ldlm_extent_shift_kms() runs for every         

cancel, under lock_res_and_lock(), and walks every lock in the extent tree       

whenever no remaining lock protects the old KMS.                                 

                                                                                 

With 20000 adjacent one-page PR locks, cancelling them all takes about 5.6 s     

on average on test clients, and 0.19 s with the patch below (30x faster, see     

"Measurements"). The cost grows with the square of the lock count, so it         

gets much worse at the lock counts seen on shared files.                         

                                                                                 

The same problem was seen together with client evictions during shared-file      

IOR with unaligned records ("Observed in the field", below). The link to         

the evictions is likely, but it is not proven. This ticket is about the          

cancel cost, which is measured.

Analysis                                                                                                                                              

__osc_dlm_blocking_ast() calls ldlm_extent_shift_kms() for every cancel, under   

lock_res_and_lock(). When no remaining lock protects the old KMS, the            

function walks every lock in the extent tree. That is O(N) per cancel and        

O(N^2) for a burst of N cancels. Other threads that need the resource lock       

spin behind it.                                                                  

                                                                                 

The client cancels its unused locks from the newest to the oldest. Locks taken   

from low to high offsets are therefore cancelled highest first, which is the     

worst case.                                                                      

                                                                                 

Related tickets: LU-12832 and LU-12377 show the same symptoms. The               

"end + 1 >= old_kms" change discussed in LU-12832 is already in the tree         

(LU-13312), and the stacks below still show the scan. It is not LU-19721:        

the client build has no invalidate_lock code in llite or osc.   

Measurements

offset first, so the locks are cancelled highest first. The time is from         

"lru_size=clear" to lock_count reaching 0 on that client. One run per build.

Workaround (from LU-12832)

This shortens how long idle locks accumulate, at the cost of more lock RPCs      

and more re-reads. It does not remove the cost of cancelling many live           

locks at once.
