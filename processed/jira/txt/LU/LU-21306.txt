--- Description ---
In an encrypted directory, ll_prep_md_op_data() stores a kmalloc'd encoded name from ll_setup_filename() in op_data->op_name and sets MF_OPNAME_KMALLOCED, so that ll_finish_md_op_data() frees it.  Two places in LMV set op_data->op_name = NULL (and op_namelen = 0) before sending a by-FID request, and never put it back.  ll_finish_md_op_data() then does kfree(NULL) and the encoded name leaks:

	lmv_intent_lookup(), for MF_GETATTR_BY_FID: ll_inode_revalidate() sets this flag (with OBD_CONNECT2_GETATTR_PFID) for every revalidate of an inode whose dentry has a parent.  So every stat() or getattr RPC of a file in an encrypted directory, when no cached lock covers it, leaks 32 bytes.

	lmv_getattr_name(), when the MDT replies with OBD_MD_MDS (the entry is on another MDT) and LMV retries the getattr by FID.  This is reached through ll_lov_getstripe_ea_info() (IOC_MDC_GETFILESTRIPE / IOC_MDC_GETFILEINFO, used by lfs find/getstripe) and ll_get_fid_by_name() for a remote entry in an encrypted directory.

Reproduced on master v2_17_62 (rocky10 aarch64, 2 MDTs, 2 OSTs, booted with kmemleak=on), client mounted with -o test_dummy_encryption:

mkdir /mnt/lustre/enc                    # on MDT0
lfs mkdir -i 1 /mnt/lustre/enc/remote
touch /mnt/lustre/enc/file

# 100 x stat with locks dropped:        100 leaked objects
for i in $(seq 100); do
        lctl set_param -n ldlm.namespaces.*mdc*.lru_size=clear
        stat /mnt/lustre/enc/file > /dev/null
done

# 100 x ioctl(enc_fd, IOC_MDC_GETFILESTRIPE, "remote"): 100 leaked objects

The name buffer is allocated with kmalloc() and not OBD_ALLOC(), so the Lustre memory leak check at module unload does not catch it.  Only kmemleak shows it.

Fix: LMV should restore op_name/op_namelen before returning from these functions, so the caller can free the buffer.
