sanity-lnet test_238 failed with "Wanted 'up' lctl found 'down'" (check_route_aliveness, sanity-lnet.sh:4508, via config_routes and do_basic_rtr_test) on change 69960 patchset 3 (https://testing.whamcloud.com/test_sessions/970901dc-649b-460b-9350-2d4aa9cf77c8), review-ldiskfs, el8.10 x86_64, build 134634.

The route was reported down by lctl, lnetctl and debugfs for the whole 20 s window and went up about 0.5 s after the check gave up. Timeline from the dmesg of the client (onyx-158vm164) and router (onyx-158vm172), in dmesg seconds:

	15346.6: router runs "lnetctl set routing 1"; "Message forwarding will be enabled in 10s"

	15351 and 15355: client logs "Peer 10.240.24.117@tcp is being used as a gateway but routing feature is not turned on" (router discovery ping replies before forwarding was on)

	15357.1: router "Message forwarding enabled"

	15367.57: client "route to tcp1 through 10.240.24.117@tcp has gone from down to up"

	15368.4: test FAIL

check_route_aliveness waits 2 * (alive_router_check_interval + router_ping_timeout) = 20 s with the options the test loads (both 5). That budget is spent entirely by the router's 10 s forwarding start delay plus one check interval (5 s) plus one ping timeout (5 s), so any extra latency on a slow VM makes the test fail with no margin. The test's own comment says to wait 2x chk_intvl + timeout; it does not count the forwarding delay.

Not an LNet product failure: the route comes up correctly, only after the test stopped looking. Candidate fix is in the test: add the router forwarding delay (10 s) to max_wait in check_route_aliveness.
