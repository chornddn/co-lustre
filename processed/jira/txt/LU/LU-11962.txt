--- Description ---
The layout manipulations required to bring an FLR file in to sync (READONLY in FLR parlance) also give SOM while the file is in sync.  This is true SOM, with no caveats, able to be used for any purpose (as distinct from lazy SOM which can only be used by tools which are aware of it).

In essence, there is no reason the SOM portion has to be associated with a replica.  Exactly the same functionality can be used just for SOM.

Because the layout state transitions for FLR require synchronous writes to the MDS each time, and because a write to the file destroys the SOM state, this is too expensive to try to use all the time. Instead, the proposal is to set it on all files a certain amount of time after they have been modified (e.g. 24h).  If there are no writes to a file for a time, and the client is returning identical size+blocks in the LSOM state at close time, we take it through the layout transitions to mark it LCM_FL_RDONLY (does not make it not writeable, just indicates the attributes are not being modified), and then it has SOM.

This would be a fairly low effort way to allow all files except those being actively modified to have true SOM and improve performance for normal stat() and similar calls.

--- Comment (paf0186, Tue, 10 Dec 2024 23:14:03 +0000) ---
I've made a significant revision to my thinking on this.

Doing an FLR state transition has a few costs:

	MDT activity - synchronous write for layout transition (I believe, Andreas indicated he thinks otherwise, need to check code)

	OST writes to update layout generation

	Cache flushing on the client

The MDT sync/flush is serious if present, but may not exist.  However, the client side cache flushing is quite bad - In this case, it would prevent a workflow like

write(), close(), read()

from hitting cache, which is unacceptable.

However, this complete cache flush is unnecessary - It's required so we can't read stale data, but the possibility of reading stale data only comes up on some layout transitions.

In particular, it happens when a replica goes from READ_ONLY/IN_SYNC to out of sync/stale - for this transition, it's critical that cached data be flushed since it might be from a replica which could become stale.

But this is the only case where this is required.  It is not required if we are not staling a replica, so it's never required for the transition to "SYNC_PENDING", or "READ_ONLY", and is not required if the only thing we're making stale is the SOM.  That has no risk of stale data.

However, we must still update the layout everywhere as part of these transitions.  This means we need something like "blocking callback with layout payload".  If the layout is included, that would let us do a special type of lock conversion where we update the layout.

Having that feature would let us update the layout everywhere, doing a convert instead of cancel.  The conflict to cause the cancellation would be implemented as something like the server requesting a PR lock (or whatever the appropriate non-exclusive mode is), and considering all locks with older layout versions as conflicting.  This conflict would be resolved by the conversion and we'd have to update the layout version for those locks on the server as well.

This is useful, but a slightly tricky proposition which would take real work, so we want to verify this is worth the trouble.  I've got a patch here to test lazy-as-strict SOM, to see the best case improvement:

https://review.whamcloud.com/c/fs/lustre-release/+/57357

--- Comment (paf0186, Wed, 11 Dec 2024 04:56:44 +0000) ---
The issue isn't atomicity, it's the state protection required, it's basically the same as for FLR - For SOM to be reliably accurate in the face of MDS evicted clients, we have to prevent writes that the MDS doesn't know about.  If an MDS evicted client were able to do a write, now SOM is wrong.  So we'll do the same stuff as regular FLR.

So the SOM files are going to go through the same state transitions of RDONLY, WRITE_PENDING, and SYNC_PENDING, and have to update the OSTs with a new generation so writes are rejected.

--- Comment (adilger, Sat, 17 Oct 2026 22:54:12 +0000) ---
Design overview for strict SOM on regular (non-FLR) files; patches to follow.

Layout: a non-mirrored file becomes an FLR file by gaining one data-less "SOM mirror": a single foreign HSM component [0, EOF) with lfm_type = LU_FOREIGN_TYPE_POSIX and a new lhm_flags = HS_SOM, the same technique PCC-RO uses. Clients 2.15 and later already handle this layout unchanged: they honour RDONLY (layout write intent before writing), send layout versions as for any FLR file, and never read from a foreign mirror. A single-mirror RDONLY layout was rejected because existing clients refuse it (lov_init_composite() requires more than one mirror when the FLR state is not NONE). The cost is that lfs getstripe shows the extra foreign mirror.

Conversion reuses the FLR resync protocol, with no new RPC and no kernel client change:

	write lease with LL_LEASE_RESYNC, then MDS_REINT_RESYNC: on a NONE file the MDT adds the (stale) SOM mirror, sets SYNC_PENDING, increments the layout generation and pushes gen | LU_LAYOUT_RESYNC to the OST objects, in a sync transaction;

	fsync() and fstat() for current size and blocks;

	lease unlock with LL_LEASE_RESYNC_DONE and no data mirror IDs: RDONLY with SOM_FL_STRICT, so with mdt.*.enable_strict_som=1 the MDT returns size/blocks and the client skips the glimpse (existing code).

A later write moves the file to WRITE_PENDING and makes SOM stale, as for FLR; converting again makes it strict again. A new writer during the conversion breaks the lease (-EBUSY).

Trigger: explicit for now, via a new llapi_file_som_sync(fd) and lfs somsync --strict. Policy is left to the caller, e.g. "lfs find /mnt -type f -mtime +1 -N 0 | xargs lfs somsync --strict". lfs migrate properly converts a file that was RDONLY before the migration to have RDONLY SOM again. Refused with EOPNOTSUPP for DoM-only, released and foreign-layout files, files with real data mirrors (use lfs mirror resync), and when enable_strict_som=0. Automatic conversion of idle files at last close is a possible follow-up using the same MDT code.

Series (based on 2.17.59):

	flr: fix the handling of foreign mirrors (pre-existing bugs: client EC lsme_dstripe_count/cstripe_count in the union clobbered the HSM flags of foreign components; an HSM mirror could be picked as the write primary; lfs mirror split could leave only a foreign mirror; lfs getstripe -N output)

	flr: fix FLR and SOM state after a layout swap (strict SOM was kept after swap_layouts and the close-time swap of lfs migrate; stale ldo_flr_state after swapping in a plain layout)

	ofd: prepare layout version checks for fencing (fallocate verifies the layout version; a client's version sets an object's first layout version only with LU_LAYOUT_RESYNC; a split to a non-FLR file pushes a plain version)

	lod: prepare for a SOM mirror in FLR files (lod_layout_add_hsm_mirror() factored out of PCC-RO, HS_SOM, RESYNC_DONE and llapi resync handling, PCC-RO ignores the SOM mirror)

	flr: add strict SOM for non-mirrored files (the conversion, llapi/lfs, man pages, sanity-flr test_44h)

Patches 1-4 are low risk and useful without the feature.

No connect flag is needed: 2.15+ clients handle the layout unchanged, and MDS and OSS versions are normally kept in step.

Known limitation: the same gap as FLR today. A client evicted by the MDT but not by the OSTs, holding the pre-conversion layout, sends no layout version (clients send one only for FLR files) and its writes are not refused, so it can change the size behind strict SOM; the OST version push is also asynchronous (OSP sync llog). The plan for full fencing, gated on OBD_CONNECT_SOM (unused since 2.7 and kept for the complete feature rather than this partial step): OSTs advertise it, clients then send a layout version with every modifying RPC for all files, an OST tunable (default off) refuses unversioned modifications to an object in a closed write era, and a SOM-only file keeps its era closed while RDONLY. Patch 3 prepares the OST side for this.
