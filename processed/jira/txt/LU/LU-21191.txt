--- Description ---
sanity-sec test_21 (mapped_trusted_noadmin) fails intermittently with

"cannot chmod mapped_trusted_noadmin:60000:c0:0:003" on code that already

contains the LU-19157 fixes (change 69458, "do not apply ban list on the

MGS", merged 2026-11-06). Failures continue after the merge: two

lustre-master-next sessions on 2026-11-09 (full-dne-ipv6-part-2) and four

review sessions on 2026-11-11 (review-dne-selinux-ssk-part-2), from

unrelated changes (patchsets 6, 12, 12 and 68627 ps19). Before the merge

the same error was linked to LU-19157 (15 failures, first seen 2026-09-30).

Rate on review runs is about 0.3% for the SSK group.

Failed subtest: https://testing.whamcloud.com/sub_tests/24359028-a659-45d4-9f42-36358f8a4c13

Session: https://testing.whamcloud.com/test_sessions/c8963db7-1a9f-448f-9628-3a01b1b4705d

What the log shows: after nodemap_modify c0 admin=1 trusted=1 (synced on

MGS and servers), the root client of c0 gets EPERM from

"lfs setdirstripe -c 1 -i 1 /mnt/lustre/d21.sanity-sec" (MDT0001), so the

later chmod finds no directory. The remote MDTs (MDT0001, MDT0003) log

repeatedly during the test:

  nm_member_reclassify_nodemap() lustre-MDT0001: not reclassifying

  10.240.46.53@tcp to nodemap c0, inconsistent with nodemap default used

  in authentication: rc = -1

so the client export stays on the default nodemap (admin=0, root

squashed) instead of c0. No ban message is logged, so this is not the

banlist path 69458 fixed; it looks like the export keeps the nodemap it

authenticated with (SSK, from LU-19079 gss_id handling) across nodemap

property/membership changes. LU-19157 itself (revoke export locks on

nodemap change) was suspected of the original test_21 regression by

Andreas on 2025-09-28.

The patch under test on this run (LU-20689, llapi size units) does not

touch nodemap code.
