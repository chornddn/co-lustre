--- Description ---
On kernels built with CONFIG_FORTIFY_SOURCE=y (all EL10 kernels), creating a file with a long name on an ldiskfs MDT triggers a kernel WARNING in ldiskfs_set_dirdata():

Cause

ext4_set_dirdata() (ext4-dirdata-core.patch) writes the LUFID record after the filename through de->name[]:

int data_offset = de->name_len + 1;
if (data) {
	de->name[de->name_len] = 0;
	memcpy(&de->name[de->name_len + 1], data, *(char *)data);   /* namei.c:1720 */
	de->file_type |= EXT4_DIRENT_LUFID;
	...

de->name is declared char name[EXT4_NAME_LEN] (255 bytes) and the LUFID record is 17 bytes. For names of 238 bytes or longer the copy runs past the declared array, and FORTIFY_SOURCE reports a field-spanning write. The bytes are still inside the directory record (rec_len reserves the space), so no memory is corrupted, but every EL10 MDS logs a WARNING the first time a client creates such a name, and a server running with panic_on_warn panics.

Reproducer

Plain long names are enough; encryption is not needed. Single-node ltvm VM, rocky10, kernel 6.12.0-124.56.1.el10_1_lustre, Lustre master b5131ea46c:

mkdir /mnt/lustre/d
for n in $(seq 200 255); do touch /mnt/lustre/d/$(printf 'a%.0s' $(seq 1 $n)); done
dmesg | grep field-spanning

The first name to warn is 238 bytes long (255 - 238 - 1 = 16 bytes left in name[] for the 17-byte record). It was first seen in sanity-sec test_46 (long ciphertext names) and is hit by any client create with a name of 238+ bytes.

Affected

ldiskfs/kernel_patches/patches/

{rhel10.0,rhel10.1,linux-6.12,linux-6.18,linux-7.0}
/ext4-dirdata-core.patch, used by the ldiskfs-6.12-rhel10.0, 6.12-rhel10.1, 6.12-rhel10.2, 6.12-ml, 6.18-ml, 7.0-ml and 7.0.0-14-ubuntu26 series.

Fix

Address the dirdata area from the start of the name instead of through de->name[], so the write is not bounded by the declared array size. The on-disk format and the bytes written are unchanged. A patch follows.

Tested with the fix on the same VM: no warning for names of 200-255 bytes, a 255-byte directory and a rename to a 255-byte name; LFSCK namespace makes no repairs and e2fsck -fn on the MDT is clean. Lustre builds cleanly for rhel10.0, rhel10.1, rhel10.2 and ubuntu26; on mainline 6.12.95, 6.18.22 and 7.0 ldiskfs compiles with the fix (the full build there fails at modpost on obd_dif_ip_fn/obd_dif_crc_fn in osd_ldiskfs.ko, which unfixed master hits too).
