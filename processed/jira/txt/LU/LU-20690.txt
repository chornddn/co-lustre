--- Description ---
EC layouts today require k >= p. This is not a Cauchy/ISA-L limit,

it comes from storing parity as RAID0|PARITY, where the p

parity objects of a raidset are concatenated along the file offset.

The parity component then needs 

stripeset_count * raidset_count * p * stripe_size of

extent, which no longer fits a finite PFL extent once p > k (for

example --ec 2+3 -E 2M).

Lifting the restriction is useful for small components that should

survive a 2-OST failure. The first component of a PFL file is only a

few stripes but covers most files, and --ec 1+2 (LU-20568) or

--ec 2+3 are exactly the layouts a k >= p rule forbids.

As suggested in LU-20568, this can be handled by giving the parity

component its own layout pattern rather than reusing RAID-0. Storing

parity as LOV_PATTERN_PARITY makes the component RAID-10 shaped:

the raidsets of one stripe set are striped like RAID-0, one

stripe_size each, while inside a raidset the p parity stripes

share a single file offset like RAID-1. The parity component then

always fits the extent of the data component, for any k and p.

Unlike RAID-1 the parity stripes are not replicas, so the client must

not fan a write out to all of them: resync and verify address one

parity stripe at a time, while punch and truncate still apply to every

parity object.

EC has not shipped, so the old RAID0|PARITY encoding does not need

to be kept. The p  checks in lfs and llapi can be

dropped, with k+p  and p  remaining.

--- Comment (adilger, Tue, 27 Oct 2026 03:08:32 +0000) ---
Landing order: patch https://review.whamcloud.com/69703 (" k" class="issue-link" data-issue-key="LU-20690">LU-20690 ec: verify parity against data, allow p > k") needs to land after patch https://review.whamcloud.com/69493 ("LU-19823 lod: unique failure domains per EC raid set").

With p > k and more than one raid set, lod_ost_alloc_rr() on master can return success with a short parity component when lod_ec_add_parities() cannot fill it, because stripe_count_min is 0 for parity.  For example "lfs setstripe -c 4 --ec 2+3" on 5 OSTs without failure domains stores 5 parity stripes instead of 6, so raid set 1 has no parity, and the new parity check in lod_verify_striping() then rejects that layout on open replay.  Before 69703 llapi refused such layouts, so this was not reachable.  69493 makes lod_ost_alloc_rr() return -ENOSPC when a parity component gets fewer than all of its stripes, as lod_ost_alloc_qos() already does.

--- Comment (adilger, Tue, 27 Oct 2026 03:43:23 +0000) ---
Patch https://review.whamcloud.com/64086 ("LU-20958 lov: handle unavailable EC stripes in lseek") needs to be updated for the new parity layout and offset calculation in this series before it can land with it:

	patch https://review.whamcloud.com/68361 (" k" class="issue-link" data-issue-key="LU-20690">LU-20690 ec: like-RAID10 parity layout") replaces RAID0|PARITY with LOV_PATTERN_PARITY, where the p parity objects of a raid set share one offset (one stripe_size per raid set per row).  64086 only handles RAID0|PARITY and returns -EOPNOTSUPP otherwise, so its parity SEEK_DATA/SEEK_HOLE path would never run, and its parity offset uses the old concatenated layout.

	the raid set row and index must be computed from the absolute data offset (row = off / (stripe_count * stripe_size), unit = (off / stripe_size) % stripe_count) rather than from offset - e_start, as described in the 68361 review, so that each raid set's parity covers the objects LOD allocated to that raid set when e_start is not a multiple of the stripe width.  64086 needs the same mapping, ideally via the shared helper in 68361.

The same applies to the parity offset in patch https://review.whamcloud.com/64919 ("LU-12669 lov: slow and dead OST detection for degraded reads").
