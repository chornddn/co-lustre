--- Description ---
Summary

Let an administrator stop a client writes, and drain existing write-back caches to the servers, without unmounting or evicting the clients. Do it by refusing and recalling write locks on a target.

The lock protocol already guarantees that a client may cache writes only under a write lock, and it flushes its dirty pages before it cancels a lock. A server that refuses write locks to a client and recalls the ones the client holds therefore drains that client’s write cache through stock client code paths, with no client change.

Questions

	Is a server-enforced client write stop and drain acceptable/desirable in Lustre? Would it be a namespace tunable, or a nodemap/export property (e.g. a nodemap readonly-style flag that drains instead of failing writes)? (I lean towards a namespace tunable)

	Is refusing with -EINPROGRESS the right client-visible behaviour, compared with, say, a dedicated error or a grant-based mechanism?

	GROUP locks are counted but can’t be recalled. Is there an accepted way for an administrator to break them?

	Would a generic lock_counts view (per-export lock and callback state) be welcome on its own? It overlaps with the LU-19157 nodemap revoke work in ldlm_revoke_export_locks().
