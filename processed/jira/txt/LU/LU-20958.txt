--- Description ---
lseek(fd, off, SEEK_DATA) and SEEK_HOLE on an EC file in RDONLY state with a data stripe on an unavailable (unmounted, failing over) OST block in ll_lseek() (CIT_LSEEK) until the OST returns, even though reads of the same file are rebuilt from parity without delay.  See the LU-20212 test results.

osc_lock_enqueue 

64086 (LU-12668) handles an OST that is deactivated (-ESHUTDOWN) but not one that is down and still active, which waits in the enqueue.

Reporting the whole extent of an unavailable stripe as data is always correct for SEEK_DATA/SEEK_HOLE, so the lseek could use a no-delay enqueue and treat an unavailable stripe that way (or use the parity stripes' extents) instead of waiting for the OST.

--- Comment (adilger, Fri, 16 Oct 2026 01:02:25 +0000) ---
Thinking about this further, we could infer the approximate offset of holes in a missing object from holes in the EC parity stripes, since the parity will also be sparse if all of the data stripes for a row are holes. That would put a bound on the start/end of holes for missing objects to be within k * stripe_size or so. That could potentially make a huge difference for large sparse files since at most a few extra MiB would be copied per hole. It might be enough to do SEEK_HOLE and SEEK_DATA on the sparse EC parity stripes, then align the offsets up or down (depending on data or hole) to the start of the raidset row.
