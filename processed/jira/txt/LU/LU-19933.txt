--- Comment (adilger, Mon, 26 Oct 2026 23:24:24 +0000) ---
[Claude] Root cause is in the test, not MDT naming. The changelog GC thread only starts on an MDT when a changelog record is written there while fail_loc 0x1316 is set (mdd_changelog_store() -> mdd_changelog_need_gc()). test_160h writes those records with "createmany -m ${tfile}bis $((MDSCOUNT*2))" in a directory striped "-c $MDSCOUNT -H all_char". The all_char hash is the sum of the name bytes modulo the stripe count, so the names f160h.sanitybis0..N never hash to some stripes.

In https://testing.whamcloud.com/test_sets/ca00dda0-f6b3-4013-ba00-21fc68b7549a the directory is "-i4 -c12 -H all_char": no name lands on stripe 4 (MDT0008 = mds9), so mds9 never starts a GC thread and cl11 stays registered ("force deregister of changelog user cl11" appears on the other MDDs, nothing on MDT0008). By the same calculation, 8 MDTs are fully covered, while 16 MDTs miss 4 stripes, 24 miss 11 and 40 miss 15.

Suggested fix: write one record per MDT explicitly (e.g. a file in an "lfs mkdir -i $idx" subdirectory per MDT) rather than relying on hash coverage. With 48 MDTs, a separate "mds17: User cl10 not registered" failure occurs because the per-MDT check loop runs longer than changelog_max_idle_time=10, so the idle time should also scale with MDSCOUNT.
