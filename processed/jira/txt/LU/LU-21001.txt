--- Description ---
With the current mkdir QoS policy, once the directory level is deeper

than RR_MAX (max_inherit_rr), new subdirectories are created on the

parent MDT unless the MDTs' space/inode usage is very unbalanced. So a

busy MDT keeps getting new directories, and all the files later

created under them.

 

This ticket proposes to also consider MDT load during mkdir:

 

1. Round-robin (within RR_MAX) and space-imbalance placement are kept

as they are. If they choose the MDT, load is ignored.

 

2. Otherwise the new directory would stay on its parent MDT. The

client first checks whether the parent MDT is busy, using the

service time estimate the MDT already sends in every reply. If it

is clearly slower than the other MDTs (lmv.*.qos_load_threshold,

default 3 seconds), the directory goes to another MDT, preferring

less busy ones.

 

3. The MDS can also refuse a mkdir when it is overloaded (all service

threads busy and requests waiting longer than

mdt.*.mkdir_redirect_qwait_ms, disabled by default). The client

then creates the directory on an MDT on another server and avoids

the busy server for a few seconds. A mkdir is moved at most once,

and is never moved if there is no other server to go to.

 

MDTs on the same server share its load, so directories are only moved

between servers.

--- Comment (JIRAUSER24000, Wed, 21 Oct 2026 18:17:50 +0000) ---
>How can this sensibly affect directory removal performance? The client can't chose which MDT to remove a directory from? 

In the current implementation, rr_max/mkdir seems to be the only way to automatically distribute the namespace/load across multiple MDTs.  However once the directory depth reaches rr_max,  the metadata load within each subtree will be limited to a single MDT.

Setting rr_max to -1 to distribute new directories at all levels is not practical for us because of the overhead of cross-MDT operations (btw: mkdir/rmdir is not rare case during RL training, especially when those codes are generated by AI itself). So I wonder whether this proposal could help mitigate the issue. We could also migrate directories to other MDTs afterward, although I assume that would incur even greater overhead.

What are your thoughts on the long-term plan? Optimizing cross-MDT operations is the most feasible solution? or are there other approaches worth considering? Thanks! adilger

--- Comment (adilger, Thu, 22 Oct 2026 00:37:03 +0000) ---
I'm definitely in favor of better dynamic MDT selection, and this seems fairly reasonable.  I think that LU-7880 could help here, in addition to the local latency.  I'm not sure if the client(s) should make totally unilateral decisions, because it might get into a cycle where MDT1 is busy, so clients all move to MDT2 (which becomes busy), then move to MDT3...  There would need to be some kind of natural distribution (I've been using the client NID) so that the clients do not move in lockstep when making global decisions.

Please see https://review.whamcloud.com/69427 for a reworked client LMV MDT weighted RR allocator.  I'd prefer that new changes to the LMV allocator not conflict with that code, but would be happy to include a performance/latency weighting into the WRR algorithm.
