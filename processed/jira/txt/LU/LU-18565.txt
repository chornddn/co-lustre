--- Comment (JIRAUSER24100, Mon, 23 Nov 2026 11:09:30 +0000) ---
Fixed on master by LU-20342 https://review.whamcloud.com/66535 (commit d72c2d3f91 "lnet: fix deadlocks during module unload", landed 2026-08, first in 2.17.58).

The timeouts linked here are lnet_selftest teardown hangs after the routed lst runs in test_220. In the latest one (https://testing.whamcloud.com/test_sets/164062ff-c12a-4a98-ab68-5cc27da74876, 2026-03-31, change 65003) a kworker is stuck in sfw_destroy_session -> sfw_destroy_test_instance -> cancel_work_sync -> flush_work, and rmmod is stuck in sfw_shutdown waiting for that zombie session. Before LU-20342, sfw_test_unit_done() destroyed the session synchronously from inside a client RPC work handler. Destroying the session cancels that same RPC work item with cancel_work_sync(), so the work item waited for itself to finish. LU-20342 hands session destruction to a separate reaper work item.

All 9 linked failures (2024-12 to 2026-03) ran on bases older than that fix. The only later test_220 timeouts are b2_15 code in full-part-1 (2026-06) and an Autotest fault on change 67173 (2026-10-16, LU-20973), not this hang. On current master (2.17.62), sanity-lnet test_220 with ONLY_REPEAT=10 passed 10/10 on a rocky9 cluster with one router and one remote peer. CI hit this hang about once in 2000 runs, so those passes back up the code analysis but do not prove the fix by themselves. A branch without d72c2d3f91 (b2_15, for example) can still hit this hang. Reopen if it shows up on a base that includes the fix.
