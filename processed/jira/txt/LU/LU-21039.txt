--- Description ---
Problem

	
	

When `kiblnd_reply()` cannot set up the source of an optimized GET, it sends nothing to the peer. The peer that sent the GET_REQ waits for the full RDMA timeout. Then `kiblnd_check_conns()` closes the whole connection. The close also fails every other transfer in flight on that connection.

The o2iblnd protocol can already fail a GET at once. When a GET_REQ matches no MD, `kiblnd_recv()` sends a GET_DONE with status `-ENODATA`. The error paths in `kiblnd_reply()` do not send this message.

	
	
		Environment

	
	

	Seen on b_es6_0. The same code is on master.

	Client: InfiniBand on ConnectX-7, `map_on_demand=1` (FastReg), AMD IOMMU in translated mode.

	Workload: OST_WRITE from a client. The OSS sends a GET_REQ for the bulk, and the client is the GET source.

	
	
		Evidence

	
	

The client could not map one 1045059-byte bulk buffer. Each resend of the same OST_WRITE failed the same way for more than 24 hours:

```

(o2iblnd.c:1922:kiblnd_fmr_pool_map()) Failed to map mr 0/1 elements

(o2iblnd_cb.c:631:kiblnd_fmr_map_tx()) Can't map 1045059 bytes (256/1)s: -22

(o2iblnd_cb.c:1871:kiblnd_reply()) Can't setup GET src for 10.50.25.30@o2ib: -22

(events.c:215:client_bulk_callback()) event type 1, status -5, desc 00000000e816b250

```

The OSS did not see an error from the client. It waited for the RDMA timeout, closed the connection, and failed the bulk:

```

LNetError: (o2iblnd_cb.c:3590:kiblnd_check_conns()) Timed out RDMA with 10.50.25.109@o2ib (8): c: 31, oc: 0, rc: 31

Lustre: ...-OST0002: Bulk IO write error with ... (at 10.50.25.109@o2ib), client will retry: rc = -110

```

The OSS logged 140 bulk errors of this type for the client. Each one cost a full RDMA timeout and a connection close.

We do not know the root cause of the map failure yet. The fault is below LNet, in the RDMA memory registration or the IOMMU mapping. This ticket does not cover that root cause. A NAK does not make the transfer succeed. It makes the failure fast, and it keeps the connection open for other traffic.

	
	
		Proposed fix

	
	

In `kiblnd_reply()`, when `kiblnd_setup_rd_kiov()` or `kiblnd_init_rdma()` fails, send a GET_DONE with the error status to the peer:

```

kiblnd_send_completion(rx->rx_conn, IBLND_MSG_GET_DONE, rc,

		       rx->rx_msg->ibm_u.get.ibgm_cookie);

```

The peer then completes the GET_REQ in `kiblnd_handle_completion()` with that status. It does not wait for the RDMA timeout or close the connection.

The "Can't get tx for REPLY" path cannot send a NAK in the same way. `kiblnd_send_completion()` also needs an idle tx. That path can stay as it is.
