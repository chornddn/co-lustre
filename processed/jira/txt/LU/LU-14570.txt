--- Description ---
Running e2fsck on a DNE filesystem where LFSCK was run reported:

Entry '..' in / (195395122) has an incorrect filetype (was 18, should be 1).
Entry '..' in / (602879869) has an incorrect filetype (was 18, should be 1).
Entry '..' in / (134818059) has an incorrect filetype (was 18, should be 1).
Entry '..' in / (134818064) has an incorrect filetype (was 18, should be 1).
Entry '..' in / (134818066) has an incorrect filetype (was 18, should be 1).

This is because the entry file_type has a flag EXT2_DIRENT_LUFID when the dirdata feature stores the FID in the directory entry, and it should be masked when checking the file type.

--- Comment (laisiyao, Thu, 5 Nov 2026 05:08:22 +0000) ---
Another real-world occurrence, with the same signature and a consequence worth flagging.

Environment: EXAScaler/Lustre 2.14.0_ddn209 (DNE, dirdata enabled), e2fsprogs 1.47.3-wc3, on an MDT that was checked offline.

Entry 'reconv_cut.hpp' in /REMOTE_PARENT_DIR/0x340013da8:0x1febe:0x0/mockturtle/algorithms (1252962143) has an incorrect filetype (was 17, should be 2).
Entry 'gates_to_nodes.hpp' in /REMOTE_PARENT_DIR/.../mockturtle/algorithms (1252962143) has deleted/unused inode 1252962256 fid=[0x340013da8:0x1ff59:0x0].
'..' in /REMOTE_PARENT_DIR/.../mockturtle/algorithms/reconv_cut.hpp (1252962204) is /REMOTE_PARENT_DIR (540801025), should be /REMOTE_PARENT_DIR/0x340013da8:0x1febe:0x0/mockturtle/algorithms (1252962143).

(filetype 17 = LUFID|FT_REG_FILE, 18 = LUFID|FT_DIR.)

Two observations beyond the original report:

	It is not confined to one target - the "incorrect filetype" findings appear on all 12 MDTs of the filesystem, at a low but non-zero rate (8-122 per MDT). So whatever produces it is a general DNE condition, not a one-off.

	The badness heuristic then deletes the affected directory. With the default inode_badness_threshold=7, the accumulated findings on inode 1252962143 reached 22 and e2fsck answered "Clear? yes" to "Inode 1252962143 is badly corrupt (badness value = 22)", deleting a live directory; it then cascaded into clearing the '..' entries of that directory's subdirectories. A subsequent e2fsck -y run re-created and re-linked the inode (it reported "Inode 1252962143 is in use, but has dtime set.  Fix? yes" and "Inode bitmap differences: +1252962143"), so repeated repair runs contradict each other and churn the namespace rather than converging. A read-only pass after the second repair still reported "WARNING: Filesystem still has errors".

Also seen alongside on the same subtree:

	Unconnected directory inode N (/REMOTE_PARENT_DIR/...) -> Connect to /lost+found? yes (cf. LU-15383)

	Inode N ref count is X, should be Y (cf. LU-11446)

Since this is reproducible via rename stress without LFSCK (per the earlier comment), it would be worth documenting that running e2fsck -y on an affected DNE MDT is unsafe with the default badness threshold, and that -E inode_badness_threshold= is needed to avoid deleting live directories until this is fixed.

--- Comment (dongyang, Thu, 5 Nov 2026 05:46:04 +0000) ---
static _INLINE_ int check_filetype(e2fsck_t ctx,
                                   struct ext2_dir_entry *dirent,
                                   ext2_ino_t dir_ino EXT2FS_ATTR((unused)),
                                   struct problem_context *pctx)
{
        int     filetype = ext2fs_dirent_file_type(dirent);
        int     should_be = EXT2_FT_UNKNOWN;
        __u16   badness = 0;
        struct ext2_inode       inode;
        __u8    dirdata = 0;

        if (ext2fs_has_feature_dirdata(ctx->fs->super)) {
                dirdata = filetype & ~EXT2_FT_MASK;
                filetype = filetype & EXT2_FT_MASK;
        }

        if (!ext2fs_has_feature_filetype(ctx->fs->super)) {
                if (filetype == 0 ||
                    !fix_problem(ctx, PR_2_CLEAR_FILETYPE, pctx))
                        return 0;
                ext2fs_dirent_set_file_type(dirent, EXT2_FT_UNKNOWN);
                return 1;
        }

        if (ctx->inode_badness) 
                ext2fs_icount_fetch(ctx->inode_badness, dirent->inode,
                                    &badness);

        if (ext2fs_test_inode_bitmap2(ctx->inode_dir_map, dirent->inode)) {
                should_be = EXT2_FT_DIR;
        } else if (ext2fs_test_inode_bitmap2(ctx->inode_reg_map,
                                            dirent->inode)) {
                should_be = EXT2_FT_REG_FILE;
        } else {
                e2fsck_read_inode(ctx, dirent->inode, &inode,
                                  "check_filetype");
                should_be = ext2_file_type(inode.i_mode);
        }
        if (filetype == should_be)
                return 0;
        pctx->num = should_be;

        if (fix_problem(ctx, filetype ? PR_2_BAD_FILETYPE : PR_2_SET_FILETYPE,
                        pctx) == 0)
                return 0;
        ext2fs_dirent_set_file_type(dirent, should_be | dirdata);
        return 1;
}

we mask EXT2_DIRENT_LUFID when checking the filetype from dirent,

and it's added back when we need to fix filetype.

I think the message could be improved like "was 17, should be 18" as 18 is the value actually written.

The default inode badness threshold is 12.
