sanity-hsm test_106c (MDS version v2_16_58-105 and later) evicts the copytool agent client from every MDT with mdt..evict_client and immediately checks that the agent uuid is gone from mdt..hsm.agents. On mds1 the uuid was still listed: "uuid found in agent list on mds1: uuid=8bd9717d-6b76-4db0-9f61-8ddc0651f3a2 archive_id=ANY requests=[current:0 ok:0 errors:0]" (check_agent_unregistered_by_mdt, sanity-hsm.sh:485, 4 MDT / 2 MDS config, el9.7 x86_64 ldiskfs).

Same signature seen before on another change: 59251 on 2025-10-07 (two failures, mds2). Rate is about 1 in 4500 suite runs. Not related to change 71187 (OFD DIO commit ordering): no HSM or MDT code is touched by that series.

The agent is removed from the list by mdt_hsm_agent_unregister() in the export disconnect path (mdt_handler.c), which runs when the evicted export is torn down, after evict_client returns. The test has no wait between the eviction and the check, so it may be a race between export teardown and the check; waiting on the agent list in the test may be the fix, but this has not been confirmed.

--- Comment (JIRAUSER24100, Sun, 22 Nov 2026 14:18:05 +0000) ---
Cause found for the failures on https://review.whamcloud.com/71187: test_106c runs against a 2.17.0 (b2_17) MDS in the Test-Parameters session "testlist=sanity-hsm serverversion=2.17.0". The test gates on MDS1_VERSION >= v2_16_58-105, which 2.17.0 satisfies, but the fix it tests (LU-18238 "mdt: ghost hsm fix", unregister the HSM agent in mdt_export_cleanup, commit 9a3b9236a9) landed on master in March 2026 ("Merged for 2.18") and is not in b2_17: b2_17 has no mdt_hsm_agent_unregister call in mdt_handler.c. So the agent is still registered after eviction, deterministically. master runs: 0 failures in about 4500 suite runs; the failing runs are the interop session (2 of 2 on change 71187: sessions 07aa3f2c and b7450ac4).

Fix is in the test: raise the version gate to the release that has LU-18238 (v2_17_52 or later), or skip for older servers.
