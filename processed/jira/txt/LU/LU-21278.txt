--- Environment ---
aarch64 clients (AL2023 6.18, RHEL 10); combined MGS/MDT0000

--- Description ---
After the MGS restarts, a client's MGC import can still report FULL while holding a stale connection handle. Nothing sends an MGC RPC in between, and the MGC pinger is suppressed while imperative recovery is in use. The next MGC RPC is the config log ldlm_enqueue for a new mount, which fails with -ENOTCONN, and the client is evicted. mgc_process_log() only retries that enqueue on -ESHUTDOWN. It falls back to the local config copy instead, which on a client-only build has nothing to parse but still returns 0. The LMV device is never set up, and the mount fails with a misleading -EINVAL:

mount.lustre: mount @tcp:/ at /mnt/lustre2 failed: Invalid argument

LustreError: 11-0: MGC@tcp: operation ldlm_enqueue to node @tcp failed: rc = -107

Lustre: Evicted from MGS (at @tcp) after server handle changed

LustreError: (llite_lib.c:304:client_common_fill_super()) MD clilmv: not setup or attached

LustreError: (super25.c:178:lustre_fill_super()) llite: Unable to mount : rc = -22

sanity test_160j reproduces this: its mount_client $MOUNT2 comes after the MDS restarts in 160a and 160h. It failed 7 of 15 runs on aarch64 clients; x86_64 passes. A user can hit the same thing mounting a second mount point after an MGS restart.

Proposed fix: also retry the config log enqueue on -ENOTCONN, once the import has reconnected.
