--- Description ---
Problem

A file that has been deleted into the Trash Can can be hard-linked back into the normal namespace:

 mkdir /mnt/lustre/d; echo x > /mnt/lustre/d/f; rm /mnt/lustre/d/fln /mnt/lustre/d/.Trash/f /mnt/lustre/d/x      # succeeds

The object now has a live namespace name, but it still carries LUSTRE_UNRM_FL, the trusted.unrm xattr and the trash uid/gid/projid. As a result:

	it bypasses lfs trash unrm, so the original owner and ids are never restored and quota stays charged to the trash projid;

	the object is still listed in .Trash, so ltrash_purge or lfs trash clean will unlink the trash name while the namespace link survives. That leaves a file with the UNRM flag and trash ownership in the namespace;

	depending on directory permissions, a user other than the owner can create the link. This is related to the authorization gap in EX-16344.

Expected

link(2) with a source inside .Trash or .lustre/.ltrash, or a source with LUSTRE_UNRM_FL, should fail with EPERM or EXDEV. The MDT should enforce this in mdt_reint_link / mdd_link_sanity_check, not only the client.
