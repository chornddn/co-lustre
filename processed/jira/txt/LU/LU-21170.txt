--- Description ---
sanity-lnet test_156 (import of ip2nets with comma-separated IP ranges) compares a full "lnetctl export --backup" taken after add_net (expected) with an export after reinit_dlc and import (actual). It failed once on lustre-reviews review-ldiskfs-arm (aarch64) with "test_156 failed with 1":

https://testing.whamcloud.com/test_sets/2806adaa-db64-465b-a375-4c011d0987aa

The expected export contains a peer that the actual export lacks:

  peer:

	primary nid: 10.240.29.33@tcp

        Multi-Rail: true

        peer ni:

	nid: 10.240.29.33@tcp

The node under test is 10.240.29.35 and the import file lists only 10.240.29.[37,39,35,41,43], so a peer for .33 is not configured by the test. It was learned (a message or discovery from another node of the cluster) in the window between add_net and the expected export, and it cannot reappear after reinit_dlc. The comparison is therefore racy when any other node sends to the test node at that point. The diff is only in the peer section; net and global sections are identical.

Rate: about 1 in 6900 runs on review-ldiskfs-arm over 400 days (no other failure of this type found; the other test_156 failures in that period are module-unload, rc = 234 and network-loss errors). It was seen on change 70374 (lnet response tracker patch), which does not create peers; the other 3 runs of the group on that change and 1511 other review runs in 30 days passed.

Possible fix: have the test export only the net and global sections, or filter out peers not created by the test, or run "lnetctl peer del" / disable discovery before taking the expected export.
