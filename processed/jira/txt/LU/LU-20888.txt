--- Description ---
When an MDT restarts while a peer MDT (MDT0000) is serving lookups for objects that live on the restarting MDT, MDT0000's regular mdt service threads all block in osp_remote_sync waiting on the restarting MDT. The restarting MDT's recovery then needs MDT0000 to accept its LWP MDS_CONNECT. That connect arrives with no export, so it is a normal-priority request, and the pool will not give it one of the threads reserved for high-priority work. It never gets serviced, the LWP never reaches FULL, FLD lookups can never be sent, and recovery waits forever.

--- Comment (aboyko, Mon, 26 Oct 2026 09:50:34 +0000) ---
We saw a similar problem during recovery. A clients connection should be high priority too, not only LWP. I've pushed a common solution for connections. 

Summary

On an MDS hosting several DNE targets, a failover can produce a self-sustaining

deadlock between the ptlrpc service threads and target recovery:

	mdt service threads block inside rename/getattr handlers waiting on

cross-MDT OSP RPCs to a target that is itself still in recovery;

	a recovering target cannot answer MDS_CONNECT because every thread in the

affected CPT partition is blocked;

	the target therefore never completes recovery, so the blocked threads are

never released.

The cycle breaks only when the recovery soft timer expires and evicts the

clients that were waiting. The connects were delivered — they sat in the

service queue and were dropped unanswered, 157s past their own deadline.

Environment

	Lustre 2.16 (cray), DNE, 4 MDTs, HA pairs.

	MDS: 64 cores / 4 NUMA nodes / npartitions: 8 -> 8 CPTs, 100 mdt threads per CPT.

	Clients on gni, servers on o2ib61, reached through LNet routers (routed traffic).

	Reproducer: MDS panic/failover loop. After the peer panicked, all four MDTs

ended up on one node.

The cycle

	MDT0000/MDT0002 fail over onto the node already hosting MDT0001/MDT0003.

	MDT0001/MDT0003 threads, handling ordinary client renames/getattrs, block in

ptlrpc_queue_wait() on OSP RPCs to MDT0000/MDT0002.

	Those threads are mdt service threads that arrived on

MDS_REQUEST_PORTAL — while blocked they still count in

scp_nreqs_active.

	MDT0002's clients send MDS_CONNECT on the same portal, into the same CPT

partition. No thread is free.

	MDT0002 cannot finish recovery (clients never connect); the threads cannot

unblock (MDT0002 has not finished recovery).

	At the 300s soft timeout the stale sweep evicts 6 clients, which releases the

threads — and one second later the queued connects are dequeued and dropped.

Why only these clients: the CPT is a function of the client NID

With the default portal_rotor = LNET_PTL_ROTOR_HASH_RT

(lnet/lnet/lib-ptl.c:17), a routed request is assigned

cpt = lnet_nid2cpt(&msg->msg_initiator, ni) (lib-ptl.c:291-306,

lib-move.c:4493) — a hash of the originating client NID, not the router. For

non-KFI NIDs this is (sum of the 8 bytes of the nid64) mod ncpt

(api-ni.c:1656-1679), i.e. for gni with 8 CPTs: CPT = (13 + addr) mod 8.

The six evicted clients were 23, 31, 47, 55, 135, 151 @gni — every one

addr = 7 (mod 8), i.e. all six hash to CPT 4. No client outside that

residue class was evicted. This is a deterministic cohort, not an unlucky tail,

and it will recur on the same 1/8 of the cluster every time.
