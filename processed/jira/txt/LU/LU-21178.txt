--- Description ---
The client hashes every stripe object of every cached inode in a single

rhashtable, and that table has no upper bound.  When it grows past 100.7M

objects the next resize asks for 2 GiB, which the kernel refuses; the resize

worker retries the allocation forever and the node spends its CPUs there.

Independently, the code path that reacts to a full table cannot make progress

and would spin forever, so any attempt to cap the table without also fixing

that path turns a warning storm into a hang.

https://review.whamcloud.com/c/fs/lustre-release/+/70674 LU-21178 obdclass: do not retry a full object hash forever

https://review.whamcloud.com/c/fs/lustre-release/+/70675 LU-21178 lov: use a separate lu_site per lovsub device

These do not cover:

	A per-site object cap, sized well below the rhashtable threshold, with a

  drop-inode policy behind it (EX-16399).  Without such a cap the fix above

  only makes the wall much less likely: one hot OST, a few-OST filesystem or

  wide striping can still fill one table.

	Making lu_cache_nr apply per site, or replacing it with a real per-site

  limit; with N sites the current per-site check against a node-global value

  allows N times as many objects.
