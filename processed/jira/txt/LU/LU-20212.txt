--- Description ---
The goal of FLR-EC is to allow a file to be accessible for reads when a file's OST object is inaccessible (for whatever reason), by reconstructing data from a parity object on another OST.

If the file data can be reconstructed from parity in limited cases, but some other common operation (e.g. open() or stat()) is blocked by the inaccessible OST object then the operational benefits of FLR-EC are lost.

Testing should be done with a variety of workloads that access the filesystem in a read-only manner to check that they do not become blocked by RPC timeout and retry.  For example, scanning and reading with "[lfs] find /mnt/testfs -size +1G -print0 | xargs -0 md5sum" or "grep -Rq test /mnt/testfs" or running "/mnt/testfs/executable" should not hang, and ideally should not pause more than a few seconds before the EC read reconstruction is activated.

The stat() calls should be handled by the SOM xattr on the MDS to return the file size and blocks instead of sending RPCs to OSTs to fetch these attributes.

LU-20211 contains a proposal to handle open(O_TRUNC) and truncate(0) in a way that would allow "read-only" EC to remove inaccessible OST objects from the file completely.

statfs()/df already has a "lazy" mechanism that should timeout if the OST is not responsive, and LU-20200 proposes that "lfs df" also send OST_STATFS RPCs in parallel to avoid long sequential waits, though the latter is not critical functionality for most workloads

Other file and filesystem access calls should be systematically reviewed and tested to ensure that file operations do not block, and fixed or the wait minimized if at all possible.

Ideally, only write(), truncate(), and maybe fallocate() to missing OST objects would block access waiting on OST recovery.

The stat() calls should be handled by the SOM xattr on the MDS to return the file size and blocks instead of sending RPCs to OSTs to fetch these attributes.

Just want to clarify the impl here.

1) if we have strict SOM on MDS, just return it and skip glimpse.

2) otherwise we need to consult OST with glimpse locks, whereas if any of the OST is imp_invalid/imp_deactive, we should

	2a) If the parity mirror is SYNCED and all its OSTs are healthy, glimpse the parity mirror and back-calculate logical file size from parity object size(maybe feasible? but still could not be that accurate)

	2b) or just return -EIO? fast fail, do not block clients.

i.e. send glimpse to remaining OSTs and do the merge operation may underestimate the real size, so it should be ruled out.

--- Comment (adilger, Tue, 2 Jun 2026 07:44:45 +0000) ---
Yes, this is correct.  The strict SOM should always be uptodate on the MDS (case 1), since we will not be allowing writes to degraded ECRO objects.  If SOM is not valid then it also means the parity is STALE and the client will need to block and wait for the OST to be restored.  While (2a) is theoretically possible, it shouldn't be the case until we have immediate write EC.  Even then, it wouldn't be possible to calculate the exact size, but it should be within (stripe_count-1) bytes of the right value.  For PFL or widely-striped files, if the degraded RAID set is not at the end of the file (i.e. none of the data stripes have a size close to EOF) then the size calculated from the data objects in the largest RAID set is likely correct).

I do not think we can get logical file size from parity object size.

Please note we can only get the size when the EC file is on RDONLY state. In this case, the MDT object usually is valid with strict SOM.

[Claude] Results of an OST outage test of read-mostly EC files, to find which operations still block.

Setup: single-node VM, 4 MDTs, 8 OSTs, client tree = master + 64919 PS50 (LU-12669 slow/dead OST detection) and the local EC hedge follow-on + 66882 PS34 (LU-20211) + 64086 PS44 (LU-12668).  Directory default -S 1M -c 4 --ec 4+2, 820 files (8x48MiB, 64 medium, 32 to be modified, 4 fio files, a git tree), all resynced to RDONLY before the test.  Client locks and page cache were dropped, then one OST was unmounted for 60s (3 runs) or 300s (1 run) and remounted.  Each operation ran in its own process under strace -tttT on files with a data stripe on that OST, in waves at T0+5s, +25s, +45s and 5s after the remount; kernel stacks of the blocked tasks were sampled.  The same test with a plain -E -1 -c 4 layout was the baseline.

With the plain layout every one of these that touches the down OST blocks until it returns.  After the remount the blocked operations finished within 1.5-2.5s (recovery took 1s, no evictions).

Errors returned to applications:

	stat() of an EC file with stale parity (after any write or truncate) returns -EAGAIN: the glimpse loops over the one usable mirror 8 times in ~65ms (lov_io_mirror_init() "move mirror from 0 to 0") and __cl_glimpse_size() returns -EAGAIN once ci_tried_all_mirrors is set.  ls, du and lfs mirror resync of such files fail the same way.  69479 (LU-20885) makes this glimpse block instead, which matches the expectation in this ticket that a file without valid SOM waits for the OST.

	open(O_CREAT|O_APPEND) of a new file under a directory with an EC default layout fails with -EINVAL (git fails to write its reflog), and after an EC default has been parsed every create under a plain v1 directory default handled by the same MDT thread fails with -EINVAL (stale llc_dstripe_count).  Both are fixed by 68932 (LU-20718).

Other findings:

	A file created in the first seconds after the OST went down was allocated a precreated object on it in 2 of 4 runs, and its writes then blocked for the whole outage: LU-20963.

	The LU-20211 trunc(0) layout replace did not trigger when the OST was unmounted, only when the OSP was also deactivated (comment in LU-20211).
