--- Description ---
When default quotas are applied, newly enforced QIDs at the quota slaves(OSTs and MDTs) don't report quota usage to the QMT.

This happens when:

	a default limit is set ("lfs setquota -U/-G/-P -B ...") while the ID already uses the default quota, or

	an ID is switched back to the default quota ("lfs setquota -u ID -D") while a default limit is set.

The usage stays unknown until the ID writes again to the same target or the quota slave reintegrates, so it is most visible with files spread over several OSTs.

Example (2 OSTs, default limit 10 MB):

	the user writes 20 MB to OST0000 while no default limit is set

	"lfs setquota -U -B 10M" is set

	the user can still write to OST0001 because OST0000 didn't report 20MB usage.

--- Comment (sergey, Wed, 25 Nov 2026 09:20:58 +0000) ---
(suggestion) This only reaches IDs that already have an lqe in qqi_site->lqs_hash. For an explicit limit, the QMT glimpses that ID, and qsd_process_upd()->lqe_locate() creates the lqe, so usage is reported even if the slave had never cached it. That path doesn't exist for a default limit.

Take an ID that never had a global index record. Writes while it is not enforced don't create one, and qsd_reconciliation() only walks the global index copy. If the OST restarts after such a write and before lfs setquota -U sets the default, the ID has no lqe on that OST. qsd_entry_def_iter_cb() never sees it, and its usage there stays unknown to the QMT until it writes to that OST again.

This isn't a regression, since the old code missed it too. It is a case the commit message's "as for an explicit limit" doesn't cover, though. Is it worth a note in the commit message or a follow-up ticket? One option would be to walk the accounting index when the default changes from 0 to non-zero.
