--- Description ---
Prototype a framework to perform fast kunit tests to act as a complement to the sanity integration tests.

Target is to have very fast tests that a developer can use when iterating.

Allowing to run more comprehensive tests including "negative tests" with invalid arguments or incorrect API use.

Reaching and testing functions not reachable from userspace.

Getting measure on coverage using KERNEL_GCOV

(also combine with DEBUG_KMEMLEAK)

--- Comment (JIRAUSER22400, Sat, 14 Nov 2026 07:33:16 +0000) ---
A little thought: upstream KUnit is a much better solution compared to the existing unit tests in lustre/kunit, as it comes equipped with modern scaffolding like mock and static_stub, giving us far more flexibility in code manipulation. The main trade-off is that it is somewhat intrusive – for example, we need to touch production source code to introduce static_stub or export symbols, and maintain kunit.list/modules.list.

Because of this, I'd suggest focusing KUnit on where it brings the most value: complex, self-contained modules and algorithms (we should not turn everything into KUnit). The LOD allocation algorithm you picked is a great fit – it's self-contained yet intricate, and KUnit allows us to cover most code paths and edge cases with very fast execution. Over time, we can gradually migrate the existing tests in lustre/kunit to use modern KUnit features and adopt it for other suitable components (potentially moving some targeted unit-level checks out of sanity as well).

Of course, given Lustre's complexity, cross-module interactions are unavoidable, so sanity remains essential. We can take a two-pronged approach: keep invoking KUnit tests within sanity as we currently do for CI/integration tests, while keep supporting direct CLI execution (e.g., sudo ./lustre/kunit/ku xxx) to speed up our local development and debugging loops.
