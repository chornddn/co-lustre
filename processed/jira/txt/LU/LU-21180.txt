--- Description ---
Prototype a framework to perform fast kunit tests to act as a complement to the sanity integration tests.

Target is to have very fast tests that a developer can use when iterating.

Allowing to run more comprehensive tests including "negative tests" with invalid arguments or incorrect API use.

Reaching and testing functions not reachable from userspace.

Getting measure on coverage using KERNEL_GCOV

(also combine with DEBUG_KMEMLEAK)

--- Comment (lixi_wc, Thu, 12 Nov 2026 02:24:46 +0000) ---
Excellent work! Just a few questions:

1. In different test scenarios, would the mocks need different implementations? Would that lead to a very large number of mock types? Could it get to the point where each new test case creates its own mock code? How do you avoid duplicated mock code? Would that result in too many mock/test files? And how should mocks and mock-based test code be clearly organized?

2. The KUnit speedup is huge—over 600x compared to the sanity scripts. But what about the build speed for KUnit code? If we modify a few lines in the Lustre code and add a bunch of KUnit test cases alongside, how much extra build time does that introduce? Build time sits inside the development loop together with KUnit's run time, after all.

3. What is the most difficult part of Lustre to add KUnit support to—for example, LNet/Router, which requires two or more peers?

4. What happens if KUnit triggers a kernel crash on the development node? Does that mean the developer loses access to it for at least a couple of minutes? Would it be possible to run KUnit tests on a remote node or a local VM?

5. Would KUnit enable TDD?
