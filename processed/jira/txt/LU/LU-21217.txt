--- Description ---
socklnd's zero-copy send does more work than it should, in two ways, both in ksocknal_lib_sendpage(). On RHEL 9 it is not zero copy at all. On kernels where it is, it hands TCP one 4 KB page per call. Both cost sender CPU on every bulk transfer, so they matter where the sender is the limit: an OSS serving reads to many clients, or a client writing fast.

1. RHEL 9: the "zero-copy" send is a copy.

socklnd picks its send method with "#ifdef MSG_SPLICE_PAGES". Upstream added that flag in 6.5 together with TCP support for it, and removed ->sendpage. RHEL 9 defines MSG_SPLICE_PAGES (include/linux/socket.h, brought in for an rxrpc backport), but its TCP never looks at the flag: nothing in net/ipv4 or net/core handles it, and tcp_sendmsg_locked() copies from the bvec iterator as for any other send. RHEL 9 still has tcp_sendpage(), which socklnd's other branch would have used. So on EL9 every bulk payload is copied, one page per call, and the sender still waits for a ZC-ACK from the peer, a protocol that only exists so the sender knows when it may reuse pages it did not copy. Checked in the Rocky 9 source, kernel 5.14.0-687.46.1.el9_8. RHEL 8, RHEL 10 and upstream 6.5 and later behave as the code assumes.

Fix: choose the method with a configure test for 'struct proto' having 'sendpage', not with the flag.

Expected gain: on EL9 senders whose CPU is the limit, probably 20 to 30% more bulk throughput. LU-19763 measured more than 30% lower throughput in VMs when socklnd's zero-copy send was turned off, the closest measurement of the same difference, and the EL9 path is somewhat worse than socklnd's own copy path, which at least sends a message in one call and asks for no ZC-ACK.

2. One page per call where splicing works.

When TCP does take MSG_SPLICE_PAGES (upstream 6.5 and later, RHEL 10), socklnd still builds the iterator over a single page per sock_sendmsg() call, a shape kept from ->sendpage when the code was ported (LU-17081). A 1 MB message takes 256 calls, each taking the socket lock and redoing TCP's per-call work, where socklnd's own copy path takes one call. MSG_SPLICE_PAGES takes the whole bio_vec array, as the NFS server and nvme-tcp use it, and a MSG_DONTWAIT call returns the bytes queued so far when the send buffer fills, which socklnd already handles.

Fix: pass the whole bio_vec array in one call when splicing. Kernels with ->sendpage still send a page per call.

Expected gain: smaller than (1). At a few tenths of a microsecond per call, 255 extra calls are on the order of 0.1 ms of sender CPU per MB, against roughly 0.6 ms per MB for a core moving 1.5 GB/s, so perhaps 10 to 15% of sender CPU per byte. This is an estimate; measurements will be added here.

Found by reading the socklnd data path (lnet/klnds/socklnd/socklnd_lib.c).

--- Comment (JIRAUSER24100, Sat, 14 Nov 2026 21:31:08 +0000) ---
Measured 70881 (with 70880 under it) between two Rocky 10 VMs (6.12 kernel, so the splice path) over a fast virtio-net switch, LNet selftest 1 MB transfers, 8 in flight. Sending a message's pages in one call roughly halves the sender's CPU and cuts the packets the receiver handles about eight times, because the sender now builds full-size TSO frames instead of 5 to 9 KB ones. Throughput in these VMs did not change beyond run-to-run noise, since the limit there is elsewhere (the receiving guest is still about 40% idle); where the sender's CPU is the limit, as on a busy OSS, the CPU saving is what turns into bandwidth.

Per 1 MB, before -> after:

```

sender tcp_sendmsg calls  258 -> 4

sender TSO frame size     5-9 KB -> 57 KB     17-42 KB -> 56 KB

receiver skbs             115-183 -> 17-18    24-56 -> 18

receiver data_ready       65-125 -> 7

receiver recvmsg calls    26-64 -> 7-8

sender guest CPU (vCPUs)  1.7-1.8 -> 0.8-1.1  1.9-2.5 -> 1.4

host CPU, sender QEMU     2.5 -> 2.0          2.3 -> 1.55

GB/s write (2 runs)       2.35/2.63 -> 2.60/2.71   3.17/2.69 -> 2.61/2.89
```

--- Comment (JIRAUSER24100, Sat, 14 Nov 2026 21:31:33 +0000) ---
Measured 70880 on RHEL 9 (Rocky 9 guests, kernel 5.14.0-611, plain virtio-net bridge), LNet selftest 1 MB transfers, 8 in flight, 5 runs each, medians. The fix cuts the sender's CPU per GB sent by 55 to 61% in every case, from about 1.0 to 0.4 CPU-seconds per GB. Before it, 43% of the sender's samples were the copy (_copy_from_iter under tcp_sendmsg_locked); after it the payload goes through tcp_sendpage and the copy is gone. So 5.14.0-611 is affected as well as 5.14.0-687.

```

                    before   after

cpp1 write GB/s     1.16     1.40   (+20%)

cpp1 read GB/s      1.34     1.53   (+14%)

cpp4 write GB/s     1.32     1.33

cpp4 read GB/s      1.35     1.39

sender CPU-s/GB     ~1.0     ~0.4   (all four cases)

```

With four connections the bridge between the VMs is the limit, so the saving shows as CPU rather than bandwidth there.
