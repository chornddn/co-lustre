--- Description ---
sanity-quota test_41 fails on ZFS with "failed to get correct statfs when statfs_project=0".

The test records the global statfs (df -kP/-iP $MOUNT) right after setting llite.statfs_project=0, then waits up to 90s for df on the project directory to match. In the failing run the block counts matched but the total inode count did not: expected 1699547, got 1699516 (a drift of 31), and it never converged in 90s.

Cause: on ZFS, osd_statfs() reports os_files = os_ffree + usedobjs, where os_ffree is estimated from the pool's available space. Total inodes therefore moves whenever pool free space changes (asynchronous frees or trim from earlier tests, txg sync). The test captures the expected value once and then requires an exact match, so a free-space change between the two df calls makes it fail. It is not related to project quota.

Seen once on review-dne-zfs-part-4 (change 69617 patchset 8, session 0d4e8f0f-0597-4c17-a39c-aba8ef6e9b89, subtest 85f3fa0b-5fd6-4bf1-befe-a9a5e0833bb2): 1 failure in about 2700 runs of this config in 30 days. That patch (LU-20517) only changes OST write quota accounting and does not touch statfs or the MDT. LU-14666 is a 2021 test_41 timeout and is a different failure.

Possible fix: in the ZFS case compare only the block counts and used inodes, or compare inode totals within a tolerance, or re-read the expected value inside the wait_update loop.
