--- Environment ---
Two-MDT Lustre lab with ldiskfs targets. MDT0 held the source directory and file object. MDT1 held the destination directory. Backend evidence collected with debugfs 1.47.3-wc2.

--- Description ---
Summary
In a two-MDT ldiskfs lab, a rename attempted while the source MDT was read-only left both names visible with the same FID and a reported link count of 1. After the source MDT returned to read-write, unlinking the destination name succeeded. The original source name remained in the local ldiskfs directory and returned ENOENT on the Lustre client.

Rename evidence

	Start with source.txt under an MDT0 directory and an absent destination name under an MDT1 directory. MDT0 owns the file FID [0x20000cf21:0x2:0x0].

	With MDT0 read-only and MDT1 writable, attempt the rename with mv -T. The client reported that the two paths were the same file. Subsequent lfs path2fid returned [0x20000cf21:0x2:0x0] for both paths, and client stat returned the same inode number, size 27, and links=1 for both.

	On MDT0, debugfs showed the source entry in parent inode 294 pointing to regular inode 307, generation 3781440640. Its LMA carried the file FID and its only linkEA record was parent [0x20000cf21:0x1:0x0], name source.txt. On MDT1 the destination entry pointed to agent inode 266 with the same FID and LMA incompat=2.

	Both names persisted after MDT0 returned to read-write and completed recovery. MDT1 remained online throughout.

Unlink evidence
On the client, rm of the MDT1 destination source.txt succeeded. Listing the original MDT0 parent then showed:

ls: cannot access '/mnt/lustre/rename-20261124T204834Z-mdt0/source.txt': No such file or directory
-????????? ? ? ? ? ? source.txt

The post-unlink raw directory listing on MDT0 still showed this record:

307  100644 (17)  0  0  0  24-Nov-2026 20:48 fid:[0x20000cf21:0x2:0x0] source.txt

This confirms the stale local directory entry and its on-disk inode reference. With a single recorded link before unlink, the expected failure mechanism is that unlink retires the file object and can free inode 307 while the source directory entry still references it, leaving an ldiskfs directory entry pointing to a free inode. A post-unlink inode bitmap check is still pending. The raw directory listing alone does not establish whether inode 307 was freed.

Expected behavior
A cross-MDT rename should leave one reachable name on success, or preserve the original reachable name if the operation cannot complete. Recovery should reconcile any partially applied rename so a subsequent unlink cannot leave another directory entry pointing to the retired object.

Related issues

	LU-21320 observed a dangling remote directory entry after rmdir returned EROFS with the parent MDT read-only. This report covers a regular file and a surviving local source entry after endpoint unlink.

	LU-20421 describes a partial distributed rename followed by unlink of the old source name, leaving the destination dangling. In this test the destination was unlinked and the source became dangling.
