--- Comment (emoly.liu, Wed, 2 Sep 2026 09:16:14 +0000) ---
Here is some AI's analysis of this OOM crash issue:

test_70b and test_71c are NOT the actual trigger — they're just innocent bystanders. The real culprit is test_56b (which runs earlier in the same sanityn.sh suite). test_56b creates a (16TB × OSTCOUNT) sparse, 2000-overstriped file via llverdev, writing 4KB chunks every 1GB offset (partial mode). When this massive sparse file is destroyed at test exit via stack_trap "rm -f", the client sends destroy RPCs and moves on quickly, but on the OSS the destroy is processed inline on the ptlrpc service thread: osd_trans_stop() → osd_unlinked_list_emptify() → osd_unlinked_object_free() → dmu_free_long_range(). This dirties the entire indirect block tree for each OST object, generating massive unreclaimable slab allocations (dbuf_dirty_record_t, dmu_buf_impl_t, zio_buf_comb_*, zfs_btree_leaf_cache, etc.) that silently exhaust free memory on the ~4GB test VM.

A userspace process (NetworkManager) does an ordinary page fault, finds no free pages, and invokes the OOM killer after ZFS consumed it all.

Reducing llverdev size in test_56b for ZFS would prevent this OOM crash, but we still need a thorough fix.
