--- Description ---
Problem

	With trash_can_{uid,gid,projid}=original and trash_can_audit=0, the MDT writes no trusted.unrm. ltrash_purge then drops every entry ("Cannot read unrm xattr"), so -max-age, uid, gid and -projid never purge anything; lfs trash state -p reports projid 0.

	In the same configuration the daemon never scans at all: ltrash_purge_trash_is_empty() reports "empty" when the trash project ID is original, cannot be read, or the quota call fails unexpectedly ("Trash Can is empty, skip scan.").

	With only an age or ID policy (no watermark), a scan reuses the MDT/OST usage sampled by a previous scan, and the "check every N deletions" logic stops the scan after the first N deletions even though the policy still matches.

	Threshold handling was inconsistent: the per-entry check used > while the scan trigger used >=, so entries were not purged exactly at the watermark.

Impact Trash Can space is never reclaimed for the "original UGP + no audit" configuration (the documented way to keep per-user quota accounting), the daemon can sleep indefinitely, and watermark purging differs from what ltrash_purge.8 / ltrash_purge.conf describe.

Expected

	Missing trusted.unrm: age/UID/GID filters keep working from the object's own attributes, project ID read with FS_IOC_FSGETXATTR, project-ID filter skipped when it cannot be read (e.g. symlink); lfs trash state -p reports the real project ID.

	Scan is skipped only when the usage is actually known to be zero.

	Each scan samples the MDT/OST usage; a scan stops only when no policy matches.

	>= everywhere; documentation states that policies are combined with OR.
