--- Comment (hornc, Wed, 28 Oct 2026 21:23:27 +0000) ---
The failure in the description is not an infrastructure flake. The test pings before the router forwards messages.

The router log shows "Message forwarding will be enabled in 10s" after "lnetctl set routing 1". LU-15135 added this delay. Until the router enables forwarding, its ping reply says that routing is off. The client then marks the route down:

1791934164.710983 lnet_router_discovery_ping_reply()) Peer 10.240.30.225@tcp is being used as a gateway but routing feature is not turned on
1791934164.711986 lnet_set_route_aliveness()) route to tcp1 through 10.240.30.225@tcp has gone from up to down

config_routes() passed check_route_aliveness() on the initial "up" state of the new route, before the first router check. The router enabled forwarding at 1791934174.91. The client ping ran at 1791934176.42, before the next router check, so the ping got -113.

The test should wait until the router enables forwarding before it checks the route. Another option is to wait for the route to go up after the first router check.

A failure with the same error message on another branch has a different cause. That cause is LU-21057. I did not look at the logs for the failures on 69203 and 68158.
